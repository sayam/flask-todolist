## สิ่งที่ตัวเลขบอก

**1. เป้าผ่านแบบมีที่ว่างเหลือไม่มาก** — p95 ที่เป้าอยู่ที่ 84ms จาก 200ms
(เหลือ ~2 เท่า) แต่ **p99 อยู่ที่ 474ms จาก 500ms คือเฉียดมาก** งานที่ทำให้ช้าลง
อีกนิดเดียวจะทำให้ p99 ตกเป้าทันที — ตัวเลขนี้คือสิ่งที่ต้องเฝ้า ไม่ใช่ p95

**2. คอขวดคือจำนวน process ที่รับงานได้พร้อมกัน ไม่ใช่ฐานข้อมูล** — throughput
ตันที่ ~57 req/s (1 replica) และ ~70 req/s (2 replica) แล้ว **ตกลง** ที่ 50+ VUs
ซึ่งเป็นรูปของคิวที่ล้น ไม่ใช่ของ query ที่ช้า · gunicorn รัน worker เดียวต่อ
container คำขอจึงถูกจัดคิวตั้งแต่ชั้นแรก — เพิ่ม `--workers` น่าจะขยับเส้นนี้ได้
มากกว่าการไปแตะ index (ดูหัวข้อ "ยังไม่ทำ")

**3. 2 replica ช่วยจริงแต่ไม่เป็นสองเท่า** — p95 ที่เป้าดีขึ้นจาก 84 เป็น 33ms
และ throughput สูงสุดขึ้นจาก 57 เป็น 70 req/s · ที่โหลดสูงมาก latency ลดลง
ราวครึ่งหนึ่ง (8.7s → 5.3s ที่ 50 VUs) ซึ่งสมเหตุสมผลกับการมีคิวสองแถว

## ⚠ เรื่องที่ใหญ่ที่สุดที่เจอ: สาย audit เขียนขนานข้าม process ไม่ได้

**อาการ**: ที่ 2 replica คำขอ `POST /add` ได้ **500** เป็นสัดส่วน 0.36% ที่เป้า
และไต่ขึ้นถึง 9.5% ที่ 100 VUs · ที่ 1 replica ไม่เกิดเลยแม้แต่ครั้งเดียว

**สาเหตุ**: `tdl_audit.uq_audit_prev_hash` ถูกละเมิด (`Duplicate entry ... for key
'tdl_audit.uq_audit_prev_hash'` 225 ครั้งในรอบเดียว) — สอง process อ่าน "แถวสุดท้าย
ของสาย" ตัวเดียวกัน แล้วต่อสายด้วย `prev_hash` เดียวกันทั้งคู่ ตัวหลังชนกุญแจ
unique แล้ว transaction ทั้งก้อนตกไป ผู้ใช้เห็น 500

**นี่ไม่ใช่บั๊กที่ไม่มีใครรู้** — `app/audit.py` เขียนข้อจำกัดนี้ไว้เองตั้งแต่
Phase 2 ว่า *"ถ้ามีสอง process เขียนพร้อมกันจริง ๆ ตัวหลังจะได้ IntegrityError …
ตั้งใจให้ดังกว่าการมี chain ที่ล้มเหลวอย่างเงียบ ๆ (scale ตอนนี้เป็น SQLite ที่ serialize
การเขียนอยู่แล้ว **ถ้าวันหนึ่งต้องเขียนขนานจริงต้องเปลี่ยนไปใช้ sequence/batch**)"*

**เงื่อนไข "วันหนึ่ง" นั้นมาถึงแล้ว** — Phase 5 ทำให้ ≥2 replica เป็นของจริง
และ Phase 6 เป็นตัวพิสูจน์ว่ามันมีราคาที่ผู้ใช้จ่าย · การเลือก unique constraint
ยังถูกอยู่ (chain ที่แตกสองสายเงียบ ๆ แย่กว่า 500) แต่ **การปล่อยให้ผู้ใช้เห็น
500 ระหว่างใช้งานปกติไม่ใช่คำตอบสุดท้าย** — ต้องทำให้การต่อสายเป็นลำดับจริง
(ล็อกแถวสุดท้าย หรือลองใหม่เมื่อชน) ซึ่งเป็นการตัดสินใจที่ต้องมี ADR

### แก้แล้ว — วัดซ้ำเมื่อ 2026-08-11 (ADR 0032)

`_last_hash()` ล็อกแถวท้ายสายด้วย `FOR UPDATE` ก่อนอ่านค่าไปต่อ ผู้เขียนราย
ที่สองจึง **รอ** แทนที่จะชนแล้วตกไป

| VUs | ล้มเหลว ก่อนแก้ | ล้มเหลว หลังแก้ | p95 ก่อน → หลัง (ms) | req/s ก่อน → หลัง |
|---|---|---|---|---|
| 5 | 0.36% | **0.00%** | 32.8 → 48.9 | 34.3 → 33.0 |
| 25 | 1.59% | **0.13%** | 1943.6 → 2542.5 | 70.1 → 49.6 |
| 100 | 9.49% | **0.00%** | 10405.9 → 13944.0 | 18.2 → 13.3 |

**`uq_audit_prev_hash` ชนกัน 0 ครั้ง** (จาก 225 ครั้งในรอบเดียวก่อนแก้)

**อ่านคอลัมน์ p95 ในตารางนี้อย่างระวัง** — เป็นตัวเลขจากรอบเดียวทั้งคู่
การรันซ้ำที่โหลดเป้า 4 รอบ (ดูหัวข้อ "ด่านของ DoD") ได้ p95 ระหว่าง 22 ถึง 38ms
ซึ่งคร่อมทั้งค่า "ก่อนแก้" (32.8) และ "หลังแก้" (48.9) ที่ตารางนี้รายงาน
· **สิ่งที่ตารางนี้พิสูจน์คือคอลัมน์อัตราล้มเหลว ไม่ใช่คอลัมน์ latency**

**ราคาที่จ่ายไปตามที่ ADR 0032 บอกไว้ล่วงหน้า**: throughput ลดลงราว 20–30%
ที่โหลดสูง เพราะการเขียนที่ต้องลง audit serialize กันทั้งระบบ — เป็นสิ่งที่
สาย hash ต้องการโดยนิยาม ไม่ใช่ผลข้างเคียงที่แก้ได้ด้วยการปรับจูน

> **แก้ไขภายหลัง (2026-08-12 · [ADR 0035](adr/0035-audit-appends-queue-on-one-row.md))**
> ตัวเลข deadlock ที่รายงานไว้ข้างล่าง **ต่ำกว่าความจริงมาก** เพราะเส้นทางที่ชุดวัด
> นี้เดินเป็นการอ่านเป็นส่วนใหญ่ · เมื่อวัดการเขียนตรง ๆ ด้วยผู้เขียน 8 ราย
> พบว่า **80% ของการเขียนล้มเหลวด้วย deadlock** (128 จาก 160) — การล็อกหางสาย
> ของ ADR 0032 ไม่เคยทำให้การเขียนเป็นลำดับเลย มันแค่เปลี่ยนชนิดของความล้มเหลว
> จาก "ชนกุญแจ unique" เป็น "deadlock" · แก้แล้วด้วยการต่อคิวที่แถวเดียว
> (deadlock 128 → **0**) และ **ตัวเลข throughput ทั้งรายงานนี้วัดกับล็อกที่ไม่
> ทำงาน จึงเทียบกับของหลังแก้ตรง ๆ ไม่ได้ ต้องวัดใหม่**

**สิ่งที่ยังเหลือและต้องพูดให้ชัด**: ที่ 25 VUs ยังมี **deadlock ของ MySQL
(error 1213) 2 ครั้ง** ทำให้เกิด 500 หนึ่งครั้งกับ 502 หนึ่งครั้ง — การล็อกแถว
เปลี่ยน *การชนแบบเป็นระบบ* (225 ครั้ง/รอบ) ให้กลายเป็น *อุบัติเหตุที่นาน ๆ ครั้ง*
(2 ครั้ง/รอบ) แต่ไม่ได้ทำให้เป็นศูนย์ · deadlock เป็นสิ่งที่ลองใหม่ได้ตามนิยาม
(ฐานข้อมูลยกเลิกฝ่ายหนึ่งให้เอง) การเพิ่ม retry สำหรับ error 1213 จึงเป็นงาน
ถัดไปที่สมเหตุสมผล — **ยังไม่ทำ และบันทึกไว้ตรงนี้แทนที่จะปล่อยให้เจอเอง**

## ด่านของ DoD — วัดที่โหลดเป้าหมายหลังแก้แล้ว 4 รอบติด

เส้นโค้งข้างบนรันด้วย `NO_THRESHOLDS=1` (ต้อง "ไม่ผ่าน" เป็นเรื่องปกติเมื่อไล่หา
จุดที่ระบบรับไม่ไหว) **ตัวที่ตัดสิน DoD คือการรันที่โหลดเป้าหมายโดยเปิด threshold ไว้
แล้วให้ k6 ตัดสินเอง** — ผ่าน = exit 0, ตกเกณฑ์ = exit 99 ไม่ต้องมีคนมาอ่านตัวเลข

2 replica · 5 VUs · 60 วินาที · **หลังแก้ ADR 0032 แล้ว**:

| รอบ | p95 (ms) | p99 (ms) | req/s | ล้มเหลว | k6 exit |
|---|---|---|---|---|---|
| 1 | 33.1 | 90.6 | 37.7 | 0% | 0 |
| 2 | 38.4 | 232.5 | 36.8 | 0% | 0 |
| 3 | 27.8 | 84.7 | 38.3 | 0% | 0 |
| 4 | 22.2 | 56.8 | 39.5 | 0% | 0 |

**รันสี่รอบไม่ใช่เพื่อความมั่นใจ แต่เพราะรอบเดียวไม่พอจะเชื่อ** — p99 ของรอบที่ 2
สูงกว่ารอบที่ 4 สี่เท่า ทั้งที่โหลด เครื่อง และโค้ดเหมือนกันทุกอย่าง · p99 คือ
สถิติของหางซึ่งกระเพื่อมมากโดยธรรมชาติ **ตัวเลขจากรอบเดียวจึงไม่ใช่หลักฐาน**
สิ่งที่เป็นหลักฐานคือ *ไม่มีรอบไหนตกเกณฑ์*

**และนี่ทำให้ต้องตีความตัวเลขก่อนแก้ใหม่ด้วย**: ตาราง 2 replica ก่อนแก้รายงาน
p99 = 574ms ที่โหลดเป้า ซึ่งตอนนั้นอ่านว่า "เกินเป้า" · เทียบกับช่วง 57–233ms
ที่วัดได้หลังแก้ ความต่างส่วนหนึ่งมาจากการที่ 500 แต่ละครั้งลาก transaction
ที่ตกไปกับการรอล็อกมาด้วย แต่**อีกส่วนคือความกระเพื่อมของ p99 เอง**
เราจึงไม่อ้างว่า "การแก้ทำให้ p99 ดีขึ้น 6 เท่า" — สิ่งที่การแก้ทำให้เป็นศูนย์
คืออัตราล้มเหลว ซึ่งเป็นตัวเลขที่ไม่กระเพื่อม

อย่าเทียบตัวเลขดิบกับตารางของ 2026-08-11 ซึ่งเป็นคนละสภาพเครื่อง

| 2 | 25.7 | 105.1 | 62.6 | 663.4 | 354.5 | 1729.5 | 242.6 |

- **ที่โหลดเป้า (5 concurrent) แทบไม่ต่างกัน** — ระบบไม่ได้ต่อคิวที่โหลดนี้
  อยู่แล้ว การเพิ่ม worker จึงไม่ซื้ออะไรให้ผู้ใช้กลุ่มเป้าหมาย
- **ที่ 25–50 concurrent ต่างจริง**: workers=2 ลด p95/p99 ราวครึ่งและได้

  ไม่ใช่ query · ส่วน 4 ให้ผลเพิ่มจาก 2 ไม่มาก (VM มี 4 vCPU ที่แชร์กับ
  MySQL/redis อยู่)

1 worker ตามเดิม)*

**คำตัดสิน: คง 1 worker เป็นค่าเริ่มต้นของ image/compose** — เหตุผลไม่ใช่
ตัวเลขข้างบน แต่คือ `/metrics`: histogram เป็นของ process นั้นคนเดียว (ADR
0031) หลาย worker หลังพอร์ตเดียวทำให้แต่ละ scrape ตกที่ worker คนละตัว
สลับกัน — time series เดียวกันจะกระโดดไปมาระหว่างตัวนับสองชุดโดยไม่มี
label แยก ซึ่งคือการทำให้ระบบวัดที่เพิ่งต่อเสร็จ (16-04) ให้ข้อมูลที่ไม่จริงอย่างเงียบ ๆ ๆ
· ใครที่รับข้อนั้นได้และต้องการ throughput: ตั้ง `WEB_CONCURRENCY=2`
(หรือ `GUNICORN_CMD_ARGS="--workers 2"`) ได้เลย — ตัวเลขข้างบนคือสิ่งที่
จะได้ และ `CACHE_URL` ของ stack ชี้ redis อยู่แล้วโควตา rate limit จึงยัง
ถูกต้อง · เส้นทางที่ถูกของการ scale ที่ไม่แตะข้อจำกัดนี้คือเพิ่ม **replica**
(แต่ละตัวยัง 1 worker — `/metrics` ต่อ replica ยังเป็นของ process เดียว)
ซึ่ง `compose.scale.yaml` มีให้แล้ว

## G5 — multi-worker แบบ metrics ถูกต้อง + คำตัดสิน caching (วัด 2026-08-16)

ปิดแผน governance (ADR 0052) — วัดสี่ config บน VM เดิม (4 vCPU · docker 29 ·
stack MySQL · code `1416c60` ที่มีโหมด multiproc แล้ว) · **เทียบกันได้เฉพาะ
ในตารางนี้ด้วยกันเอง** — ตัวเลขดิบต่างจากตาราง 16-05 ที่วัดคนละวันอย่างมี
นัย (เช่น W1R1@50: p95 3157 ที่นี่ vs 759 เมื่อวาน) ซึ่งตอกย้ำกฎเดิม:
การวัดรอบเดียว/ต่างวันไม่ใช่หลักฐานเปรียบเทียบ

ที่โหลดเป้า (5 VUs · เปิด threshold · 4 รอบต่อ config): **exit 0 ทั้ง
16 รอบ ไม่มีรอบไหนตกเกณฑ์ ล้มเหลว 0%** — ช่วงค่า p95/p99 ต่อ config:

| config | p95@5 (ช่วง 4 รอบ) | p99@5 (ช่วง 4 รอบ) | p95@25 | p99@25 | rps@25 | p95@50 | rps@50 |
|---|---|---|---|---|---|---|---|
| 1 worker · 1 replica | 23.6–44.6 | 167–258 | 461 | 2285 | 113 | 3157 | 61 |
| **2 workers · 1 replica** | **14.2–17.8** | 195–253 | **246** | **1442** | **142** | **1581** | **140** |
| 1 worker · 2 replicas | 20.3–25.6 | 361–477 | 925 | 2669 | 98 | 5212 | 37 |
| 2 workers · 2 replicas | 12.1–21.9 | 303–378 | 277 | 1847 | 130 | 3454 | 89 |

**สิ่งที่ตัวเลขบอก:**

1. **workers=2 ใน container เดียวชนะทุกสนามบนเครื่องเดี่ยว** — p95 ที่ 25
   VUs ลดครึ่ง (461→246) และที่ 50 VUs ได้ throughput +129% (61→140 rps)
   ยืนยันผล 16-05 อีกรอบ — และตอนนี้**เปิดได้โดย `/metrics` ยังรายงานตรงตามจริง**
   (โหมด multiproc — ADR 0052)
2. **ผลที่ไม่คาด: บนเครื่องเดียว 2 replica แย่กว่า 1 replica ทุกระดับโหลด**
   (p95@25: 925 vs 461 · rps@50: 37 vs 61) — สมเหตุผลเมื่อคิดตาม: vCPU
   4 ตัวเดิมถูกหารด้วย process มากขึ้น + เพิ่ม hop ของ nginx + การเขียนที่
   ลง audit ต้อง serialize ข้าม process ผ่านแถวล็อก (ADR 0035) ซึ่งแพง
   กว่าการ serialize ใน process เดียว · **replica มีไว้เพื่อ availability
   และ rolling upgrade (ADR 0048) ไม่ใช่เพื่อ throughput บน host เดียว**
   — ถ้ามีหลาย host จริง สมการเปลี่ยน ต้องวัดใหม่ที่นั่น
3. ที่โหลดเป้า ทุก config สบาย — ผู้ใช้กลุ่มเป้าหมาย (5 concurrent)
   ไม่ได้อะไรจากการปรับทั้งคู่ เหมือนที่ 16-05 พบ

**พิสูจน์ multiproc บน gunicorn จริง** (W2R1 — ไม่ใช่แค่ unit test):
HELP ประกาศ "รวมทุก worker ของ container นี้" · ไฟล์ snapshot สองใบ
(worker pid 7 และ 8) อยู่ใน `/tmp/metrics` จริง · ยิง /login ~80 ครั้ง
กระจายสอง worker แล้ว count = 81 (worker เดียวจะเห็นราวครึ่ง) · scrape
ถัดไป monotonic (88 ≥ 81) — ค่าจาก worker ที่ไม่ได้รับ scrape ตามหลังได้
ไม่เกิน `DUMP_INTERVAL_SECONDS` (1 วิ) ตามที่ออกแบบ ซึ่งมองไม่เห็นที่
รอบ scrape จริงของ Prometheus (15 วิ)

**คำตัดสิน caching (ADR 0052 ข้อ 2 — วัดก่อน): ไม่ทำ cache ของข้อมูลแอป**
— หลักฐานชี้ทางเดียวกันทั้งหมด: throughput ขยับตามจำนวน worker process
(61→140 rps เมื่อเพิ่ม worker) ไม่ใช่ตามอะไรที่ cache ช่วยได้ และที่โหลด
เป้าไม่มี endpoint ไหนช้าพอให้ cache มีความหมาย — cache layer ที่เพิ่มตอนนี้
คือ invalidation bug ที่รอวันเกิดโดยไม่มีอะไรให้แลก · **เงื่อนไขทบทวน**:
เมื่อ `/metrics` ชี้ว่า endpoint ที่ DB-bound ครอง p95 ที่โหลดเป้า หรือ
ข้อมูลผู้ใช้จริงโตจนพฤติกรรม query เปลี่ยน (ตอนนั้นวัดใหม่ก่อนเสมอ)

## การสลับ plugin ระหว่างมีโหลด (Phase 10 · 10-03 — วัด 2026-08-14)

migration class ที่ประกาศใน manifest (ADR 0041) ต้องมีตัวเลขรองรับ — วัดบน
stack 2 replica หลัง nginx (compose scale) ใน VM (ubuntu-docker-vm-6, 8GB RAM,
docker 29) · โหลดพื้นหลัง 10 rps ที่ `/login` + อีกสายด้วย session ที่ login
ค้างไว้ · ทุกสถานการณ์มี**ตัวคุมว่าการสลับมีผลจริง** (stylesheet ต้อง 404
ระหว่างธีมหาย · `plugin-list` ต้องไม่เห็น totp · env/ยี่ห้อ db ตรวจจาก
container จริง) — สามรอบแรกของ secrets เคยวัดทั้งที่แหล่ง file **ไม่ถูกอ่านเลย**
เพราะชื่อไฟล์ผิดตัวพิมพ์ ตัวคุมสองทิศจับได้แล้ววัดใหม่

**สิ่งที่ตัวเลขบอก**
- `live` สองตัวคือของจริง: ถอด/คืนไดเรกทอรีใต้โหลด **ไม่มี request ไหนล้ม**
  และตัวคุมยืนยันว่าแอปเห็นการหายไปจริง
- **cache ถูกลดชั้นจาก live → warm ด้วยการวัด** — rolling บน nginx แบบ DNS
  (ไม่มี upstream retry) หลุด 1 request ที่จังหวะฆ่า replica ใน 2/6 รอบ ·
  เกณฑ์ live คือ "ไม่มีรอบไหนตก" จึงไม่ผ่าน · session รอดครบทุกรอบ = warm
  · **วัดซ้ำหลังมี graceful shutdown + readyz (เฟส 16 · 2026-08-15): ยังหลุด**
  — 1/3 รอบ fails=7, gap ≈3.1s ทั้ง anon และ session (session ยังใช้ต่อได้
  หลังจบ = warm เหมือนเดิม) · ยืนยันว่ากลไกของการหลุดอยู่ที่ **ฝั่ง proxy**
  (nginx resolve ชื่อ replica ตอนโหลด config แล้วจำ IP — ตัวที่ถูกฆ่ายังถูก
  ส่งงานจนกว่า config จะถูกอ่านใหม่) ไม่ใช่ฝั่งแอป `--graceful-timeout`
  จึงแก้ไม่ได้ · ทางแก้จริงคือ dynamic resolver/upstream ของ nginx —
  จดเป็นงานค้าง ไม่เปลี่ยนคำประกาศ class
- `cold` มีตัวเลขจริงแทนคำว่า "ช่วงสั้น ๆ": secrets ≈ 4.2–4.7 วิ (restart
  พร้อมอ่านแหล่งใหม่) · db ≈ 17–22 วิ (ยี่ห้อใหม่ ฐานเปล่า + migrate —
  **ไม่รวมการย้ายข้อมูล** ซึ่งตัดไว้ใน ADR 0040)

**ของจริงที่ bench ขุดเจอ (นอกเหนือตัวเลข)**
1. **สอง overlay ของ db ใช้ named volume `db-data` ก้อนเดียวกัน** — สลับยี่ห้อ
   ทับ datadir เดิมล้มเหลวทันที (`Unknown storage engine: InnoDB`) · ขั้นตอนที่ถูก
   คือ dump → volume ใหม่ → restore — ยังไม่ได้เขียนเป็น runbook (งานค้างจริง)
2. **หน้า login ยังเสนอปุ่ม SSO แม้ไม่มี config OIDC เลย** (plugin อยู่ +
   ตารางติดตั้งแล้ว) — กดแล้วได้ 400 · ทางปิดที่ถูกคือ `DISABLED_PLUGINS`
   ซึ่งวัดแล้วทำงานตรงคาด แต่ "มี env ครบไหม" ควรเป็นเงื่อนไขของ available()
   ด้วย — บันทึกเป็นงานค้าง
3. plugin ที่มีตารางของตัวเอง ต้อง `flask plugin-install` เป็นส่วนหนึ่งของ
   runbook การเปิดใช้ — bench เจอเองตอนปุ่ม SSO ไม่โผล่ (พฤติกรรมออกแบบไว้
   ถูกต้อง: ตารางไม่มา = ข้ามเงียบอย่างถูกต้อง)
