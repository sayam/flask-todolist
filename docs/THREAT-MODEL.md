# Threat model และการวิเคราะห์ผิวการโจมตี

เอกสารนี้ตอบคำถามที่ทะเบียนความเสี่ยงกับใบประเมิน ASVS/ISO ตอบไม่ได้:
**ใครโจมตีอะไรได้บ้าง ผ่านทางไหน และอะไรขวางอยู่** — ทะเบียนความเสี่ยง
([RISK-ASSESSMENT.md](RISK-ASSESSMENT.md)) จัดลำดับความเสี่ยง *ระดับโปรเจกต์*
ส่วน [ASVS.md](ASVS.md) กับ [ISO27001.md](ISO27001.md) ตอบว่าเรามีการควบคุมข้อไหน ·
ทั้งสามอย่างไม่ทับกัน และทั้งสามอย่างจำเป็น (`OSPS-SA-03.02`)

**ทุก gate ที่อ้างในหน้านี้ถูกเทสต์ตรวจว่ามีอยู่จริง** และรายการ route ที่เปิด
สาธารณะถูกผูกสองทิศกับตัวบังคับจริง (`tests/test_threat_model.py`) — model ที่
ไม่มีอะไรผูกกับโค้ด คือเอกสารที่จริงเฉพาะวันที่เขียน

## 1. ขอบเขต

**อยู่ในขอบเขต**: ตัวแอป Flask ที่รันจริง · ฐานข้อมูล · ผิว HTTP ทั้งหมด (เว็บ ·
`/api/v1` · `/metrics` · `/healthz`+`/readyz`) · CLI ของผู้ดูแล · จุด plug ของ
plugin ทั้ง 5 ชนิด · ความลับตอนรัน · image กับ compose stack ที่ deploy จริง ·
เส้นทางจาก commit ถึง release (supply chain)

**อยู่นอกขอบเขตโดยตั้งใจ**: ความปลอดภัยทางกายภาพของโฮสต์ · ความปลอดภัยของ
เบราว์เซอร์ผู้ใช้ · การโจมตีระดับเครือข่ายใต้ TLS (จัดการโดย reverse proxy) ·
ผู้ให้บริการที่เราพึ่ง (มีทะเบียนแยกที่ [SUPPLY-CHAIN.md](SUPPLY-CHAIN.md))

**สมมติฐานที่ถ้าผิดแล้ว model นี้ผิดทั้งใบ**: (ก) ผู้ดูแลคนเดียวยังคุมบัญชี
GitHub ของตัวเองอยู่ (ข) TLS ถูกยุติที่ proxy ที่เราตั้งเอง (ค) ไม่มีใครมีสิทธิ์
เขียนฐานข้อมูลนอกจากตัวแอปกับผู้ดูแล

## 2. สิ่งที่ต้องปกป้อง เรียงตามความเสียหายถ้าเสีย

| ทรัพย์สิน | ชั้นข้อมูล | เสียแล้วเกิดอะไร |
|---|---|---|
| รหัสผ่านและความลับ TOTP ของผู้ใช้ | C1 | ยึดบัญชีได้ · ความลับ TOTP ถูก encrypt at rest (ADR 0046) รหัสผ่านเป็น scrypt |
| ข้อมูลงานและหมวดของผู้ใช้ | C2 | ความเป็นส่วนตัวของเจ้าของข้อมูลเสีย (PDPA) |
| ความต่อเนื่องของสาย audit | C2 | **ตรวจสอบย้อนหลังไม่ได้อีกเลย** — เป็นของที่กู้คืนไม่ได้ ต่างจากข้อมูลที่มี backup |
| API token | C1 | เข้าถึง `/api/v1` ของเจ้าของ token ได้เต็มสิทธิ์ |
| ความลับของ CI (`POSTURE_TOKEN`) | C1 | อ่านท่าทีของ repo ได้ (อ่านอย่างเดียว) |
| ตัวตนของ release ที่เซ็นแล้ว | — | ผู้ใช้ปลายทางติดตั้งของปลอมโดยเชื่อว่าเป็นของเรา |

## 3. ผู้กระทำและเส้นแบ่งความเชื่อ

| ผู้กระทำ | เข้าถึงอะไรได้ | เส้นแบ่งที่เขาข้ามไม่ได้ | อะไรบังคับ |
|---|---|---|---|
| คนนอกที่ไม่มีตัวตน | route สาธารณะ 11 ตัว (ข้อ 4) | ทุกอย่างที่เหลือ | `gate route-authz-enumerated` · `gate csrf-guards-every-form` |
| ผู้ใช้ที่ login แล้ว | ข้อมูล**ของตัวเอง**เท่านั้น | ข้อมูลของคนอื่น · หน้าผู้ดูแล | `gate authz-in-service-layer` (ตรวจที่ service ไม่ใช่ที่ route) · ADR 0004 (ของคนอื่น = 404 ไม่ใช่ 403) |
| ผู้ดูแล (admin) | ข้อมูลของคนอื่นผ่านหน้า admin | ค่า C1/C3 ไม่ออกจอ · C2 ถูก mask | ADR 0045 · `gate every-column-classified` · unmask เป็น POST ที่ลง audit |
| ผู้ถือ API token | `/api/v1` ในสิทธิ์ของเจ้าของ token | หน้าเว็บ HTML (loader จำกัดด้วย path `/api/`) · การออก token ใบใหม่ | ADR 0017 · ADR 0018 |
| ผู้ใช้ CLI บนโฮสต์ | ทุกอย่างในฐาน | — (ตัวตนที่แรงที่สุดโดยตั้งใจ) | เป็นเส้นทางกู้ระบบ · ทุกการเขียนยังลง audit |
| โค้ดของ plugin | เฉพาะตารางของตัวเอง | ตารางของ core · migration ของ core | ADR 0023 · ชื่อตารางถูกบังคับตอนโหลด |
| CI (workflow) | secret ที่ job นั้นประกาศ | secret ของ job อื่น · การเขียน main | `permissions:` ต่อ job · `gate platform-posture-verified` |
| ผู้ร่วมพัฒนาภายนอก | fork + PR | secret ทุกใบ · การ merge | GitHub ไม่ส่ง secret ให้ fork · required check 27 ตัว |

## 4. ผิวการโจมตี — ทางเข้าที่มีอยู่จริง

| ผิว | ทางเข้า | ภัยหลักที่คิดถึง | อะไรขวางอยู่ |
|---|---|---|---|
| HTTP ที่ไม่ต้องมีตัวตน | `login` · `verify` · `sso_begin` · `sso_callback` · `privacy` · `set_language` · `set_mode` · `theme_stylesheet` · `healthz` · `readyz` · `metrics` | เดารหัสผ่าน · ยัด session · path traversal ผ่านชื่อธีม · ดูดข้อมูลจาก endpoint ของเครื่อง | `gate login-rate-limited-two-ways` (ต่อ IP **และ** ต่อชื่อผู้ใช้) · ไอดีธีมถูกตรวจกับรายการจริง · `/metrics` ต้องมี token เสมอ · `/healthz` ไม่แตะ DB |
| HTTP ที่มีตัวตน | ทุก route ที่เหลือ | ยกระดับสิทธิ์ · IDOR · CSRF · XSS | filter `user_id` ทุก query · CSP `'self'` ไม่มี `unsafe-inline` · `CSRFProtect` ทั้งแอป · `gate csp-no-inline` |
| `/api/v1` | token ใน header | token รั่ว · CSRF ข้ามชั้น · ยิงสุ่มพารามิเตอร์ | เก็บ sha256 ไม่ใช่ token ดิบ · เทียบด้วย `compare_digest` · ด่านตรวจ `g.api_token` ไม่ใช่ session · `gate api-fuzzed-from-spec` ยิง fuzz จาก spec ทุก push |
| session | คุกกี้ | ขโมยคุกกี้ · session fixation · ใช้คุกกี้เก่าหลังเปลี่ยนรหัส | ผูก HMAC กับ `password_hash` ปัจจุบัน · ล้าง session ทั้งใบตอน login · idle 30 นาที + absolute 12 ชม. ตรวจที่ server · `gate session-hardening` |
| สาย audit | ทุกการเขียน DB | แก้/ลบร่องรอย · ตัดสายเงียบ ๆ | เติมได้อย่างเดียว (`before_flush` ปฏิเสธ update/delete) · hash chain + แถวล็อกเดียว (ADR 0035) · `gate every-write-audited` |
| จุด plug ของ plugin | ไดเรกทอรีบนดิสก์ | โค้ดแปลกปลอม · ไลบรารีของ plugin ลากของเข้ามา | plugin import ได้แค่ stdlib + ที่ manifest ประกาศ (สแกน AST) · ตารางต้องขึ้นต้นด้วย prefix ของตัวเอง · `DISABLED_PLUGINS` ปิดได้ทันทีโดยไม่ต้อง deploy |
| ความลับตอนรัน | env · ไฟล์ · Vault | ความลับหลุดเข้า git · ความลับหายแล้วแอปตกกลับค่าเริ่มต้น | `gate push-secret-scan` (gitleaks ทุก push) + push protection · `gate config-fails-loud` (ไม่มี `SECRET_KEY` = ไม่ start) · "ถามแหล่งไม่ได้" ≠ "ไม่มีชื่อนั้น" (ADR 0030) |
| image และ stack | container ที่ deploy | base image มี CVE · image ของ service ถูกสลับ | `gate image-os-cve-audit` (trivy สองทิศ) · `gate image-digest-pinned` · `gate stack-images-pinned-and-moved` |
| supply chain | dependency · action · release | ของปลอมถูกติดตั้ง · ของที่เซ็นไม่ใช่ของเรา | ตรึงด้วย hash ทุกภาษา · `gate actions-sha-pinned` · `gate release-signed-and-attested` (keyless + SLSA verify สองทิศก่อนแนบ) |
| ท่าทีของแพลตฟอร์ม | GitHub settings | ปิด branch protection เงียบ ๆ | `gate platform-posture-verified` เทียบ API กับที่ ADR 0053 ประกาศทุก push |

## 5. สามเส้นทางที่ถ้าพังแล้วเจ็บที่สุด

**5.1 login → session** · ผู้โจมตีที่รู้รหัสผ่านแต่ไม่มีปัจจัยที่สอง **ต้องหยุดที่
ครึ่งทาง**: `/login/verify` ไม่เรียก `login_user()` ก่อน จึงไม่มีสิทธิ์อะไรเลย
แม้จะพิมพ์ URL อื่น (ADR 0024) · สถานะครึ่งทางมีอายุ 5 นาทีและมีโควตาต่อบัญชี ·
คุกกี้ผูกกับ `password_hash` ปัจจุบัน การเปลี่ยนรหัสจึงตัดคุกกี้ทุกใบทันที
**สิ่งที่ยังเปิดอยู่**: ไม่มีหน้า "อุปกรณ์ที่ login อยู่" เพราะยังไม่มี session
store ฝั่ง server (ADR 0020) — ไล่ออกทีละเครื่องไม่ได้ ทำได้แค่เปลี่ยนรหัส

**5.2 การต่อสาย audit** · ทุกการเขียนต้องต่อ hash chain และผู้เขียนหลายรายต้อง
ต่อคิวกันที่แถวล็อกเดียว (ADR 0035) — **ผลที่ยอมรับโดยรู้ตัวคือการเขียนที่ต้องลง
audit serialize กันทั้งระบบ** ซึ่งเป็นสิ่งที่สายแบบนี้ต้องการโดยนิยาม ·
การ purge ตัดได้จากหัวสายเท่านั้น และต้องเขียน checkpoint ก่อนลบ ไม่งั้นสายที่
เหลือจะ "ผ่าน" โดยไม่ผูกกับประวัติที่มันอ้างว่าแทน

**5.3 การโหลด plugin** · registry อ่านดิสก์ทุกครั้ง ไม่มี cache — ใครวางไดเรกทอรี
ลงไปได้ ก็รันโค้ดในสิทธิ์ของแอปได้ · **นี่คือขอบเขตของสมมติฐานข้อ (ค)**: การเขียน
ไฟล์ลง `app/plugins/` ถือเป็นการเข้าถึงระดับโฮสต์ ซึ่ง model นี้ถือว่าเทียบเท่า
การยึดเครื่องแล้ว · สิ่งที่ยังบังคับได้คือ *ขอบเขตของ plugin ที่ตั้งใจติดตั้ง*:
import ได้เฉพาะที่ประกาศ · ตารางต้องมี prefix ของตัวเอง · ปิดด้วยสวิตช์ได้ทันที

## 6. สิ่งที่รู้ว่ายังไม่ได้ป้องกัน (residual)

| ช่องที่เปิดอยู่ | ทำไมยังเปิด | อยู่ที่ไหน |
|---|---|---|
| ไม่มีผู้อนุมัติคนที่สองก่อน merge | ผู้ดูแลคนเดียว | ADR 0053 · `OSPS-QA-07.01` |
| ไม่มี recovery code ของ MFA | ทางกู้คือ CLI ของผู้ดูแล ซึ่งเพียงพอในสเกลนี้ | ADR 0033 · `CLAUDE.md` หัวข้อยังไม่ได้ทำ |
| ไม่มี session store ฝั่ง server | ต้องมีที่เก็บเพิ่มและตัวหมดอายุของมันเอง | ADR 0020 |
| ยังไม่ลองใหม่เมื่อ MySQL deadlock | ดีดกลับเป็น 500 ให้ผู้ใช้เห็น 2 ครั้งต่อรอบที่ 25 VUs | `CLAUDE.md` หัวข้อยังไม่ได้ทำ |
| ยังไม่เคย pentest โดยคนนอก | มีแถวรอบตรวจพร้อมเงื่อนไขเริ่ม | [SECURITY-CADENCE.md](SECURITY-CADENCE.md) |

## 7. สิ่งที่ model นี้ตอบไม่ได้

- **ไม่ได้ให้คะแนนความน่าจะเป็น** — นั่นเป็นงานของทะเบียนความเสี่ยงซึ่งมีสูตรของมัน
- **ไม่ครอบ threat ที่มาจากผู้ให้บริการ** — อยู่ใน [SUPPLY-CHAIN.md](SUPPLY-CHAIN.md)
- **ไม่ใช่ผลของการทดสอบเจาะระบบ** — เป็นการวิเคราะห์จากภายใน · ข้อจำกัดนี้เป็น
  เหตุผลที่แถว pentest ในตารางรอบตรวจยังต้องอยู่
