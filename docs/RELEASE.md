# ขั้นตอนออก release — และงานที่ผูกกับรุ่นถัดไป

ขั้นตอนมาตรฐานเคยอยู่แค่ในบันทึกการทำงาน — เขียนเป็นเอกสารตั้งแต่รอบนี้
เพราะรุ่นถัดไปมี**งานที่สัญญาไว้ในเอกสารอื่นสี่ชิ้น**ผูกอยู่ ลืมชิ้นไหน
คำสัญญาในไฟล์นั้นกลายเป็นเท็จทันที · แถวทวงอยู่ในตาราง cadence ของ
`SECURITY-CADENCE.md` (เงื่อนไข "เมื่อจะออก release ถัดไป")

## ขั้นตอนมาตรฐาน (ใช้จริงมาแล้ว v1.1.0–v1.5.0 — รุ่นหลังคือรอบแรกของเส้นทางเซ็น)

1. รอบตรวจเอกสารก่อนออก — ทุก claim ปัจจุบันต้องตรงความจริง
2. `CHANGELOG.md`: ยก `[Unreleased]` เป็น `[X.Y.Z] — วันที่` + เติม
   `[Unreleased]` ว่างใหม่ + ลิงก์เทียบรุ่นท้ายไฟล์
3. ขยับ `__version__` ใน `app/__init__.py` (เทสต์ผูกกับ CHANGELOG สองที่)
4. PR → `gh pr merge N --rebase --delete-branch --auto` (**ทางเดียว — ADR
   0053 ไม่มี bypass** · auto-merge ให้ GitHub ตัดสินตอน 27 check ครบ)
5. tag แบบ annotated บน merge commit → push tag → job `n-1` ขยับ anchor เอง
6. `gh release create` พร้อม notes — **ไม่ต้องแนบ SBOM เอง**: `release.yml`
   (ADR 0058) generate + เซ็น + แนบให้ตอน publish · รอ workflow จบแล้ว
   ยืนยันจำนวน asset (SBOM 8 + bundle ลายเซ็น 8) และหน้า release ตอบ 200
7. อัปเดตช่อง About ของ repo — **สองช่อง ไม่ใช่ช่องเดียว**:
   - `description`: อัปเดตเลขรุ่น (เคยพลาดค้าง v1.1.0 มาสามรุ่นเพราะ
     ขั้นตอนนี้เขียนแค่ "อัปเดต About" โดยไม่บอกว่ามีอะไรบ้าง)
   - `Website` (homepage): ตั้งเป็น
     `https://github.com/sayam/flask-todolist/releases/latest` **ถาวรแล้ว**
     (2026-08-16) — มัน redirect ไปรุ่นล่าสุดเอง ห้ามเปลี่ยนกลับเป็น URL
     ของ tag ใดตายตัว ขั้นตอนนี้จึงเหลือแค่ตรวจว่าค่ายังถูก

## งานที่ผูกกับรุ่นถัดไป (ตั้งแต่ v1.5.0)

### 1. ระบุ CVE ที่แก้ลง release notes — **ทำแล้วใน v1.5.0 · เป็นกฎประจำทุกรุ่น**

v1.5.0 เป็นรุ่นแรกที่เข้าเงื่อนไขและ notes ระบุครบทั้งเจ็ด CVE ของ
cryptography · **กฎประจำจากนี้**: ทุกรุ่นที่ CHANGELOG มีหัวข้อ Security
ที่แก้ CVE ของ*ของที่ ship จริง* → notes ต้องมีหัวข้อ Security ระบุ ID ครบ
(ฝั่งเครื่องมือ CI เล่าเป็นหมายเหตุได้ แต่ไม่นับเป็น "ซอฟต์แวร์ที่โครงการ
ผลิต") · รุ่นที่ไม่มี CVE ใหม่ = ช่อง `release_notes_vulns` ของ
bestpractices คงชี้ v1.5.0 ต่อได้ ไม่ต้องแก้

### 2. เซ็น release + provenance — **สร้างแล้ว (ADR 0058)**

`release.yml` ทำงานเองตอน release ถูก publish: generate SBOM จากโค้ดของ
tag → เซ็น keyless → verify สองทิศ → แนบ provenance → อัปโหลด · ขั้นตอน
manual จึงเปลี่ยนเป็น **สร้าง release พร้อม notes เปล่า ๆ ไม่ต้องแนบ SBOM
เอง** (workflow แนบให้) · ล้มกลางทางรันซ้ำด้วย workflow_dispatch ใส่ tag
· signed commits เลื่อนต่อพร้อมเงื่อนไขใน ADR 0058

### 3. ปรับ bestpractices.dev (#14085) — ช่องที่ผูกกับรุ่น

- `release_notes_vulns`: เลิกตอบ "ยังไม่เคยมี" → ชี้ notes ของรุ่นใหม่ (ข้อ 1)
- `version_unique` / `version_tags`: เขียนแบบช่วง — แก้เลขปลายเป็น tag ใหม่
- `maintained`: เลขรุ่น + วันที่ล่าสุด
- `description`: เลขรุ่น (และเลข check ถ้าเปลี่ยน)
- ถ้าทำข้อ 2 แล้ว: ทบทวนเกณฑ์กลุ่ม `signed_releases` ด้วย
- verify จาก `https://www.bestpractices.dev/projects/14085.json` เสมอ
  (repo_url ต้องเป็นของเรา — เคยได้เลขโครงการผิดมาสามรอบ)

### 4. ขยับ badge เวอร์ชันใน `README.md`

badge ท้ายไฟล์เป็น static — แก้เลขในบรรทัด
`img.shields.io/badge/version-vX.Y.Z-blue` ให้ตรง tag ใหม่
(หรือเปลี่ยนเป็น `img.shields.io/github/v/release/...` ให้ขยับเองก็ได้
— ตัดสินตอนนั้น) · ช่อง About (ขั้นตอนมาตรฐานข้อ 7) ไปด้วยกัน

### 5. รุ่นที่เปลี่ยนสัญญาอนุญาต — ทำครั้งเดียวที่ v2.0.0 (ADR 0070)

ถ้ารุ่นไหนเปลี่ยน license ต้องเพิ่มสามอย่างในรุ่นนั้น: **notes ต้องบอกเส้นแบ่ง
ให้ชัด** ว่าอะไรยังเป็นสัญญาเดิม (ที่นี่: ทุกอย่างถึง `v1.6.0` ยังเป็น MIT
ตลอดไป) · ตรวจว่า GitHub ตรวจจับ license ใหม่ได้จริง
(`gh api repos/:owner/:repo --jq .license.spdx_id`) · และทบทวนช่อง
`floss_license*` ของ bestpractices

**DOI**: เมื่อเชื่อม Zenodo กับ repo แล้ว tag ถัดไปจะถูก archive อัตโนมัติ ·
`CITATION.cff` กับ `.zenodo.json` อยู่ที่รากแล้ว — Zenodo อ่านสองไฟล์นั้นเอง

**ตรวจว่าเชื่อมแล้วจริง ก่อนสร้าง release เสมอ** (บทเรียนจากรอบ v2.0.0–v2.0.2):

```
gh api repos/:owner/:repo/hooks --jq 'length'    # ต้องได้ 1 ไม่ใช่ 0
```

Zenodo มินต์ DOI ให้เฉพาะ release ที่สร้าง **หลัง** เปิดสวิตช์ของ *repo นั้น*
และ **ไม่ archive ย้อนหลัง** · การสมัครบัญชี Zenodo กับการเปิดสวิตช์ต่อ repo
เป็นคนละขั้น — ขั้นที่สองคือขั้นที่ติดตั้ง webhook ให้ ซึ่งคำสั่งข้างบนเห็น ·
เสียไปสองรุ่นเพราะเชื่อว่า "สมัครแล้ว = เชื่อมแล้ว" โดยไม่ได้ตรวจ ทั้งที่มีคำสั่ง
ที่ตอบได้ในหนึ่งบรรทัด — **สัญญาณที่วัดได้มีอยู่ ก่อนที่จะต้องเดา**

**แล้วต้องตรวจอีกครั้ง *หลัง* สร้าง release — ที่ Zenodo ไม่ใช่ที่ GitHub**
(บทเรียนจากรอบ v2.1.0):

```
curl -s "https://zenodo.org/api/records?q=conceptrecid:22015133&all_versions=true&size=50" \
  | python3 -c "import json,sys; [print(h['metadata']['version'], h['doi']) \
                for h in json.load(sys.stdin)['hits']['hits']]"
```

รุ่นที่เพิ่งออกต้องอยู่ในรายการนั้น · **คำสั่งนับ webhook ข้างบนตอบคนละคำถาม** —
มันตอบว่า "สายยังต่ออยู่ไหม" ไม่ได้ตอบว่า "รุ่นนี้ถูก archive แล้วหรือยัง"

v2.1.0 ทำให้เห็นว่าทำไมสองคำถามนี้แยกกันไม่ได้: หน้า webhook ของ GitHub รายงาน
ว่า delivery **ล้มเหลวทุกใบ** (`created`/`published` ได้ 500 พร้อมข้อความ
`context deadline exceeded ... giving up after 1 attempt` · `released` ได้ 403
· มี 502 อีกใบ) แต่ Zenodo **archive สำเร็จ** และมินต์ `10.5281/zenodo.22027978`
ให้เรียบร้อย — ที่ timeout คือ *response ขากลับ* ไม่ใช่ตัวงาน และ GitHub
ไม่ลองใหม่ให้

สถานะที่ GitHub แสดงจึงเป็นเท็จได้ทั้งสองทิศ: แดงทั้งที่สำเร็จ (รอบนี้) และ
วันหนึ่งจะเขียวทั้งที่ Zenodo ปฏิเสธ · **ตัวที่ตอบได้คือระบบที่ถือคำตอบอยู่**
ซึ่งก็คือ Zenodo — หลักเดียวกับที่ `ci:siem` ถามสถานะ alert จาก ruler ของ Loki
ตรง ๆ แทนที่จะดูว่า stack ขึ้นได้ไหม

### token ของ Zenodo — **หมุนไม่ได้ และห้ามพิมพ์ออกมา**

token อยู่ใน **query string ของ URL ปลายทางของ webhook** (ดีไซน์ของ Zenodo เอง)
คำสั่งที่ list hook ของ repo จึงคืนมันมาเป็น plaintext · **เรียกแบบกรองเสมอ**
อย่าเรียกทั้งก้อนแล้วอ่านเอา:

```
gh api repos/:owner/:repo/hooks --jq '.[] | {id, active, events, host: (.config.url | split("?")[0])}'
```

ที่เหลือของหัวข้อนี้คือผลการทดลองเมื่อ 2026-08-20 ที่จบลงด้วยคำตอบว่า
**ไม่มีทางหมุนผ่านหน้าเว็บ** — เขียนไว้เพื่อไม่ให้ใครเสียเวลาลองซ้ำ:

| ทางที่ลอง | ผล |
|---|---|
| Zenodo → Applications → Personal access tokens | **ใบนี้ไม่อยู่ในรายการ** — เป็น token ที่ Zenodo สร้างและถือไว้เองสำหรับ GitHub integration ไม่ใช่ personal access token จึงไม่มีปุ่มถอน |
| Zenodo → GitHub → ปิดสวิตช์ของ repo แล้วเปิดใหม่ | ได้ hook **ใบใหม่** (`id` เปลี่ยน · `created_at` เป็นวันนี้) แต่ **ค่า token เดิมทุกตัวอักษร** — Zenodo หยิบใบที่บัญชีมีอยู่แล้วมาใส่กลับ |
| Zenodo → Linked accounts → GitHub | **ไม่มีปุ่ม disconnect** เพราะ GitHub เป็นทางล็อกอิน Zenodo ของบัญชีนี้ |
| GitHub → Applications → Authorized OAuth Apps → Zenodo → Revoke | **ตัดคนละใบ** — ใบนั้นคือสิทธิ์ที่ *Zenodo* ใช้อ่าน repo และดาวน์โหลด tarball ของ release · ตัดแล้วใบที่หลุดยัง live เหมือนเดิม ส่วนการ archive พังเพราะ Zenodo ดึงไฟล์ไม่ได้ — เสียทั้งสองทาง |

**เกณฑ์ตัดสินว่าหมุนสำเร็จ คือค่าของ token ไม่ใช่เลข `id`** — บทเรียนของรอบนั้น
เอง: เกณฑ์ "`id` ต้องเป็นเลขใหม่" ที่เขียนไว้ก่อนหน้า **ผ่านได้ทั้งที่ token
ไม่ได้เปลี่ยน** ซึ่งเป็นด่านที่วัดสัญญาณผิดตัวอีกใบ ในเอกสารที่เพิ่งเขียนขึ้น
มาแก้ปัญหาชนิดเดียวกัน · เทียบด้วยลายนิ้วมือ ไม่ใช่ด้วยตา และไม่พิมพ์ค่าออกมา:

```
TOKEN=$(gh api repos/:owner/:repo/hooks --jq '.[0].config.url' | sed 's/.*access_token=//')
printf %s "$TOKEN" | sha256sum | cut -c1-16      # 2026-08-20: fe36a137c98aceee
unset TOKEN
```

ความเสี่ยงที่เหลือถูกรับไว้อย่างเปิดเผยพร้อมเงื่อนไขปลดใน
[RISK-ASSESSMENT.md](RISK-ASSESSMENT.md) — **ตัวจับคือขั้นถาม Zenodo หลังออกรุ่น**
ข้างบน: record ที่โผล่มาโดยไม่มีใครสั่ง จะเห็นที่นั่นเป็นที่แรก

## หลังออกรุ่น

- แถว cadence ของงานชุดนี้: ขยับ "ครั้งล่าสุด" แล้วเปลี่ยนเงื่อนไขครบ
  กำหนดเป็นของรุ่นถัดไป (ข้อ 1/3/4 เป็นงานประจำทุกรุ่น · ข้อ 2 สร้างเสร็จ
  แล้ว — เหลือแค่ยืนยันว่า workflow เขียวทุกรุ่น)
- **ยืนยันว่ารุ่นนี้ถูก archive จริง — ถามที่ Zenodo** (คำสั่งอยู่ในหัวข้อ
  DOI ข้างบน) · หน้า webhook ของ GitHub ตอบคำถามนี้ไม่ได้ และเคยตอบผิดมาแล้ว
  ทั้งที่ Zenodo ทำงานสำเร็จ (v2.1.0)
- อัปเดต `docs/BEST-PRACTICES.md` ให้ตรงกับที่กรอกจริง — **เลขรุ่นในไฟล์นั้นมี
  เทสต์อ่านคู่กับ `__version__` แล้ว** (`tests/test_contributor_docs.py`) ดังนั้น
  ถ้าลืม จะไม่ใช่การล้าสมัยอย่างเงียบ ๆ แต่เป็น CI แดง · รอบ v1.6.0 ลืมจริงและไม่มีอะไร
  ฟ้องจนถึงรอบตรวจถัดมา ซึ่งเป็นเหตุที่เทสต์นั้นเกิด
