# 0028 — OIDC เป็นปัจจัยหลักตัวที่สอง: IdP บอกว่า "ใคร" แอปยังเป็นคนบอกว่า "ทำอะไรได้"

สถานะ: accepted (2026-08-10) — Phase 5 · P5-13

**บริบท:** ADR 0024 วาง seam ของปัจจัยที่สองไว้แล้ว และประกาศว่า `password` เป็น
plugin ชนิด `auth` ที่เป็น `"factor": "primary"` — แต่ยังเป็น plugin ที่มีแต่
manifest เพราะ core ยังเรียก `check_password()` ตรง ๆ **จุดที่จะพิสูจน์ว่า seam
นั้นเป็นของจริง คือวันที่มีปัจจัยหลักตัวที่สอง** ซึ่งคือ ADR นี้

SSO ถูกเลื่อนจาก Phase 4 มาที่นี่ด้วยเหตุผลข้อเดียว: **DoD คือ login กับ IdP จริง
ไม่ใช่ mock** ซึ่งต้องมี container stack ของเฟสนี้ก่อน (มีแล้วตั้งแต่ P5-10 —
Keycloak 26 ใน `compose.sso.yaml`)

## คำตัดสิน

### 1. **ไม่มี user store ใหม่** — `sub` ผูกเข้ากับ `tdl_user` เดิม

ตารางของ plugin (`tdl_auth_oidc_identity` ตาม ADR 0023) เก็บแค่คู่
`(issuer, sub) → user_id` **ไม่เก็บชื่อ ไม่เก็บอีเมล ไม่เก็บ token**
ทุกอย่างที่แอปใช้ตัดสินใจยังอยู่ใน `tdl_user` ตัวเดิม

ผลที่ตั้งใจ: ทุกอย่างที่เขียนมาสี่เฟส — `user_id` ในทุก query, soft delete,
audit, purge, RBAC — ใช้ได้กับผู้ใช้ที่มาจาก IdP **โดยไม่ต้องแก้อะไรเลย**
และ **ถอน plugin ทิ้ง = ตารางผูกหายไป ผู้ใช้ยังอยู่ครบ** (กลับไป login ด้วย
รหัสผ่าน ซึ่งผู้ดูแลตั้งให้ใหม่ได้ด้วย `flask set-password`)

**ผูกด้วย `sub` ไม่ใช่ชื่อผู้ใช้** เพราะ `sub` เป็นตัวระบุที่ IdP รับประกันว่า
ไม่ซ้ำและไม่เปลี่ยน ส่วน `preferred_username` เปลี่ยนได้ — ผูกด้วยชื่อแปลว่า
วันที่มีคนเปลี่ยนชื่อตัวเองใน IdP เป็นชื่อของคนอื่นที่เพิ่งลาออก เขาจะได้บัญชีนั้นไป

### 2. **การผูกครั้งแรกใช้ `preferred_username` และนั่นคือความไว้วางใจที่ต้องพูดออกมา**

ครั้งแรกที่ `sub` ยังไม่เคยผูกกับใคร ระบบหาผู้ใช้จาก `preferred_username`
**ถ้าไม่เจอ = ปฏิเสธ** (ดูข้อ 3) ถ้าเจอก็ผูกแล้วจำไว้ตลอด ครั้งต่อไปใช้ `sub` อย่างเดียว

ข้อนี้แปลว่า **IdP ต้องไม่ปล่อยให้ผู้ใช้เปลี่ยน `preferred_username` เป็นอะไรก็ได้**
ไม่งั้นคนที่เปลี่ยนชื่อตัวเองเป็น `somchai` ก่อนที่ `somchai` ตัวจริงจะเคย
login ผ่าน SSO จะได้บัญชีนั้นไป — เขียนไว้ตรงนี้เพราะเป็นเงื่อนไขที่มองไม่เห็น
จากในโค้ด และเป็นความไว้วางใจชนิดเดียวกับที่เราให้ IdP อยู่แล้วตอนยอมให้มัน
บอกว่าใครเป็นใคร (ต่างกันแค่ว่าข้อนี้ไม่มีใครนึกถึง)

### 3. **สร้างผู้ใช้ให้อัตโนมัติ = ปิดไว้เป็นค่าเริ่มต้น** (`OIDC_AUTO_CREATE`)

CLAUDE.md บันทึกไว้ตั้งแต่ต้นว่า "ไม่มีหน้าสมัครสมาชิก โดยตั้งใจ" — การเปิด SSO
แล้วให้ใครก็ตามใน IdP มีบัญชีที่นี่ทันทีคือการยกเลิกคำตัดสินนั้นเงียบ ๆ ผ่าน
ประตูหลัง องค์กรที่ IdP ครอบทุกคนในบริษัทจะได้ผู้ใช้เท่าจำนวนพนักงานโดยไม่มีใครสั่ง

ค่าเริ่มต้นจึงเป็น "ผู้ดูแลสร้างบัญชีไว้ก่อนด้วย `flask create-user` แล้ว SSO
แค่ผูกให้" · เปิด `OIDC_AUTO_CREATE=1` ได้เมื่อ**ตั้งใจ**ให้ IdP เป็นคนตัดสินว่า
ใครมีบัญชี ซึ่งเป็นคำตอบที่ถูกสำหรับหลายองค์กร แต่ต้องเป็นการเลือก ไม่ใช่ผลข้างเคียง

### 4. **ยืนยัน ID token ด้วย TLS ไม่ใช่ด้วยลายเซ็น — และนั่นคือสิ่งที่สเปกอนุญาต**

OIDC Core 1.0 หัวข้อ 3.1.3.7 ข้อ 6: ID token ที่ได้มาจาก **token endpoint โดยตรง**
ผ่านช่องทางที่ TLS ยืนยันตัวตนของ server แล้ว **ใช้การยืนยันของ TLS แทนการตรวจ
ลายเซ็นได้** ซึ่งตรงกับสถานการณ์ของเราเป๊ะ: authorization code flow กับ client
ที่มีความลับ (confidential) และเราเป็นคนเปิดการเชื่อมต่อไปหา token endpoint เอง

**นี่ไม่ใช่การเขียน crypto เอง แต่คือการไม่ต้องมี crypto ตั้งแต่แรก** — ต่างจาก
TOTP (ADR 0024) ที่เขียน HMAC-SHA1 เองเพราะมี test vector ทางการให้ยืนยัน
การตรวจลายเซ็น JWT ต้องมี JWKS, การเลือก key ตาม `kid`, RSA/EC และการหมุนคีย์
ซึ่ง**ไม่ควรเขียนเอง** ทางเลือกจึงมีสองทางคือแบก dependency หรือใช้ข้อที่สเปกให้
เราเลือกทางหลัง แลกกับข้อจำกัดที่ต้องรักษาไว้ให้ครบ:

- **รับเฉพาะ authorization code flow** — implicit/hybrid ที่ ID token เดินทาง
  ผ่าน browser **ต้องตรวจลายเซ็น** ไม่มีข้อยกเว้น ถ้าวันหนึ่งมีใครเพิ่ม flow นั้น
  ข้อนี้ตกทันทีและต้องกลับมาแก้ ADR ก่อน
- **`issuer` ต้องเป็น https และใบรับรองต้องถูกตรวจจริง** ยกเว้นเมื่อตั้ง
  `OIDC_INSECURE_ISSUER=1` ซึ่งมีไว้สำหรับ IdP ทดสอบในเครื่องเท่านั้น และ
  **แอปจะ log เตือนทุกครั้งที่ start** — ปิด TLS แล้วข้อ 4 ทั้งข้อไม่เหลืออะไรเลย
- ยังต้องตรวจ `iss`, `aud`, `exp`, `nonce` เองครบทุกตัว การไม่ตรวจลายเซ็น
  ไม่ได้แปลว่าเชื่อเนื้อในดิบ ๆ

เพิ่ม `state` + PKCE (S256) ด้วย ซึ่งกันคนละเรื่องกัน: `state` กัน CSRF ของ
callback, PKCE กันคนที่ขโมย code ระหว่างทางเอาไปแลก token, `nonce` กัน
การเอา ID token เก่ามาใช้ซ้ำ

**ผลพลอยได้ที่สำคัญ: plugin นี้ไม่มี `requires.pip` เลย** ใช้ stdlib ล้วน
ถอนไดเรกทอรีทิ้งแล้วไม่มี supply chain อะไรค้าง (ADR 0025 ในรูปที่แข็งแรงที่สุด)

### 5. **group → role ที่มีอยู่แล้ว และ IdP เป็นเจ้าของคำตอบ**

ถ้าตั้ง `OIDC_ADMIN_GROUP` ไว้ ระบบอ่าน claim `groups` แล้วตั้ง `User.role`
ตามนั้น **ทุกครั้งที่ login** — อยู่ในกลุ่ม = `admin`, ไม่อยู่ = `user`
การถอดสิทธิ์ที่ IdP จึงมีผลจริงโดยไม่ต้องมาไล่แก้ที่นี่ (ซึ่งคือเหตุผลที่
องค์กรใช้ SSO ตั้งแต่แรก)

**ไม่ตั้ง = ไม่แตะ `role` เลย** ไม่ใช่ตั้งเป็น `user` — เพราะผู้ดูแลที่ตั้ง
บทบาทเองด้วย `flask set-role` ไว้ ต้องไม่ถูกลดสิทธิ์เพราะ IdP ไม่ได้ส่ง claim
ที่เราไม่ได้ขอ

### 6. **ปัจจัยที่สองยังเป็นของแอป ไม่ใช่ของ IdP**

login ผ่าน SSO สำเร็จแล้ว **ยังต้องเดินผ่านด่าน MFA เดิม** ถ้าผู้ใช้เปิดไว้
(เส้นทางเดียวกับรหัสผ่านเป๊ะ — `_complete_login()` ตัวเดียวกัน)

เหตุผล: ADR 0024 ตัดสินว่า "หยุดครึ่งทางก่อนเรียก `login_user()`" เพื่อไม่ให้คน
ที่ผ่านปัจจัยแรกอย่างเดียวเข้าถึงข้อมูลได้ ปัจจัยแรกจะเป็นรหัสผ่านหรือ IdP
ไม่ได้เปลี่ยนเหตุผลนั้น · IdP ที่บังคับ MFA ของตัวเองอยู่แล้วก็ยังปิดของแอปได้
เป็นราย ๆ (ผู้ใช้ไม่ต้องลงทะเบียนปัจจัยที่สองที่นี่) แต่นั่นเป็นการ *เลือก*

### 7. **รหัสผ่านยังใช้ได้เสมอ ปัจจัยหลักสองตัวอยู่ร่วมกัน**

หน้า login มีทั้งฟอร์มรหัสผ่านและปุ่มของ IdP — **ไม่มีโหมด "SSO เท่านั้น"**
เพราะวันที่ IdP ล่มหรือ config ผิด ทางเข้าที่เหลืออยู่คือสิ่งเดียวที่ทำให้
แก้ปัญหาได้ (หลักเดียวกับที่ไม่มี self-service reset แต่มี `flask set-password`)
ผู้ดูแลที่ต้องการปิดรหัสผ่านของใครทำได้ด้วยการล้าง `password_hash` ของคนนั้น
ซึ่งเป็นการตัดสินใจต่อบัญชี ไม่ใช่สวิตช์ระดับระบบ

### 8. core ยังไม่รู้จักชื่อ `oidc`

`app/services/sso.py` ทำหน้าที่เดียวกับ `app/services/mfa.py`: ถามทุก plugin
ชนิด `auth` ที่เป็น `"factor": "primary"` **ที่ไม่ใช่ `password`** ว่าเริ่มการ
login อย่างไรและรับ callback อย่างไร — `tests/test_plugins.py` ที่ grep หาชื่อ
plugin ในโค้ด core ยังบังคับข้อนี้อยู่เหมือนเดิม

## ผลที่ตามมา

- **ถอน plugin แล้วหน้า login กลับเป็นรหัสผ่านล้วนทันที** ไม่มีโค้ด core ตรงไหน
  ล้มเหลวเพราะหาไม่เจอ (สัญญาเดียวกับธีมตั้งแต่ ADR 0006)
- `DISABLED_PLUGINS` ปิดได้ และเป็นคีย์ที่ต้องมี log เตือนแยกเหมือน MFA เพราะ
  การปิดปัจจัยหลักคือการตัดทางเข้าของคนที่ไม่มีรหัสผ่านในระบบ
- `tdl_auth_oidc_identity` เป็นตารางของ plugin จึงอยู่นอกสาย migration ของ core
  และต้อง `flask plugin-install auth/oidc` เอง (ADR 0023)
- ต้องจำแนกชั้นข้อมูลของคอลัมน์ใหม่ใน `docs/DATA-CLASSIFICATION.md` — `sub`
  เป็นตัวระบุบุคคลจาก IdP ไม่ใช่ความลับ แต่ก็ไม่ใช่ของสาธารณะ
- **ยังไม่ทำ**: single logout (RP-initiated logout ที่ IdP), refresh token
  (แอปไม่เก็บ token ใด ๆ เลยหลังแลกเสร็จ — session ของแอปเป็นของแอป),
  การผูกหลาย IdP กับผู้ใช้คนเดียว
