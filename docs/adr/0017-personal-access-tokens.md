# 0017 — personal access token: กุญแจของเครื่อง แยกจาก session cookie

สถานะ: accepted (2026-08-03) — Phase 3 ด่านที่สอง

**บริบท:** `/api/v1` (ADR 0018) ต้องมีวิธียืนยันตัวตนที่ **ไม่ใช่ session
cookie** เพราะ cookie ถูกออกแบบมาสำหรับเบราว์เซอร์ที่มีคนนั่งอยู่หน้าจอ:
มันถูกแนบไปเองทุกคำขอ (จึงต้องมี CSRF token กำกับ) และหมดอายุตามรอบ session
สคริปต์ที่รันจาก cron ไม่มีทั้งเบราว์เซอร์และคนกรอกรหัสผ่าน

ทางที่ห้ามเลือกตั้งแต่ต้นคือ "ให้สคริปต์เก็บ username/password ไว้แล้ว login
เอง" — นั่นคือการเอาความลับที่กู้บัญชีได้ทั้งใบไปวางไว้ในไฟล์ config ของ
เครื่องอื่น เพิกถอนทีเดียวไม่ได้ จำกัดขอบเขตไม่ได้ และไปโผล่ในสคริปต์ backup

## คำตัดสิน

**ออก personal access token (PAT) เป็นความลับแยกใบต่อการใช้งานหนึ่งอย่าง**
เก็บในตาราง `tdl_api_token` (หนึ่งแถว = หนึ่งใบ) ผูกกับ `tdl_user.id`

### รูปแบบ: `tdl_<id>_<ความลับ>`

* `<id>` = เลขแถว ทำให้หาแถวได้ตรง ๆ ด้วย index หลัก ไม่ต้องอ่านทั้งตาราง
  มาไล่เทียบ hash ทีละใบ (ซึ่งจะกลายเป็น O(n) ต่อหนึ่ง request)
* `<ความลับ>` = `secrets.token_urlsafe(32)` = สุ่ม 256 บิต
* prefix `tdl_` ที่ตายตัวทำให้เครื่องมือสแกน secret (gitleaks ฯลฯ) เขียนกฎจับได้
  ต่างจากสตริงสุ่มเปล่า ๆ ที่แยกไม่ออกจาก id หรือ hash อะไรก็ไม่รู้

### เก็บเป็น sha256 ไม่ใช่ scrypt — ต่างจาก `password_hash` โดยตั้งใจ

เหตุผลของ scrypt/bcrypt คือ "รหัสผ่านที่คนตั้งเองมีเอนโทรปีต่ำ ต้องทำให้การ
ไล่เดาแพงต่อครั้ง" ซึ่งใช้กับค่าสุ่ม 256 บิตไม่ได้เลย — ไม่มี dictionary ของ
ค่าสุ่ม และไม่มี rainbow table ให้ salt ป้องกัน

ในทางกลับกัน scrypt ต่อหนึ่ง request คือ **ช่องยิงถล่มด้วยการเรียก API รัว ๆ**
(คนละสถานการณ์กับหน้า login ที่เกิดไม่บ่อยและมี rate limit คุมอยู่แล้ว)
เทียบค่าด้วย `hmac.compare_digest` ไม่ใช่ `==` เพื่อไม่ให้เวลาที่ใช้เทียบ
บอกใบ้ว่าตรงกันไปกี่ตัวอักษร

`token_hash` เป็น**ชั้น C1** เท่ากับ `password_hash` (docs/DATA-CLASSIFICATION.md)
— ห้ามออกจากระบบทุกกรณี ห้ามลง audit แม้แต่ในรูป hash

### ความลับแสดงครั้งเดียว

`issue()` คืนสตริงเต็มกลับไปครั้งเดียวตอนสร้าง หลังจากนั้นไม่มีทางดูอีก
ทำหายแล้วออกใบใหม่ **นี่คือข้อจำกัดที่ตั้งใจ ไม่ใช่ฟีเจอร์ที่ยังไม่ได้ทำ** —
ระบบที่ "ดูอีกครั้ง" ได้แปลว่ามันเก็บของจริงไว้ที่ไหนสักแห่ง

### เพิกถอน = ล้าง hash ทิ้ง ไม่ใช่แค่ซ่อนแถว

`revoke()` ทั้ง `soft_delete()` และเขียนทับ `token_hash` ด้วย `DISABLED_SECRET`
(`"!"` ตามธรรมเนียม `/etc/shadow`) ทันที ไม่รอ grace period 30 วันเหมือนข้อมูล
ชั้นอื่น เพราะสิ่งที่คนกดเพิกถอนคาดหวังคือ "ใช้ไม่ได้แล้วตั้งแต่วินาทีนี้"
ผลพลอยได้: ต่อให้มีใครกู้แถวคืนมา ใบนั้นก็ยังใช้ไม่ได้

`flask delete-user` ก็ทำแบบเดียวกันกับทุกใบของคนนั้น — ตัวกรอง soft delete
ซ่อนเจ้าของไปแล้วก็จริง แต่ปิดสองชั้นถูกกว่าการต้องพิสูจน์ว่าชั้นเดียวไม่มีทางพลาด

### มีวันหมดอายุเป็นค่าเริ่มต้น (90 วัน)

ใบที่ไม่มีวันหมดอายุต้องขอเป็นพิเศษ (`--expires-days 0`) กุญแจที่ลืมไว้ในเครื่อง
ที่เลิกใช้แล้วคือช่องโหว่ที่ไม่มีใครสังเกตเห็น เพราะมันไม่เคยแจ้งอะไรเลย

### ไม่มีคอลัมน์ `last_used_at`

เขียนทุกครั้งที่เรียก API แปลว่ามี write หนึ่งครั้งต่อหนึ่ง request ซึ่ง
`after_flush` ของ ADR 0015 จะแปลงเป็น **แถว audit หนึ่งแถวต่อหนึ่ง request**
กลบสายหลักฐานด้วยเสียงรบกวนจนอ่านไม่ออก คำถาม "ใบนี้ถูกใช้ครั้งล่าสุดเมื่อไหร่"
ตอบจาก log ที่มี `token_id` อยู่แล้ว (ชั้น C6 เก็บ 90 วัน)

### token ยกระดับเป็น `current_user` แต่ cookie ไม่ยกระดับเป็น token

การยืนยันด้วย token ต้องทำให้ `current_user` ใช้งานได้ ไม่งั้น `actor_id` ใน
audit จะว่างและเราจะไม่รู้ว่าใครแก้ข้อมูล **แต่ทิศกลับกันห้ามเกิด**: endpoint
ของ API ต้องเช็คว่าตัวตนนี้มาจาก token จริง ๆ ไม่ใช่แค่ `current_user
.is_authenticated` — ไม่งั้นเบราว์เซอร์ที่ login ค้างอยู่จะยิง API ที่ยกเว้น CSRF
ได้จากหน้าเว็บของคนอื่น ซึ่งเท่ากับเปิดรู CSRF ที่ปิดไว้ตั้งแต่ Phase 1 กลับมา
(รายละเอียดการบังคับอยู่ใน ADR 0018)

## ผลที่ตามมา

* ตารางใหม่ `tdl_api_token` (migration `c7f1db5e54e4`) เข้าเส้นทางเดิมทุกอย่าง:
  soft delete อัตโนมัติ, audit อัตโนมัติ (`api_token.insert` / `.delete`),
  ถูกล้างจริงโดย `purge-expired` เท่านั้น
* ออก/ดู/เพิกถอนผ่าน CLI ก่อน (`token-create` / `token-list` / `token-revoke`)
  **ยังไม่มีหน้าเว็บ** — หน้า `/settings` จะเพิ่มทีหลังเมื่อ API นิ่งแล้ว
  (การออกกุญแจจากหน้าเว็บต้องคิดเรื่อง re-authentication ก่อน ซึ่งเป็นงานคนละก้อน)
* ยังไม่มี scope/permission ต่อใบ — ทุกใบมีสิทธิ์เท่าเจ้าของ เลือกไว้แบบนี้
  เพราะ scope ที่ไม่มีใครใช้คือความซับซ้อนที่ตรวจสอบไม่ได้ว่าถูกต้อง
  ตัวตารางเพิ่มคอลัมน์ทีหลังได้โดยไม่ต้องเปลี่ยนรูปแบบ token
* ยังไม่มี rate limit เฉพาะของ API (Phase 4 — ต้องมี storage ที่ไม่ใช่ `memory://`
  ก่อน ไม่งั้นเพดานจะกลายเป็น N เท่าตามจำนวน worker)

## ทางเลือกที่ไม่เลือก

* **JWT** — ข้อดีของมันคือ verify ได้โดยไม่แตะฐานข้อมูล ซึ่งแลกมาด้วยการ
  **เพิกถอนทันทีไม่ได้** ต้องมี blocklist ที่ต้องแตะฐานข้อมูลอยู่ดี เท่ากับจ่าย
  ความซับซ้อนแล้วไม่ได้ข้อดีกลับมา ระบบนี้ query ฐานข้อมูลทุก request อยู่แล้ว
* **OAuth 2.0 / OIDC เต็มรูปแบบ** — เหมาะกับการให้ third-party เข้าถึงข้อมูล
  แทนผู้ใช้ ตอนนี้ไม่มี third-party และไม่มีหน้าจอ consent ให้กด เลื่อนไป Phase 5
  ตัว PAT วางไว้เป็น seam ให้เปลี่ยนตัวยืนยันได้โดยไม่ต้องรื้อ service layer
* **HTTP Basic ด้วย username/password** — เอาความลับหลักไปแปะไว้ในทุกเครื่อง
  เพิกถอนแยกใบไม่ได้ และต้องผ่าน scrypt ทุก request
* **API key ใบเดียวต่อผู้ใช้** — เปลี่ยนกุญแจทีเดียวพังทุกเครื่องพร้อมกัน
  คนเลยไม่กล้าเปลี่ยน ซึ่งแย่กว่าการมีหลายใบที่เพิกถอนทีละใบได้
