# 0019 — นโยบายรหัสผ่านตาม NIST SP 800-63B: ยาว + ไม่เคยหลุด ไม่ใช่ "ซับซ้อน"

สถานะ: accepted (2026-08-04) — Phase 4 ด่านแรก

**บริบท:** ก่อนหน้านี้กติกาเดียวที่มีคือ "ยาวอย่างน้อย 8 ตัว" ซึ่งเขียนอยู่ใน
`app/cli.py` จุดเดียว แปลว่า (1) ทางอื่นที่ตั้งรหัสได้ในอนาคตจะไม่มีกติกาเลย
และ (2) `password123` ซึ่งอยู่ในรายการรหัสที่หลุดแล้วทุกฉบับ ผ่านสบาย ๆ

คำถามที่ต้องตัดสินคือ "เพิ่มกฎอะไร" ซึ่งคำตอบที่คนคุ้นเคยที่สุด (ต้องมีตัวใหญ่
ตัวเลข อักขระพิเศษ และเปลี่ยนทุก 90 วัน) คือคำตอบที่ NIST **ถอนออกจากคำแนะนำ
ไปแล้ว** ตั้งแต่ SP 800-63B rev.3 เพราะมีข้อมูลว่ามันได้ผลตรงกันข้าม

## คำตัดสิน

**ยึด NIST SP 800-63B ตรง ๆ** โดยตรรกะทั้งหมดอยู่ใน `app/services/passwords.py`
ที่เดียว (ตาม ADR 0016) — CLI, หน้าเว็บ และทางที่จะเพิ่มทีหลังเรียกตัวเดียวกัน

### กฎที่ตั้งใจ *ไม่* ใส่ (สำคัญเท่ากับกฎที่ใส่)

* **ไม่มี composition rule** — บังคับให้มีตัวใหญ่/ตัวเลข/อักขระพิเศษ แล้วคนจะได้
  `Password1!` ซึ่งเป็นรูปแบบที่เครื่องมือไล่เดารู้จักดีที่สุด กฎพวกนี้ลดพื้นที่
  ค้นหาลงมากกว่าจะเพิ่ม
* **ไม่บังคับเปลี่ยนตามรอบ** — บังคับแล้วคนจะเติมเลขต่อท้ายเป็นวงจร
  (`summer2025` → `summer2026`) และจดไว้ที่ไหนสักแห่ง เปลี่ยนเมื่อ**มีเหตุ**
  (สงสัยว่าหลุด) เท่านั้น
* **ไม่มีคำใบ้รหัสผ่าน (password hint) และไม่มีคำถามกู้บัญชี** — ทั้งคู่คือการ
  เก็บความลับที่อ่อนกว่ารหัสผ่านไว้ข้าง ๆ รหัสผ่าน
* **ไม่ตัดปลายและไม่ตัดช่องว่าง** — ตัดทิ้งเงียบ ๆ แปลว่าความยาวที่ผู้ใช้ตั้งใจ
  ไม่ได้ถูกใช้จริง คนที่ใช้ passphrase จะโดนลดความปลอดภัยโดยไม่รู้ตัว

### กฎที่ใส่

| กฎ | ค่า | เหตุผล |
|---|---|---|
| ความยาวขั้นต่ำ | 8 | NIST SHALL — และเป็นค่าที่บังคับอยู่แล้ว ไม่ทำให้ของเดิมพัง |
| เพดานความยาว | 128 | NIST บังคับให้รับอย่างน้อย 64 — เพดานมีไว้กันคนส่งข้อความขนาดเมกะไบต์มาให้ scrypt ทำงาน ไม่ใช่กัน passphrase |
| ไม่อยู่ในรายการที่หลุดแล้ว | 46,483 รายการ | เทียบแบบไม่สนตัวพิมพ์ |
| ไม่มี username ของตัวเองอยู่ในนั้น | username ≥ 3 ตัว | NIST: context-specific words |

### รายการรหัสที่หลุด: bundled offline ไม่ใช่ HIBP k-anonymity

`app/password_blocklist.txt` เป็นไฟล์ที่ generate มาจากรายการ 100k รหัสที่ถูกใช้
บ่อยที่สุดในคลัง Have I Been Pwned ซึ่ง **NCSC (UK) เผยแพร่ไว้ให้เอาไปทำ
blocklist โดยเฉพาะ** (`scripts/build_password_blocklist.py`)

*ทำไมไม่เรียก HIBP API แบบ k-anonymity:* เพราะมันบังคับให้ต้องตอบคำถาม
"เน็ตล่มแล้วจะทำยังไง" ซึ่งมีแต่คำตอบที่แย่ทั้งคู่ — ปล่อยผ่านไปก่อน
(= นโยบายมีผลเฉพาะตอนเน็ตดี ซึ่งไม่ใช่นโยบาย) หรือปฏิเสธทั้งหมด
(= เน็ตล่มแล้วตั้งรหัสไม่ได้เลย) รายการ bundled ตัดสินใจได้เองเสมอ
ตอบเร็วเท่ากันทุกครั้ง และไม่ส่งอะไรออกนอกเครื่องแม้แต่ prefix ของ hash

*ทำไมกรองเหลือเฉพาะที่ยาว ≥ 8:* รหัสที่สั้นกว่านั้นถูกกฎความยาวปฏิเสธไปก่อน
อยู่แล้ว เก็บไว้ในไฟล์ก็ไม่มีทางถูกเอาไปเทียบ — 100k เหลือ 46k
ไฟล์เล็กลงครึ่งหนึ่งโดยไม่ลดการป้องกันลงแม้แต่รหัสเดียว

*ข้อจำกัดที่รู้ตัว:* เทียบแบบตรงตัวเท่านั้น ไม่ลองแปลง leetspeak หรือถอด
เลขท้ายออก — รายการจริงมีตัวแปลงพวกนั้นอยู่ในตัวมันเองเป็นล้านตัวแล้ว
การเดาเพิ่มเองมีแต่จะปฏิเสธรหัสที่ยังปลอดภัยและอธิบายกับผู้ใช้ไม่ได้

### normalize (NFKC) อยู่ที่ model ไม่ใช่ที่ service

NIST กำหนดให้ normalize ด้วย NFKC ก่อนเทียบ ประเด็นคือ**ต้องเกิดคู่กันเสมอ**
ระหว่างตอนตั้งกับตอนตรวจ ถ้าเกิดข้างเดียวคนที่ตั้งรหัสเป็นภาษาไทย
(สระอำ ถูกแตกเป็นสองอักขระ) หรือใช้ input method ที่ให้ตัวเต็มความกว้าง
จะ login ไม่ได้ทั้งที่พิมพ์เหมือนเดิมเป๊ะ **และจะไม่มีใครหาสาเหตุเจอ**

จึงวางไว้ใน `User.set_password()`/`check_password()` (เรียก `normalize()` ของ
service) แทนที่จะให้ผู้เรียกจำเอง — หลักเดียวกับตัวกรอง soft delete และ audit
hook: วิธีที่ต้องจำคือวิธีที่ลืมได้

ส่วน `casefold` ใช้เฉพาะตอนเทียบกับ blocklist **ไม่ใช่ตอนเก็บ** — รหัสผ่านยัง
case-sensitive อยู่ตามเดิม

## ผลที่ตามมา

* `flask create-user` และหน้า `/settings` ใช้กติกาชุดเดียวกัน — ไม่มีประตูหลัง
  ที่ยอมให้ตั้งรหัสอ่อนกว่า (ประตูหลังคือทางที่คนจะใช้จริงเพราะมันสะดวกกว่า)
* มี `flask set-password <ชื่อผู้ใช้>` เป็นทางกู้บัญชีของผู้ดูแลระบบ —
  **โดยเจตนาว่าไม่มี self-service reset** เพราะระบบไม่เก็บอีเมล (ชั้น C2 ที่
  ไม่มีเหตุผลให้เก็บ) การกู้บัญชีจึงเป็นเรื่องที่ต้องคุยกับคนดูแลจริง ๆ
* audit ได้ชื่อเหตุการณ์ตามความหมาย: `auth.password_change` (เปลี่ยนเอง),
  `auth.password_reset` (ผู้ดูแลตั้งให้), `auth.password_failed` (กรอกรหัสเดิมผิด
  ทั้งที่ login อยู่ — สัญญาณของ session ที่ถูกยึด) แถว `user.update` อัตโนมัติ
  ยังมีอยู่แต่บอกได้แค่ว่าคอลัมน์ชั้น C1 เปลี่ยน ซึ่งค้นหาไม่เจอเวลาสืบ
* รหัสในเทสต์ต้องผ่านนโยบายด้วย (`tests/conftest.py`) เพราะเทสต์บางตัวสร้าง
  ผู้ใช้ผ่าน CLI จริง — ค่าเดิม `password123` อยู่ในรายการที่หลุด
* **ผู้ใช้เดิมที่รหัสอ่อนกว่าเกณฑ์ไม่ถูกบังคับให้เปลี่ยน** ตอนนี้ ตรงกับข้อ
  "ไม่บังคับเปลี่ยนตามรอบ" — นโยบายมีผลกับการ*ตั้ง*รหัสใหม่เท่านั้น
  ถ้าวันหนึ่งต้องบังคับ (เช่นรู้ว่าหลุดจริง) ให้ทำเป็นเหตุการณ์เฉพาะกิจ
  ไม่ใช่กฎประจำ

## ทางเลือกที่ไม่เลือก

* **zxcvbn (วัดความแข็งแรงแบบให้คะแนน)** — ให้ผลดีกับ UI ที่โชว์แถบสี แต่
  เพิ่ม dependency ที่ต้องดูแลและตัวคะแนนอธิบายเป็นนโยบายยาก ("ทำไมรหัสนี้ได้ 2")
  ส่วนที่ได้ผลจริงของมันคือ dictionary ซึ่งเราได้จาก blocklist อยู่แล้ว
* **บังคับ MFA แทนที่จะสนใจคุณภาพรหัสผ่าน** — MFA อยู่ในเฟสนี้เหมือนกัน
  (ADR ของ auth plugin) แต่มันเป็นชั้นที่*เพิ่ม* ไม่ใช่ชั้นที่*แทน*
* **บังคับความยาว 15 ตัวตามที่ NIST rev.4 แนะนำ (SHOULD)** — ตัดสินใจไว้ที่ 8
  (SHALL) ก่อน เพราะการขยับเพดานขึ้นทำได้ทีหลังโดยไม่ทำให้ของเดิมพัง
  ส่วนการขยับลงทำไม่ได้ (ต้องบอกคนที่ตั้งไปแล้วว่ารหัสตัวเองไม่ผ่าน)
