# 0021 — โควตา login ต่อชื่อผู้ใช้: กันคนเปลี่ยน IP โดยไม่ล็อกบัญชีถาวร

สถานะ: accepted (2026-08-04) — Phase 4

**บริบท:** ตั้งแต่ Phase 0 หน้า login มีโควตาต่อ IP (`5 ครั้ง/นาที` หักเฉพาะตอน
ได้ 401) และ CLAUDE.md บันทึกช่องที่รู้ตัวไว้ตรง ๆ ว่า *"ยังไม่กันตาม username —
คนเดารหัสที่เปลี่ยน IP ไปเรื่อย ๆ ยังไล่เดาได้"*

ช่องนี้ไม่ใช่เรื่องทฤษฎี: การไล่เดารหัสผ่านสมัยนี้ยิงจาก botnet ที่มี IP เป็น
หมื่น แต่ละ IP ยิงบัญชีละไม่กี่ครั้ง — โควตาต่อ IP มองไม่เห็นอะไรเลยทั้งที่
บัญชีเดียวถูกลองรหัสไปแล้วเป็นพัน

## คำตัดสิน

**เพิ่มโควตาชั้นที่สองที่นับตาม "บัญชีที่ถูกยิง" ไม่ใช่ "ที่มาของคำขอ"**
ใช้ `flask_limiter` ตัวเดิมซ้อนอีกชั้นบน route เดียวกัน โดยเปลี่ยน `key_func`

```
LOGIN_RATE_LIMIT           = 5 ครั้ง/นาที; 20 ครั้ง/ชม.   (ต่อ IP)
LOGIN_USERNAME_RATE_LIMIT  = 10 ครั้ง/5 นาที; 60 ครั้ง/ชม. (ต่อชื่อผู้ใช้)
```

### ตั้งหลวมกว่าฝั่ง IP โดยตั้งใจ

โควตานี้เป็นของ **เหยื่อ** ไม่ใช่ของคนยิง — คนยิงเป็นคนใช้มันจนหมด แล้วคนที่
ถูกกันออกไปคือเจ้าของบัญชีตัวจริง นี่คือ **DoS ต่อบัญชีคนอื่น** ที่แลกมากับ
การกัน brute force และเป็นเหตุผลว่าทำไมถึง:

* ตั้งเพดานสูงกว่าฝั่ง IP (ต้องพยายามมากกว่าถึงจะทำให้คนอื่นเดือดร้อนได้)
* ใช้หน้าต่างสั้น (5 นาที) **ไม่ใช่การล็อกบัญชีที่ต้องให้ผู้ดูแลปลด** —
  ล็อกถาวรแปลว่าใครก็ได้ปิดบัญชีใครก็ได้อย่างถาวรด้วยคำขอไม่กี่ครั้ง
* หักโควตาเฉพาะคำขอที่ได้ 401 เหมือนฝั่ง IP — คนที่พิมพ์รหัสถูกไม่กินโควตา
  ของตัวเอง คนยิงจึงเป็นคนจ่ายค่าโควตาทั้งหมด

### กุญแจเป็น hash ของชื่อ ไม่ใช่ชื่อดิบ

กุญแจของ limiter จะไปนอนอยู่ใน storage (ตอนนี้ `memory://` วันหนึ่งคือ redis
ที่ใช้ร่วมกัน — ROADMAP ข้อ 4.3) ชื่อผู้ใช้เป็นชั้น C2 ตาม
docs/DATA-CLASSIFICATION.md จึงไม่ควรไปนอนอยู่ในระบบที่ไม่ได้ออกแบบมาเก็บ PII
และไม่มีนโยบายเก็บรักษาของตัวเอง

normalize ด้วย `casefold()` ก่อน hash ไม่งั้นคนยิงแค่สลับตัวพิมพ์ใหญ่เล็ก
(`tester` → `Tester` → `TESTER`) ก็ได้โควตาใหม่ทั้งชุดฟรี ๆ

### บัญชีที่ไม่มีอยู่จริงก็ถูกนับด้วย

โควตาผูกกับ **ชื่อที่กรอกมา** ไม่ใช่กับแถวในฐานข้อมูล ชื่อที่ไม่มีอยู่จริงจึง
โดนกันแบบเดียวกันเป๊ะ ถ้าทำตรงข้าม (นับเฉพาะบัญชีที่มีจริง) ความต่างของคำตอบ
จะกลายเป็นช่องไล่เดาว่ามีใครอยู่ในระบบบ้าง — ซึ่งเป็นสิ่งเดียวกับที่
"ไม่แยกว่า user ผิดหรือรหัสผิด" พยายามปิดมาตั้งแต่ต้น

## ผลที่ตามมา

* ช่องที่ CLAUDE.md บันทึกไว้ใน "ยังไม่ได้ทำ" ถูกปิดแล้ว
* **ข้อจำกัดเดิมยังอยู่ครบ:** `memory://` นับแยกต่อ process ถ้าวันหนึ่งรัน
  หลาย worker เพดานจริงจะกลายเป็น N เท่า — ทั้งสองมิติมีปัญหานี้เหมือนกัน
  แก้ทีเดียวตอนย้ายไป redis (Phase 5) ไม่ใช่หนี้ใหม่ที่เพิ่งก่อ
* คนที่ลืมรหัสตัวเองแล้วลองซ้ำ ๆ จะโดนกัน 5 นาที ซึ่งเป็นราคาที่ยอมรับได้
  (ไม่มี self-service reset อยู่แล้ว — ADR 0019)

## ทางเลือกที่ไม่เลือก

* **นับจากตาราง audit** (`auth.login_failed` ที่บันทึกอยู่แล้ว) — สวยตรงที่ไม่
  ต้องเพิ่มที่เก็บใหม่เลย แต่ audit บันทึก `row_id` ของบัญชีที่มีจริงเท่านั้น
  (ตั้งใจ — ห้ามเก็บ username ที่คนนอกกรอกมา) จึงกันบัญชีที่ไม่มีอยู่จริงไม่ได้
  และการ query ตาราง append-only ทุกครั้งที่มีคน login คือภาระที่โตตามประวัติ
* **หน่วงเวลา (`sleep`) แทนการปฏิเสธ** — ฟังดูนุ่มนวลกว่า แต่แปลว่าคนยิงจอง
  worker ของเราไว้ได้ฟรี ๆ กลายเป็น DoS ต่อ *ทั้งระบบ* แทนที่จะเป็นต่อบัญชีเดียว
* **CAPTCHA หลังพลาด N ครั้ง** — ได้ผลจริงกับ botnet แต่ต้องโหลดของจากภายนอก
  ซึ่งชน CSP `'self'` ล้วน (ADR 0010) และเพิ่ม third-party ที่เห็นทราฟฟิกของเรา
* **ล็อกบัญชีจนกว่าผู้ดูแลจะปลด** — เปลี่ยน brute force ให้กลายเป็นปุ่มปิดบัญชี
  คนอื่นแบบถาวร
