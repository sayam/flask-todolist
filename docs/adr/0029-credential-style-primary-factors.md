# 0029 — ปัจจัยหลักมีสองรูปแบบ: แบบที่พาผู้ใช้ออกไป กับแบบที่รับ credential มาเอง

สถานะ: accepted (2026-08-11) — Phase 5 · P5-14

**บริบท:** ADR 0028 วางสัญญาของปัจจัยหลักไว้เป็น `begin(redirect_uri)` /
`finish(params, pending)` ซึ่งเป็นรูปของโพรโทคอลที่ **พาผู้ใช้ออกไปยืนยันตัวตน
ที่อื่นแล้วให้เดินกลับมา** (OIDC, SAML, OAuth ทุกตัว)

**LDAP ไม่ใช่แบบนั้น** — มันรับชื่อผู้ใช้กับรหัสผ่านแล้วตอบว่าใช่หรือไม่ใช่
ไม่มีการเดินทาง ไม่มี callback ไม่มี state ให้ฝากไว้ การยัด LDAP ลงสัญญาเดิม
ต้องปลอมขั้นตอนที่ไม่มีอยู่จริง (`begin` ที่คืน URL ของหน้า login ตัวเอง แล้ว
`finish` ที่อ่านรหัสผ่านจากที่ไหนสักแห่ง) ซึ่งอ่านแล้วไม่มีใครเข้าใจว่าเกิดอะไรขึ้น

คำถามที่ต้องตัดสินก่อนเขียนโค้ด: **ขยายสัญญาเดิม หรือยอมรับว่ามีสองรูปแบบ**

## คำตัดสิน

### 1. ยอมรับว่ามีสองรูปแบบ และ **ให้ manifest ประกาศ ไม่ใช่ให้ core เดา**

`"factor": "primary"` เหมือนเดิม แล้วเพิ่ม `"style"`:

| style | สัญญา | ตัวอย่าง |
|---|---|---|
| `redirect` | `begin` / `finish` | OIDC (ADR 0028) · SAML ในอนาคต |
| `credential` | `authenticate(username, password)` | LDAP · RADIUS ในอนาคต |

**ประกาศ ไม่ใช่เดาจากฟังก์ชันที่มี** — การเดาแปลว่าวันที่มีคนพิมพ์ชื่อฟังก์ชันผิด
plugin จะเงียบ ๆ กลายเป็นอีกรูปแบบหนึ่งแทนที่จะพังพร้อมบอกว่าตกอะไร (หลักเดียว
กับ `PLUGIN_PICKS` ใน ADR 0025 ที่ไม่ยอมเดาให้เมื่อมีผู้ให้บริการหลายตัว)

**ไม่ประกาศ `style` = `redirect`** เพื่อความเข้ากันได้กับ plugin ที่เขียนไว้ก่อน
ADR นี้ — และเพราะแบบนั้นคือแบบที่มีอยู่แล้วตัวเดียวตอนเขียน

### 2. **รหัสผ่านในเครื่องมาก่อนเสมอ** แล้วค่อยถาม directory ภายนอก

ลำดับใน `POST /login`: หา user จากชื่อ → `check_password()` ของที่นี่ →
ถ้าไม่ผ่าน จึงถามปัจจัยหลักแบบ `credential` ทีละตัว

เหตุผลคือข้อเดียวกับ ADR 0028 ข้อ 7: **วันที่ directory ล่ม ทางเข้าที่เหลืออยู่
คือสิ่งเดียวที่ทำให้แก้ปัญหาได้** ถ้าถาม LDAP ก่อน ผู้ดูแลที่มีรหัสผ่านของที่นี่
จะเข้าไม่ได้พร้อมกับคนอื่นทั้งองค์กร

ผลข้างเคียงที่ยอมรับ: รหัสผ่านที่พิมพ์ผิดหนึ่งครั้งทำให้เกิด bind ไปที่ LDAP
หนึ่งครั้ง ซึ่งเป็นราคาที่ถูกกว่าการทำให้ระบบไม่มีทางเข้าสำรอง

### 3. **การผูกบัญชีใช้กติกาเดียวกับ ADR 0028 ทุกข้อ**

ตารางของ plugin เก็บ `(directory, dn) → user_id` · ผูกครั้งแรกด้วยชื่อผู้ใช้ ·
ไม่สร้างบัญชีให้เองเว้นแต่สั่ง (`LDAP_AUTO_CREATE`) · group → role ทุกครั้งที่
login ถ้าตั้ง `LDAP_ADMIN_GROUP` ไว้ · ไม่ตั้ง = ไม่แตะ `role` เลย

**ตั้งใจให้ซ้ำกับ ADR 0028 ไม่ใช่ลอกมาเพราะขี้เกียจคิด** — กติกาการผูกบัญชีเป็น
เรื่องของ *ที่นี่* ไม่ใช่ของโพรโทคอล ถ้าสองแหล่งผูกบัญชีคนละแบบ คำถามว่า
"ผู้ใช้คนนี้มาจากไหนและมีสิทธิ์อะไร" จะมีคำตอบสองชุดที่ต้องเทียบกันทุกครั้ง

### 4. **`dn` ที่ผูกไว้คือความจริง ไม่ใช่ชื่อผู้ใช้**

เหตุผลเดียวกับที่ ADR 0028 ผูกด้วย `sub`: ชื่อผู้ใช้ใน directory เปลี่ยนได้
และชื่อที่ว่างลงจะถูกเอาไปให้คนใหม่ · `dn` ก็เปลี่ยนได้ถ้ามีการย้าย OU ซึ่ง
**เป็นข้อจำกัดที่ต้องรู้**: ย้ายผู้ใช้ข้าม OU แล้วการผูกจะขาด และครั้งถัดไป
จะผูกใหม่ด้วยชื่อ (ถ้าชื่อยังตรง) หรือถูกปฏิเสธ (ถ้าไม่ตรง)
ทางแก้ที่ถูกกว่าคือผูกด้วย `entryUUID`/`objectGUID` แต่ชื่อ attribute นั้น
**ต่างกันตามยี่ห้อของ directory** จึงเปิดเป็น config (`LDAP_ID_ATTRIBUTE`)
ที่ตกกลับไปใช้ `dn` เมื่อไม่ได้ตั้ง — ไม่ใช่เดาจากยี่ห้อ

### 5. **bind ด้วยรหัสของผู้ใช้เอง ไม่ใช่ค้นด้วยบัญชีบริการแล้วเชื่อ**

การยืนยันตัวตนคือการ **bind สำเร็จด้วย credential ของผู้ใช้นั้น** เท่านั้น
บัญชีบริการ (`LDAP_BIND_DN`) มีไว้ *ค้นหา* `dn` จากชื่อผู้ใช้ก่อนเท่านั้น
เพราะรูปแบบ `dn` ต่างกันตาม directory — **ห้ามใช้ผลการค้นหาแทนการ bind**

**ไม่ยอมให้รหัสผ่านว่าง** เด็ดขาด: LDAP หลายตัวตีความ bind ที่รหัสผ่านว่าง
เป็น *anonymous bind* ซึ่ง **สำเร็จ** — แปลว่าใครก็ตามที่ส่งรหัสผ่านว่างมา
จะ "ยืนยันตัวตนผ่าน" ทั้งที่ไม่รู้อะไรเลย ด่านนี้ต้องอยู่ในโค้ดของเรา
ไม่ใช่หวังว่า directory ปลายทางจะตั้งค่าปิดไว้

### 6. **TLS ไม่ใช่ตัวเลือกเมื่อไม่ใช่การทดสอบ**

รหัสผ่านของผู้ใช้เดินทางไป directory ทุกครั้งที่ login — `ldap://` เปล่า ๆ
คือการส่งรหัสผ่านเป็นข้อความธรรมดา ระบบจึงรับเฉพาะ `ldaps://` หรือ StartTLS
ยกเว้นเมื่อตั้ง `LDAP_INSECURE=1` ซึ่ง **เตือนทุกครั้งที่ถูกใช้**
(หลักและเหตุผลเดียวกับ `OIDC_INSECURE_ISSUER` ใน ADR 0028)

## ผลที่ตามมา

- **plugin ตัวนี้มี `requires.pip`** (ไลบรารี LDAP) ต่างจาก `auth/oidc` ที่เป็น
  stdlib ล้วน — เข้า category ของตัวเองตาม ADR 0025 ถอนไดเรกทอรีแล้ว supply
  chain หายไปด้วย และ `PLUGIN_DEPS_BUDGET` ต้องขยับ ซึ่งบังคับให้มีคนมองว่า
  เทสต์ที่ต้องมีไลบรารีเพิ่มขึ้นจริงตามที่ตั้งใจ
- job `bare` ยังต้องเขียว: **ไม่มีไลบรารี = plugin ปิดตัวเอง ไม่ใช่พัง**
  หน้า login กลับไปเป็นรหัสผ่านล้วน (สัญญาเดิมตั้งแต่ ADR 0006)
- DoD เดียวกับ P5-13: **bind กับ directory จริงใน CI ไม่ใช่ mock**
- **ยังไม่ทำ**: การเขียนกลับไปที่ directory (เปลี่ยนรหัสผ่านจากที่นี่),
  การ sync ผู้ใช้แบบเป็นรอบ, nested group
