# 0045 — หน้า admin เห็นข้อมูลผู้ใช้แบบ mask โดยค่าเริ่มต้น ตามชั้นข้อมูล

สถานะ: accepted (2026-08-14) — เฟส 14-02 ([ROADMAP-FEATURES.md](../ROADMAP-FEATURES.md)
· ตอบข้อ 10/16 ของรายการ idea) · ต้องเสร็จ**ก่อน**หน้า admin ใหม่ทุกหน้า (ADR 0044)

**บริบท:** admin ทำงานกับข้อมูลของคนอื่นโดยนิยาม — และ `docs/DATA-CLASSIFICATION.md`
จัดชั้นข้อมูลทุกคอลัมน์ไว้แล้วพร้อมเทสต์บังคับความครบ (ADR 0014) · สิ่งที่ขาด
คือชั้นข้อมูลนั้น**ยังไม่มีผลกับสิ่งที่ admin เห็นบนจอ** — first_name โชว์เต็ม
ทั้งที่เป็น C2

## คำตัดสิน

การแสดงข้อมูลผู้ใช้ในหน้า admin ถูกตัดสิน**ต่อคอลัมน์**ใน
`app/services/masking.py` ด้วยสามค่า และค่าเริ่มต้น derive จากชั้นข้อมูล:

| ชั้น | ค่าเริ่มต้น | เหตุผล |
|---|---|---|
| C1 (ความลับ) | `hidden` — ไม่แสดงแม้แต่แบบ mask | admin ไม่มีงานไหนต้องเห็น hash |
| C2 (PII) | `masked` — อักษรแรก + `•••` | งานบริหารส่วนใหญ่ไม่ต้องเห็นชื่อเต็ม |
| C3 (เนื้อหาผู้ใช้) | `hidden` | เนื้อหางานเป็นของเจ้าของ ไม่ใช่ของผู้ดูแล |
| C4–C6 | `visible` | metadata/หลักฐาน — งานบริหารใช้ของพวกนี้ |

**ข้อยกเว้นต้องประกาศพร้อมเหตุผลรายคอลัมน์** (`EXCEPTIONS` ในไฟล์เดียวกัน)
— ตัวแรก: `tdl_user.username` เป็น `visible` เพราะเป็นตัวระบุที่งานบริหารทุกงาน
ต้องอ้าง (เปลี่ยนบทบาท · `set-password` · `export-user` ล้วนรับ username)
และ log/audit ของระบบใช้มันเป็น actor อยู่แล้ว (ADR 0011)

**invariant ที่เทสต์บังคับ** (`tests/test_masking.py` — แบบแผนเดียวกับ
`NOT_EXPORTED` ของ ADR 0034):

1. ทุกคอลัมน์ของทุกตารางใน metadata มีคำตัดสิน (partition เต็ม)
2. คำตัดสิน**เข้มกว่าค่าเริ่มต้นของชั้นได้ แต่หลวมกว่าไม่ได้** เว้นแต่อยู่ใน
   `EXCEPTIONS` พร้อมเหตุผล — เทียบกับชั้นที่ parse จาก
   `docs/DATA-CLASSIFICATION.md` (เอกสารเป็นแหล่งของ*ชั้น* · โค้ดเป็นแหล่งof
   *คำตัดสินการแสดงผล* · เทสต์บังคับให้สองอย่างสอดคล้อง)
3. template ของ admin ไม่มีการอ้างค่าดิบของคอลัมน์ที่ไม่ visible

**การเปิดดูค่าเต็ม (unmask) เป็นการกระทำที่ลง audit**: `POST` ต่อผู้ใช้ทีละคน
→ `audit.record("admin.unmask", ...)` บันทึก*ว่าดูของใคร* (row id — ไม่บันทึก
ค่าที่เห็น ตามกติกา audit ห้ามเก็บค่าของ C1/C2/C3) → หน้าแสดงค่าเต็มของแถวนั้น
เฉพาะ response นั้น ไม่มีสถานะค้าง

## ทางเลือกที่ไม่เอา

- **mask ที่ template ด้วย filter ของ Jinja** — จุดตัดสินกระจายตามหน้า =
  หน้าใหม่ลืมได้ · จุดตัดสินต้องมีที่เดียวใน service (หลัก ADR 0016)
- **unmask ด้วยการยืนยันรหัสผ่านซ้ำ (step-up)** — ยังไม่ทำรอบนี้: admin
  เพิ่ง login ด้วย session ที่ idle 30 นาทีอยู่แล้ว และการกระทำถูก audit ·
  **เงื่อนไขทบทวน**: มี admin มากกว่าหนึ่งคนจริง หรือ session policy ผ่อนลง
- **mask แบบซ่อนความยาวสมบูรณ์** — `•••` คงที่ก็พอ ความยาวชื่อไม่ใช่ความลับ
  ที่คุกคามจริงในบริบทนี้ (บันทึกไว้เผื่อทบทวน)

## ผลที่ตามมา

- หน้า admin ใหม่ทุกหน้าในเฟส 14 ต้องเรียกผ่านชั้นนี้ — ADR 0044 ผูกไว้เป็น
  กติกาของ panel แล้ว
- gate `admin-masking-by-classification` เป็น `layer: internal` ไปก่อน —
  จะยกเป็น portable ได้ต่อเมื่อเขียน checker ของ overlay ที่ตรวจเรื่องนี้ใน
  โปรเจกต์อื่นได้จริง (invariant ของ ADR 0042: portable ทุกตัวต้องถูก overlay
  ครอบ — ประกาศ portable โดยไม่มีตัวบังคับคือคำขวัญ)
