# 0022 — RBAC ขั้นต่ำ: หนึ่งคนหนึ่งบทบาท ตรวจที่ service ไม่ใช่ที่ route

สถานะ: accepted (2026-08-04) — Phase 4

**บริบท:** ก่อนหน้านี้ระบบมีสิทธิ์อยู่ระดับเดียวคือ "เจ้าของข้อมูล" — ทุก query
filter ด้วย `user_id` และของคนอื่นตอบ 404 (ADR 0004) ซึ่งพอสำหรับแอปที่ทุกคน
เท่ากันหมด แต่ไม่พอกับสองอย่างที่กำลังจะมา:

1. งานของผู้ดูแล (ดูว่ามีใครในระบบบ้าง, ตั้งสิทธิ์) ที่ตอนนี้ทำได้ทาง CLI
   บนเครื่อง server เท่านั้น
2. **SSO ที่ต้อง map กลุ่มจาก IdP มาเป็นบทบาท** — ถ้าไม่มีบทบาทให้ map
   งาน SSO จะต้องคิดเรื่องนี้ไปพร้อมกัน ซึ่งเป็นสองการตัดสินใจในคราวเดียว

## คำตัดสิน

### หนึ่งคนหนึ่งบทบาท เก็บเป็นสตริงในคอลัมน์เดียว

`tdl_user.role` ∈ {`user`, `admin`} — **ไม่ใช่** ตาราง role/permission แบบ
many-to-many ที่ประกอบสิทธิ์ย่อยได้ เพราะตอนนี้มีสองบทบาทและไม่มี permission
ย่อยจริง ๆ ให้ประกอบ โครงที่ยืดหยุ่นกว่านี้โดยยังไม่มีใครใช้คือความซับซ้อนที่
ทดสอบไม่ได้ว่าถูกต้อง — และเปลี่ยนทีหลังได้ด้วย migration ตัวเดียว

คอลัมน์เป็น `NOT NULL` + `server_default='user'` — แถวที่มีอยู่ก่อน migration
ได้ `'user'` ไม่ใช่ NULL เพราะ NULL แปลว่า "ไม่รู้ว่ามีสิทธิ์แค่ไหน"
ซึ่งเป็นสถานะที่ระบบสิทธิ์ต้องไม่มี

### ด่านอยู่ใน service ไม่ใช่ใน route

`roles.require_admin()` ถูกเรียกจาก**ในตัวฟังก์ชัน service เอง** (ทุกตัวรับ
"คนที่กำลังทำ" เป็นอาร์กิวเมนต์แรก) ไม่ใช่เป็น decorator ที่ route ต้องแปะ

เหตุผลเดียวกับที่ audit ดักที่ ORM และตัวกรอง soft delete เติมให้อัตโนมัติ:
ตอนนี้มี adapter สามทางแล้ว (HTML, API, CLI) ถ้าด่านอยู่ที่ adapter คนเขียน
ทางที่สี่ต้องจำเองว่าต้องตรวจอะไรบ้าง **วิธีที่ต้องจำคือวิธีที่ลืมได้**

ผลข้างเคียงที่ตั้งใจ: เทสต์ที่เรียก service ตรง ๆ (ไม่ผ่าน HTTP) ก็ยังถูกด่าน
ตรวจอยู่ดี — ด่านจึงถูกพิสูจน์ในทุกชั้น ไม่ใช่แค่ชั้นบนสุด

### 403 ไม่ใช่ 404 — ต่างจาก ADR 0004 โดยตั้งใจ

ADR 0004 ให้ตอบ 404 กับข้อมูลของคนอื่น เพื่อไม่ยืนยันว่า id นั้นมีอยู่จริง
ตรงนี้ต่างกัน: สิ่งที่ถูกปฏิเสธคือ**ความสามารถที่ประกาศไว้ในซอร์สโค้ดอยู่แล้ว**
ไม่มีความลับให้ปกปิด และการตอบ 404 ให้ผู้ดูแลที่เพิ่งถูกถอดสิทธิ์จะทำให้เขา
ไล่หาสาเหตุผิดทาง (นึกว่า URL พิมพ์ผิด) จึงเพิ่ม `ForbiddenError` เป็นชนิด
ที่สี่ของ `ServiceError` และ map เป็น 403 ทั้งฝั่ง HTML และฝั่ง API

### ห้ามแก้บทบาทของตัวเองบนหน้าเว็บ

ผู้ดูแลคนสุดท้ายที่เผลอถอดสิทธิ์ตัวเอง = ไม่เหลือใครเข้าหน้าผู้ดูแลได้อีกเลย
และต้องไปแก้ผ่าน CLI บนเครื่อง server กติกานี้ยังกันการยกระดับตัวเองไว้ล่วงหน้า
เผื่อวันที่มีบทบาทที่สูงกว่า `admin`

**ทางกลับกัน `flask set-role` ไม่มีข้อจำกัดนี้** เพราะ (1) มันคือทางเดียวที่
ตั้งผู้ดูแล *คนแรก* ได้ในระบบที่ยังไม่มีใครเป็นผู้ดูแลเลย และ (2) คนที่รัน
คำสั่งบนเครื่อง server แก้ฐานข้อมูลตรง ๆ ได้อยู่แล้ว การกันตรงนั้นเป็นพิธีกรรม

### `role` เป็นชั้น C4 ที่บันทึกค่าจริงลง audit

ต่างจาก C2/C3 ที่เก็บเป็น HMAC — "ใครยกระดับใครเป็น admin เมื่อไหร่" เป็นคำถาม
แรก ๆ ตอนสืบเหตุ ถ้าค่าถูกปิดบัง แถว audit นั้นก็ตอบอะไรไม่ได้เลย
(บันทึกใน docs/DATA-CLASSIFICATION.md แล้ว)

## ผลที่ตามมา

* หน้า `/admin/users` เป็น**พื้นผิวเดียว**ของผู้ดูแลตอนนี้: ดูรายชื่อ + ตั้งบทบาท
  เมนูบน nav โผล่เฉพาะผู้ดูแล **แต่การซ่อนเมนูไม่ใช่การกันสิทธิ์** (หลักเดียวกับ
  ปุ่มลบหมวดที่ถูก disable ไว้ — การกันจริงอยู่ที่ชั้นล่าง)
* **`/api/v1` ไม่มี endpoint ของผู้ดูแล** สัญญา v1 จึงไม่เปลี่ยนเลย
  (`docs/openapi.json` ไม่ขยับ) — token ยังทำได้เท่าที่เจ้าของทำได้ ไม่มี scope
  (ADR 0017) วันที่มี endpoint ของผู้ดูแลจริง ต้องคิดเรื่อง scope ต่อ token ก่อน
  ไม่งั้น token ที่ออกไว้ทำงานทั่วไปจะกลายเป็นกุญแจของผู้ดูแลไปโดยปริยาย
* SSO (งานถัดไป) map กลุ่มจาก IdP มาที่คอลัมน์นี้ได้ตรง ๆ
* ยังไม่มี: บทบาทที่สาม, permission ย่อย, การมอบสิทธิ์ชั่วคราว — เพิ่มทีหลังได้
  โดยไม่ต้องรื้อ เพราะทุกจุดที่ตรวจสิทธิ์เรียกผ่าน `require_admin()` ตัวเดียว

## ทางเลือกที่ไม่เลือก

* **ตาราง `role` + `permission` เต็มรูปแบบ (RBAC ตามตำรา)** — ถูกต้องในระยะยาว
  แต่ตอนนี้จะได้ตารางสองตัวที่มีข้อมูลสองแถวและโค้ดตรวจสิทธิ์ที่ไม่มีใครใช้ครบ
* **flag แบบ `is_superuser` (boolean)** — เพิ่มบทบาทที่สามไม่ได้โดยไม่เพิ่ม
  คอลัมน์ใหม่ ซึ่งจะกลายเป็นชุด boolean ที่ขัดกันเองได้ (`is_admin=false`
  แต่ `is_auditor=true` แปลว่าอะไร)
* **ตรวจสิทธิ์ด้วย decorator ที่ route** — อ่านง่ายกว่าตอนสแกนไฟล์ route จริง
  แต่ครอบได้แค่ทางที่ผ่าน HTTP และแปะตกเมื่อไหร่ก็เงียบ
