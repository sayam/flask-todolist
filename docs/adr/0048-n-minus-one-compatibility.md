# 0048 — สัญญา N-1: schema ใหม่ต้องไม่ทำให้โค้ดรุ่นก่อนหน้าพัง

สถานะ: **accepted** (2026-08-15 — เปิดเฟส 16)

**บริบท:** การ deploy แบบ rolling (เฟส 10 วัดไว้แล้วกับ ≥2 replica) มีจังหวะ
ที่ **โค้ดรุ่นเก่ากับรุ่นใหม่รันพร้อมกันบน schema เดียว** เสมอ — migration ที่
ถูกต้องสำหรับโค้ดใหม่แต่ฆ่าโค้ดเก่า แปลว่าการอัปเดตทุกครั้งคือ downtime
ที่ไม่มีใครประกาศ · จนถึงวันนี้ไม่มีอะไรบังคับข้อนี้นอกจากความระวัง

## คำตัดสิน

- **ช่วงเข้ากันได้คือ N-1**: โค้ดของ release ก่อนหน้า (tag ล่าสุด) ต้องทำงาน
  ได้บน schema ของ HEAD — แค่หนึ่งรุ่น ไม่ใช่ทุกรุ่น (ช่วงที่กว้างกว่านี้คือ
  ภาระที่ไม่มีผู้ใช้จริงมาเรียกร้อง — แอปนี้ deploy จาก tag ถึง tag)
- **วินัย expand–contract**: release เดียวกันห้ามทั้ง "เพิ่มของใหม่" และ
  "ทำลายของเก่า" ในคอลัมน์เดียวกัน
  - *expand* (release N): เพิ่มตาราง/คอลัมน์ใหม่แบบ nullable หรือมี default ·
    โค้ดใหม่เริ่มเขียน–อ่านของใหม่ · **ห้าม drop/rename/เปลี่ยนชนิดของที่
    รุ่น N-1 ยังใช้**
  - *contract* (release N+1 เป็นต้นไป): ค่อย drop ของที่ไม่มีโค้ดรุ่นไหน
    ที่ยังรันอยู่ใช้แล้ว
  - rename ที่จำเป็นจริงทำเป็น เพิ่มคอลัมน์ใหม่ + เขียนสองที่ + ย้ายข้อมูล +
    drop ในรุ่นถัดไป — ไม่มีทางลัด
- **ด่านคือ CI job `n-1`** (ไม่ใช่แค่กติกาในเอกสาร): สร้างฐานข้อมูลด้วย
  migration ของ HEAD แล้ว**รันโค้ดของ tag ล่าสุดทับมันจริง** — สมัครผู้ใช้
  ผ่าน CLI เก่า · login · สร้าง/ปิดงาน ผ่าน HTTP จริง · ล้มข้อไหน = แดง
  (สัญญาที่ไม่มีด่านรันหนุนคือสัญญาที่รอวันเน่า — บทเรียนเฟส 8)
- **readiness/liveness แยกกันและไม่ต้องมี token**:
  - `GET /healthz` (liveness) — โปรเซสยังหายใจไหม ตอบ 200 เปล่า ๆ ไม่แตะ DB
    (liveness ที่แตะ DB คือ liveness ที่สั่ง restart ทุก replica พร้อมกัน
    ตอน DB สะดุด — แปลงเหตุขัดข้องหนึ่งชั้นให้เป็นสองชั้น)
  - `GET /readyz` (readiness) — พร้อมรับงานไหม: `SELECT 1` ถึงฐานข้อมูลจริง
    ตอบ 200/503 · proxy/orchestrator ใช้ตัวนี้ตัดสินว่าจะส่งงานให้ไหม
  - ทั้งคู่**ไม่มีข้อมูลภายในใน body** (แค่ `ok`/`not ready`) จึงเปิดได้โดย
    ไม่มี token — ต่างจาก `/metrics` ที่มีข้อมูลจริงและต้องมี token เสมอ
    (ADR 0031) · ไม่ลง log รายคำขอ (มันมาทุกไม่กี่วินาทีและไม่มีสาระ)
- **graceful shutdown เป็นส่วนหนึ่งของสัญญา rolling**: gunicorn ได้
  `--graceful-timeout` ชัดเจน — คำขอที่กำลังทำอยู่ต้องได้จบก่อนโปรเซสตาย

## ผลที่ตามมา

- migration ใหม่ทุกตัวต้องถามตัวเองว่า "รุ่นก่อนหน้ายังรันทับได้ไหม" —
  ถ้าไม่ ให้แตกเป็นสองรุ่นตาม expand–contract
- job `n-1` ต้องติดตั้ง dependency ของ **tag เก่า** ตาม lock ของมันเอง
  (โค้ดเก่า + ไลบรารีใหม่ = ทดสอบสิ่งที่ไม่มีใคร deploy)
- วันที่ v1.1.0 ออก tag ล่าสุดขยับ — job นี้เริ่มพิสูจน์ 1.1.0 ↔ HEAD ให้เอง
  โดยไม่ต้องแก้อะไร
