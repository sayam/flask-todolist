# 0023 — plugin ที่มีข้อมูล ดูแลตารางของตัวเอง นอกสาย migration ของ core

สถานะ: accepted (2026-08-04) — Phase 4 (ค้างมาตั้งแต่ ADR 0006)

**บริบท:** สัญญาของสถาปัตยกรรม plugin (ADR 0006) เขียนไว้ตั้งแต่ต้นว่า
*"plugin ที่ต้องเก็บข้อมูลเพิ่มต้องดูแล table ของตัวเอง"* แต่ตอนนั้นยังไม่มี
plugin ชนิดนั้นจริง ๆ จึงไม่มีกลไก มีแค่ประโยคในเอกสาร

พอ Phase 4 ต้องมี MFA เป็น plugin (ADR 0024) ซึ่ง **ต้องเก็บความลับต่อผู้ใช้**
คำถามจึงกลายเป็นของจริง: ตารางนั้นเกิดตอนไหน หายตอนไหน และใครเป็นคนดูแล

ปัญหาที่ต้องแก้ไม่ใช่ "จะสร้างตารางยังไง" (ง่าย) แต่คือ **"จะกันไม่ให้ core
เผลอไปยุ่งกับมันยังไง"**: `flask db migrate` ของ core มองเห็นทุกตารางที่อยู่ใน
`db.metadata` ถ้าไม่ทำอะไรเลย

* วาง plugin ลงไป → migration ตัวถัดไปของ core จะมี `create_table` ของ plugin ติดไป
* ถอน plugin ออก → migration ตัวถัดไป **`drop_table` ทิ้งเงียบ ๆ**

แปลว่าวงจรชีวิตของข้อมูลผู้ใช้จะขึ้นกับว่า *ใครบังเอิญรัน `db migrate` ตอนที่
ไดเรกทอรีไหนอยู่บนดิสก์* ซึ่งไม่ใช่สิ่งที่ใครตั้งใจ

## คำตัดสิน

### 1. plugin ประกาศ model ใน `models.py` ของตัวเอง

ชื่อตารางต้องขึ้นต้นด้วย `tdl_<ชนิด>_<ไอดี>_` **บังคับตอนโหลด ไม่ใช่แค่ธรรมเนียม**
(`plugins.load_models()` raise `PluginError` ถ้าไม่ตรง และถูกเรียกใน
`check_installation()` ตอน start — ล้มเหลวตั้งแต่ต้นดีกว่าล้มเหลวตอนมีคนกด install)

### 2. core รู้ว่าตารางไหนของใคร จาก "อะไรโผล่เข้า metadata ระหว่าง import"

ไม่ใช่จากการให้ plugin ประกาศรายชื่อตารางไว้ใน manifest — รายชื่อที่ประกาศซ้ำ
คือรายชื่อที่วันหนึ่งจะไม่ตรงกับของจริง (มีคนเพิ่ม model แล้วลืมแก้ manifest)

### 3. ตารางของ plugin อยู่นอกสาย migration ของ core

`migrations/env.py` มี `include_object` ที่กรอง `plugins.owned_tables()` ออก
ทั้ง autogenerate และ `flask db check` — core จึงไม่มีวันสร้างหรือ drop มัน

วงจรชีวิตเป็นของ plugin เอง ผ่านคำสั่งที่เพิ่มมาสามตัว:
`flask plugin-list` / `plugin-install <ชนิด>/<ไอดี>` / `plugin-uninstall <ชนิด>/<ไอดี>`

**ถอนแล้วข้อมูลหายจริง** ไม่ใช่ soft delete: ข้อมูลของความสามารถที่ไม่มีอยู่แล้ว
คือข้อมูลที่ไม่มีใครดูแล — และ purge job ของ core ก็ไม่รู้จักตารางนี้อยู่แล้ว
ถ้าซ่อนไว้ก็จะไม่มีใครมาล้างให้เลย (คำสั่งถามยืนยันก่อน และมี `--yes` สำหรับสคริปต์)

### 4. ข้อมูลของ plugin ยังอยู่ใต้กติกาของ core ทุกข้อ

* **ถูกจำแนกชั้นใน `docs/DATA-CLASSIFICATION.md`** เหมือนคอลัมน์ของ core
  (`tests/test_data_classification.py` สแกน `db.metadata` ซึ่งรวมตารางของ plugin)
* **ถูกบันทึกลง audit อัตโนมัติ** เพราะ hook ผูกที่ระดับ Session ไม่ใช่ที่ model
  ของ core (ผลตอบแทนของ ADR 0015 ที่จ่ายไปแล้ว)
* **อยู่ใต้ `tests/test_write_discipline.py`** เหมือนกัน — การลบจริงของ
  `auth/totp` ต้องขึ้นทะเบียนใน `ALLOWED_LINES` พร้อมเหตุผล ไม่ใช่ยกเว้นให้
  เพราะเป็น plugin

### 5. โมดูลของ plugin ถูกโหลดตาม path ไม่ใช่ตามชื่อโมดูล

`load_module(plugin, "models" | "factor")` ใช้ `spec_from_file_location`
เพราะไอดีของ plugin คือ**ชื่อไดเรกทอรี** ซึ่งมีขีดกลางได้ ถ้า import ตามชื่อ
โมดูลปกติ กติกา "ไอดีคือชื่อไดเรกทอรี" จะกลายเป็น "ไอดีต้องเป็นชื่อโมดูล
python ที่ถูกต้อง" โดยไม่มีใครประกาศไว้

## ผลที่ตามมา

* `db.create_all()` (ที่เทสต์ใช้) สร้างตารางของ plugin ให้ด้วยเพราะมันอยู่ใน
  metadata — เทสต์จึงไม่ต้อง install เอง แต่**ของจริงต้อง `plugin-install`**
  (ความต่างนี้ตั้งใจ: เทสต์ต้องการสภาพ "ติดตั้งครบ" เป็นค่าเริ่มต้น)
* `tests/test_migrations.py` ต้องกรองด้วยเกณฑ์เดียวกับ `env.py` ไม่งั้นเทสต์
  จะแดงทั้งที่ `flask db check` เขียว — ทั้งสองที่จึงเรียก `owned_tables()`
  ตัวเดียวกัน ไม่ใช่เขียนเงื่อนไขซ้ำ
* **core ต้องถาม `is_installed()` ก่อนใช้งาน plugin ที่มีข้อมูล** — ผลข้างเคียง
  ที่ตามมาจากข้อ 3 คือ "วางไดเรกทอรีแล้วใช้ได้ทันที" ใช้กับ plugin ที่มีตาราง
  ไม่ได้ ต้อง `plugin-install` ก่อน และถ้า core ไม่ตรวจ ทุกหน้าที่แตะ plugin นั้น
  จะล้มเหลวด้วย `no such table` — **รวมถึงหน้า login** ซึ่งแปลว่าการวาง plugin
  ผิดขั้นตอนทำให้ทั้งระบบเข้าไม่ได้ (เจอจริงตอน Phase 4: job `a11y` ใน CI ล้ม
  ทั้ง job เพราะที่นั่นรันแค่ `flask db upgrade` ตามที่ควรเป็น)
  ตารางที่ยังไม่ถูกสร้าง = ยังไม่มีใครลงทะเบียน การข้าม plugin นั้นไปจึงเป็น
  คำตอบที่ถูกต้อง ไม่ใช่การปิดด่านความปลอดภัยเงียบ ๆ
* plugin ที่มีข้อมูลยัง **ไม่มี**สาย migration ของตัวเอง (เปลี่ยน schema ของ
  plugin = ถอนแล้วติดตั้งใหม่ = ข้อมูลหาย) พอสำหรับ plugin ที่เก็บ credential
  ซึ่งออกใหม่ได้เสมอ **แต่ไม่พอสำหรับ plugin ที่เก็บข้อมูลที่สร้างใหม่ไม่ได้**
  ตัวนั้นต้องมี `version_locations` แยกของ alembic ซึ่งยกไว้จนกว่าจะมี plugin
  แบบนั้นจริง (บันทึกไว้เพื่อไม่ให้ลืมว่าข้อจำกัดนี้มีอยู่)

## ทางเลือกที่ไม่เลือก

* **ให้ plugin มี alembic branch ของตัวเอง (`version_locations`)** — ตอบโจทย์
  การอัปเกรด schema ของ plugin ได้จริง แต่เพิ่มความซับซ้อนของ migration
  ทั้งระบบเพื่อ plugin ตัวเดียวที่ยังไม่ต้องการมัน
* **ให้ plugin เก็บข้อมูลลงตารางของ core (คอลัมน์ใหม่ใน `tdl_user`)** — ผิด
  สัญญาข้อ "ห้ามแก้ table ของ core" ตรง ๆ และทำให้ถอน plugin แล้วเหลือคอลัมน์
  ที่ไม่มีใครใช้ค้างอยู่ในตารางหลักตลอดไป
* **ตาราง key-value กลางให้ plugin ทุกตัวใช้ร่วมกัน** — ได้ schema ที่ตรวจอะไร
  ไม่ได้เลย (ทุกอย่างเป็น JSON ในคอลัมน์ text) และการถอน plugin กลายเป็นการ
  ไล่ลบแถวตาม prefix ซึ่งพลาดง่ายกว่า drop ตารางทั้งใบมาก
