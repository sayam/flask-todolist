# 0060 — preflight บนเครื่อง สะท้อนคำสั่งของ CI แทนที่จะลอกมาเก็บไว้

สถานะ: **accepted** (2026-08-17 — ข้อเสนอข้อ 2 ของ audit governance รอบ 6:
"ระบบทนต่อผู้ปฏิบัติที่พลาดซ้ำแค่ไหน")

## บริบท

hook ก่อน commit ตรวจ `ruff check` · `ruff format` · `mypy` เท่านั้น ส่วน
**xenon · interrogate · coverage floor · diff-cover · การ regenerate ไฟล์ที่
derive มา** อยู่ใน CI อย่างเดียว — ช่องว่างนี้มีราคาที่วัดได้: PR #88 แดงสองรอบ
ติดกันด้วยคลาสเดียวกันทั้งคู่ (xenon rank C ที่ `mfa_disable` · diff-cover ขาด
3 บรรทัดใน `app/cli.py`) ทั้งที่ทุกอย่างเขียวบนเครื่องก่อน push · หนึ่งรอบของ CI
ใช้เวลา ~8 นาที ความผิดพลาดคลาสนี้จึงแพงกว่าตัวมันเองหลายเท่า

รอบ 6 ยังนับได้ว่ามี commit ที่ขึ้นต้นด้วย `fix(` ตามหลังด่านแดง **14 ตัว** —
ระบบจับได้ทุกครั้ง แต่จับ*หลัง*จากที่คนเสียเวลาไปแล้ว

## คำตัดสิน

1. **`scripts/preflight.py` เดินด่านของ CI บนเครื่อง** โดย**อ่านคำสั่งจาก
   `.github/workflows/ci.yml`** — job `lint` และ `test` ตามลำดับ step เดิม
2. **ห้ามลอกคำสั่งมาเก็บไว้ในสคริปต์** (ADR 0039) — ที่ที่สองของคำสั่งจะ drift
   ทันทีที่มีคนแก้ฝั่งเดียว และ preflight ที่ drift แล้วคือเครื่องมือที่บอกว่า
   "ผ่าน" ในจังหวะที่ CI กำลังจะบอกว่าไม่ · ตัวสคริปต์แทนค่า
   `${{ github.base_ref }}` ให้ ส่วน expression อื่นที่แทนไม่ได้ = **ข้ามพร้อม
   เหตุผล**
3. **ข้ามอะไรต้องพิมพ์เหตุผลทุกครั้ง** (แบบเดียวกับ `scripts/run_gates.py`) —
   step ที่เป็น action (hadolint: ตัวตัดสินคือรุ่นใน CI) และ step ที่จัด
   สภาพแวดล้อม (`pip install` / `pipenv sync` — มันแก้ `.venv` ของคนที่กดรัน)
4. **ไม่ผูกเข้า pre-commit hook** — `pytest --cov` ใช้เวลา ~4 นาที การบังคับทุก
   commit จะทำให้คนเลี่ยง hook ทั้งชุด และ hook ที่ถูกเลี่ยงแย่กว่าไม่มี hook
   (มันให้ความรู้สึกว่าถูกตรวจแล้ว) · preflight เป็นของที่เรียกเองก่อนเปิด PR
   **CI ยังเป็นผู้ตัดสินคนเดียวเหมือนเดิม**
5. **ไม่ครอบ job ที่ต้องมี docker/service/secret ของ CI** (`stack` `dast`
   `image` `dialects` `siem` ฯลฯ) — ประกาศขอบเขตตรง ๆ ดีกว่าปล่อยให้คนเข้าใจว่า
   "preflight เขียว = CI เขียว"

## ทางที่ไม่ได้เลือก

- **Makefile/justfile ที่เขียนคำสั่งซ้ำ** — ปัดตก: สร้างที่ที่สองของคำสั่งพอดี
  กับที่ ADR 0039 ห้าม · ข้อดีเดียวคืออ่านง่ายกว่า ซึ่งแลกกับความจริงไม่คุ้ม
- **`act` (รัน workflow จริงในคอนเทนเนอร์)** — ปัดตก *เป็นค่าเริ่มต้น*: ต้องมี
  docker และดึง image ทุกครั้ง ช้ากว่าการรันตรงหลายเท่าสำหรับคำถาม "ลืม xenon
  หรือเปล่า" · ยังเป็นทางเลือกที่ถูกต้องสำหรับคนที่อยากได้ทั้ง workflow จริง
- **ทำเป็น pre-push hook** — ปัดตก: รอ ~4 นาทีทุก push จะถูกปิดด้วย
  `--no-verify` ภายในสัปดาห์เดียว แล้วเราจะเสียทั้ง hook เดิมไปด้วย

## เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ

- **preflight เขียวแต่ CI แดงด้วยคลาสเดียวกันเกินสองครั้ง** = ขอบเขตที่ mirror
  ไว้แคบไป ให้ขยาย `MIRRORED_JOBS` หรือประกาศว่าเลิกใช้ ไม่ใช่ปล่อยให้มันเป็น
  เครื่องมือที่คนเชื่อครึ่งเดียว
- **ถ้า CI ย้ายจาก GitHub Actions** ตัวอ่าน workflow ต้องย้ายตาม — สัญญาของ
  ADR นี้คือ "อ่านจากแหล่งเดียวกับที่ CI ใช้" ไม่ใช่ "อ่าน YAML ของ GitHub"

## โน้ต 2026-08-18 — กลไกถูกขยายโดย ADR 0063

`preflight.py` ถูกส่งออกไปกับ overlay แล้ว จึงเลิกอ่านเฉพาะ
`.github/workflows/ci.yml` และเลิกฝังชื่อ job ของ repo นี้: อ่าน workflow **ทุกไฟล์**
(repo นี้เองก็ต้องการ — job `posture` ของ ADR 0061 อยู่คนละไฟล์) และรับชื่อ job จาก
`scaffold.json` คีย์ `preflight_jobs` · **สัญญาข้อหลักไม่เปลี่ยน**: คำสั่งอ่านจาก
แหล่งเดียวกับที่ CI ใช้ ไม่ลอกมาเก็บที่สอง

## ผลที่ตามมา

- gate `fail-fix-harness-honest` ครอบ harness สองตัว (`run_gates.py` ที่ไล่
  gate ทีละตัว · `preflight.py` ที่เดินด่านของ CI) ด้วยคุณสมบัติเดียวกัน:
  **รายงานตรงความจริงและไม่ทิ้งอะไรเงียบ ๆ**
- รอบแรกที่รันจริงจับของได้ทันที: ruff แดงสองข้อในไฟล์ของ preflight เอง
