# 0074 — คำสัญญาของผู้เฝ้าต้องสั้นกว่าหน้าต่างเงียบของแพลตฟอร์ม

สถานะ: **accepted** (2026-08-23)

## บริบท

[ADR 0066](0066-watched-severity.md) ให้ทุก gate ที่บล็อกใครไม่ได้ประกาศ
`watched_by.within_days` — "ใครเห็นความล้มเหลวนี้ และภายในกี่วัน" · ตั้งแต่นั้นมา
มีสองด่านคอยดูว่าคำสัญญานั้นสมเหตุผล: `tests/test_gates.py` บังคับว่ามัน**ไม่เร็ว
กว่า**กลไกที่ตัวเองอ้าง และ `scripts/red_streak_census.py` วัดว่าความแดงจริงเคย
ยืนอยู่นานกว่าที่สัญญาไว้หรือเปล่า

ทั้งสองด่านถามคำถามเดียวกันจากข้างล่างขึ้นบน: *เร็วเกินไปไหม* · audit รอบ 26 ถาม
คำถามที่ไม่มีใครถาม — **ช้าเกินไปเมื่อเทียบกับอะไร**

คำตอบอยู่นอกรีโป · GitHub เขียนไว้ตรง ๆ ในเอกสารของ `schedule`:

> In a public repository, scheduled workflows are automatically disabled when
> no repository activity has occurred in 60 days.

gate ที่บล็อกไม่ได้ทั้งห้าตัวของ repo นี้ถูกบังคับด้วย job ที่ไม่รันบน
`pull_request` — ทางเดียวที่มันได้รันโดยไม่มีใครลงมือคือ `on.schedule` · และ
สี่ในห้าตัวอยู่ในไฟล์เดียวกันคือ `scorecard.yml`

ผลที่วัดได้ตอนนั้น:

| gate | สัญญาไว้ | ทริกเกอร์ที่รอดเมื่อไม่มีใคร push |
|---|---|---|
| `schedules-still-fire` | 90 วัน | cron รายสัปดาห์ของ `scorecard.yml` |
| `platform-posture-verified` | 180 วัน | เดียวกัน |
| `watched-promises-are-measured` | 180 วัน | เดียวกัน |
| `openssf-scorecard` | 365 วัน | เดียวกัน |

`schedules-still-fire` ถูกสร้างขึ้นมาเพื่อจับกฎ 60 วันข้อนี้**โดยเฉพาะ** —
`born_from` ของมันเอ่ยถึงกฎนี้ตรง ๆ ตั้งแต่ audit รอบ 10 · แต่ตัวมันเองรันอยู่ใน
cron ตัวที่ถูกปิด **ตัวเฝ้าจึงอยู่ใต้สิ่งที่มันเฝ้า** และดับในวินาทีเดียวกับที่มี
เรื่องให้รายงาน · ที่แย่กว่านั้นคือคำสัญญา 90 วันของมัน**ยาวกว่า**หน้าต่าง 60 วัน
ที่สร้างความล้มเหลว: ผู้เฝ้ามาถึงช้ากว่าเครื่องที่มันเฝ้าอย่างน้อยหนึ่งเดือน
**โดยไม่ผิดสัญญาสักข้อ**

## คำตัดสิน

1. **หน้าต่างเงียบของแพลตฟอร์มเป็นเพดานของคำสัญญา ไม่ใช่ข้อมูลประกอบ** —
   `PLATFORM_SILENCE_DAYS = 60` เป็นค่าของ GitHub ไม่ใช่ของเรา · ขยับไม่ได้
   ด้วยการตัดสินใจฝั่งเรา และการไม่รู้ว่ามันมีอยู่ไม่ได้ทำให้มันไม่บังคับใช้

2. **บังคับข้อเดียว: ต้องมีคำสัญญาอย่างน้อยหนึ่งข้อที่สั้นกว่าหน้าต่างนั้น**
   ไม่ใช่ทุกข้อ — เพราะ**การลงมือหนึ่งครั้งรีเซ็ตนาฬิกาของแพลตฟอร์มให้ทั้ง repo
   พร้อมกัน** พอมีคนกลับมาทันเวลา cron ก็ไม่ถูกปิด แล้วคำสัญญาที่ยาวกว่าของข้ออื่น
   ก็ยังทำได้จริงตามเดิม · คำสัญญาที่สั้นที่สุดคือตัวที่ค้ำตัวอื่นไว้ทั้งหมด
   (หลักเดียวกับ `promised_days()` ที่หยิบค่าน้อยที่สุดต่อไฟล์)

3. **`schedules-still-fire` ลดจาก 90 เหลือ 45 วัน** — ต่ำกว่าเพดานโดยมีระยะเผื่อ
   จริง · คำสัญญาที่พอดีเป๊ะกับเพดานคือคำสัญญาที่มาถึงในวินาทีเดียวกับความล้มเหลว

4. **มีแถวเดียวใน `docs/SECURITY-CADENCE.md` ที่รับหน้าที่นี้ — "แถวรักษาชีพ"**
   รอบ 45 วัน · เนื้องานคือทบทวนของที่รันตามเวลา **และแตะ PR ของ Dependabot
   อย่างน้อยหนึ่งใบ** · แถวเดียวปิดสองนาฬิกาที่เป็นของคนอื่นทั้งคู่:
   60 วันของ schedule และ 90 วันของ Dependabot pause (ดู [ADR 0025](0025-plugin-dependencies-are-plugin-scoped.md)
   เรื่องทำไมการ pin ต้องมีคนขยับ)

5. **รอบใน cadence เขียนเป็น "N วัน" ได้แล้ว** — ตัวอ่านเดิมรู้จักแต่ "N เดือน"
   และคืน `0` ให้รูปอื่น ซึ่งแปลว่า "ผูกกับเหตุการณ์ เร็วพอเสมอ" · แถวที่มีรอบ
   สั้นกว่าหนึ่งเดือนจึงจะทำให้ด่านที่พึ่งตัวเลขนี้**เขียวฟรี** ถ้าไม่แก้ตัวอ่าน

6. **กฎนี้ต้องแดงเมื่อสมมติฐานของมันหายไป** — ถ้าวันหนึ่งไม่มี workflow ไหน
   พึ่ง cron อย่างเดียวแล้ว กฎจะผ่านฟรีตลอดกาลโดยไม่มีอะไรบอก · จึงมีข้อที่สอง
   ที่แดงเมื่อไม่เหลือ workflow แบบนั้น พร้อมบอกว่าให้ถอดกฎออกไปด้วย
   (บทเรียนของ audit รอบ 16: ของที่ถูกถอดออกต้องมีคนเห็น)

## ผลที่ยอมรับ

- **แถวรักษาชีพเป็นงานประจำที่ถี่ที่สุดในตาราง** (45 วัน · ที่เหลือคือ 3/6/12 เดือน)
  — ยอมรับเพราะมันเป็นแถวเดียวที่ถ้าไม่ทำ **ทุกแถวที่เหลือกลายเป็นข้อความบนกระดาษ
  พร้อมกันทั้งตาราง** ไม่ใช่แค่แถวของตัวเอง
- **กฎนี้ไม่ได้ทำให้ระบบรอดถ้าไม่มีใครกลับมาเลย** และไม่ได้ตั้งใจจะทำ · มันย้าย
  ความล้มเหลวจาก "เงียบและไม่มีใครรู้" ไปเป็น "มีวันครบกำหนดที่เขียนไว้และมีเทสต์
  ทวง" ซึ่งเป็นสิ่งเดียวที่กลไกในรีโปทำได้จริงกับปัญหาที่อยู่นอกรีโป
- **เพดาน 60 อาจถูกแพลตฟอร์มเปลี่ยนโดยไม่บอกเรา** — ตัวเลขอยู่ที่เดียวใน
  `tests/test_watcher_windows.py` พร้อมคำพูดต้นทาง และมีเทสต์บังคับว่าเอกสารที่
  คนอ่านต้องเอ่ยถึงมัน · การเปลี่ยนจึงเป็นการแก้ค่าคงที่หนึ่งที่ ไม่ใช่การไล่หา

## ทางที่ไม่ได้เลือก

- **บังคับให้ทุกคำสัญญาสั้นกว่า 60 วัน** — จะเปลี่ยนงานทบทวนสี่รายการให้เป็นรอบ
  สองเดือนทั้งหมด โดยไม่ได้ความปลอดภัยเพิ่มเลย เพราะนาฬิกาที่กำลังพูดถึงเป็น
  นาฬิกาเดียวของทั้ง repo ไม่ใช่นาฬิกาต่อ gate
- **ย้าย census ออกไปเป็น workflow ของตัวเองที่มี cron แยก** — ไม่ช่วยอะไร
  กฎ 60 วันของ GitHub ปิด schedule **ทุกไฟล์**ใน repo นั้นพร้อมกัน ไม่ใช่ทีละไฟล์
- **ให้บริการข้างนอกยิงเข้ามาแทน cron** (cron-as-a-service · เครื่องที่บ้าน) —
  แลกความเงียบของ GitHub กับความเงียบของปลายทางที่ยิ่งไม่มีใครเฝ้า และเพิ่ม
  ผู้ให้บริการหนึ่งรายในทะเบียนเพื่อแก้ปัญหาที่การกลับมาดูทุก 45 วันแก้ได้อยู่แล้ว
