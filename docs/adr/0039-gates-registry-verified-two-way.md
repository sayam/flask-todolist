# 0039 — `gates.yaml` เป็นดัชนี enforcement ที่ตรวจสองทิศ ไม่ใช่ตัว generate CI

สถานะ: accepted (2026-08-13) — เปิดเฟส 8 ตาม [ROADMAP-INFRA.md](../ROADMAP-INFRA.md)

**บริบท:** [INFRA-VISION.md](../INFRA-VISION.md) ข้อ 3.1 ต้องการไฟล์นิยาม gate
ที่เครื่องอ่านได้ เพื่อให้ policy แยกจากโค้ดและ import ไป project อื่นได้ —
ข้อนี้ถูก: ความรู้ว่า "repo นี้มีด่านอะไรบ้าง" วันนี้ตอบได้ด้วยการอ่าน
เทสต์ 61 ไฟล์กับ job 22 ตัวเท่านั้น ไม่มีที่ไหนให้เครื่องถามเป็นชุด ·
แต่เอกสารเสนอทิศว่า "CI ถูก generate จาก gates.yaml" ซึ่งขัดกับแบบแผน
ที่ repo นี้พิสูจน์แล้วซ้ำ ๆ ว่าแข็งกว่า

## คำตัดสิน

`gates.yaml` ที่รากของ repo เป็น **ดัชนีของกลไกบังคับที่มีอยู่จริง** —
ความจริง (เทสต์ + job) ยังเป็นแหล่ง และ `tests/test_gates.py` บังคับว่า
ดัชนีกับความจริง**ตรงกันทั้งสองทิศ** · ไม่มีการ generate CI และไม่มีการ
generate ทับ `docs/ASVS.md`

### โครงต่อ gate

```yaml
- id: logic-knows-no-http          # kebab-case, ห้ามซ้ำ
  title: ...                       # หนึ่งบรรทัด ภาษาคน
  kind: test | step | job          # ดูข้อ "สามชนิด" ข้างล่าง
  severity: blocking | warning     # ตรงกับความจริงของ job (plugin-audit/scorecard = warning)
  enforced_by:
    job: test                      # ต้องมีจริงใน workflow
    step: ...                      # เฉพาะ kind: step — ชื่อ step ต้องตรงเป๊ะ
    tests: [tests/test_x.py, ...]  # เฉพาะ kind: test
  standard: [ASVS-V7.1.1]          # ว่างได้ — กฎของเราเองที่มาตรฐานไม่มีข้อให้อ้าง
  requires: []                     # สิ่งแวดล้อมที่ต้องมี เช่น docker-compose, github-actions
  portable: true|false             # กฎสากล → ขึ้น SKILL.md ในเฟส 9
  born_from: "..."                 # บังคับเมื่อ portable — กับดักที่ให้กำเนิดกฎ
```

### สามชนิดของ gate

| kind | ตัวบังคับ | การอ้างอิง |
|---|---|---|
| `test` | ไฟล์เทสต์ pytest — รันอยู่ใน job `test` ทั้งหมด | รายชื่อไฟล์ (ต้องมีจริงบนดิสก์) |
| `step` | step ที่**มีชื่อ**ใน job | `(job, ชื่อ step)` ต้องตรงเป๊ะกับ workflow |
| `job` | ทั้ง job เป็นด่านเดียว | ชื่อ job ต้องมีจริง |

### กติกาที่ `tests/test_gates.py` บังคับ

1. **ทิศไป**: ทุก gate ชี้ไปหา job/step/ไฟล์เทสต์ที่มีอยู่จริง
2. **ทิศกลับ (job)**: ทุก job ใน `ci.yml` + `scorecard.yml` มี gate อย่างน้อยหนึ่งตัว
   — job ใหม่ที่ไม่มี gate = แดง
3. **ทิศกลับ (เทสต์) — partition**: ไฟล์ `tests/test_*.py` **ทุกไฟล์**ต้องถูก
   ตัดสินว่าเป็นของ gate ตัวไหน ตัวเดียวเท่านั้น (แบบแผนเดียวกับ
   `DATA-CLASSIFICATION.md` ที่บังคับให้ทุกคอลัมน์ถูกตัดสิน) — ไฟล์ใหม่ที่
   ไม่ลงทะเบียน = แดง · ไฟล์เดียวสอง gate = แดง
4. `standard` ที่อ้างต้องมีแถวจริงใน `docs/ASVS.md` และแถวนั้นต้องสถานะ
   **ผ่าน** — อ้างแถว "ไม่เกี่ยวข้อง" หรือ "ยังไม่ผ่าน" คือดัชนีที่ขัดกับ
   คำตัดสินของผู้ประเมิน = แดง
5. `portable: true` ต้องมี `born_from` — กฎสากลที่เล่าไม่ได้ว่ามาจากกับดักไหน
   คือกฎที่จะถูกลบทิ้งวันที่ไม่มีใครจำเหตุผลได้

## เหตุผล

1. **ด่านของ repo นี้แข็งเพราะมันคือเทสต์ที่ถูก mutation-test** — การย้ายมัน
   ไปเป็นเอนทรี YAML ไม่ได้เพิ่มความแข็งสักหน่วย สิ่งที่ขาดคือ*ดัชนี*
   ให้เครื่องอ่าน ไม่ใช่ตัวรันตัวใหม่
2. **generator คือการสร้าง "ที่ที่สอง" ถาวร** — ความรู้ของ job (service
   container, ลำดับ step, กับดัก User-Agent ของ ZAP) ต้องย้ายเข้า YAML
   ทั้งหมดหรือไม่ก็ค้างอยู่สองที่ · repo นี้เพิ่งจ่ายบทเรียนนี้เมื่อวาน:
   ขอบเขต semgrep ที่ประกาศสองที่ทำให้ตัวตรวจคำนวณเซตที่คาดหวังผิด
   และ `tests/` หายไป 61 ไฟล์โดยไม่มีอะไรฟ้อง
3. **เอกสารวิสัยทัศน์เปิดทางนี้ไว้เอง**: "หรืออย่างน้อยมีเทสต์พิสูจน์ว่า CI
   กับ gates.yaml ตรงกัน ไม่มีการเขียนมือคู่ขนานสองที่" — ทางที่เลือกคือ
   ทางนั้น ทำให้เป็นสองทิศ และ partition ทำให้ "ตรงกัน" มีนิยามที่ตรวจได้
4. **`docs/ASVS.md` ถือคำตัดสินของคน** (ผ่าน/ไม่เกี่ยวข้อง/ยังไม่ผ่าน พร้อม
   เหตุผล) ซึ่งเป็นคนละชนิดข้อมูลกับกลไกบังคับ — สองไฟล์ สองหน้าที่
   เชื่อมด้วย id ไม่มีช่องข้อมูลซ้ำกัน จึงไม่ใช่ทะเบียนคู่ขนาน

## ทางเลือกที่ไม่ได้เลือก

| ตัวเลือก | ทำไมไม่เลือก |
|---|---|
| CI generate จาก `gates.yaml` | ที่ที่สองถาวร (เหตุผลข้อ 2) · และ template ของ workflow เป็นงานของ overlay ในเฟส 9 อยู่แล้ว |
| `ASVS.md` generate จาก `gates.yaml` | ทำลายการเก็บคำตัดสินของผู้ประเมินที่ `build_asvs_worksheet.py` ออกแบบไว้ ("สคริปต์ไม่เคยทับคำตัดสิน") |
| เก็บคำสั่งของ step ไว้ใน `check:` แบบ verbatim | drift หนึ่งอักขระ = สองที่ไม่ตรงกันเงียบ ๆ — อ้างด้วย `(job, step)` แล้วให้ผู้ใช้ (คนหรือ harness เฟส 11) ดึงคำสั่งจริงจาก workflow แทน |
| gate เฉพาะเทสต์นโยบาย ปล่อยเทสต์พฤติกรรมนอกดัชนี | เส้นแบ่ง "นโยบาย/พฤติกรรม" ตัดสินด้วยเครื่องไม่ได้ → ใช้ partition เต็ม ทุกไฟล์ต้องถูกตัดสิน (ราคาคือหนึ่งบรรทัดต่อไฟล์ใหม่ ซึ่ง repo นี้จ่ายแบบเดียวกันกับทุกคอลัมน์ใหม่อยู่แล้ว) |

## ผลที่ตามมา

- เพิ่มไฟล์เทสต์ = ต้องลงทะเบียนใน `gates.yaml` (gate ใหม่หรือแถวใน
  `app-behavior-suite`) · เพิ่ม job = ต้องมี gate — ทั้งคู่มีข้อความ error
  ที่บอกว่าขาดอะไร ทำหน้าที่แทน generator
- เฟส 9 อ่าน `portable: true` ไปสร้าง `SKILL.md` · เฟส 11 อ่านทั้งไฟล์ไปรัน
  โดยดึงคำสั่งจริงจาก workflow ตาม `(job, step)` — ไม่มีใครเก็บคำสั่งซ้ำ
