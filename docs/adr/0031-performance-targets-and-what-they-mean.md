# 0031 — เป้าประสิทธิภาพเป็นตัวเลข และ *ตัวเลขนั้นแปลว่าอะไร*

สถานะ: accepted (2026-08-11) — Phase 6 ด่านแรก

**บริบท:** ROADMAP ของ Phase 6 เขียนไว้ว่าเป้าหมายคือ "ตัวเลขจริง ไม่ใช่คำว่า
เร็วพอ" พร้อมเงื่อนไขที่สำคัญกว่าตัวเลขเสียอีก: **"N มาจากการประเมินผู้ใช้จริง
ไม่ใช่เดา"** — เพราะเป้าที่ตั้งลอย ๆ ทำให้ทั้งเฟสวัดสิ่งที่ไม่มีใครต้องการ

## คำตัดสิน

### 1. **N = 5 concurrent** มาจากการใช้งานจริงที่ตั้งใจ ไม่ใช่ตัวเลขกลม ๆ

ระบบนี้ตั้งเป้ารองรับ **การใช้ส่วนตัวหรือในครอบครัว (~1–5 คน)** ซึ่งเจ้าของ
ระบบยืนยันเอง · ผู้ใช้ 5 คนที่ใช้งานพร้อมกันจริง ๆ ทุกคนคือกรณีที่แทบไม่เกิด
(คนอ่านหน้าจอ พิมพ์ แล้วค่อยกดอีกที) การตั้ง N = จำนวนผู้ใช้ทั้งหมด จึงเป็น
เป้าที่ **หลวมกว่าความจริงอยู่แล้ว** ซึ่งเป็นทิศที่ถูกสำหรับตัวเลขที่จะเอาไป
สัญญากับตัวเอง

**สิ่งที่ ADR นี้ *ไม่* อ้าง**: ระบบนี้ไม่ได้ถูกพิสูจน์ว่ารองรับองค์กรขนาดกลาง
รายงานของเฟสนี้ตอบได้แค่ "ที่ 5 concurrent เร็วเท่าไหร่" กับ "มันเริ่มพังที่
เท่าไหร่" — ใครจะเอาไปใช้กับผู้ใช้หลักร้อยต้องวัดใหม่เอง ไม่ใช่ขยายผลจากที่นี่

### 2. เป้า **p95 < 200ms · p99 < 500ms** ที่ N = 5 — และ **ต้องมีจุดที่พังด้วย**

รายงานที่มีแต่ตัวเลขที่ผ่านคือรายงานที่ไม่ได้บอกอะไร: ที่ 5 concurrent ระบบนี้
แทบจะผ่านทุกอย่างโดยไม่ต้องพยายาม สิ่งที่มีค่าจริงคือ **เส้นโค้ง** — วัดที่
1, 5, และไล่ขึ้นไปจนเห็นจุดที่ p95 ทะลุเป้า แล้วบันทึกว่าจุดนั้นอยู่ตรงไหน

เหตุผล: วันที่มีคนเพิ่มฟีเจอร์ที่ทำให้ช้าลงสองเท่า ตัวเลขที่ 5 concurrent
อาจยังผ่านอยู่ แต่จุดที่พังจะขยับเข้ามาใกล้อย่างเห็นได้ชัด — **ระยะห่างจาก
ขอบคือสิ่งที่บอกว่าเรามีที่ว่างเหลือแค่ไหน** ไม่ใช่ตัวเลขที่จุดเดียว

### 3. **ตัวเลขที่ใช้ตัดสินมาจากฝั่ง client ไม่ใช่จากฝั่ง server**

`p95` ที่ DoD พูดถึงคือเวลาที่ **ผู้ใช้รอ** ซึ่งรวมคิวใน gunicorn, เวลาที่
reverse proxy ใช้, และการรอ connection ของฐานข้อมูล — ทั้งหมดนี้เกิด *ก่อน*
โค้ดของเราเริ่มจับเวลา ตัวเลขจาก middleware ของเราเองจึงสวยกว่าความจริงเสมอ
โดยเฉพาะตอนระบบเริ่มอิ่มตัว ซึ่งเป็นจุดที่เราสนใจที่สุดพอดี

**middleware มีไว้เพื่อ *วินิจฉัย* ว่า endpoint ไหนช้า ไม่ใช่เพื่อออกใบผ่าน**

### 4. **metrics ในหน่วยความจำเป็นของ process นั้นคนเดียว** — และต้องเขียนไว้ให้ชัด

*(อัปเดต 2026-08-16 — ADR 0052/G5: ข้อจำกัดนี้แก้แล้วแบบ opt-in — ตั้ง
`METRICS_MULTIPROC_DIR` แล้ว `/metrics` รวมทุก worker ของ container ถูกต้อง
· หลาย worker โดยไม่ตั้ง = ไม่ start · ค่าเริ่มต้น worker เดียวพฤติกรรม
ตามข้อนี้ทุกประการ)*

หลาย worker (gunicorn) หรือหลาย replica แปลว่าคำขอไปตกที่ process ไหนก็ได้
ส่วน `/metrics` ก็ถูกตอบโดย process ที่บังเอิญรับ scrape นั้น — **ตัวเลขที่ได้
คือมุมมองของ worker ตัวเดียว ไม่ใช่ของทั้งระบบ**

นี่คือปัญหาตระกูลเดียวกับโควตา rate limit ที่นับแยกต่อ process (P5-07) แต่
**คำตอบต่างกัน**: โควตาต้องรวมกันจริง ๆ ไม่งั้นเพดานเพี้ยน ส่วน metrics แบบ
Prometheus ออกแบบมาให้ **แต่ละ instance ถูก scrape แยกแล้วรวมที่ Prometheus**
การยัดให้รวมกันเองใน redis จึงเป็นการสู้กับโมเดลของเครื่องมือ

ทางที่เลือก: **ยอมรับว่ามันเป็นต่อ process แล้วเขียนไว้ในเอกสารกับใน
`/metrics` เอง** (คำอธิบายของ metric บอกไว้) ไม่ใช่ปล่อยให้คนอ่านตัวเลขแล้ว
เข้าใจว่าเป็นของทั้งระบบ · การ scrape แต่ละ replica แยกกันเป็นงานของ Phase 7
ถ้าถึงตอนนั้นยังต้องการ

### 5. `/metrics` **ต้องมี token เสมอ** ไม่มีโหมดเปิดสาธารณะ

metrics บอกรูปแบบการใช้งานของระบบ: path ไหนถูกเรียกกี่ครั้ง, มี error ตรงไหน,
ช้าตรงไหน — ซึ่งเป็นข้อมูลที่ช่วยคนที่กำลังหาช่องโหว่มากกว่าช่วยคนนอกทั่วไป
ใช้ด่านเดียวกับ `/api/v1` (PAT — ADR 0017) **ไม่สร้างกลไกตรวจสิทธิ์ตัวที่สอง**

### 6. **ห้ามใส่ค่าที่ผู้ใช้ควบคุมได้ลงใน label**

path อย่าง `/edit/123` ต้องกลายเป็นชื่อ endpoint (`main.edit`) ไม่ใช่ path ดิบ
ไม่งั้นจำนวน time series จะโตตามจำนวนงานในระบบ ("cardinality explosion")
ซึ่งกินหน่วยความจำของทั้งแอปและของ Prometheus จนล้ม — **เป็นช่องที่คนนอกยิงได้
ด้วยการขอ path มั่ว ๆ** ถ้าเผลอใช้ `request.path`

## ผลที่ตามมา

- รายงานของเฟสนี้ต้องมี **ทั้งจุดที่ผ่านและจุดที่เริ่มพัง** ไม่งั้นถือว่ายังไม่เสร็จ
- เครื่องที่รัน load test เป็นตัวแปรหนึ่งของผลลัพธ์ — รายงานต้องบอกว่ารันบนอะไร
  ไม่งั้นตัวเลขเปรียบเทียบข้ามครั้งไม่ได้
- **ไม่ตั้งด่าน CI ที่ตัดสินด้วยเวลา** — runner ของ CI ใช้เครื่องร่วมกับคนอื่น
  ตัวเลขจึงกระเพื่อมพอที่ด่านแบบนั้นจะแดงสุ่ม ๆ แล้วคนจะเลิกเชื่อมัน
  (ด่านที่คนเลิกเชื่อคือด่านที่ถูกลบในอีกสามเดือน) · CI ตรวจได้แค่ว่า
  **ชุด load test ยังรันจบและยังวัดได้จริง** ส่วนตัวเลขเป็นเรื่องของการรันบน
  เครื่องที่ควบคุมได้แล้วบันทึกลงรายงาน
- **ยังไม่ทำ**: การ scrape แยกต่อ replica, dashboard, alert rule
