## คำตัดสิน

1. **`severity` มีสามค่า และต้องตรงกับอำนาจจริง**
   - `blocking` — job รันบน `pull_request` และล้มได้ → **บล็อก merge ได้จริง**
   - `watched` — ตรวจจริงและล้มได้ **แต่ไม่บล็อกใคร** (ไม่รันบน PR)
   - `warning` — **ไม่ล้มโดยตั้งใจ** (เช่น `plugin-audit` ที่เตือนแทนการบล็อก
     เพราะคำตอบของ CVE ที่ถอดได้คือ "ถอดก่อน" — ADR 0025)

   `tests/test_gates.py` บังคับสองทิศ: gate ที่ประกาศ `blocking` ต้องถูกบังคับด้วย
   job ที่รันบน `pull_request` จริง · และ job ที่รันบน PR ต้องไม่ถูกประกาศเป็น
   `watched` (ซึ่งจะเป็นการซ่อนอำนาจที่มีอยู่)

2. **ทุก gate ที่บล็อกไม่ได้ ต้องประกาศ `watched_by:`** — ผู้รับ (`who`) ·
   กรอบเวลาที่ต้องรับรู้ (`within_days`) · และกลไกที่ทำให้เห็น (`how` ซึ่งต้องอ้าง
   ของที่มีอยู่จริงใน backtick แบบเดียวกับ `docs/RISK-ASSESSMENT.md`)

   เขียนลงไปว่า "ผู้ดูแล ภายใน 7 วัน" **เปลี่ยนความเงียบจากสภาพปกติเป็นสิ่งที่
   ผิดนัดได้** — นั่นคือทั้งหมดที่ฟิลด์นี้ทำ และเป็นสิ่งที่ระบบยังไม่มีภาษาจะพูด

3. **ตัวตรวจท่าทีตรวจทิศที่สาม** — `scripts/audit_posture.py` เดิมถามสองทิศ
   (job บน PR ต้องถูกบังคับ · required ต้องไม่มีชื่อผี) · เพิ่มทิศที่สาม:
   **check ที่ repo ผลิตได้แต่ไม่อยู่ในรายการบังคับ ต้องอยู่ใน `EXEMPT` พร้อมเหตุผล**
   และรายการใน `EXEMPT` ต้องชี้ไปหา job ที่มีจริง — ทะเบียนจึงถูกปรึกษาทุกครั้งที่รัน
   แทนที่จะเป็นข้อความที่อ่านแล้วเข้าใจว่ามีการบังคับอยู่

## ทางที่ไม่ได้เลือก

- **บังคับ `scorecard`/`posture` ให้เป็น required check** — ทั้งคู่ไม่รันบน
  `pull_request` การบังคับจึงเท่ากับให้ PR ทุกใบรอ check ที่ไม่มีวันมา ·
  และ `scorecard` เป็น *คะแนน* ไม่ใช่ผ่าน/ตก ด่านที่ไม่มีเส้นแบ่งชัดไม่ควรบล็อกคน
- **ย้าย `posture` ไปรันบน PR ด้วย** — มันอ่าน branch protection ของ `main`
  ซึ่งเป็นสถานะระดับ repo ไม่ใช่ของ commit · รันบน PR แล้วจะแดง/เขียวตามสิ่งที่
  PR นั้นไม่ได้แตะ และการแก้ต้องเกิดนอก PR อยู่ดี
- **ถอด `severity` ทิ้งเพราะไม่มีใครอ่าน** — ฟิลด์ที่ไม่มีใครอ่านควรถูกทำให้มีคนอ่าน
  ก่อนถูกถอด · หลังข้อ 1 มันเป็นตัวจำแนกที่มีผลจริงแล้ว
- **on-call / rota / SLA รายชั้นแบบ ITIL** — ผู้ดูแลคนเดียวและไม่มีผู้ใช้ภายนอก
  การตั้งเวรเป็นพิธีกรรม · รับแต่แก่นของมัน (ประกาศผู้รับ + กรอบเวลา) ซึ่งจริง
  แม้ผู้รับจะเป็นคนเดียวกันทุกช่องทาง

## เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ

- **วันที่มีผู้ดูแลคนที่สอง** — `who` ที่เป็น "ผู้ดูแล" ลอย ๆ จะไม่พอทันที
  ต้องระบุบทบาทที่ชี้ตัวได้ ไม่งั้นทุกคนคิดว่าอีกคนดูอยู่
- **วันที่มีปลายทางแจ้งเตือนที่มีคนรับจริง** (ADR 0037 ข้อที่ยังเปิดอยู่) —
  `how` ของหลาย gate จะเปลี่ยนจาก "สำมะโนตามรอบ" เป็น "แจ้งเตือนที่วิ่งมาหา"
  และ `within_days` ควรหดตามลงมาเป็นชั่วโมง

## ผลที่ตามมา

- **ต้นทุน**: gate ใหม่ที่ไม่ได้รันบน PR เขียนยากขึ้นหนึ่งขั้น — ต้องตอบให้ได้ว่า
  ใครเห็นและภายในกี่วัน · นั่นคือคำถามที่ควรตอบตั้งแต่ตอนสร้างด่านอยู่แล้ว
- **สิ่งที่ยังไม่ปิด**: `within_days` เป็นคำสัญญาที่ยังไม่มีเครื่องวัดว่าทำได้จริง
  — ระบบรู้ว่า "ควรรับรู้ภายใน 7 วัน" แต่ยังวัด *เวลาที่รับรู้จริง* ไม่ได้
  จนกว่าจะมีปลายทางที่บันทึกการอ่าน · จดไว้ตรง ๆ ดีกว่าอ้างว่าปิดแล้ว

**โน้ต 1 (2026-08-18 — audit รอบ 12 ข้อ 2: ตัวเลขที่ไม่มีอะไรรองรับ)**: ใบนี้บังคับ
ให้ทุก gate ที่บล็อกไม่ได้ประกาศ `within_days` — และรอบ 12 ถามข้อที่ค้างอยู่ว่า
**ตัวเลขนั้นมาจากไหน** · คำตอบคือ ไม่ได้มาจากอะไรเลย: กลไกที่เร็วที่สุดที่ทำให้ *คน*
รู้เรื่องคือแถวใน `docs/SECURITY-CADENCE.md` ซึ่งมีรอบ 90–365 วัน ขณะที่ตัวเลขที่
ประกาศไว้คือ 7–30 วัน — **สี่ในหกใบสัญญาเร็วกว่าเครื่องมือที่ตัวเองอ้างถึง 3–12 เท่า**

`watched_by` จึงได้ฟิลด์ `cadence:` ที่ต้องชี้ไปหาแถวจริงในตารางนั้น และเทสต์บังคับว่า
**`within_days` ต้องไม่เล็กกว่ารอบของแถวที่มันอ้าง** · ผลคือตัวเลขถูกขยับขึ้นให้ตรง
ความจริงในวันนี้ (7→180 · 14→90 · 30→180 · 30→365) ซึ่งอ่านแล้วดูเหมือนถอย
แต่เป็นการเลิกอ้างสิ่งที่ทำไม่ได้
