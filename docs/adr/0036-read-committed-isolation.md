# 0036 — อ่านแบบ READ COMMITTED บนยี่ห้อที่มี MVCC

สถานะ: accepted (2026-08-12) — Phase 7 · อนุมัติโดยเจ้าของโปรเจกต์
· ทำให้ [ADR 0035](0035-audit-appends-queue-on-one-row.md) ใช้ได้จริงข้ามยี่ห้อ

**บริบท:** ADR 0035 ให้ผู้เขียนสาย audit ต่อคิวกันที่แถวเดียวของ `tdl_audit_lock`
แล้วอ่านหางสายจากแถวนั้น · วิธีนี้ผ่านบน MySQL 8 แต่ **MariaDB 11.8 ปฏิเสธ**
ด้วย `(1020) Record has changed since last read in table 'tdl_audit_lock'`

สาเหตุคือ MariaDB 11.6 ขึ้นไปเปิด `innodb_snapshot_isolation=ON` เป็นค่าเริ่มต้น
ซึ่งบังคับ snapshot isolation จริง ๆ: **transaction ที่ตั้ง snapshot ไปแล้ว
จะล็อกแถวที่ถูกแก้หลังจากนั้นไม่ได้** ต้อง error แทนที่จะอ่านค่าใหม่ให้

**MariaDB ถูก** — สิ่งที่โค้ดของเราพึ่งอยู่คือพฤติกรรมของ MySQL ที่ยอมให้
locking read เห็นค่าที่ใหม่กว่า snapshot ของตัวเอง ซึ่งเป็นความไม่สอดคล้อง
ที่ MariaDB ตั้งใจปิด

## สิ่งที่วัดได้ (writer 8 ราย · แต่ละรายอ่านก่อนเขียนเหมือนคำขอจริง)

| | MySQL 8 | MariaDB 11.8 |
|---|---|---|
| REPEATABLE READ (ค่าเริ่มต้น) | ผ่าน | **19/120** — ที่เหลือ error 1020 |
| REPEATABLE READ + ขอคิวเป็น statement แรก | ผ่าน | 120/120 |
| **READ COMMITTED** | 120/120 | **120/120** |

## คำตัดสิน

### 1. ตั้งระดับการแยกเป็น **READ COMMITTED** สำหรับยี่ห้อที่มี MVCC

ทุก connection ของ MySQL/MariaDB สั่ง `SET SESSION TRANSACTION ISOLATION LEVEL
READ COMMITTED` · แต่ละ statement จึงเห็นสิ่งที่ commit แล้ว ณ ตอนนั้น —
การอ่านหางสายหลังได้คิวจึงได้ค่าล่าสุดเสมอ โดยไม่ต้องพึ่งพฤติกรรมของยี่ห้อใด

### 2. **ทางเลือกที่ไม่เลือก: บังคับให้ทุกเส้นทางขอคิวเป็น statement แรก**

วัดแล้วว่าใช้ได้เหมือนกัน (120/120) แต่มันเป็น**วินัยที่ลืมได้** — ต้องประกาศ
ตัวเองที่ `before_request` ของทุกเมธอดที่เขียน ที่ CLI ทุกคำสั่งที่เขียน และที่
`/lang` กับ `/mode` ซึ่งเป็น GET ที่เขียนโปรไฟล์ (ช่องว่าง ASVS V3.5.3 ที่บันทึกไว้แล้ว)
· ลืมจุดใดจุดหนึ่ง = 500 บน MariaDB ในวันที่มีคนใช้พร้อมกัน ซึ่งเป็นวันที่แย่ที่สุด
ที่จะค้นพบว่าลืม · และมันถือล็อกยาวขึ้นตลอดคำขอ แลกกับ throughput ของการเขียน

**กติกาที่ต้องมีคนจำ แพ้กติกาที่ระบบบังคับให้เองเสมอ**

### 3. **ค่านี้อยู่ใน `backend.py` ของยี่ห้อ ไม่ใช่ที่ core**

SQLite ไม่รู้จักระดับนี้ด้วยซ้ำ การตั้งที่ core แปลว่าต้องมี `if` ของยี่ห้อ
ในโค้ดที่ไม่ควรรู้จักยี่ห้อไหนเลย ([ADR 0026](0026-db-backend-as-a-plugin.md))
— หลักเดียวกับ `PRAGMA foreign_keys` ที่อยู่ใน backend ของ SQLite เอง

### 4. สิ่งที่แลกไป และทำไมถึงรับได้

**การอ่านซ้ำใน transaction เดียวอาจได้คนละค่า** (non-repeatable read) ·
รับได้เพราะรูปของงานในระบบนี้:

- คำขอหนึ่งใบสั้นและอ่านของตัวเองครั้งเดียวเป็นส่วนใหญ่
- สิ่งที่ต้องการลำดับจริง ๆ คือสาย audit ซึ่งมี**ล็อกของตัวเอง**อยู่แล้ว ไม่ได้
  พึ่งระดับการแยก
- `purge-expired` อ่านชุดแล้วลบ — แถวที่เพิ่งหมดอายุระหว่างทางจะถูกลบรอบถัดไป
  ซึ่งไม่ต่างจากการที่มันหมดอายุช้าไปหนึ่งวินาที
- ตัวกรองและหน้ารายการเป็น query เดียวจบ

**และมันเป็นค่าเริ่มต้นของ PostgreSQL** — ยี่ห้อที่แผนบอกว่าจะรองรับต่อไป
การยึด READ COMMITTED เป็นฐานจึงทำให้พฤติกรรมข้ามยี่ห้อเหมือนกันมากขึ้น ไม่ใช่น้อยลง

## ผลที่ตามมา

- **ต้องมีเทสต์ที่วัดค่าที่ connection ใช้จริง** ไม่ใช่ตรวจว่ามีบรรทัดที่สั่ง —
  ค่านี้เป็นของต่อ session การตั้งพลาดจึงเงียบสนิท แล้วโผล่เป็นการเขียนที่ล้ม
  เป็นครั้งคราวด้วยข้อความที่ไม่ได้ชี้มาทางนี้
  (`tests/test_db_backend.py::test_the_connection_really_runs_at_read_committed`)
- ยี่ห้อใหม่ที่มี MVCC ต้องตั้งค่านี้ในตัวเอง — ไม่มีอะไรใน core บังคับให้
  ซึ่งเป็นราคาของการให้ backend เป็นเจ้าของทางที่ข้อมูลวิ่งผ่าน
- ยังไม่ทำ: วัด throughput ใหม่หลังเปลี่ยนระดับการแยก (READ COMMITTED ไม่จับ
  gap lock จึงน่าจะเร็วขึ้น แต่ **น่าจะ ไม่ใช่หลักฐาน**)
