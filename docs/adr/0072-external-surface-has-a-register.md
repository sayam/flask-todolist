# 0072 — ผิวนอกรีโปมีทะเบียนเดียว และทุกแถวต้องบอกว่าใครเทียบมันกับของจริง

สถานะ: **accepted** (2026-08-22 — ข้อ 3 ของ audit governance รอบ 24)

## บริบท

ยี่สิบสามรอบก่อนหน้าตรวจของที่อยู่*ในรีโป*เกือบทั้งหมด — ทะเบียน gate · ข้อยกเว้น ·
ADR · เกณฑ์ · หลักฐาน · เอกสาร · แม้แต่ตัวตรวจเอง · ส่วนของที่อยู่*นอก*รีโปถูกตรวจ
เป็นรายชิ้นตอนที่มีใครสังเกตเห็นเท่านั้น และเกือบทุกครั้งคือหลังจากที่มันค้างไปแล้ว

`scripts/audit_posture.py` (ADR 0061) มีอยู่ก่อนแล้วและทำหน้าที่ของมันได้ครบ —
แต่ขอบเขตของมันสืบทอดมาจากคำถามที่สร้างมันขึ้นมา คือ *"สิ่งที่ ADR 0053 ประกาศไว้
ยังจริงไหม"* มันจึงตรวจของที่เราเคยประกาศได้ทุกข้อ และมองไม่เห็นของที่เราไม่เคย
ประกาศ · วัดจริงเมื่อ 2026-08-22: สาม endpoint ที่มันเรียกอยู่แล้วคืนค่ากลับมา
**75 ฟิลด์** และมันอ่านอยู่ **12 ฟิลด์**

ที่เหลือไม่ได้ถูกตัดสินว่าไม่สำคัญ มันแค่ไม่เคยถูกสำรวจ — และในกองนั้นมีของที่กฎ
ในรีโปพึ่งอยู่จริง (`default_workflow_permissions` · `can_approve_pull_request_reviews`)
กับของที่ค้างอยู่แล้วโดยไม่มีใครเห็น (ช่อง About โฆษณาสี่ตัวเลข ตัวตรวจอ่านตัวเดียว)

รอบเดียวกันยังพบสิ่งที่ผิวนอกทำได้และผิวในทำไม่ได้: **บัตรประจำตัวของงาน
(`CITATION.cff` กับ `.zenodo.json`) บอกจำนวนรอบ audit ไว้คนละค่า** และค่าที่ถูก
ตีพิมพ์ใต้ DOI ถาวรคือค่าที่เก่าที่สุด — ยิ่งข้อความเดินทางไกลจากรีโป เครื่องที่
เฝ้ามันยิ่งน้อยลง ทั้งที่ปลายทางไกลสุดคือปลายทางเดียวที่แก้ย้อนหลังไม่ได้

## คำตัดสิน

1. **มีทะเบียนเดียวของผิวนอกรีโป** — `docs/EXTERNAL-SURFACE.md` · ครอบ setting
   ของแพลตฟอร์ม · วัตถุบนแพลตฟอร์มที่ไม่ใช่ setting (secret · webhook · label ·
   ป้ายบน issue) · และบริการภายนอกที่ตีพิมพ์แทนเรา (Zenodo · bestpractices.dev)
2. **ทุกแถวต้องบอกว่าใครเทียบ และคำศัพท์ปิด** — `ci:posture` · `tests/<ไฟล์>` ·
   `cadence:<คำค้นในตารางรอบตรวจ>` · หรือ `ยังไม่มีใคร` · คำที่ห้าไม่มี เพราะ
   ช่องที่เขียนอะไรก็ได้คือช่องที่ทุกแถวจะกลายเป็น "มีคนดูแลอยู่" ภายในสองเดือน
3. **`ยังไม่มีใคร` เขียนได้ แต่ถูกนับ** — เพดาน `external_surface_unowned` ใน
   `pyproject.toml` เดินทางเดียวเหมือนเพดานอื่น (`scripts/check_ratchets.py`) ·
   ค่าตั้งต้นคือ 19 ซึ่งเป็นจำนวนที่วัดได้จริงในวันที่ตั้งทะเบียน ไม่ใช่เลขที่เผื่อไว้
4. **ทะเบียนผูกสองทิศกับตัวตรวจ** — `tests/test_external_surface.py` เทียบรายชื่อ
   ฟิลด์ที่ `audit_posture.judged_fields()` ตัดสินจริง กับแถวที่อ้างว่า `ci:posture`
   ดูแลอยู่ · ตัวตรวจเลิกอ่านฟิลด์ไหน ทะเบียนต้องเปลี่ยนตามในคอมมิตเดียวกัน
5. **ตัวตรวจอ่านเพิ่มสามอย่างในรอบนี้** — `default_workflow_permissions` ·
   `can_approve_pull_request_reviews` (endpoint `actions/permissions/workflow`)
   และ **ตัวเลขทั้งชุดในช่อง About** ไม่ใช่แค่เลขรุ่น: จำนวน gate · ADR ·
   รอบ audit · required check ทุกตัวนับจากดิสก์ได้ จึงไม่มีเหตุผลให้ค้างเงียบ ๆ
6. **สิ่งที่ตีพิมพ์ไปแล้วไม่มีใครแก้ได้ จึงต้องถูกกันที่ต้นทาง** —
   `tests/test_identity_cards.py` (gate `identity-cards-agree`) บังคับให้
   `CITATION.cff` กับ `.zenodo.json` ตรงกันเองและตรงกับ `docs/AUDIT-LOG.md`
   **ก่อน**ที่ Zenodo จะอ่านมันไปตีพิมพ์

## ผลที่ยอมรับ

- **ช่อง About จะแดงได้เมื่อเราเพิ่ม gate แล้วยังไม่อัปเดตหน้าเว็บ** — นั่นเป็น
  ความจริงที่เราอยากเห็น ไม่ใช่ผลข้างเคียง: หน้าร้านที่โฆษณาเลขเก่าคือหน้าร้าน
  ที่ผิด · แก้ด้วยคำสั่งเดียว (`gh api -X PATCH repos/:owner/:repo -f description=…`)
  และขั้นตอนอยู่ใน `docs/RELEASE.md` ข้อ 7 อยู่แล้ว
- **job `posture` ไม่รันบน pull request** (ADR 0066) ความแดงจึงมาถึงหลัง merge
  เสมอ — เป็นข้อจำกัดเดิมของ job นี้ ไม่ใช่ของทะเบียน
- **ทะเบียนนี้เก่าได้เหมือนทุกทะเบียน** — สิ่งที่กันไว้คือการเก่าแบบเงียบ:
  ฝั่งที่ผูกกับตัวตรวจแดงทันที ส่วนฝั่งที่เหลือมีแถวรอบตรวจ 6 เดือนที่
  `docs/SECURITY-CADENCE.md` และมีเพดานที่โตไม่ได้
