# 0064 — "ของเราล้มเหลว" หรือ "โลกล้มเหลว" อ่านจากข้อความของความล้มเหลว ไม่ใช่ชื่อ step

สถานะ: **accepted** (2026-08-18 — ช่องว่าง D1 กับ D2 ของ audit governance รอบแปด
· แก้กลไกที่ ADR 0059/0062 พึ่งอยู่ทั้งคู่)

**บริบท:** `scripts/rerun_census.py` (เกิดจาก audit r7) นับความล้มเหลวของ CI รวม
ของที่ถูก rerun จนหายไปจากสถิติ แล้วแยก "ของแพลตฟอร์ม" ออกจาก "ของเรา" เพื่อไม่ให้
เกณฑ์ flake ใน `docs/SECURITY-CADENCE.md` และหลักฐาน `proved_by` (ADR 0059) ถูก
มลพิษด้วยเรื่องที่เราแก้ไม่ได้ · **สัญญาณที่มันใช้แยกคือชื่อ step ที่ล้ม**
(`Set up job`) ซึ่งเป็นรูปที่เราเห็นตอนเขียน

วันที่ GitHub ล่มจริง (2026-08-17/18) ข้อมูลภาคสนามชุดแรกมาถึง: `codeql` ล้ม
**สี่ครั้งที่ step `Run github/codeql-action/init@…`** ซึ่งข้างในคือ HTTP 503 ของ
GitHub เอง — ตัวนับอ่านว่า "ของเรา" ทั้งสี่ครั้ง (ผิด 4 จาก 9 ครั้งในวันนั้น)
**ชื่อ step บอกว่าล้มตรงไหน มันไม่ได้บอกว่าใครล้มเหลว**

## คำตัดสิน

1. **สัญญาณคือข้อความของความล้มเหลว** — annotation ระดับ `failure` ของ check run
   ที่ผูกกับ job นั้น (`check_run_url` ที่ Actions API คืนมาให้อยู่แล้ว) ·
   ชื่อ step ยังใช้ได้แต่เป็น**บริบท** ไม่ใช่หลักฐาน
2. **สามคลาส ไม่ใช่สอง** — `platform` · `ของเรา` · **`ต้องอ่านเอง`** ·
   ชั้นที่สามรับทุกอย่างที่ตัดสินด้วยเครื่องไม่ได้ (ไม่มี annotation ให้อ่าน ·
   ล้มใน action ของคนอื่นโดยไม่มีร่องรอยว่าฝั่งไหนล้มเหลว) — **ห้ามตกไปอยู่ "ของเรา"
   เงียบ ๆ** เพราะนั่นคือความผิดพลาดที่ฉบับแรกทำ และมันเอียงไปทางที่ทำให้เรา
   สรุปว่าด่านของเราไม่เสถียรทั้งที่ไม่ได้เสีย
3. **รหัสสถานะนับเป็นหลักฐานของแพลตฟอร์มเฉพาะเมื่อมีบริบท HTTP กำกับ** — แอปนี้
   ตอบ 503 ที่ `/readyz` โดยตั้งใจและเทสต์ assert เลขนั้นตรง ๆ · ตัวจับ "503"
   ลอย ๆ จะย้ายความล้มเหลวของเราไปฝั่งแพลตฟอร์ม ซึ่งคือความผิดพลาดเดิมกลับด้าน
   (ตรวจแล้วว่าถ้อยคำที่ใช้เป็นหลักฐาน — "service unavailable" ฯลฯ — ไม่ปรากฏ
   ที่ไหนเลยใน `app/` `tests/` `scripts/` จึงชนกันเองไม่ได้)
4. **อ่าน annotation ไม่ได้ ต้องคืนค่าว่าง ห้าม raise** — สำมะโนที่ตายเพราะ job
   เดียวอ่านไม่ได้ คือสำมะโนที่รันไม่ได้ตอนแพลตฟอร์มมีปัญหา ซึ่งเป็นตอนที่
   ต้องการมันที่สุด · ผลคือความล้มเหลวนั้นตกชั้น `ต้องอ่านเอง` ตามข้อ 2
5. **ขั้นตอนก่อนกด rerun เป็นเอกสาร ไม่ใช่ความเคยชิน** (D2) — `docs/OPERATIONS.md`:
   ถาม `githubstatus.com` ก่อนเสมอ → ไม่ปกติแปลว่า **รอ ไม่ใช่ยิงซ้ำ** → จำแนก
   ด้วยตัวนับ → rerun ได้เฉพาะที่สรุปได้ว่าเป็นของแพลตฟอร์ม · "ของเรา" ที่รันใหม่
   แล้วเขียวคือ flake ที่ต้องขึ้นทะเบียน ไม่ใช่เรื่องที่ผ่านไปได้

## ทางที่ไม่ได้เลือก

- **เดาจากชื่อ job** (เช่น "codeql มักล้มเพราะ GitHub") — ปัดตก: เป็นสถิติของ
  อดีตที่แปะทับหลักฐานของปัจจุบัน วันที่ codeql ล้มเหลวเพราะโค้ดเราจริงจะถูกกลบ
- **ให้ทุกอย่างที่ไม่ชัดเป็น `platform`** — ปัดตก: เอียงอีกทางแล้วเกณฑ์ flake
  จะเงียบตลอดกาล ด่านที่ไม่เสถียรจริงจะไม่มีวันเข้าเกณฑ์
- **ดึง annotation ของ job ที่เขียวด้วย** — ไม่ทำ: คำขอต่อ job ที่ไม่ได้ล้ม
  ไม่ได้ตอบคำถามอะไร และทำให้สำมะโนช้าลงตามขนาดของ matrix

## ผลที่ตามมา

- `classify()` เป็นฟังก์ชันเดี่ยวที่เทสต์ยิงตรงได้ (`tests/test_checker_logic.py`
  — mutation ห้าทิศ รวมทิศกลับด้านของข้อ 3) · แถวในทะเบียนผู้ให้บริการ
  (`docs/SUPPLY-CHAIN.md`) กับเกณฑ์ flake ที่เคยระบุ `Set up job` แก้ตามแล้ว
- **บทเรียนที่ใหญ่กว่าตัวแก้** (r8): mutation test พิสูจน์ว่า*กฎที่เราเขียนไว้*
  ทำงาน — ไม่ได้พิสูจน์ว่ากฎนั้นตรงกับโลก · ตัวจำแนกเดิมผ่าน mutation ครบห้าทิศ
  แล้วยังอ่านผิด 4 ใน 9 ครั้งในวันแรกที่มีข้อมูลจริง · **ตัวจำแนก/ตัวตัดสินใหม่
  ทุกตัวต้องตอบให้ได้ว่า "ตัวอย่างจริงชุดแรกจะมาจากไหน และเราจะรู้ได้อย่างไรว่า
  มันจำแนกผิด"** ก่อนถือว่าเสร็จ
