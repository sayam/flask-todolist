# 0015 — audit trail: ดักที่ไหน เชื่อได้แค่ไหน และตัดทิ้งยังไงไม่ให้พัง

สถานะ: accepted (2026-08-03) — ปิด Phase 2

**บริบท:** ADR 0014 ตัดสินแล้วว่า *อะไร* ลงตาราง audit ได้บ้าง (ไม่มี PII)
ฉบับนี้ตัดสิน *กลไก* — ดักตรงไหน, พิสูจน์ความไม่ถูกแก้ยังไง, และล้างของเก่า
โดยไม่ทำลายสิ่งที่มันควรพิสูจน์

## 1. ดักที่ ORM ไม่ใช่ที่ route

**ทางเลือกที่ทิ้ง:** เรียก `audit.record(...)` ในแต่ละ route/service

ตรงไปตรงมากว่าและควบคุมข้อความได้ละเอียดกว่า แต่ **ต้องอาศัยความจำของคนเขียน**
route ใหม่ที่ลืมเรียกจะไม่ถูกบันทึกโดยไม่มีอะไรแดง และตัวที่ลืมง่ายที่สุดคือ
สคริปต์กับ CLI ซึ่งเป็นทางที่อันตรายที่สุดเพราะไม่มีด่านอะไรกั้นเลย

**ที่เลือก:** ผูก `after_flush` ของ SQLAlchemy `Session` ทุกการเขียนผ่าน ORM
จึงถูกบันทึกเอง ไม่ว่ามาจาก HTTP, `flask` CLI หรือ shell — เหตุผลเดียวกับที่
soft delete เลือกเติมตัวกรองอัตโนมัติแทนการให้เรียก helper เอง (ADR 0014 / Phase 2)

**ราคาที่จ่าย:** สิ่งที่ไม่ผ่าน ORM ก็ไม่ถูกบันทึก — bulk `UPDATE`/`DELETE`
ระดับ Core, `executemany` และ raw SQL มองไม่เห็นทั้งหมด ตอนนี้ระบบไม่มีการเขียน
แบบนั้นเหลืออยู่เลย (purge job เป็นที่เดียวที่ลบจริงและใช้ ORM) และมีเทสต์
ที่ทำให้การเพิ่มเข้ามาใหม่ถูกจับได้ แต่ต้องรู้ตัวว่านี่คือขอบของกลไกนี้

เหตุการณ์ที่ไม่ใช่การเขียน DB (login/logout/login ไม่ผ่าน) ยังต้องเรียก
`audit.record()` เอง เพราะไม่มี write ให้ดัก — เป็นทางออกที่ยอมรับได้เพราะมีอยู่
ไม่กี่จุดและอยู่ในไฟล์เดียว

## 2. hash chain + `prev_hash` unique

แต่ละแถวเก็บ hash ของแถวก่อนหน้า แก้แถวเก่าแถวเดียวทำให้ทุกแถวถัดไปตรวจไม่ผ่าน

เพิ่มจากแผนเดิม: **บังคับ `prev_hash` ให้ unique ที่ระดับ DB** ทำให้สายแตกเป็น
สองสายไม่ได้เลย ไม่ใช่แค่ "ตรวจเจอทีหลัง"

**ราคาที่จ่าย:** ถ้ามีสอง process เขียนพร้อมกันจริง ๆ ตัวหลังจะได้ IntegrityError
แล้ว transaction ตกไป **ตั้งใจให้ดังกว่าการมี chain ที่พังเงียบ** — scale ตอนนี้
เป็น SQLite ที่ serialize การเขียนอยู่แล้ว วันที่ต้องเขียนขนานจริง (Phase 5
ขึ้น PostgreSQL/MySQL) ต้องเปลี่ยนเป็นการจองลำดับผ่าน sequence หรือรวมเป็น batch
**ให้ถือว่าข้อนี้เป็นหนี้ที่รู้ตัว ไม่ใช่ของที่เสร็จแล้ว**

## 3. ตัดของเก่าได้จากหัวสายเท่านั้น

retention ของ audit คือ 1 ปี แต่ `DELETE WHERE created_at < cutoff` เฉย ๆ **ผิด**
ถ้านาฬิกาเครื่องถูกปรับย้อนหลัง (NTP) จะมีแถวที่เวลาเก่ากว่าไปนั่งอยู่กลางสาย
การลบมันคือการเจาะรูตรงกลาง ซึ่ง checkpoint กู้ไม่ได้เพราะ checkpoint รับรอง
ได้แค่ช่องว่างที่ต้นสาย ผลคือ `verify` ไม่ผ่านไปตลอดกาลโดยไม่มีใครทำอะไรผิด

**กติกา:** ลบได้เฉพาะ **คำนำหน้า** ของสาย — ไล่จากหัวแล้วหยุดที่แถวแรกที่ยัง
ไม่หมดอายุ แถวเก่าที่ตกค้างอยู่หลังจากนั้นถูกเก็บเกินระยะไปอีกพักหนึ่ง
**ยอมเก็บเกินดีกว่าทำหลักฐานพัง**

checkpoint ถูกเขียน**ก่อน**ลบเสมอ เพื่อให้มันเกาะปลายสายเดิมได้ตามธรรมชาติ
(ถ้าลบก่อนแล้วค่อยเขียน จะไม่มีอะไรให้เกาะเมื่อลบหมดทั้งตาราง)

## 4. append-only บังคับที่โค้ด ไม่ใช่แค่ "ไม่มีหน้าจอให้แก้"

การไม่มี UI แก้ log คือการ *ไม่ได้ทำ* ไม่ใช่การ *กันไว้* — สคริปต์หรือ shell
เขียนทับได้อยู่ดี จึงมีด่านใน `before_flush` ที่ปฏิเสธการแก้/ลบแถว audit
ทุกกรณี ยกเว้น purge job ที่ต้องขอสิทธิ์เป็นการเฉพาะและคืนสิทธิ์ทันทีที่เสร็จ

ยังไม่ได้กันระดับ DB (trigger / สิทธิ์ของ role แยก) เพราะ SQLite ไม่มีระบบสิทธิ์
ให้ใช้ — ยกไปพร้อม Phase 5 ตอนขึ้น DB ที่มี role จริง

## 5. "ที่ไหน" ตอบด้วย `request_id` ไม่ใช่ IP

IP เป็นข้อมูลส่วนบุคคลที่ชั้น C6 ให้อายุ 90 วัน ถ้าก๊อปมาเก็บในตาราง audit ด้วย
มันจะกลายเป็นข้อมูล 1 ปีโดยไม่มีใครตั้งใจ — เก็บ `request_id` ซึ่งเป็น UUID
ที่ไม่บอกอะไรเลยด้วยตัวเอง แล้วให้ไปค้นต่อใน log ระหว่างที่ log ยังไม่หมดอายุ
**ผลที่ยอมรับ:** พ้น 90 วันแล้วจะรู้แค่ว่าใครทำอะไร ไม่รู้ว่ามาจากที่ไหน

## 6. เวลาในตาราง audit เก็บแค่ระดับวินาที

MySQL `DATETIME` ปัดเศษ microsecond ทิ้งเอง ถ้า hash ค่าที่ละเอียดกว่าที่ DB
เก็บได้ พออ่านกลับมาคำนวณใหม่จะไม่ตรงทันทีที่ย้ายยี่ห้อ DB — ตัดเศษทิ้งฝั่งแอป
ก่อนทั้งเก็บและ hash (ROADMAP ข้อ 4.5) ลำดับของสายมาจาก `prev_hash` ไม่ใช่จาก
เวลา ความละเอียดระดับวินาทีจึงไม่ทำให้เสียอะไร

## สรุปว่าตกลง "เชื่อได้แค่ไหน"

| คำถาม | ตอบได้ไหม |
|---|---|
| มีใครแก้แถวที่ยังอยู่ไหม | **ได้** — `flask audit-verify` |
| มีใครลบแถวกลางสายไปไหม | **ได้** — แถวถัดไปจะไม่ต่อ |
| มีใครตัดหางสายทิ้งทั้งท่อนไหม | **ไม่ได้** — ตัดท้ายแล้วส่วนที่เหลือยังสอดคล้องกันเอง |
| มีใครลบทั้งตารางแล้วสร้างใหม่ไหม | **ไม่ได้** |

สองข้อล่างต้องการ storage แบบ write-once ภายนอกหรือการส่ง hash ล่าสุดออกไป
เก็บที่อื่น (SIEM/anchor) ซึ่งเกินความจำเป็นของ scale นี้ — **ยกไป Phase 7
พร้อมงานต่อท่อ SIEM** และบันทึกไว้ตรงนี้ว่ารู้ตัว ไม่ใช่มองข้าม
