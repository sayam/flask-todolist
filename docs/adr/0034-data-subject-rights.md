# 0034 — สิทธิ์ของเจ้าของข้อมูลบนระบบที่ไม่มีหน้าสมัคร

สถานะ: accepted (2026-08-11) — Phase 7 · อนุมัติโดยเจ้าของโปรเจกต์

**บริบท:** PDPA ให้สิทธิ์เจ้าของข้อมูลขอสำเนาข้อมูลของตัวเองและขอให้ลบ
[ADR 0014](0014-pdpa-vs-audit-retention.md) ตัดสินไปแล้วว่า *อะไรชนะอะไร*
เมื่อสิทธิ์นั้นชนกับ audit ที่ลบไม่ได้ — แต่ยังไม่ได้ตัดสินว่า **ใครกดปุ่มได้**
และ **ปุ่มนั้นทำอะไรบ้าง**

ระบบนี้ **ไม่มีหน้าสมัครสมาชิกโดยตั้งใจ** ทุกบัญชีมาจาก `flask create-user`
ของผู้ดูแล คำถามจึงไม่ใช่คำถามซ้ำซากว่า "ควรมีปุ่มลบบัญชีไหม" แต่คือ "บัญชี
ที่องค์กรเป็นคนสร้างให้ เจ้าตัวลบเองได้หรือเปล่า"

## คำตัดสิน

### 1. **เจ้าตัวลบบัญชีตัวเองได้ทันที** ไม่ต้องรออนุมัติ

เจ้าของโปรเจกต์ตัดสินแล้ว และเหตุผลตรงไปตรงมา: ระบบนี้เก็บข้อมูลส่วนตัวของ
คนใช้ ไม่ใช่บันทึกของหน่วยงานที่ผู้ใช้เป็นเพียงผู้กรอก · การให้ต้องขออนุมัติ
สร้างสถานะ "คำขอที่รออยู่" ซึ่งต้องมีหน้า มีการแจ้งเตือน และมีคนคอยดู —
โครงสร้างถาวรที่ต้องดูแลตลอดไปเพื่อรองรับเหตุการณ์ที่เกิดปีละไม่กี่ครั้ง

**ข้อยกเว้นข้อเดียว: ผู้ดูแลคนสุดท้ายลบตัวเองไม่ได้** เพราะระบบที่ไม่เหลือ
ผู้ดูแลคือระบบที่ไม่มีใครสร้างบัญชีหรือกู้รหัสผ่านให้ใครได้อีกเลย — ต้องยก
ใครสักคนขึ้นเป็นผู้ดูแลก่อน · หลักเดียวกับที่แก้บทบาทตัวเองบนหน้าเว็บไม่ได้
([ADR 0022](0022-minimal-rbac.md)) และข้อความที่ปฏิเสธต้องบอกทางออก
ไม่ใช่บอกแค่ว่าทำไม่ได้

### 2. **ทั้ง export และ delete ต้องกรอกรหัสผ่านซ้ำ**

ทั้งคู่เป็นการกระทำที่ session ที่ถูกยึดใช้ทำความเสียหายได้มากที่สุด —
อันหนึ่งดูดข้อมูลทั้งบัญชีออกไปในคำขอเดียว อีกอันทำลายมันทั้งหมด ·
หลักเดียวกับการออก API token และการปิดปัจจัยที่สอง ซึ่งบังคับรหัสผ่านซ้ำอยู่แล้ว

### 3. **export คือ JSON ก้อนเดียว และเส้นแบ่งคือชั้นข้อมูล ไม่ใช่ความสะดวก**

| ชั้น | อยู่ในไฟล์ไหม | เหตุผล |
|---|---|---|
| C1 ความลับ | **ไม่** แม้แต่ในรูป hash | ADR 0014 — `password_hash` ห้ามออกจากระบบทุกกรณี · ความลับ TOTP ก็เช่นกัน (บอกได้แค่ว่า "เปิดใช้อยู่") |
| C2 ระบุตัวบุคคล | ใช่ | เป็นข้อมูลของเขาโดยตรง |
| C3 เนื้อหาของผู้ใช้ | ใช่ | งาน หมวด ชื่อ token — สิ่งที่เขาพิมพ์เอง |
| C4 การตั้งค่า | ใช่ | ภาษา ธีม โซนเวลา บทบาท เวลาสร้าง/แก้ |
| C5 audit | ใช่ **แต่เฉพาะส่วนที่เป็นเรื่องของเขา** | เหตุการณ์ + เวลา + แถวที่ถูกแตะ · **ไม่รวม `changes`, `prev_hash`, `row_hash`** เพราะเป็นกลไกพิสูจน์ความครบถ้วนของสาย ไม่ใช่ข้อมูลส่วนบุคคล และค่าใน `changes` เป็น HMAC ที่อ่านไม่ออกอยู่แล้ว |
| C6 log ปฏิบัติการ | **ไม่ได้** | ออก stdout ไปอยู่นอกแอปตั้งแต่วินาทีแรก แอปไม่มีทางค้นมันเลย — **ต้องบอกข้อจำกัดนี้ในไฟล์ที่ส่งออก** ไม่ใช่เงียบแล้วให้เข้าใจว่าครบ |

**ใครทำอะไร บอกเป็นบทบาทไม่ใช่ id** — แถว audit ที่ผู้ดูแลเป็นคนทำ
(เช่นเปลี่ยนบทบาท) บอกว่า `"by": "administrator"` ไม่ใช่เลข `actor_id`
ของคนนั้น เพราะ id ของผู้ดูแลไม่ใช่ข้อมูลส่วนบุคคลของผู้ขอ

**ไฟล์ต้องตอบ `no-store` และชื่อไฟล์สร้างฝั่งเซิร์ฟเวอร์** ไม่รับจากผู้ใช้
(ASVS V5.4.1) · และเนื้อหาทั้งก้อนเป็น C2/C3 จึงห้ามแคชที่ไหนทั้งสิ้น

### 4. **delete ทำอะไรบ้าง — และทำ "ทันที" กับ "ตามระยะ" คนละอย่าง**

ทันทีที่กดยืนยัน:

- `password_hash` ถูกล้าง (C1 ไม่รอ grace — ADR 0014)
- **ความลับของทุกปัจจัยที่สองที่เปิดอยู่ ถูกลบจริง** ผ่าน `mfa.disable()`
  ซึ่ง core เรียกโดย**ไม่รู้จักชื่อ plugin ตัวไหน** ([ADR 0024](0024-mfa-as-an-auth-plugin.md))
- API token ทุกใบถูกเพิกถอน (ล้าง hash) ไม่ใช่แค่ซ่อน ([ADR 0017](0017-personal-access-tokens.md))
- คุกกี้ทุกใบตายทันที เพราะมันผูกกับ `password_hash` ที่เพิ่งหายไป ([ADR 0020](0020-session-lifetime-and-binding.md))
- แถวของผู้ใช้ งาน และหมวด ถูก soft delete

ตามระยะ (30 วัน) `flask purge-expired` ลบจริงและเหลือ tombstone ที่
`username` → `#deleted-<id>` ให้ audit อ้าง `actor_id` ได้ต่อ

**ข้อบกพร่องที่ ADR นี้เป็นตัวหาเจอ**: `flask delete-user` ที่มีอยู่แล้ว
ล้างรหัสผ่านและ token ครบ แต่ **ไม่ได้แตะความลับของปัจจัยที่สองเลย** —
ขัดกับกติกา C1 ของ ADR 0014 ที่ตัวมันเองอ้างถึงในคอมเมนต์ · ทางเดียวที่กันไม่ให้
เกิดซ้ำคือ **ให้ CLI กับหน้าเว็บเรียก service ตัวเดียวกัน** ไม่ใช่ต่างคนต่างไล่ลบ

### 5. **สิ่งที่ลบไม่ได้ ต้องบอกก่อนกด ไม่ใช่หลังกด**

แถว audit ยังอยู่ครบตาม ADR 0014 — และนั่นเป็นเรื่องที่ยอมรับได้เพราะ
**ไม่เคยมี PII ของใครอยู่ในนั้นตั้งแต่แรก** มีแค่ `actor_id` ที่เป็นเลข
กับ HMAC ที่ย้อนกลับไม่ได้ · หน้ายืนยันการลบต้องเขียนข้อนี้ให้ผู้ใช้อ่าน
ก่อนตัดสินใจ ไม่ใช่ซ่อนไว้ในเอกสารที่ไม่มีใครเปิด

## ผลที่ตามมา

- **ตรรกะอยู่ใน service ตัวเดียว** ทั้ง HTML/API/CLI เรียกตัวเดียวกัน ([ADR 0016](0016-service-layer-boundary.md))
  — ไม่งั้นข้อบกพร่องแบบข้อ 4 จะเกิดซ้ำทุกครั้งที่เพิ่มช่องทางใหม่
- **export ต้องมีเทสต์ว่าของคนอื่นไม่หลุดเข้าไป** และว่า C1 ไม่โผล่ในไฟล์
  แม้แต่ชื่อฟิลด์ — เทสต์ที่ตรวจแค่ "ไฟล์มีงานของฉันครบ" ผ่านได้ทั้งที่มีของคนอื่นปนอยู่
- **การเพิ่มคอลัมน์ใหม่ต้องตัดสินใจว่ามันอยู่ใน export ไหม** ในจังหวะเดียวกับ
  ที่จำแนกชั้นใน `docs/DATA-CLASSIFICATION.md` — ทางที่ทำให้ลืมไม่ได้คือให้
  เทสต์เทียบรายชื่อฟิลด์ใน export กับ metadata ของตาราง ไม่ใช่รายการที่พิมพ์มือ
- ยังไม่ทำ: การส่งออกในรูปแบบที่เครื่องอื่นนำเข้าได้ตามมาตรฐาน (data portability
  แบบเต็ม), การขอแก้ไขข้อมูลผ่านช่องทางที่บันทึกเป็นคำขอ, และการลบแบบ
  "ทันทีจริง ๆ" โดยไม่รอ 30 วัน — ระยะนั้นเป็นค่าที่อนุมัติไว้แล้วใน ADR 0014
