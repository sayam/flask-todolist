# 0059 — ด่านต้องเก็บหลักฐานว่าเคยแดง (`proved_by`)

สถานะ: **accepted** (2026-08-17 — ข้อเสนอข้อ 1 ของ audit governance รอบ 6:
"ด่านที่สร้างมาเคยจับของจริงไหม")

## บริบท — ตัวเลขที่ตอบคำถามไม่ได้

รอบ 6 ของ audit วัดจาก **200 run ล่าสุดของ CI**: สำเร็จ 185 · ล้ม 13 (92.5%) ·
เวลาเฉลี่ย ~8 นาที/run · run ที่ล้ม **13 จาก 13 อยู่บน branch ไม่ใช่ main**
(เส้นทางบังคับของ ADR 0053 พิสูจน์ตัวเองด้วยข้อมูล) — แต่เมื่อแยกตาม job
ได้ภาพที่ตอบคำถามไม่ได้:

- **9 job เคยแดง** — `test` 7 · `lint` 3 · `release-sign` 2 · `dast` 2 ·
  `stack`/`siem`/`image`/`dialects`/`bare` อย่างละ 1
- **21 job ไม่เคยแดงเลยสักครั้ง**

"ไม่เคยแดง" จากภายนอกแยกไม่ออกระหว่าง **ของดีจริงจึงไม่แดง** กับ **ด่านนั้น
ไม่ได้ตรวจอะไร** — และคำตอบของสองอย่างนี้ต่างกันคนละขั้ว นี่คือกับดักเดียวกับ
ที่ `SKILL.md` ข้อ 2 เขียนไว้เองว่า *"ด่านที่ผ่านหน้าตาเหมือนด่านที่ไม่ได้ตรวจ
เสมอ จนกว่าจะวัดว่ามันตรวจอะไรจริง"* — repo นี้บังคับ mutation test กับ**เทสต์**
มาตลอด แต่ไม่เคย**เก็บ**ผลนั้นไว้ที่ไหน พอเวลาผ่านไปจึงไม่มีใครตอบได้ว่า gate
ตัวไหนเคยพิสูจน์ตัวเองแล้วบ้าง

## คำตัดสิน

1. **`gates.yaml` มีฟิลด์ `proved_by`** — รายการหลักฐานว่าด่านนี้เคยแดง
   *ตอนที่ของเสียจริง* สองชนิด:
   - `kind: ci-red` · `ref: run/<id>` — แดงเองใน CI · ตรวจซ้ำได้ด้วย
     `gh run view <id> --log-failed` · แข็งกว่าเพราะไม่มีใครจัดฉาก
   - `kind: mutation` · `ref: pr/<number>` — แดงตอนทำให้โค้ดผิดโดยตั้งใจตอนเขียนด่าน
     ซึ่งเป็นวินัยของโปรเจกต์อยู่แล้ว แค่ไม่เคยถูกเก็บให้ค้นได้
   ทุกรายการมี `date` และ `caught` (มันจับ*อะไร*ได้ — ไม่ใช่แค่ว่ามันแดง)
2. **gate ใหม่ต้องมาพร้อมหลักฐานตั้งแต่เกิด** · gate ที่มีอยู่ก่อนกติกานี้
   อยู่ในรายการ `UNPROVEN` ของ `tests/test_gate_evidence.py` ซึ่ง **หดได้
   ทางเดียว** (ratchet แบบเดียวกับ `UNASSESSED_CEILING` ของ ASVS) — สองทิศ:
   ชื่อผีในรายการแดง และตัวที่พิสูจน์แล้วแต่ยังค้างในรายการก็แดง
3. **หลักฐานชุดแรก 14 gate มาจาก run จริงทั้งหมด** ไม่ใช่ของที่จัดฉากย้อนหลัง —
   ตัวอย่างที่เล่าตัวเองได้: `image-os-cve-audit` แดงด้วย CVE-2026-53615 หลัง
   เปิดใช้วันเดียว · `stack`/`siem`/`dast` แดงพร้อมกันจากบั๊กเดียว (`/readyz`
   ตอบ 302 หลังปิด TLS ที่ proxy → healthcheck ไม่เคยผ่าน) · `release-sign`
   แดงสองรอบจาก glob ที่กว้างเกินตอน v1.5.0
4. **ผลพลอยได้ที่ตั้งใจเก็บ: ด่านที่แดงบ่อยที่สุดของ repo กลับไม่มีแถวในดัชนี** —
   `diff-cover` (5 จาก 13 run ที่ล้ม) ไม่เคยถูกลงทะเบียน เพราะกฎ "ทุก job ต้องมี
   gate" ถือว่า job `test` ถูกครอบด้วย gate ของไฟล์เทสต์ไปแล้ว → เพิ่ม gate
   `changed-lines-fully-tested` (kind: step) พร้อมหลักฐานของมันเอง
5. **กติกานี้ไหลออกไปกับ overlay/SKILL** — โปรเจกต์ปลายทางมี gate ของตัวเอง
   ที่ต้องพิสูจน์เหมือนกัน (gate `gates-carry-red-evidence` · baseline · portable)

## สิ่งที่ตั้งใจ *ไม่* ทำ

- **ไม่ตรวจ `ref` กับ GitHub ตอนรันเทสต์** — ชุดเทสต์ต้องรันได้ออฟไลน์ และด่าน
  ที่ต้องต่อเน็ตคือด่านที่แดงเพราะเน็ต (หลักเดียวกับ `docs/asvs-5.0.0.json`
  ที่ตรึงไว้) · เทสต์บังคับ*รูป*ของหลักฐานให้ตามกลับไปดูของจริงได้เท่านั้น
- **ไม่ไล่พิสูจน์ 81 gate ที่เหลือย้อนหลังในรอบเดียว** — การนั่งล้มเหลว 81 จุดเพื่อ
  เก็บหลักฐานให้ครบคือพิธีกรรมที่ราคาแพงและได้ของที่จัดฉากทั้งชุด · ให้หลักฐาน
  มาตามธรรมชาติ: ทุกครั้งที่ด่านแดงจริง หรือทุกครั้งที่ gate นั้นถูกแก้แล้วต้อง
  mutation ใหม่อยู่ดี
- **ไม่บังคับว่าต้องเป็น `ci-red`** — mutation ที่บันทึกไว้ก็เป็นหลักฐานที่
  ตรวจซ้ำได้ · การบังคับ `ci-red` จะสร้างแรงจูงใจให้ปล่อยของเสียเข้า CI

## เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ

- **รายการ `UNPROVEN` ไม่หดเลยภายใน 12 เดือน** (ทบทวนตามแถว "เงื่อนไขทบทวนของ
  ADR" ใน `docs/SECURITY-CADENCE.md`) = กติกานี้ไม่ได้ผลจริง ให้เลือกทางใดทางหนึ่ง
  อย่างเปิดเผย: ไล่พิสูจน์เป็นแบตช์ หรือถอนกติกา — ไม่ใช่ปล่อยให้เป็นฟิลด์ประดับ
- **ถ้าเริ่มมีคนเติมชื่อลง `UNPROVEN` แทนการพิสูจน์** ratchet จะแดงก่อน แต่ถ้า
  เพดานถูกขยับเมื่อไหร่ ให้ถือว่าเป็นสัญญาณว่ากติกาแพงเกินจริง และต้องบันทึก
  เหตุผลใน ADR ใหม่ ไม่ใช่แก้ตัวเลขเงียบ ๆ

## โน้ต 2026-08-17 (audit รอบ 7) — ตัวเลขตั้งต้นข้างบนต่ำกว่าจริง

**ไม่แก้ตัวเลขในบริบทข้างบน แต่บันทึกความคลาดเคลื่อนไว้ตรงนี้** — ADR ฉบับนี้อ้าง
"ล้ม 13 จาก 200 run" ซึ่งได้มาจาก `gh run list --json conclusion` ที่รายงานผลของ
**attempt สุดท้ายเท่านั้น** · ความล้มเหลวที่ถูก rerun จนเขียวจึงหายไปจากการนับ ·
วัดใหม่ด้วย `scripts/rerun_census.py` ที่ไล่ทุก attempt: 100 run ล่าสุด **เห็น 7
ซ่อนอีก 3** (`dast` สองครั้ง · `codeql` หนึ่งครั้ง)

ผลกระทบต่อคำตัดสินของ ADR นี้: **ไม่มี** — เหตุผลของ `proved_by` คือ "ไม่เคยแดง
แยกไม่ออกจากไม่ได้ตรวจอะไร" ซึ่งจริงขึ้นเมื่อรู้ว่าการ rerun ทำให้ job ที่เคยแดง
**กลับไปเป็นไม่เคยแดง**ได้ด้วย · แต่มันเปลี่ยนวิธีทำงานสองข้อ:

1. หลักฐาน `kind: ci-red` ที่มาจาก run ซึ่งถูก rerun ภายหลัง **ยังใช้ได้**
   (ช่อง `caught` เล่าเรื่องได้เองโดยไม่ต้องเปิด log) แต่คนตามรอยต้องรู้ว่าต้องดู
   `/runs/<id>/attempts/<n>/jobs` ไม่ใช่หน้า run เปล่า ๆ
2. ทุกที่ที่นับความล้มเหลวของ CI ต้องใช้ `scripts/rerun_census.py` — รวมแถวทบทวน
   flake ใน `docs/SECURITY-CADENCE.md` ที่เดิมสั่งวิธีนับแบบเก่า (แก้แล้วในรอบเดียวกัน)

## ผลที่ตามมา

- ดัชนี `gates.yaml` ตอบคำถามใหม่ได้: *"ด่านตัวนี้เคยจับอะไรได้บ้าง"* ซึ่งเป็น
  คำถามที่ผู้ตรวจภายนอกถามก่อนคำถามว่า "มีด่านกี่ตัว"
- gate ปัจจุบัน 95 (baseline 70 · business 10 · internal 15 · portable 79)

---

**โน้ต (2026-08-18 — audit r9 ข้อ 1 · หลักฐานต้องเก็บตอนที่มันเกิด)**: กติกาใบนี้
กันรายการ `UNPROVEN` ไม่ให้โตได้จริง แต่ **ไม่มีแรงใดผลักให้หด** — วัดตอนนั้น
76 จาก 97 gate (78%) ยังไม่มีหลักฐาน และรายการนั่งอยู่ที่เพดานพอดี ขณะที่ CI
แดงจริงหลายครั้งต่อสัปดาห์แล้วหลักฐานหายไปกับ log ที่ไม่มีใครเปิด

เพิ่มสองอย่างที่ทำงานคู่กัน: `scripts/rerun_census.py --evidence` อ่านชื่อไฟล์
เทสต์ที่แดงจาก log ของ job แล้วแม็ปกลับเป็น gate ด้วย partition ที่
`tests/test_gates.py` คุมอยู่แล้ว → **เสนอ**แถว `proved_by` ที่คนอ่านแล้วรับเอง ·
และแถวทวงทุก 6 เดือนใน `docs/SECURITY-CADENCE.md` ที่บังคับให้ลด
`UNPROVEN_CEILING` ตามจำนวนที่หดจริง

**เครื่องมือหยุดที่การเสนอโดยตั้งใจ** — การตัดสินว่าความแดงครั้งนั้น*พิสูจน์*อะไร
ได้จริงเป็นงานของคน (เทสต์แดงเพราะ fixture ล้มเหลว ไม่ใช่หลักฐานว่า gate จับของเสีย)
เครื่องมือที่เขียน `proved_by` ให้เองจะทำให้รายการหดโดยที่คุณภาพของหลักฐานหายไป
ซึ่งแย่กว่าการมีหนี้ที่มองเห็น
