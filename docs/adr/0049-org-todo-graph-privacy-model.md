# 0049 — privacy model ของ org todo graph

สถานะ: **accepted** (2026-08-15 — เจ้าของอนุมัติตามร่าง พร้อมตัดสินคำถามเปิด
ทั้งสามข้อตามข้อเสนอ · เปิดเฟส 18)

**บริบท:** feature ธงของแผน 1.1 — ให้คนในองค์กรประกาศว่า "งานของฉันขึ้นกับ
งานของคุณ" แล้วระบบประเมินผลกระทบ (งานที่เราพึ่งเลยกำหนด = ความเสี่ยงของเรา)
**โดยไม่เปิดเผยเนื้อหางาน private ของใคร** · ความตึงหลักคือ dependency มี
ประโยชน์ก็ต่อเมื่อมันข้ามคน แต่ทุกอย่างที่ข้ามคนคือช่องรั่วที่ต้องออกแบบ

## คำตัดสิน

### 1. หน่วยของการแบ่งปันคือ "งานที่ถูกแชร์" ไม่ใช่ "บัญชีที่ถูกเปิด"

- งานทุกใบเป็น **private โดยค่าเริ่มต้น** — เหมือนที่เป็นมาตลอด ไม่มีอะไรเปลี่ยน
  สำหรับคนที่ไม่ใช้ feature นี้ (opt-in ต่อใบ ไม่ใช่ opt-out)
- เจ้าของงานเลือก **แชร์งานทีละใบ** เข้า "วง" (team) — งานที่แชร์แล้วเผย
  เฉพาะ: **ชื่องาน · กำหนดส่ง · สถานะเสร็จ/ไม่เสร็จ · ชื่อเจ้าของ** ต่อสมาชิกวง
- **งาน private เผยอะไรให้ใครไม่ได้เลย รวมทั้ง "การมีอยู่"** — ตัวเลือกที่เผย
  แค่การมีอยู่ (`มีงานลับ 3 ใบบล็อกคุณอยู่`) ถูกปัดตกเพราะมันคือ metadata
  ที่บอกปริมาณ/จังหวะงานของคนอื่น และขัดหลัก ADR 0004 (การยืนยันว่าของมีอยู่
  ก็คือข้อมูล)

### 2. dependency เกิดจาก เชิญ → ยอมรับ เท่านั้น

- คนขอพึ่ง (A) ชี้ได้เฉพาะ **งานที่ถูกแชร์เข้าวงที่ A อยู่แล้ว** — ไม่มีการพิมพ์
  id ที่ไม่ถูกต้องเพื่อ probe (id นอกวง = 404 ตาม ADR 0004 เสมอ)
- การประกาศ dependency ต้องให้**เจ้าของงานปลายทางยอมรับ**ก่อนถึงจะมีผล —
  unilateral ไม่ได้ เพราะ dependency ที่ค้างอยู่คือช่องให้เดาสถานะงานคนอื่น
  ผ่านสัญญาณ impact และคือการเอาชื่อเราไปแขวนใน UI ของคนอื่นโดยไม่ถาม
- ถอนได้ทั้งสองฝั่งทุกเมื่อ · เจ้าของเลิกแชร์งาน = dependency ที่ชี้มาหางานนั้น
  ถูกตัดพร้อมแจ้งฝั่งที่พึ่ง (เห็นแค่ "งานที่คุณพึ่งถูกเลิกแชร์" ไม่บอกเหตุผล)

### 3. impact ประเมินจากของที่แชร์แล้วเท่านั้น และเป็น deterministic

- สัญญาณเดียวในเฟสแรก: **ห่วงโซ่กำหนดส่ง** — งานที่เราพึ่ง (ตรงหรือผ่านโซ่)
  เลยกำหนด/ยังไม่เสร็จทันเวลา = ป้ายความเสี่ยงบนงานของเรา
- คำนวณจาก**เฉพาะงานที่แชร์และ dependency ที่ยอมรับแล้ว** — ไม่มีการโดยไม่ได้สั่งรวม
  งาน private เข้าโซ่ (ต่อให้แม่นขึ้นก็ตาม) เพราะผลรวมที่ "รู้มากกว่าที่เห็น"
  คือช่องรั่วแบบ inference
- ไม่มี ML/คะแนนถ่วงน้ำหนักในเฟสนี้ (ตัดตาม ADR 0043) — ตัวเลขที่อธิบายไม่ได้
  ตรวจ privacy ไม่ได้

### 4. โครงข้อมูลและกติกาที่ตามมา

- ตาราง core ใหม่ (`tdl_team` · `tdl_team_member` · `tdl_todo_share` ·
  `tdl_todo_dependency`) เดินครบวงจรเดิมทุกข้อ: จำแนกชั้นใน
  DATA-CLASSIFICATION · ตัดสินใน export (ม.30) · audit อัตโนมัติ ·
  migration ของ core
- ปิดบัญชี/ระงับบัญชี: งานที่แชร์ของคนที่ปิดบัญชีหายจากวงพร้อมกัน (ตาม
  วงจร close_account เดิม) — dependency ที่ชี้มาถูกตัดแบบเดียวกับการเลิกแชร์
- `/api/v1` เพิ่มแบบ additive เท่านั้น (ADR 0018) · ทุกสิ่งที่ประกาศว่า
  "ไม่เห็น" ต้องมีเทสต์พิสูจน์ว่า**ไม่รั่วผ่านทุกช่องทาง** (หน้าเว็บ · API ·
  สัญญาณ impact · ข้อความ error) — ไม่ใช่แค่ "ไม่มีปุ่ม"

## คำถามเปิด — เจ้าของตัดสินแล้ว (2026-08-15)

1. **ไม่มีระดับ "แชร์แบบปิดชื่อ" ในเฟสแรก** — สถานะที่สามทำ privacy matrix
   ซับซ้อนขึ้นโดยที่งานปิดชื่อไม่ช่วยให้ฝั่งพึ่งตัดสินใจอะไรได้จริง ·
   เพิ่มทีหลังแบบ additive ได้ถ้ามีความต้องการจริง
2. **วง (team) สร้าง/จัดการโดย admin เท่านั้น** — สอดคล้องกับที่ระบบนี้ไม่มี
   self-service มาตลอด (สมัครสมาชิก/กู้รหัสก็ผ่าน admin — ADR 0019)
   ผู้ใช้ทั่วไปตั้งวงเองเป็นการขยายทีหลังได้
3. **ป้าย impact อยู่ในหน้า list หลัก** — ป้ายเล็กบนแถวงานที่เสี่ยง แบบเดียว
   กับป้าย overdue ที่มีอยู่ · หน้าแยกคือหน้าที่ไม่มีใครเปิด
