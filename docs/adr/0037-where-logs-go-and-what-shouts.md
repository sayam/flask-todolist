# 0037 — log ไปไหน และอะไรเป็นตัวส่งเสียง

สถานะ: accepted (2026-08-12) — Phase 7 · P7-10 · เจ้าของโปรเจกต์เลือก Loki + Grafana

**บริบท:** [ADR 0011](0011-structured-json-logging.md) ตัดสินไว้ตั้งแต่ Phase 1
ว่า log เป็น JSON บรรทัดละ event ออก stdout **เพื่อให้ Phase 7 ต่อปลายทางได้
โดยไม่ต้องไล่แก้จุดที่เขียน log** — วันนั้นมาถึงแล้ว

ROADMAP เขียนไว้ว่า "ELK/Graylog" ตอนที่ยังไม่ได้ดูของจริง · เมื่อดูแล้ว
Elasticsearch กิน RAM มากกว่าที่ระบบขนาดนี้ควรจ่าย และ Graylog ต้องลาก MongoDB
กับ OpenSearch มาด้วย — สำหรับระบบที่ตั้งเป้าไว้ที่ผู้ใช้ 1–5 คน
([ADR 0031](0031-performance-targets-and-what-they-mean.md)) นั่นคือโครงสร้างที่
ใหญ่กว่าสิ่งที่มันเฝ้าอยู่

## คำตัดสิน

### 1. Loki เก็บ · Alloy เก็บของมาส่ง · Grafana ให้คนดู

**แอปไม่รู้จักปลายทางนี้เลย** — ยังออก stdout อย่างเดียวเหมือนเดิม ตัวเก็บอ่านจาก
ไฟล์ log ที่ docker เขียนไว้ให้ container ทุกตัว · ถอด `compose.siem.yaml` ทิ้ง
แล้วแอปทำงานเหมือนเดิมทุกประการ ซึ่งเป็นเงื่อนไขเดียวกับที่ ADR 0011 ตั้งไว้

### 2. **กฎแจ้งเตือนอยู่ที่ ruler ของ Loki ไม่ใช่ที่ Grafana**

เพราะสถานะของกฎถามผ่าน API ได้ตรง ๆ — ด่านใน CI จึงถามได้ว่า *"กฎนี้ firing
หรือยัง"* โดยไม่ต้องคลิกอะไรบนหน้าจอ · **ระบบแจ้งเตือนที่ไม่เคยมีใครเห็นมันดัง
คือระบบที่ไม่มีใครรู้ว่ามันตายไปแล้ว** และวิธีเดียวที่จะรู้คือทำให้มันดังทุก push

กฎอยู่ในไฟล์ใน repo ไม่ใช่ใน UI ที่คลิกไว้ — ของที่ตั้งด้วยการคลิกคือของที่หายไป
พร้อม volume ที่ถูกลบ

### 3. **ระยะเก็บรักษาในไฟล์ config คือสิ่งที่ทำให้ตัวเลขในเอกสารเป็นจริง**

`retention_period: 2160h` = 90 วัน ตรงกับชั้น C6 ใน
[DATA-CLASSIFICATION.md](../DATA-CLASSIFICATION.md) · และต้องเปิด compactor
ด้วย ไม่งั้นค่านั้นเป็นแค่ตัวเลขในไฟล์ที่ไม่มีอะไรบังคับ

### 4. สามกฎ และทุกกฎต้องตอบได้ว่า "ดังแล้วต้องไปทำอะไร"

| กฎ | สัญญาณ | ทำอะไรต่อ |
|---|---|---|
| `LoginFailuresBurst` | คำขอ `/login` ที่ได้ 401 หรือ 429 เกิน 5 ครั้งใน 1 นาที | [RUNBOOK-BREACH.md](../RUNBOOK-BREACH.md) ข้อ 1 |
| `ServerErrors` | มี 5xx แม้ครั้งเดียว | หา `request_id` แล้วไล่ดู traceback ที่ id เดียวกัน |
| `UnhandledException` | มี traceback | RUNBOOK ข้อ 2 — คัดลอก log ก่อน restart |

**กฎที่ดังแล้วไม่มีใครรู้ว่าต้องทำอะไรต่อ จะถูกปิดเสียงภายในสองสัปดาห์ แล้วกฎ
ที่เหลือก็ถูกมองข้ามไปด้วย** — annotation `runbook` จึงเป็นส่วนบังคับของทุกกฎ

### 5. **ยังไม่ส่งเสียงออกไปไหน และนั่นตั้งใจ**

ruler ไม่ต่อกับ Alertmanager · สถานะอ่านผ่าน API และดูบน Grafana ได้
การส่งอีเมล/แชทเป็นงานของวันที่มี*คนรับ* — ปลายทางที่ไม่มีใครอ่านคือปลายทางที่
ทำให้เชื่อว่ามีคนเฝ้าอยู่ ทั้งที่ไม่มี

## สิ่งที่การทำจริงสอน และไม่ได้อยู่ในแผน

**ด่านของแอปเองบังการมองเห็น** — กฎแรกนับเฉพาะ 401 ซึ่งดูสมเหตุสมผล
แต่โควตา login ตัดที่ 5 ครั้ง ([ADR 0021](0021-per-username-login-throttle.md))
คำขอที่เหลือจึงเป็น 429 ทั้งหมด · วัดจริง: ยิง 12 ครั้งได้ 401 ห้าครั้ง
429 เจ็ดครั้ง — **กฎที่นับแต่ความล้มเหลวจะนับได้น้อยลงเรื่อย ๆ ยิ่งคนยิงหนักขึ้น
แล้วเงียบสนิทพอดีตอนที่การโจมตีหนักที่สุด**

นี่เป็นรูปเดียวกับบทเรียนที่เจอซ้ำมาทั้งเฟส 5–7 (ด่านที่วัดสัญญาณผิดตัว)
แต่ย้ายมาอยู่ที่ระบบเฝ้าระวัง ซึ่งเป็นที่ที่มันเจ็บที่สุด เพราะความเงียบของมัน
ถูกอ่านว่า "ไม่มีอะไรเกิดขึ้น"

## ผลที่ตามมา

- job `siem` ยิงจริงทุก push และต้องเห็น alert **ดังจริง** ไม่ใช่แค่ stack ขึ้นได้
- **ปิด ASVS V16.4.3** (log ถูกส่งไปเก็บที่ระบบแยกต่างหาก) และ **V16.4.2 บางส่วน** —
  log ที่ส่งออกไปแล้วแก้ที่ต้นทางไม่ได้ แต่ Loki เองยังอยู่ในเครื่องเดียวกัน
- **ยังไม่ทำ**: ส่งไปเครื่องอื่นจริง ๆ · Alertmanager และปลายทางที่คนอ่าน ·
  บันทึกเหตุการณ์ความปลอดภัยที่ไม่ใช่ HTTP (403/CSRF ที่ถูกปฏิเสธ — ASVS V16.3.2/V16.3.3
  ยังต้องเพิ่มที่ตัวแอปก่อน กฎถึงจะมีอะไรให้มอง)
- รหัสของ Grafana มีผลเฉพาะตอน start ครั้งแรก — เปลี่ยนตัวแปรแล้ว restart
  ไม่เปลี่ยนอะไร (บันทึกไว้ใน `compose.siem.yaml` เพราะเสียเวลาไปแล้วหนึ่งรอบ)
