# 0025 — จุด plug ซ้อนชั้น: ถอด plugin ต้องถอด supply chain ออกไปด้วย

สถานะ: accepted (2026-08-04) — Phase 4.5 ด่านแรก

**บริบท:** ADR 0006 วางสถาปัตยกรรม plugin ไว้โดยให้เหตุผลเรื่องการต่อขยาย
(แบบ Moodle) แต่เหตุผลที่หนักกว่านั้นและเพิ่งชัดตอน Phase 4 คือ
**การจำกัดความเสี่ยงของ supply chain**: ความสามารถที่เป็นส่วนเสริมไม่ควรลาก
ภาระการเฝ้าระวังช่องโหว่ของไลบรารีมาผูกกับระบบทั้งระบบ วันที่ไลบรารีตัวหนึ่งมี
CVE ที่ยังไม่มี patch คำตอบควรเป็น "ถอดออกก่อน ระบบยังทำงานได้" ไม่ใช่
"รอ upstream แล้วภาวนา"

**QR ของ MFA (ADR 0024) เปิดโปงช่องโหว่ของสัญญาปัจจุบัน** — ลบไดเรกทอรี
`app/plugins/auth/totp/` ทิ้งวันนี้ ระบบยังทำงานได้จริงตามสัญญา **แต่ `segno`
ยังอยู่ใน `[packages]` ของ `Pipfile`** จึงยังถูกติดตั้งทุกครั้งที่ deploy
ยังอยู่ใน SBOM และยังต้องเฝ้า CVE ต่อไป — *ถอดโค้ดได้ แต่ถอด supply chain ไม่ได้*

ปัญหาที่สองที่โผล่มาพร้อมกัน: **ระดับของการถอดหยาบเกินไป** ตัว TOTP เองไม่ต้อง
พึ่งไลบรารีใดเลย (เขียนตาม RFC เอง) ไลบรารีมาจาก **ส่วนที่เพิ่มความสะดวก**
อย่างเดียว การจะปิดแค่ QR โดยเก็บ TOTP ไว้ ทุกวันนี้ต้องแก้โค้ดใน `factor.py`

## คำตัดสิน

### 1. กติกาเดียว ใช้ซ้อนชั้น

> **ไดเรกทอรีที่มี `plugin.json` คือจุด plug หนึ่งจุด**

ใช้กฎเดิมของ ADR 0006 ซ้ำแบบ recursive ได้อีกชั้น — ไม่มีแนวคิดใหม่ให้ต้องจำ:

```
app/plugins/auth/            ← ชั้น 1 ชนิด (extension point ของ core)
└── totp/                    ← ชั้น 2 ความสามารถ    requires: ไม่มี
    ├── plugin.json
    ├── factor.py            สัญญา is_enrolled/verify
    └── enhancements/
        └── qr-segno/        ← ชั้น 3 ส่วนเสริม     requires: segno
            ├── plugin.json  provides: "qr"
            └── provide.py   สัญญาของ host: render(text) -> (mimetype, bytes)
```

ลบ `enhancements/qr-segno/` → หน้าลงทะเบียนกลับไปแสดง secret + `otpauth://`
เหมือนตอนที่ยังไม่เคยมี QR โดย**ไม่มีโค้ดส่วนใดล้มเหลว** และ `segno` หลุดจากสายพันธะไปด้วย

### 2. host ขอ "ความสามารถ" ไม่ได้ขอ "ตัว implementation"

manifest ของส่วนเสริมประกาศสองอย่าง:

```json
{
  "name": "QR code (segno)",
  "version": "1.0.0",
  "provides": "qr",
  "requires": { "pip": ["segno~=1.6"] }
}
```

**ชื่อ category ของ pipenv ไม่ได้ประกาศใน manifest แต่คำนวณจากคีย์ของจุด plug**
(`auth/totp` → `plugin-auth-totp`, `auth/totp#qr-segno` → `plugin-auth-totp-qr-segno`)
ค่าที่ประกาศซ้ำได้คือค่าที่วันหนึ่งจะไม่ตรงกัน

`provides` คือชื่อความสามารถ — วางสองไดเรกทอรีที่ `provides` ค่าเดียวกันแต่ใช้
ไลบรารีคนละเจ้าไว้พร้อมกันได้ แล้วสลับด้วย config โดยไม่แตะโค้ด

**กติกาที่ทำให้การสลับเป็นการ "สลับ" จริง ๆ: ส่วนเสริมห้ามเป็นเจ้าของข้อมูลถาวร**
ถ้าความสามารถนั้นต้องเก็บข้อมูล ข้อมูลเป็นของ plugin แม่ (ซึ่งเป็นเจ้าของตาราง
อยู่แล้วตาม ADR 0023) เสมอ — ไม่งั้น "เปลี่ยน implementation" จะกลายเป็น
"ย้ายข้อมูล" ซึ่งไม่ใช่การ plug อีกต่อไป

### 3. dependency ประกาศต่อจุด plug และติดตั้งแยกกลุ่ม

`[packages]` ของ `Pipfile` เหลือเฉพาะของ core ส่วนของ plugin/ส่วนเสริมอยู่ใน
**category ของ pipenv** ตามที่ manifest ประกาศ (`Pipfile.lock` ยัง pin ครบ
ทุกตัวเหมือนเดิม แค่แยกกลุ่มให้รู้ว่าอะไรเป็นของใคร)

ผลที่ต้องการ: `pipenv sync` ของ core ไม่ลากไลบรารีของส่วนเสริมมาด้วย และคำถาม
"ตัวนี้มาจากไหน ถอดได้ไหม" ตอบได้จากไฟล์เดียว

### 4. ไม่มีไลบรารี = ปิดตัวเอง ไม่ใช่ล้มเหลว

การ `import` ที่ล้มเพราะยังไม่ได้ติดตั้ง **เป็นสถานะปกติที่ออกแบบไว้** ไม่ใช่
ข้อผิดพลาด — จุด plug นั้นถูกข้ามไปเหมือนไม่เคยมี หลักเดียวกับ
`plugins.is_installed()` ที่ทำไปแล้วสำหรับตารางที่ยังไม่ถูกสร้าง (ADR 0023)

**และเส้นทาง "ไม่มีส่วนเสริม" ต้องเป็นโค้ดเส้นเดียวกับตอนที่ยังไม่เคยมี**
ไม่ใช่เส้นทางที่สองที่เขียนเพิ่มไว้รองรับ — เส้นทางสำรองที่ไม่มีใครเดินคือ
เส้นทางที่ล้มเหลวโดยไม่มีใครรู้

### 5. กำกวมเมื่อไหร่ = ปิดไว้ก่อน (fail closed)

* มีตัวเดียวที่ `provides` ความสามารถนั้น → ใช้ตัวนั้น
* มีหลายตัวและ config ระบุว่าเอาตัวไหน → ใช้ตามที่ระบุ
* **มีหลายตัวแต่ config ไม่ได้เลือก → ปิดทั้งหมด + log เตือน**

ข้อสุดท้ายสำคัญ: การเดาให้ (เช่นเรียงตามชื่อแล้วหยิบตัวแรก) แปลว่าวางไดเรกทอรี
เพิ่มแล้วพฤติกรรมของระบบเปลี่ยนโดยไม่มีใครสั่ง

และเมื่อมีตัวเลือกระบุไว้แล้ว **ตัวเลือกนั้นชนะเสมอแม้จะเหลือผู้ให้บริการตัวเดียว**
ไม่งั้นการปิดตัวที่ถูกเลือก (เพราะ CVE) จะกลายเป็นการ *เปิด* ตัวที่ไม่ได้ถูกเลือก
ซึ่งเป็นการเปลี่ยนพฤติกรรมโดยไม่มีใครสั่งเหมือนกัน

### 6. สวิตช์ปิดที่ไม่ต้องรอ deploy

`DISABLED_PLUGINS` ปิดได้ทุกชั้นด้วยคีย์เดียวกับที่ CLI ใช้:
`themes/ocean`, `auth/totp`, `auth/totp#qr-segno`
ส่วน `PLUGIN_PICKS` เลือก implementation: `auth/totp#qr=qr-segno`
(รายการของ `PLUGIN_PICKS` มี `=` เสมอ ของ `DISABLED_PLUGINS` ไม่มีเลย —
จึงไม่กำกวมแม้ใช้เครื่องหมาย `#` เหมือนกัน)

registry อ่านดิสก์ทุกครั้งอยู่แล้ว การปิดจึงมีผลทันทีที่ config เปลี่ยน
เพราะวันที่ CVE ออกตอนบ่ายสาม "แก้โค้ดแล้ว deploy" ไม่ใช่คำตอบที่ทันการณ์

**ปิดแล้วต้องเหมือนไม่เคยวางไดเรกทอรีลงไป** ไม่ใช่สถานะที่สาม — ของที่ปิดหายไป
จาก `discover()`/`enhancements()` ตั้งแต่ต้นทาง โค้ดที่เหลือทั้งระบบจึงเดินเส้นทาง
"ไม่มีของชิ้นนี้" ซึ่งถูกทดสอบไว้แล้วทั้งชุด ถ้าทำเป็นเงื่อนไขกระจายตามที่ใช้งาน
มันจะกลายเป็นเส้นทางใหม่ที่ไม่มีใครเคยเดินผ่าน — ซึ่งคือสิ่งที่เราหลีกเลี่ยงมาตลอด

สองข้อยกเว้นที่จำเป็น:

* **ปิด plugin ของ core ไม่ได้** — แอปไม่ start พร้อมข้อความที่บอกตรง ๆ ว่าเพราะ
  คีย์ไหนใน `DISABLED_PLUGINS` ถ้าปล่อยผ่านมันจะไปล้มเหลวทีหลังด้วยข้อความ
  "ไม่พบธีม core" ซึ่งชี้ไปผิดที่ (ไดเรกทอรียังอยู่ครบ)
* **สวิตช์ปิด *โค้ด* ไม่ได้ปิด *ข้อมูล*** — ความเป็นเจ้าของตาราง (`owned_tables()`)
  และคำสั่ง `plugin-install`/`plugin-uninstall` อ่านจากดิสก์ตรง ๆ ไม่ผ่านสวิตช์
  ไม่งั้นตารางของ plugin ที่ถูกปิดจะกลายเป็นตารางไม่มีเจ้าของ แล้ว `flask db migrate`
  ตัวถัดไปของ core จะออก migration ที่ **drop มันทิ้ง** เพราะการปิดสวิตช์ชั่วคราว
  (วงจรชีวิตของข้อมูลเป็นของคำสั่ง install/uninstall เท่านั้น — ADR 0023)

ทุก ๆ ครั้งที่แอป start จะ log ว่าตอนนั้นอะไรถูกปิดอยู่บ้าง เพราะ "ระบบเดินอยู่โดย
ไม่มีความสามารถ X" เป็นข้อเท็จจริงที่ต้องมีร่องรอย ไม่ใช่ความรู้ที่อยู่ในหัวคนตั้ง config

### 7. บังคับด้วยเครื่อง ไม่ใช่ด้วยความจำ

สองด่านที่ทำให้ทั้งหมดข้างบนเป็นความจริงที่ตรวจได้ทุก push:

* **เทสต์สแกน import** — โค้ดในไดเรกทอรีของจุด plug ห้าม import อะไรที่ไม่ได้
  ประกาศไว้ใน manifest ของตัวเอง (นอกจาก stdlib และของ core) วิธีเดียวกับ
  `tests/test_service_layer.py` ที่สแกน AST อยู่แล้ว
* **job `bare` ใน CI** — รันชุดเทสต์ทั้งชุด**โดยไม่ติดตั้ง category ของ plugin เลย**
  ต้องเขียว นี่คือด่านเดียวที่ทำให้คำว่า "ถอดแล้วระบบยังทำงานได้" เป็นข้อเท็จจริงที่วัดได้
  แทนที่จะเป็นความตั้งใจที่เขียนไว้ในเอกสาร

## ขอบเขตที่ ADR นี้ **ไม่** ครอบคลุม

เขียนไว้ให้ชัดเพราะการเข้าใจผิดข้อนี้อันตรายกว่าการไม่มีกลไกเลย:

* **ไม่ใช่ sandbox** — plugin ยังรันในโปรเซสเดียวกัน มีสิทธิ์เท่าแอปทุกประการ
  แตะฐานข้อมูล อ่านไฟล์ ต่อเน็ตได้หมด สิ่งที่ได้คือ **ลดพื้นที่ CVE ที่ต้องเฝ้า
  และถอดออกได้เร็ว** ไม่ใช่การกันโค้ดที่ตั้งใจร้าย
* **ไม่ได้กันการ import ข้ามกันตอนรัน** — เมื่อไลบรารีถูกติดตั้งแล้ว โค้ดไหนก็
  import ได้ตามระบบของ python เทสต์สแกน import เป็นด่านตอนรีวิว ไม่ใช่กำแพงตอนรัน
* **ไม่ลดความเสี่ยงของ dependency ของ core** (Flask, SQLAlchemy, werkzeug) —
  พวกนั้นถอดไม่ได้โดยนิยาม และไม่ควรพยายามทำให้ถอดได้
* **ไม่ใช่ระบบติดตั้ง plugin จากภายนอก** — ไม่มีการดาวน์โหลดโค้ดมารัน
  ทุก plugin มาพร้อม repo และผ่าน gate เดียวกับโค้ดอื่น

## ผลที่ตามมา

* `pipenv sync --dev` ไม่ติดตั้งไลบรารีของส่วนเสริมอีกต่อไป — คนที่ dev ในเครื่อง
  ต้องรัน `flask plugin-deps` เพื่อดูว่าขาดอะไร (ต้องเขียนใน OPERATIONS/CLAUDE.md)
* CI ต้องรันชุดเทสต์ **สองรอบ** (ครบทุก category + `bare`) — จ่ายเวลา CI เพิ่ม
  ประมาณหนึ่งเท่าตัวของ job `test` เพื่อแลกกับการรู้ทุก push ว่าถอดได้จริง
* `pip-audit`/SBOM แยกตาม category → ตอบได้ว่า CVE ตัวนี้เป็นของ plugin ไหน
  และ **CVE ของส่วนเสริมไม่ควรทำให้ job ของ core แดง** แต่ต้องดังพอให้เห็น
* คนอ่านโค้ดต้องเรียนสามชั้นแทนสองชั้น — ต้นทุนที่ยอมจ่าย เพราะกฎเป็นกฎเดิม
  ที่ใช้ซ้ำ ไม่ใช่กฎใหม่
* Phase 5 ที่กำลังจะเพิ่ม redis, driver ของ MySQL/MariaDB และ authlib (OIDC)
  จะลงบนฐานนี้ตั้งแต่แรก **นี่คือเหตุผลที่เฟสนี้ต้องแทรกก่อน ไม่ใช่ทำทีหลัง**

## ทางเลือกที่ไม่เลือก

* **venv หรือโปรเซสแยกต่อ plugin** — เป็น isolation จริงเพียงทางเดียวใน python
  แต่ต้องมี IPC และสอง interpreter ในเครื่องเดียว เกินขนาดของแอปนี้มาก
  (ถ้าวันหนึ่งรับ plugin จากคนนอกจริง ๆ ต้องกลับมาทบทวนข้อนี้ใหม่ทั้งข้อ)
* **vendor ไลบรารีเข้ามาในไดเรกทอรี plugin** — ได้ isolation แลกกับการไม่มีวัน
  ได้ security patch ซึ่งขัดกับเป้าหมายของ ADR นี้ตรง ๆ
* **`try: import ... except ImportError: pass` กระจายในโค้ด** — ได้พฤติกรรม
  "ไม่มีก็ยังทำงานได้" เหมือนกัน แต่ไม่มีการประกาศ ไม่มีใครตอบได้ว่าระบบนี้พึ่งอะไรบ้าง
  และไม่มีอะไรบังคับว่าต้องมีเส้นทางสำรองจริง
* **extras ของ packaging (`pip install app[qr]`)** — เป็นคำตอบมาตรฐานของโลก
  python และดีกว่าถ้าเราแจกเป็นแพ็กเกจ แต่แอปนี้ deploy จาก git ด้วย pipenv
  category ของ pipenv ให้ผลเดียวกันโดยที่ `Pipfile.lock` ยังคุมเวอร์ชันครบ
* **ใช้ feature flag เฉย ๆ โดยไม่แตะเรื่อง dependency** — ปิดฟีเจอร์ได้ แต่
  ไลบรารียังถูกติดตั้งและยังต้องเฝ้า CVE อยู่ดี ซึ่งคือปัญหาตั้งต้นทั้งหมดของ ADR นี้

**โน้ต 1 (2026-08-19 — audit รอบ 13 ข้อ 2: ครึ่งหลังของประโยคไม่เป็นจริง)**:
ใบนี้เขียนไว้ว่า CVE ของไลบรารีที่ถอดได้ **ไม่ควรทำให้ pipeline ของ core แดง
แต่ต้องดังพอให้เห็น** — ครึ่งแรกยังถูกและไม่ถูกกลับ · ครึ่งหลังวัดได้แล้วว่าไม่จริง:
สัญญาณดังใส่ `::warning::` ของ job ที่เขียวอยู่ ซึ่งไม่มีใครเปิดอ่าน

เมื่อ audit รอบ 12 บังคับให้ตัวรับสัญญาณประกาศกรอบเวลาตามกลไกจริง ตัวเลขที่ได้คือ
**90 วัน** ขณะที่ `docs/SECURITY-CADENCE.md` ประกาศว่า CVE ระดับ critical ต้องแก้

   ถูกที่สุด: `DISABLED_PLUGINS` ใช้ได้ทันทีโดยไม่ต้อง deploy
3. เขียนบรรทัดในทะเบียนพร้อมเหตุผล = รับความเสี่ยงอย่างเปิดเผย
