# 0061 — ท่าทีฝั่งแพลตฟอร์มต้องถูกเครื่องตรวจ ไม่ใช่แค่ประกาศไว้

สถานะ: **accepted** (2026-08-17 — ข้อ D2 ของ audit governance รอบ 7)

## บริบท

ADR 0053 ประกาศกติกาที่ทุกอย่างในเรโปนี้พิงอยู่: **main รับของทาง PR เท่านั้น ·
บังคับถึงผู้ดูแล (`enforce_admins`) · required check ครบทุก job ที่รันบน pull
request · linear history · ห้าม force push** — และ `docs/SECURITY-CADENCE.md`
เล่าซ้ำพร้อมตัวเลข "required check 27 จาก 29"

**ทั้งหมดนี้เป็น setting ฝั่ง GitHub และไม่มีอะไรในเรโปอ่านมันเลย** · กดปิดใน
หน้า settings, ลบ required check ตอนแก้ชื่อ job, หรือ GitHub เปลี่ยนพฤติกรรม
เมื่อไหร่ — เอกสารก็ยังอ้างเหมือนเดิม และด่านทุกตัวที่ *พึ่ง* กติกานั้นยังเขียว
เพราะมันไม่ได้ตรวจเรื่องนี้อยู่แล้ว · `scorecard` เห็นบางส่วนแต่ **ไม่บล็อก** และ
ไม่ยืนยันคำอ้างเฉพาะของเรา

ตรวจ API ตอนทำ audit ยังพบด้วยว่า **`sha_pinning_required` ปิดอยู่** ทั้งที่
เราบังคับ SHA pinning ด้วยเทสต์ของตัวเองมาตั้งแต่เฟส 9 — แพลตฟอร์มมีสวิตช์ให้
บังคับตรง ๆ และเราไม่ได้ใช้

## คำตัดสิน

1. **job `posture`** (อยู่ใน `scorecard.yml` เพราะ trigger ตรงกันพอดี —
   `branch_protection_rule` ยิงทันทีที่กฎของ branch เปลี่ยน) เรียก
   `scripts/audit_posture.py` ซึ่งเทียบสามแหล่ง:
   - **required check สองทิศ** — job ที่รันบน PR ทุกตัวต้องถูกบังคับ (ยกเว้นที่
     ประกาศไว้พร้อมเหตุผล) **และ** รายการบังคับต้องไม่มีชื่อผี (context ที่ไม่มี
     job ไหนสร้างได้ = PR ที่รอ check ซึ่งไม่มีวันมา)
   - **ธงของ branch protection** ตามที่ ADR 0053 ประกาศ
   - **สวิตช์ระดับ repo**: auto-merge และ `sha_pinning_required`
2. **เลขที่เอกสารโฆษณาถูกอ่านคู่ด้วย** — "required NN จาก MM" ใน
   `docs/SECURITY-CADENCE.md` ต้องตรงกับ API และกับจำนวน check ที่ workflow
   ผลิตได้จริง (หลักเดียวกับ `contributor-docs-truthful`)
3. **อ่านไม่ได้ = แดง (exit 2) ไม่ใช่ข้าม** — ทั้ง 403 (สิทธิ์ไม่พอ) และ 5xx
   (GitHub เองมีปัญหา) · ด่านที่ข้ามตอนอ่านไม่ได้ คือด่านที่รายงานว่าเรียบร้อย
   ในวันที่มันมองไม่เห็นอะไรเลย — ซึ่งเป็นรูปเดียวกับกับดักที่รอบ 5 เจอกับ
   `flask --help` ที่คืน 0 แม้โหลดแอปไม่สำเร็จ
4. **เปิด `sha_pinning_required`** ให้แพลตฟอร์มบังคับสิ่งที่เทสต์เราบังคับอยู่แล้ว
   — สองชั้นคนละกลไก: ของเราจับตอนเขียน (AST ของ workflow) ของ GitHub จับตอนรัน

## ทางที่ไม่ได้เลือก

- **บังคับเป็น required check บน PR** — ปัดตก: มันไม่รันบน pull request (ต้องการ
  trigger `branch_protection_rule`) การบังคับจึงเท่ากับ PR ทุกใบรอ check ที่ไม่มี
  วันมา ซึ่งเป็นข้อผิดพลาดที่ตัวมันเองถูกสร้างมาจับพอดี
- **ประกาศท่าทีที่คาดหวังไว้ในไฟล์ config แยก** — ปัดตก: จะกลายเป็นทะเบียนที่สาม
  ที่ drift ได้ · ที่นี่**อนุมานจาก workflow จริง** (job ไหนรันบน PR บ้าง) แล้ว
  เทียบกับ API — ทั้งสองข้างเป็นความจริง ไม่มีข้างไหนเป็นสำเนา
- **ใช้ PAT ของเจ้าของ** — ปัดตก *เป็นค่าเริ่มต้น*: `GITHUB_TOKEN` +
  `permissions: administration: read` พอสำหรับการอ่าน · ถ้าวันหนึ่งมันไม่พอ
  ด่านจะแดงพร้อมข้อความที่บอกทางแก้ ไม่ใช่เงียบ
  — **ข้อนี้ผิด ดูโน้ตท้ายใบ**: `administration` ไม่ใช่ scope ที่ `GITHUB_TOKEN`
  มีเลย และการประกาศมันทำให้ workflow ไม่ start ทั้งไฟล์ · คำตัดสินจริงกลับด้าน
  เป็น PAT อ่านอย่างเดียว (`POSTURE_TOKEN`)

## เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ

- **ถ้า `GITHUB_TOKEN` อ่าน branch protection ไม่ได้จริง** (403 ในการรันจริง
  ครั้งแรก) ให้เปลี่ยนไปใช้ token ที่อ่านได้ **หรือ**ประกาศว่าตรวจไม่ได้อย่าง
  เปิดเผยในทะเบียนความเสี่ยง — ห้ามลดด่านเป็น warning เงียบ ๆ
- **ถ้า GitHub เลิกให้ค่า `sha_pinning_required`** หรือเปลี่ยนรูป API ตัวตรวจจะ
  แดง — นั่นคือพฤติกรรมที่ต้องการ (ผู้ให้บริการเปลี่ยนสัญญาแล้วเรารู้ทันที)
  แต่ต้องรีบตัดสินใหม่ ไม่ใช่ปิดด่านทิ้ง

## ผลที่ตามมา

- gate `platform-posture-verified` (baseline · portable) — โปรเจกต์ปลายทางที่
  รับ overlay ไปก็มีกติกาเดียวกัน: ท่าทีที่ประกาศต้องมีเครื่องอ่าน
- ตอบช่องว่างที่ ISO `A.5.36` / `A.8.9` มีอยู่จริงแต่หลักฐานเดิมไม่ได้ครอบ —
  configuration ที่บังคับนโยบายไม่ได้มีแค่ config ของแอป

**โน้ต (2026-08-18 — audit r9 · ด่านนี้ไม่เคยรันเลยตั้งแต่เกิด)**: job `posture`
ประกาศ `permissions: administration: read` ซึ่ง **ไม่ใช่ scope ที่ `GITHUB_TOKEN`
มีให้** · GitHub ปฏิเสธไฟล์ตั้งแต่ก่อนสร้าง job ผลคือ **`scorecard.yml` ล้มทุก
run รวมบน main ตั้งแต่ commit ที่เพิ่ม job นี้ (22 จาก 30 run ล่าสุดตอนที่จับได้)
โดยไม่มีใครเห็น** เพราะ workflow นี้ไม่ใช่ required check และ run ที่ล้มแบบไม่มี
job เลยก็หายไปจากสำมะโนของ `rerun_census.py` ด้วย (จุดบอดที่ปิดพร้อมกัน)

สิ่งที่แก้: ถอด scope ที่ไม่มีจริงออก · สิทธิ์อ่านมาจาก `POSTURE_TOKEN`
(fine-grained PAT · Administration: read — วิธีออกอยู่ใน `docs/OPERATIONS.md`) ·
ไม่มี token แล้ว**แดง** ตามข้อ 3 ของ ADR ใบนี้เหมือนเดิม · และ
`tests/test_workflow_validity.py` ตรวจ scope ของทุก workflow เทียบรายการที่
GitHub รับ เพื่อไม่ให้คลาสนี้เงียบอีก

**บทเรียน**: ด่านที่ไม่ได้ตั้งเป็น required check ต้องมีวิธีอื่นที่ทำให้ความล้มเหลว
ของมันมองเห็นได้ — ไม่งั้น "ด่านมีอยู่" กับ "ด่านไม่เคยทำงาน" หน้าตาเหมือนกันทุกวัน

**โน้ต 2 (2026-08-18 — การรันจริงครั้งแรกให้ผลบวกลวงทันที)**: `posture` รันได้จริง
ครั้งแรกด้วย `POSTURE_TOKEN` แล้วรายงานว่า **`allow_auto_merge` ปิดอยู่** ซึ่ง
**ไม่จริง** — auto-merge เปิดและถูกใช้ทุก PR · ต้นเหตุ: เอกสารของ GitHub ระบุว่า
ฟิลด์กลุ่ม merge settings จะถูกคืนก็ต่อเมื่อ caller มี `contents:read` **และ**
`contents:write` · token อ่านอย่างเดียวจึงได้ `None` ไม่ใช่ `False`

**คำตัดสิน: ไม่ยกสิทธิ์ token เป็น write เพื่อดูบูลีนตัวเดียว** — ตัวตรวจที่มี
หน้าที่อ่าน ไม่ควรถือสิทธิ์เขียนโค้ดของ repo ที่มันตรวจ · แทนที่ด้วยสามชั้น:

1. ตัวตรวจแยก **"ปิดอยู่" (False → แดง)** ออกจาก **"มองไม่เห็น" (None → หมายเหตุ)**
   — รายงานผิดฝั่งคือการโกหก และครั้งนี้มันโกหกในทิศที่ทำให้เราไปแก้ของที่ไม่ได้เสีย
2. แถว cadence ทุก 3 เดือน ตรวจด้วยมือจากเครื่องผู้ดูแล (token ของ `gh` มีสิทธิ์ครบ)
3. **ตัวชดเชยที่ทำงานทุกวัน**: ถ้า auto-merge ถูกปิดจริง `gh pr merge --auto` ของ
   ทุก PR จะล้มทันที — ไม่ใช่ความเงียบ

**บทเรียน**: ด่านที่เพิ่งได้รันครั้งแรก **ต้องอ่านผลของมันด้วยความสงสัยเท่ากับที่
อ่านโค้ดที่มันตรวจ** · ถ้าเชื่อผลแรกทันที เราจะไปนั่งเปิดสิ่งที่เปิดอยู่แล้ว หรือแย่
กว่านั้นคือยกสิทธิ์ให้ token เพื่อให้ด่านเขียว
