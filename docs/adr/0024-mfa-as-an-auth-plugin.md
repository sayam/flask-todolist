# 0024 — MFA เป็น plugin ชนิด `auth`: core ถามปัจจัย ไม่ใช่รู้จักปัจจัย

สถานะ: accepted (2026-08-04) — Phase 4

**บริบท:** ROADMAP กำหนดให้ auth เป็น plugin ชนิดที่สองบน registry เดิม
โดย `password` เป็น core plugin แล้วเพิ่ม `totp` เป็นปัจจัยที่สอง
คำถามจริงคือ **"core ต้องรู้อะไรบ้างเกี่ยวกับปัจจัยที่สอง"** — ถ้าตอบผิด
จะได้โค้ดที่เขียนว่า `if user.totp_enabled:` กระจายอยู่ทั่ว ซึ่งเท่ากับ
สถาปัตยกรรม plugin ที่มีไว้ประดับ

## คำตัดสิน

### core รู้แค่สองคำถาม

ทุก plugin ชนิด `auth` ที่ประกาศ `"factor": "second"` ต้องมี `factor.py`
ที่มีสองฟังก์ชัน — **นี่คือทั้งหมดที่ core เรียกตอน login**:

* `is_enrolled(user)` — คนนี้เปิดใช้คุณอยู่ไหม
* `verify(user, code)` — รหัสนี้ผ่านไหม (และถือว่า "ถูกใช้ไปแล้ว" หลังจากนี้)

`app/services/mfa.py` ทั้งไฟล์คือ 5 ฟังก์ชันที่วนถามทุกตัวที่ค้นเจอ
`plugins.check_installation()` ตรวจสัญญานี้ตอน start (ปัจจัยที่ทำสัญญาไม่ครบ
= ด่าน login ที่ล้มเหลวตอนมีคนพยายาม login จริง)

**เทสต์บังคับว่าคำว่า `totp` ต้องไม่โผล่ในโค้ด core เลยแม้แต่ในคอมเมนต์**
(เกณฑ์เดียวกับที่ใช้กับชื่อธีมตั้งแต่ ADR 0006) ถอนไดเรกทอรีทิ้งแล้วระบบกลับไป
เป็น login ด้วยรหัสผ่านอย่างเดียวทันที โดยไม่มีอะไรล้มเหลว

ฟังก์ชันสำหรับ "เปิด/ปิดเองจากหน้าเว็บ" (`start_enrollment`, `setup_details`,
`confirm`, `disable`, `is_pending`) เป็น**สัญญาชุดที่สองที่ไม่บังคับ** — ปัจจัย
ที่ไม่มีชุดนี้ยังใช้ยืนยันตัวตนได้ แค่ต้องไปเปิดด้วยวิธีอื่น (เช่น hardware key
ที่ต้องลงทะเบียนคนละแบบ) หน้า settings แสดงเฉพาะตัวที่มีครบ

`setup_details()` คืนคู่ (ป้าย, ค่า) เป็นภาษาอังกฤษตายตัว **ไม่ผ่าน gettext**
เหมือน `Plugin.name` — plugin ที่อยากแปลต้องมี lang pack ของตัวเอง

### login หยุดครึ่งทาง ไม่ใช่ login แล้วค่อยถาม

รหัสผ่านถูก + มีปัจจัยที่สอง → **ไม่เรียก `start_session()`** แต่เก็บสถานะ
"ใครกำลังรอ" ไว้ใน session แล้วเด้งไป `/login/verify` ถ้าเรียก `login_user()`
ไปก่อนแล้วค่อยถาม คนที่รู้แค่รหัสผ่านจะเข้าถึงข้อมูลได้ทันทีด้วยการพิมพ์ URL อื่น
— เท่ากับมี MFA ไว้เฉย ๆ โดยไม่ได้บังคับอะไรเลย

สถานะครึ่งทางมีอายุ 5 นาที (`MFA_PENDING_SECONDS`) เพราะมันคือ "ผ่านรหัสผ่านแล้ว"
ซึ่งเป็นครึ่งหนึ่งของการยืนยันตัวตน ปล่อยค้างไว้นานเท่ากับลดค่าของขั้นที่สองลง

ขั้นที่สองมี**โควตาต่อบัญชี**เหมือนหน้า login (ADR 0021) เพราะรหัสหกหลัก
ไล่เดาได้จริงถ้าไม่มีเพดาน

### เขียน TOTP เองไม่ใช้ไลบรารี

เหตุผลเดียวกับตารางดวงอาทิตย์ (ADR 0007): อัลกอริทึมคือ HMAC-SHA1 +
dynamic truncation ตาม RFC 4226/6238 ซึ่งสั้นกว่าโค้ดที่ต้องเขียนเพื่อห่อ
ไลบรารีเสียอีก และ **RFC มี test vector อย่างเป็นทางการ** ให้ยืนยันความถูกต้อง
ตรง ๆ (`tests/test_totp.py` เทียบครบทั้ง 6 ค่า) ส่วน dependency ที่เพิ่มมา
ต้องตามดู CVE ไปตลอดอายุโครงการ

(ตรงข้ามกับ QR ที่ **ยอมรับ dependency** หนึ่งตัว — การวาด QR ให้ถูกต้องตาม
มาตรฐานรวม Reed–Solomon กับ mask pattern ซึ่งยาวกว่าตัว TOTP หลายเท่าและ
ไม่มี test vector ทางการให้เทียบ)

### QR code: มี แต่ต้องไม่แลกอะไรเลย

รอบแรกตัดสินว่า **ไม่ทำ** (คัดลอก `otpauth://` ไปวางเอาก็ได้) ด้วยเหตุผลว่า
ต้องเพิ่ม dependency และต้องผ่อน CSP ให้รับ `data:` URI — **ทบทวนใหม่แล้วพบว่า
ข้อหลังไม่จริง** ถ้าเสิร์ฟเป็นไฟล์แทนการฝังในหน้า จึงทำเพิ่มโดยมีเงื่อนไขสามข้อ
ที่ต้องจริงพร้อมกัน (ทุกข้อมีเทสต์บังคับใน `tests/test_totp.py`):

1. **ไม่มีความลับอยู่ใน URL** — path เป็น `/settings/mfa/<ไอดี plugin>/image`
   ความลับถูกอ่านจากฐานข้อมูลตาม `current_user` ถ้าใส่ไว้ใน query string มันจะ
   ไปโผล่ใน log ของเราเอง (`path` เป็นชั้น C6 อายุ 90 วัน), log ของ reverse proxy,
   ประวัติเบราว์เซอร์ และ header `Referer` ที่ส่งต่อไปหน้าอื่น
2. **CSP ไม่ถูกผ่อนแม้แต่นิดเดียว** — เสิร์ฟเป็นไฟล์ SVG จาก origin เดียวกัน
   `img-src 'self'` เดิมรับได้อยู่แล้ว (เทสต์ยืนยันว่าไม่มี `data:` ใน CSP ทั้ง
   หน้า settings และตัวรูป) และ SVG เป็นข้อความล้วน ไม่ต้องมีไลบรารีวาดภาพ
   — `segno` ไม่มี dependency ต่อ
3. **`no-store` + หายไปทันทีที่ยืนยันเสร็จ** — ใบที่เปิดใช้แล้วขอรูปได้ 404
   เหมือนกับที่ดูความลับเป็นข้อความซ้ำไม่ได้

สีของ QR **ฝังอยู่ในตัว SVG ไม่ได้มาจากธีม** เพราะตัวสแกนต้องการโมดูลเข้มบน
พื้นอ่อนเสมอ ถ้าปล่อยพื้นหลังโปร่งใสตามค่าเริ่มต้น โหมดมืดจะได้ดำบนดำ = สแกนไม่ได้
(เป็นข้อกำหนดของเครื่องอ่าน ไม่ใช่การตัดสินใจเรื่องสไตล์ — จึงไม่ขัดกับกติกา
"ห้ามมีสีดิบใน base.css")

ข้อความ `otpauth://` ยังแสดงคู่กันเสมอ เพราะเครื่องที่ไม่มีกล้องต้องตั้งค่าได้ด้วย

### กติกาสามข้อที่ทำให้ MFA ไม่ใช่แค่พิธีกรรม

1. **ใบที่ยังไม่ยืนยันไม่นับว่าเปิด MFA** — คนที่กดเปิดแล้วสแกนไม่ทันต้องไม่
   ล็อกตัวเองออกจากบัญชี
2. **รหัสที่ใช้ไปแล้วใช้ซ้ำไม่ได้** (จำหมายเลขช่วงเวลาล่าสุดไว้) — คนที่เห็นโดยไม่ได้รับอนุญาต
   รหัสบนจอมีเวลาถึง 30 วินาทีเสมอถ้าไม่กันข้อนี้
3. **ปิด MFA ต้องกรอกรหัสผ่านซ้ำ** และ **ออกความลับใบใหม่ทับใบที่เปิดอยู่ไม่ได้**
   — ไม่งั้น session ที่ถูกยึดจะถอดปัจจัยที่สองทิ้งได้ในคลิกเดียว ซึ่งทำให้
   MFA ไม่ได้ป้องกันสถานการณ์ที่มันถูกสร้างมาเพื่อป้องกันพอดี

## ผลที่ตามมา

* ความลับ TOTP เป็นชั้น C1 ที่ **เก็บเป็นค่าจริงไม่ใช่ hash** (ธรรมชาติของ
  algorithm ไม่ใช่ทางลัด) ชดเชยด้วยการลบทิ้งทันทีที่ปิด — ดู ADR 0023
* ตาราง `tdl_auth_totp_secret` เป็นของ plugin ล้วน ๆ ไม่อยู่ในสาย migration
  ของ core ต้อง `flask plugin-install auth/totp` ก่อนใช้งานจริง
* **ยังไม่มี recovery code** — ทำโทรศัพท์หายแล้วต้องให้ผู้ดูแลปิด MFA ให้ผ่าน
  CLI ของ plugin (ยังไม่มีคำสั่งนั้น — งานที่เหลืออยู่จริง บันทึกไว้ใน ROADMAP)
* **API ยังไม่รู้จัก MFA** — token ที่ออกไว้แล้วใช้ต่อได้ตามปกติ (มันเป็นกุญแจ
  ของเครื่อง ไม่ใช่ของคน — ADR 0017) และการออก token ผ่าน CLI ก็ไม่ผ่าน MFA
  ซึ่งถูกต้อง เพราะคนที่รันคำสั่งบนเครื่อง server มีสิทธิ์เหนือทุกอย่างอยู่แล้ว
* `password` เป็น plugin ที่มี manifest แต่ยังไม่มีโค้ด — ตัว core ยังเรียก
  `user.check_password()` ตรง ๆ อยู่ **นี่คือหนี้ที่รู้ตัว**: จะแปลงเป็น
  ปัจจัยหลักแบบ plugin จริง ๆ ตอนทำ SSO (ซึ่งจะมีปัจจัยหลักตัวที่สอง) ไม่ใช่
  ตอนนี้ที่ยังมีตัวเดียวและการห่อมันจะเป็น indirection เปล่า ๆ

## ทางเลือกที่ไม่เลือก

* **บังคับ MFA ทุกคน** — แอปนี้ยังไม่มีทางกู้บัญชี (ไม่เก็บอีเมล) การบังคับ
  จึงแปลว่าคนทำโทรศัพท์หายเสียบัญชีถาวรจนกว่าจะไปหาคนดูแล
* **SMS OTP** — NIST ถอดออกจากคำแนะนำแล้ว (SIM swap) และต้องพึ่งผู้ให้บริการ
  ภายนอกที่เห็นเบอร์โทรของผู้ใช้ทุกคน
* **WebAuthn/passkey** — ปลอดภัยกว่า TOTP จริง และเป็นทางที่ควรไปในระยะยาว
  แต่ต้องมี HTTPS จริงก่อน (Phase 5) จึงจะทดสอบได้ — สัญญา `factor.py`
  ที่วางไว้รองรับการเพิ่มเป็น plugin ตัวที่สองโดยไม่ต้องแก้ core
