# 0056 — ด่านสะดุด performance ต่อ push (k6 journey เกณฑ์หลวมบน runner)

สถานะ: **accepted** (2026-08-16 — ช่องว่างข้อ 6 จากผล audit governance
5 มิติ: pillar performance เป็นอันดับสองของธรรมนูญแต่ไม่มีด่าน latency
ต่อ push เลยสักตัว)

**บริบท:** เป้า performance มีที่มาและมีหลักฐาน (ADR 0031 · p95<200ms
p99<500ms ที่ 5 VUs · วัดซ้ำหลายรอบใน `docs/PERFORMANCE.md` รวมสี่ config
ของ G5) แต่การวัดทั้งหมด**เป็นงานมือ** — regression ก้าวกระโดด (query
N+1 ใหม่ · migration ที่ทำ index หาย · middleware ที่แพงขึ้นสิบเท่า)
เข้า main ได้โดยไม่มีอะไรฟ้อง จนกว่าจะมีคนรัน load test ครั้งถัดไป
ซึ่งอาจเป็นอีกหลายสัปดาห์และหลายสิบ commit ให้ไล่ย้อน

## คำตัดสิน

1. **job `perf-smoke` ทุก push**: ขึ้น stack SQLite จาก image จริง
   (`docker compose up` — ของที่ ship ไม่ใช่ dev server) แล้วเดิน
   `loadtest/journey.js` **ชุดเดียวกับที่ใช้วัดจริง** ที่ 5 VUs 60 วินาที
   — k6 ตัดสินเองจาก exit code ไม่มีคนอ่านตัวเลข
2. **เกณฑ์หลวมกว่าเป้าจริงโดยตั้งใจ**: p95<400ms · p99<1000ms (สองเท่า
   ของเป้า ADR 0031) — runner ของ GitHub แชร์ CPU ตัวเลขแกว่งเกินกว่าจะ
   ตัดสินที่เป้าจริงโดยไม่ flaky · override ผ่าน env `P95_MS`/`P99_MS`
   ใน journey.js ซึ่ง**ค่าเริ่มต้นยังเป็นเป้าจริง** (คนรันมือนอก CI ได้
   เกณฑ์จริงเสมอ ไม่ต้องรู้ว่าด่านนี้มีอยู่)
3. **ด่านนี้เป็น tripwire ไม่ใช่การวัด** — บทเรียน "วัดรอบเดียวไม่ใช่
   หลักฐาน" ยังจริงทุกประการ: ตัวเลขจากด่านนี้ห้ามเอาไปอ้างใน
   `docs/PERFORMANCE.md` และการผ่านด่านนี้ไม่ใช่หลักฐานว่าเป้าจริงผ่าน
   สิ่งเดียวที่มันพิสูจน์คือ "ไม่มีอะไรล้มเหลวแบบก้าวกระโดดใน commit นี้"

## ทางที่ไม่ได้เลือก

- **ตัดสินที่เป้าจริง 200/500 บน runner** — ปัดตก: p99 ของรอบที่เหมือนกัน
  ทุกอย่างต่างกันได้สี่เท่า (วัดจริงตอน Phase 6) ด่านที่ flaky จะถูกกด
  rerun จนไม่มีใครอ่าน แล้ววันที่มันแดงจริงก็ถูก rerun เหมือนกัน
- **วัดหลายรอบใน CI แล้วเอา median** — ปัดตก: คูณเวลา job โดยได้ความ
  เชื่อมั่นเพิ่มน้อย — จุดตัดสินใจของเราไม่ใช่ "ผ่านเป้าไหม" (นั่นเป็นงาน
  ของรอบวัดจริง) แต่คือ "ล้มเหลวก้าวกระโดดไหม" ซึ่งรอบเดียวที่เกณฑ์สองเท่า
  ตอบได้พอ
- **เพิ่มเข้า job `stack` แทนที่จะแยก** — ปัดตก: `stack` พิสูจน์การต่อสาย
  ของ compose หลาย override อยู่แล้วและยาวพอสมควร ด่านที่ตัดสินคนละ
  คำถามควรแดงแยกกันอ่านออก (job ที่แดงด้วยสองเรื่องคือ job ที่เสียเวลา
  ไล่ทุกครั้ง)

## ผลที่ตามมา

- pillar performance มีด่านต่อ push ตัวแรก (gate `perf-regression-tripwire`
  — pillar performance ตัวที่ 4) · `perf-smoke` ต้องเข้า required checks
  ของ branch protection หลัง merge (26 → 27)
- เงื่อนไขทบทวน: ถ้าด่านนี้ flaky เกินหนึ่งครั้งต่อเดือนโดยไม่มี regression
  จริง ให้ขยับเกณฑ์ขึ้นหรือเพิ่ม duration ก่อนจะคิดปิด — ด่านที่ถูกปิด
  เสียงเพราะ flaky คือด่านที่ตายทั้งที่ยังเขียว
