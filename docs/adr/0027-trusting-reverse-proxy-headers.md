# 0027 — เชื่อ header ของ reverse proxy เป็น "จำนวนชั้น" ไม่ใช่สวิตช์เปิด/ปิด

สถานะ: accepted (2026-08-10) — Phase 5 · P5-11

**บริบท:** DoD ของ Phase 5 คือ "app รัน ≥2 replica พฤติกรรมถูกต้อง" ซึ่งบังคับ
ให้มี reverse proxy อยู่หน้า app (host มีพอร์ตเดียว แต่ replica มีหลายตัว)
พอมี proxy สิ่งที่ WSGI เห็นจะเป็นของ *proxy* ไม่ใช่ของผู้ใช้:

- `REMOTE_ADDR` เป็นไอพีของ proxy **ทุกคำขอ** → กุญแจของ rate limit ต่อไอพี
  (มิติแรกของ ADR 0021) กลายเป็นก้อนเดียวสำหรับคนทั้งโลก คนที่ไล่เดารหัสผ่าน
  คนเดียวจะกินโควตาของผู้ใช้ทุกคนจนหมด แล้ว **ทั้งระบบ login ไม่ได้**
  และ `remote_addr` ชั้น C6 ใน log ก็เลิกตอบคำถามว่าใครยิงมา
- `wsgi.url_scheme` เป็น `http` แม้ผู้ใช้จะเข้ามาทาง https → `HTTPS_ENABLED=1`
  จะสั่ง redirect ไป https ทุกคำขอ = **วนไม่รู้จบจน login ไม่ได้**
  (CLAUDE.md เตือนอาการนี้ไว้ตั้งแต่ Phase 1 แต่ยังไม่มีทางแก้ที่ถูกต้อง)

ทั้งสองอย่างพังเงียบ ไม่มี error ให้เห็นฝั่ง server

## คำตัดสิน

### 1. ค่าเริ่มต้นคือ **ไม่เชื่อ header อะไรเลย**

`X-Forwarded-For` เป็น header ธรรมดาที่ client ตั้งเองได้ ถ้าเชื่อโดยไม่มีใคร
ล้างค่าให้ก่อน คนยิงจะปลอมไอพีใหม่ทุกคำขอแล้ว **หลุด rate limit ต่อไอพีทั้งหมด**
ซึ่งแย่กว่าอาการ "ทุกคนใช้โควตาก้อนเดียวกัน" ที่เรากำลังจะแก้เสียอีก

เลือกฝั่งที่ "ผิดแล้วเห็น" มากกว่าฝั่งที่ "ผิดแล้วเงียบ": ไม่ตั้งค่าแล้วรันหลัง proxy
จะเห็นอาการทันที (ทุกคนโดนกันพร้อมกัน) ส่วนการเชื่อ header โดยไม่มี proxy
จะไม่มีอาการอะไรเลยจนกว่าจะมีคนใช้ประโยชน์จากมัน

### 2. ค่าที่ตั้งเป็น **จำนวนชั้นของ proxy** (`TRUSTED_PROXY_HOPS`) ไม่ใช่ boolean

proxy แต่ละชั้น **ต่อท้าย** ค่าที่ตัวเองเห็นลงใน `X-Forwarded-For` ค่าที่ client
แนบมาเองจึงอยู่ **ซ้ายสุด** เสมอ การอ่านค่าที่ N จากขวาโดยที่ N ตรงกับจำนวน
proxy ที่เรารันจริง คือสิ่งเดียวที่แยก "ไอพีของ client" ออกจาก "ค่าที่ client
อยากให้เราเชื่อ"

boolean ตอบคำถามนี้ไม่ได้ — มันบอกได้แค่ "เชื่อ" กับ "ไม่เชื่อ" ซึ่งในทางปฏิบัติ
แปลว่า "เชื่อค่าซ้ายสุด" = ให้คนยิงตั้งไอพีของตัวเองได้ตามใจ
**ตั้งเกินจำนวนจริงเมื่อไหร่ ก็เท่ากับเชื่อค่าปลอมเช่นกัน** ตัวเลขนี้จึงเป็นส่วนหนึ่ง
ของสถาปัตยกรรมที่ deploy จริง ไม่ใช่ค่าปรับแต่งตามรสนิยม

### 3. เชื่อเฉพาะสาม header ที่มีคนใช้จริง

`x_for` (rate limit + log), `x_proto` (Talisman/HSTS ตอน TLS จบที่ proxy)
และ `x_host` (`url_for` แบบเต็ม URL) — **ไม่เปิด `x_port`/`x_prefix`**
ทุก header ที่เราประกาศว่าเชื่อ คือหนึ่งค่าที่ proxy ต้องรับผิดชอบล้างให้
รายการที่สั้นกว่าคือสัญญาที่ตรวจได้ง่ายกว่า

### 4. ผูกใน `create_app` **ก่อน** `init_security_headers()`

Talisman ตัดสินใจ redirect จาก `request.scheme` ถ้าลำดับสลับ การเปิด HSTS
ตอน P5-12 จะได้ redirect วนแทน — ข้อจำกัดลำดับแบบเดียวกับ `db_engine.load()`
ที่ต้องมาก่อน `db.init_app()` (ADR 0026)

## ผลที่ตามมา

- คนที่รันหลัง proxy **ต้องตั้งค่าเอง** ไม่มีการเดาให้ — `compose.scale.yaml`
  ตั้ง `TRUSTED_PROXY_HOPS=1` มาให้แล้วเพราะไฟล์นั้นเป็นคนวาง nginx เอง
  จึงรู้จำนวนชั้นแน่นอน (config กับ topology อยู่ในไฟล์เดียวกัน ขัดกันเองไม่ได้)
- `TestConfig` ตรึงค่าไว้ที่ 0 ด้วยเหตุผลเดียวกับ `RATELIMIT_ENABLED`/
  `DISABLED_PLUGINS` — `.env` ของเครื่องที่รันต้องไม่ทำให้เทสต์ตีความ header
  ที่ตัวเทสต์ไม่ได้ตั้งใจส่ง
- ค่าติดลบ **ทำให้แอปไม่ start** ไม่ใช่ตกกลับเป็น 0 เงียบ ๆ (หลักเดียวกับ
  scheme ที่ไม่มี backend รองรับใน ADR 0026)
- ยังไม่ทำ: จำกัดว่า *ไอพีไหน* ที่เป็น proxy ได้บ้าง (`ProxyFix` นับชั้นอย่างเดียว
  ไม่ตรวจว่าใครส่งมา) ถ้าวันหนึ่ง app ถูก expose ตรงพร้อมกับอยู่หลัง proxy
  ด้วย จะต้องมีรายการไอพีที่เชื่อได้เพิ่ม — วันนี้ compose ไม่ publish พอร์ตของ
  app ออกนอก stack เลย ทางเข้าจึงมีทางเดียวคือผ่าน proxy
