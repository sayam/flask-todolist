# 0044 — admin เป็น package ของ core ที่เสียบ panel ได้ ไม่ใช่ plugin

สถานะ: accepted (2026-08-14) — เปิดเฟส 14 ([ROADMAP-FEATURES.md](../ROADMAP-FEATURES.md)
· ตอบข้อ 8 ของรายการ idea ที่ถามว่า "ควรแยก module admin ออกมาพิเศษไหม")

**บริบท:** เฟส 14 จะเพิ่มหน้า admin หลายหน้า (environment · SBOM · lifecycle ·
observability) และ `app/admin.py` เดิมเป็นไฟล์เดียว 47 บรรทัด — ต้องตัดสินก่อน
โตว่าโครงเป็นอะไร: plugin ที่ถอดได้ หรือของ core

## คำตัดสิน

**admin เป็นของ core** — ยกจากไฟล์เดียวเป็น package `app/admin/` ที่มี
**registry ของ panel**: หน้าใหม่ลงทะเบียนตัวเอง (endpoint + ชื่อ) แล้ว nav
ของ admin วนจาก registry ไม่ hardcode รายชื่อหน้า

เหตุผลที่ไม่เป็น plugin:

1. **admin ทำงานกับข้อมูลของคนอื่น** — มันต้องอยู่ใต้วินัยที่แรงที่สุดของ repo
   เสมอ: RBAC ตรวจใน service (ADR 0022) · ทุกการเขียนลง audit · **masking
   ตามชั้นข้อมูล (ADR 0045)** · ความสามารถถอดได้ = วินัยถอดได้
2. plugin ของ repo นี้นิยามด้วย "ถอดแล้วระบบที่เหลือทำงานเหมือนเดิม" —
   ระบบที่ไม่มีทางบริหารผู้ใช้ไม่ใช่ระบบเดิม (ทางกู้เดียวที่เหลือคือ CLI
   ซึ่งเป็นทางฉุกเฉิน ไม่ใช่ทางปกติ)
3. สิ่งที่อยากได้จากความเป็น plugin คือ*การต่อขยาย* ไม่ใช่*การถอด* —
   registry ของ panel ให้สิ่งนั้นโดยไม่เสียวินัย: plugin ลงทะเบียน panel
   เพิ่มได้ในอนาคตผ่านหลัก capability เดิม (ADR 0025)

## กติกาของ panel

- panel = (endpoint, ชื่อที่แปลได้) ลงทะเบียนผ่าน `app.admin.register_panel()`
  ตอน import — ลำดับตามการลงทะเบียน
- ทุก view ใต้ `/admin` ตรวจสิทธิ์ผ่าน service (`require_admin`) เหมือนเดิม —
  registry ไม่ใช่ด่านสิทธิ์ (การซ่อนเมนูไม่ใช่การกันสิทธิ์ — กติกาเดิม)
- **ข้อมูลผู้ใช้ทุกชิ้นที่ panel แสดง ต้องผ่านชั้น masking (ADR 0045) —
  ไม่มีข้อยกเว้นสำหรับ panel ที่มาทีหลัง** นี่คือเหตุผลที่ masking ต้องเสร็จ
  ก่อนหน้าใหม่ทุกหน้า (ลำดับใน ROADMAP-FEATURES เฟส 14)

## ทางเลือกที่ไม่เอา

- **admin เป็น plugin ชนิดใหม่** — ขัดข้อ 1–2 ข้างบน
- **แยกเป็นแอป/บริการต่างหาก** — service layer เดียวกันต้องถูก import สองที่
  หรือกลายเป็น API ภายใน = พื้นที่ผิวเพิ่มโดยไม่มีผู้ใช้ที่ต้องการมัน
- **คงเป็นไฟล์เดียวแล้วโตไปเรื่อย ๆ** — ไฟล์ route ที่ยาวคือที่ที่ตรรกะจะ
  โดยไม่ได้สั่งรั่วเข้ามา (บทเรียนที่ทำให้เกิด ADR 0016)

## เงื่อนไขทบทวน

มี use case จริงที่ต้อง deploy admin แยกเครื่องจากตัวแอป (เช่น network
segmentation ตามนโยบายองค์กร) — วันนั้นค่อยคุยเรื่อง API ภายใน
