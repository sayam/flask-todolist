## 2. กรอบ maturity ขององค์กร (CMMI · TOGAF · ITIL · COBIT · CISSP-alignment)

เป็นกรอบประเมิน*องค์กรและกระบวนการของคน* — โปรเจกต์ผู้ดูแลคนเดียวเคลม
alignment ไม่ได้โดยพิสูจน์ได้ ซึ่งขัดหลักที่แรงที่สุดของ repo:
**เคลมเฉพาะที่มีตัวบังคับ** (แบบเดียวกับที่ ASVS ผ่าน 138 ไม่ใช่ 253 และเขียน
ตรง ๆ ว่า 48 ไม่ผ่าน) · การเขียน mapping โดยไม่มีเครื่องตรวจคือการสร้าง
เอกสารเน่าเพิ่มหนึ่งใบ
· **ที่รับแทน:** ISO/IEC/IEEE 42010 อย่างเดียว (13-05) — architecture
description ที่ rationale ชี้ไป ADR จริงและมีเทสต์ตรวจ citation
· **เงื่อนไขทบทวน:** มีทีมจริง (คน ≥2 + กระบวนการที่ประเมินได้)

## 3. In-process encryption

ไม่มีกลไกจริงระดับแอป Python — memory encryption เป็นเรื่องของ hardware/enclave
(SGX ฯลฯ) ซึ่งอยู่นอกอำนาจของโค้ดแอปโดยสิ้นเชิง · เคลม "at rest + in transit +
in process" โดยข้อสามไม่มีตัวบังคับ = คำขวัญ · at rest ทำจริงเฟส 15 ·
in transit มีแล้ว (TLS + PFS วัดจริงตอน PR #9)
· **เงื่อนไขทบทวน:** ย้ายไป runtime ที่มี enclave จริงและมีเหตุให้ใช้

## 4. Benchmark runner ในหน้า admin

Phase 6 พิสูจน์แล้วว่า**ตัวเลขที่ตัดสินต้องมาจากฝั่ง client (k6)** — เวลาที่
ผู้ใช้รอรวมคิวของ gunicorn ซึ่งเกิด*ก่อน*ตัวจับเวลาฝั่ง server ทำงาน การยิง
โหลดจากในแอปใส่ตัวเองยิ่งผิดซ้ำสอง (วัดผ่านตัวเองและกินทรัพยากรของสิ่งที่วัด)
· **ที่รับแทน:** หน้า observability อ่าน `/metrics` ของ process ตัวเอง
พร้อมป้ายกำกับข้อจำกัดตาม [ADR 0031](0031-performance-targets.md) (14-06)

## 5. Fragment cache ร้อน/อุ่น/เย็น — **เลื่อน ไม่ใช่ตัดถาวร**

Phase 6 วัดแล้ว: คอขวดคือจำนวน process ที่รับงาน ไม่ใช่ render/query —
เพิ่มชั้น cache ตอนนี้คือแก้สิ่งที่การวัดไม่ได้บอกว่าเสีย และเพิ่มสถานะ
(invalidation) ที่ต้องดูแลตลอดไป
· **เงื่อนไขปลดล็อก (วัดได้):** หลังปรับ workers และวัดใหม่ (16-05) ยังมี
endpoint ที่ p95 ตกเกณฑ์และ profile ชี้ว่าเวลาไปลงที่ render/query — เมื่อนั้น
ค่อยออกแบบ cache ให้ตรง endpoint นั้น พร้อม ADR ของตัวเอง
