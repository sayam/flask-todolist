# 0051 — ธรรมนูญของโปรเจกต์: ลำดับความสำคัญสี่ชั้น และกระบวนการรับของใหม่

สถานะ: **accepted** (2026-08-15 — เจ้าของอนุมัติตามร่าง "เห็นด้วยตามข้อเสนอ
ทั้ง 3 ข้อ" และตัดสินคำถามเปิดทั้งสาม: ISO 27001 ประเมิน**ครบ** ·
`pillar:` **บังคับทุก gate** · **G2 ก่อน G3** — เปิดแผน G · ADR นี้คือการ
ตีความปรัชญาที่เจ้าของประกาศให้เป็นกติกาที่ตรวจได้)

**บริบท:** โปรเจกต์เดินมา 18 เฟส + 2 รุ่น โดยลำดับความสำคัญอยู่ในหัวของ
เจ้าของและกระจายอยู่ในคำตัดสินราย ADR (เช่น `/metrics` ต้องมี token แม้
แลกกับความสะดวก · คง 1 worker แม้ 2 worker เร็วกว่า เพราะความถูกต้องของ
ตัววัดมาก่อน) — เมื่อโปรเจกต์เริ่มรับ**ของจากภายนอก**เป็นกิจวัตร (skill ·
idea · มาตรฐานใหม่) การตัดสิน "รับ/ไม่รับ/รับแบบไหน" ต้องมีเกณฑ์ที่เขียนไว้
ไม่ใช่ตัดสินใหม่จากศูนย์ทุกครั้ง

## คำตัดสิน 1 — ลำดับความสำคัญสี่ชั้น (priority stack)

สำหรับ**การพัฒนา web application** (ขอบเขตเดียวของโปรเจกต์นี้):

1. **Security first** (แนวทาง CISSP) —
   ประกอบด้วยสามแกนที่ต้องผ่านทั้งหมด:
   - **กฎหมายรายประเทศ**: ประเทศแรกที่ craft คือไทย (PDPA —
     `docs/PDPA.md` มีแล้ว) · โครงรองรับประเทศถัดไปแบบ additive
   - **มาตรฐานสากล**: ISO/IEC/IEEE 42010:2022 (`docs/ARCHITECTURE.md`
     มีแล้ว) · **ISO/IEC 27001:2022 (ยังไม่มี — งานใหม่ของแผนนี้)** ·
     ASVS 5.0 L2 (มีแล้ว) เป็นชั้นเทคนิคใต้ 27001
   - **supply chain แยกเป็นแกนอิสระ**: มีชิ้นส่วนครบแล้ว (pins/ · SBOM ·
     plugin category · Scorecard · Dependabot · plugin-audit) แต่กระจาย —
     ต้องมีดัชนีแกนของตัวเอง
2. **Scalable & performance second** — multiple worker · caching · ฯลฯ
   ข้อจำกัดที่ security กำหนดมาก่อนเสมอ (ตัวอย่างจริง: multi-worker ติด
   เงื่อนไข `/metrics` per-process ของ ADR 0031 — แก้ได้ด้วยการออกแบบ
   ไม่ใช่ด้วยการลดด่าน)
3. **Manageable third** — plug/unplug · ถอด package ที่มีช่องโหว่ได้จริง
   (มีแล้วเป็นสถาปัตยกรรม plugin + `DISABLED_PLUGINS`) · ของใหม่ต้อง
   เข้ารูปนี้ ไม่สร้างของที่ถอดไม่ได้
4. **DevOps/DevSecOps friendly fourth** — skill · overlay · เครื่องมือ
   ที่ทำให้คนอื่น (และ agent) ทำงานตามวินัยนี้ได้

**กติกาการชน**: ความกังวลชั้นล่างขัดกับชั้นบน → ชั้นบนชนะโดยไม่ต้องเถียง
ใหม่ · ขัดกันในชั้นเดียวกัน → ตัดสินด้วย ADR · การยกเว้นชั่วคราวต้องมี
ADR ที่ระบุเงื่อนไขหมดอายุ

## คำตัดสิน 2 — กระบวนการรับของใหม่ (intake)

เมื่อมี skill / idea / มาตรฐาน / เครื่องมือ ใหม่เข้ามา:

1. **baseline ไม่ถูก break** — นิยาม "break" ให้ตรวจได้: gate ใดใน
   `gates.yaml` ถูกทำให้แดง ถูกลดความเข้ม หรือถูกถอด โดยไม่มี ADR ที่
   อธิบายและเจ้าของอนุมัติ = break · ratchet ทุกตัวขยับลงไม่ได้เช่นเดิม
2. **จำแนกก่อนรับ** — เทียบกับ baseline แล้วลงหนึ่งในสี่ช่อง:
   - **ดีกว่าของเดิม** → ปรับมาใช้แทน (ผ่าน ADR ถ้าแทนที่คำตัดสินเดิม)
   - **ไม่เคยมี** → หาทางปรับเข้ามาให้เข้ารูปของ repo (generate/gate/plugin)
   - **ดีเฉพาะบางสถานการณ์** → รับแบบจำกัดขอบเขต (plugin · config ·
     หมวดเฉพาะในเอกสาร) พร้อมประกาศสถานการณ์ที่ใช้
   - **ขัดกับชั้นที่สูงกว่า** → ปัดตก พร้อมจดเหตุผล (การปัดตกที่ไม่จดคือ
     การเถียงซ้ำในอนาคต)
3. **ทุกการรับเข้า/ปัดตกที่มีนัยจดเป็น ADR** — ADR คือ intake log อยู่แล้ว
   ไม่สร้างทะเบียนที่สอง · ตัวอย่างที่เดินกระบวนการนี้แล้วจริงสามตัว:
   bmad-method → รับเฉพาะ story-file discipline (ใช้ตอนงานแผนใหญ่) ·
   impeccable → รับ mode framework + bounded verification เป็น
   `docs/DESIGN.md` (ADR-less เพราะไม่แทนที่คำตัดสินเดิม — มี gate แทน) ·
   skillsmp → รับรูปแบบแพ็กเกจเป็น `skill/` (ADR 0050)

## คำตัดสิน 3 — ปรัชญาต้องถูกเครื่องตรวจ ไม่ใช่คำขวัญ

- **ทุก gate ใน `gates.yaml` ประกาศ `pillar:`** — `security` /
  `performance` / `manageability` / `devx` (ชั้น 1–4) · เทสต์บังคับครบ
  ทุก gate (partition แบบเดียวกับ `layer:`) — ผลพลอยได้: ตอบได้ทันทีว่า
  แต่ละชั้นของปรัชญามีด่านจริงกี่ตัว และชั้นไหนพูดมากกว่าทำ
- ธรรมนูญนี้เข้า `docs/ARCHITECTURE.md` §2 (stakeholders & concerns —
  ที่ที่ 42010 ให้ความกังวลอยู่แล้ว) ไม่สร้างเอกสารปรัชญาแยก (ที่ที่สาม =
  ที่ให้ drift) · กระบวนการ intake เข้า `CONTRIBUTING.md` เป็นกฎข้อ 10

## งานที่ตามมา (จะแตกเป็น story ราย PR — แผน G ใน ROADMAP-GOVERNANCE.md)

- **G1**: ธรรมนูญ + intake เข้าเอกสาร + `pillar:` ครบทุก gate + เทสต์คุม
- **G2**: **ISO/IEC 27001:2022 self-assessment** (`docs/ISO27001.md`) —
  worksheet แบบ ASVS/PDPA: Annex A ทั้ง 93 controls + clause 4–10
  ประเมินครบทุกข้อ (คาดว่า organizational controls จำนวนมากจะ
  "ไม่เกี่ยวข้อง" สำหรับโปรเจกต์คนเดียว — การจดว่าไม่เกี่ยวข้องพร้อมเหตุผล
  คือการประเมิน ไม่ใช่การข้าม) + เทสต์ตรวจหลักฐานแบบ `test_asvs.py`
- **G3**: **ดัชนีแกน supply chain** (`docs/SUPPLY-CHAIN.md`) — รวมของที่มี
  (pins/SBOM/category/Scorecard/Dependabot/accepted-advisories) เป็นแกน
  เดียวที่ชี้ gate จริง + เทสต์กันล้าสมัย
- **G4**: **โครง compliance รายประเทศ** — `docs/COMPLIANCE.md` เป็นดัชนี
  (ไทย = PDPA ที่มีแล้ว · ประเทศใหม่ = เพิ่มไฟล์แบบ additive ไม่แตะของเดิม)
- **G5 (ชั้น 2 — หลัง G1–G4)**: multi-worker ที่ไม่ลดด่าน (ทางที่บันทึกไว้:
  metrics aggregate ข้าม process หรือ scale ด้วย replica ตามเดิม) + คำตัดสิน
  caching layer — แต่ละเรื่องมี ADR ของตัวเอง

## คำถามเปิด — เจ้าของตัดสินแล้ว (2026-08-15)

1. **ขอบเขต ISO 27001: ประเมินครบ** ทั้ง clause 4–10 + Annex A 93 controls
   — หลัก "ประเมินครบ ไม่เกี่ยวข้องก็จดพร้อมเหตุผล" เดียวกับ ASVS 253 ข้อ
2. **`pillar:` บังคับทุก gate** — partition แบบเดียวกับ `layer:`
   (ผลจริงตอนประกาศ: security 52 · manageability 14 · devx 13 ·
   performance 2 — ชั้น performance มีด่านน้อยสุดตรงกับที่ load test
   ยังเป็นงานรันมือ ภาพนี้คือสิ่งที่ pillar มีไว้เผย)
3. **G2 (ISO 27001) ก่อน G3 (supply-chain index)** — มาตรฐานใหญ่ที่ยัง
   ไม่มีมาก่อนการจัดดัชนีของที่มีแล้ว
