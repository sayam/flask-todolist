# 0014 — ข้อขัดแย้งระหว่างสิทธิ์ลบข้อมูล (PDPA) กับ audit trail ที่ลบไม่ได้

สถานะ: accepted (2026-08-03) — อนุมัติโดยเจ้าของโปรเจกต์

**บริบท:** Phase 2 กำลังจะสร้าง audit trail แบบ append-only ที่มี hash chain
เป็นหลักฐานว่าไม่ถูกแก้ย้อนหลัง พร้อมกับ soft delete + purge job ที่ต้องรองรับ
"คำขอลบ" ของเจ้าของข้อมูล สองอย่างนี้ขัดกันโดยธรรมชาติ —
อย่างหนึ่งบอกว่า "ห้ามแก้ห้ามลบ" อีกอย่างบอกว่า "ต้องลบให้ได้"

ต้องตัดสินใจ**ก่อน**เขียนโค้ด เพราะการเลือกผิดแปลว่าต้องรื้อโครงสร้างตาราง audit
ทีหลัง ซึ่งก็คือการทำลายหลักฐานที่เพิ่งสร้าง

## ปัญหาที่แผนเดิมมองข้าม

ROADMAP ร่างแรกเสนอว่า *"audit log เก็บครบตาม retention โดยแทนที่ PII ใน log
ด้วย pseudonym"* — **ทำไม่ได้จริงเมื่อ audit เป็น hash chain** เพราะการแก้ค่า
ในแถวเก่าทำให้ hash ของแถวนั้นและ**ทุกแถวถัดไป**ใช้ไม่ได้ ต้อง re-chain ใหม่ทั้งสาย
ซึ่งเท่ากับทำลายคุณสมบัติ tamper-evident ที่เป็นเหตุผลเดียวของการมี chain
(ระบบที่ re-chain ได้ตามใจ = ระบบที่คนมีสิทธิ์แก้ย้อนหลังได้โดยไม่ทิ้งร่องรอย)

## คำตัดสิน — ออกแบบไม่ให้มี PII ใน audit ตั้งแต่แรก

แทนที่จะลบ PII ทีหลัง ให้ **ไม่เคยเขียน PII ลง audit เลย** ปัญหาจึงไม่เกิด

1. **actor เก็บ `actor_id` (เลข) อย่างเดียว ไม่เก็บ username**
   ลบ PII ที่ตาราง user แล้ว audit แสดงผลเป็น "ผู้ใช้ที่ถูกลบ #7" เอง
   โดยไม่ต้องแตะแถว audit แม้แต่แถวเดียว
2. **payload เก็บค่าจริงเฉพาะคอลัมน์ชั้น C4** (`is_done`, `category_id`,
   `locale`, `theme`, timestamp ของแถว ฯลฯ) ส่วน C2/C3 เก็บแค่
   **ชื่อคอลัมน์ + HMAC ของค่าเก่า/ใหม่**
3. **C1 ไม่ลง audit เลย แม้แต่ในรูป hash** — การเปลี่ยนรหัสผ่านบันทึกแค่ว่า
   "เกิดเหตุการณ์ password.change เมื่อไหร่ โดยใคร"

ตัวอย่างแถว audit:

```json
{
  "event": "todo.update", "actor_id": 7,
  "table_name": "tdl_todo", "row_id": 42,
  "changes": {
    "title":      {"from_hash": "a3f1…", "to_hash": "9c02…"},
    "due_date":   {"from_hash": null,    "to_hash": "5b7e…"},
    "is_done":    {"from": false, "to": true},
    "updated_at": {"from": "2026-08-01T09:00:00", "to": "2026-08-03T04:12:00"}
  }
}
```

**หมายเหตุ (แก้ 2026-08-03 ตอนลงมือทำ):** ร่างแรกของ ADR นี้ยกตัวอย่าง
`due_date` เป็นค่าจริง ซึ่ง**ขัดกับ DATA-CLASSIFICATION.md ที่จัด `due_date`
/`start_date` ไว้ชั้น C3** — ยึดตามเอกสารจำแนกชั้นเป็นหลัก วันครบกำหนดจึงถูก
HMAC เหมือน `title` audit ยังตอบได้ว่า "กำหนดส่งถูกเปลี่ยนเมื่อไหร่ โดยใคร"
แค่ไม่บอกว่าเปลี่ยนเป็นวันไหน ถ้าวันหนึ่งเห็นว่าเข้มเกินไป ให้**ย้ายชั้นใน
เอกสารจำแนกก่อน** แล้วโค้ดค่อยตามหลัง — ไม่ใช่ยกเว้นเป็นราย ๆ ในโค้ด

**ต้องเป็น HMAC ไม่ใช่ hash เปล่า** — ค่าอย่างชื่อคนหรือชื่องานสั้นและเดาได้
`sha256("สยาม")` ถูกไล่เดาด้วย dictionary ได้ในไม่กี่วินาที จึงใช้ HMAC-SHA256
กับคีย์ฝั่งเซิร์ฟเวอร์ที่**ไม่ได้เก็บในตาราง audit** ผลที่ได้คือ

- ตอบได้: "ค่าเปลี่ยนไหม", "ค่าเคยเท่ากับ X ไหม" (ถ้ามี X มาเทียบ)
- ตอบไม่ได้: "ค่าคืออะไร" — ตั้งใจ

ผลข้างเคียงที่ยอมรับ: **เปลี่ยน/ทำคีย์ HMAC หายแล้วเทียบค่าเก่าไม่ได้อีก**
(ตัว chain ยังตรวจได้ตามปกติ เพราะ chain แฮชทั้งแถวไม่ใช่แค่ค่าฟิลด์)

## ปัญหาที่สอง: purge audit ก็ทำ chain ขาดเหมือนกัน

retention ของ audit คือ 1 ปี แต่การลบแถวที่เก่ากว่านั้นทำให้แถวแรกที่เหลืออยู่
ชี้ไป hash ของแถวที่ถูกลบไปแล้ว — verify ไม่ผ่านทั้งสาย

**ทางแก้:** purge job ต้องเขียนแถวชนิด `checkpoint` แทนช่วงที่ลบ เก็บ
hash ของแถวสุดท้ายที่ถูกลบ, จำนวนแถวที่ลบ และช่วงเวลาที่ครอบคลุม
การ verify เริ่มนับจาก checkpoint ล่าสุดเสมือนเป็นจุดกำเนิด

ความซื่อสัตย์กับข้อจำกัด: checkpoint พิสูจน์ได้แค่ว่า**แถวที่ยังเหลืออยู่**
ไม่ถูกแก้ ไม่ได้พิสูจน์ว่าแถวที่ถูกลบไปมีอะไร คนที่ควบคุมทั้ง purge job และ
ฐานข้อมูลยังตัดประวัติทิ้งได้อยู่ดี — immutability จริงต้องใช้ storage
แบบ write-once ภายนอก ซึ่งเกินความจำเป็นของ scale นี้ (บันทึกไว้ว่ารู้ตัว)

## สรุปว่าอะไรชนะอะไร

| ประเด็น | ผู้ชนะ | เหตุผล |
|---|---|---|
| **การมีอยู่**ของแถว audit | audit | ลบร่องรอยว่า "เคยมีการแก้ไข" ไม่ได้ ไม่งั้นไม่ใช่หลักฐาน |
| **เนื้อหา** PII ในแถว audit | PDPA | แก้ที่ต้นทาง: ไม่เคยเขียนลงไปตั้งแต่แรก |
| ข้อมูลปฏิบัติการ (C2/C3) | PDPA | soft delete 30 วัน แล้ว purge จริง |
| credential (C1) | PDPA | ล้างทันทีที่ปิดบัญชี ไม่รอ grace |

**ผล:** คำขอลบของเจ้าของข้อมูลทำได้ครบโดย**ไม่ต้องแตะตาราง audit เลยสักแถว**
ซึ่งแปลว่า hash chain ไม่มีเหตุให้ต้อง re-chain ตลอดอายุระบบ

ค่าที่อนุมัติแล้ว: soft delete 30 วัน / audit 1 ปี / log ปฏิบัติการ 90 วัน
รายละเอียดต่อชั้นอยู่ใน [docs/DATA-CLASSIFICATION.md](../DATA-CLASSIFICATION.md)
