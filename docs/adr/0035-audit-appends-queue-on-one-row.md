# 0035 — ต่อคิวสาย audit ที่แถวเดียว ไม่ใช่ที่หางสาย

สถานะ: accepted (2026-08-12) — Phase 7 · **แทนที่วิธีของ [ADR 0032](0032-serialising-audit-appends.md) ข้อ 1**
(คำตัดสินอื่นของ ADR 0032 ยังใช้อยู่ทั้งหมด)

**บริบท:** ADR 0032 แก้ปัญหา "สอง replica ต่อสายด้วย `prev_hash` เดียวกันแล้ว
ตัวหลังชนกุญแจ unique" ด้วยการล็อกแถวท้ายสาย:

```sql
SELECT row_hash FROM tdl_audit ORDER BY id DESC LIMIT 1 FOR UPDATE
```

การวัดหลังแก้บอกว่าการชนกุญแจ unique หายไปจริง (225 ครั้ง/รอบ → 0) **แต่มี
deadlock ของ MySQL โผล่มาแทน 2 ครั้ง/รอบ** ซึ่งตอนนั้นบันทึกไว้ว่าเป็น
"อุบัติเหตุที่นาน ๆ ครั้ง" และยกไปเป็นงานถัดไป

**สิ่งที่การบันทึกแบบนั้นพลาด**: deadlock ไม่ใช่ผลข้างเคียงที่หลงเหลือ
มันคือ**อาการของการที่ล็อกนั้นไม่เคยทำงานอย่างที่เราคิด**

## สิ่งที่วัดได้ และเป็นตัวเปลี่ยนคำตัดสิน

job `dast` ของ Phase 7 แดงเพราะ deadlock ตัวนี้ ทั้งที่ ZAP crawl ด้วย thread
เดียว — ซึ่งไม่ควรเป็นภาระอะไรเลย เมื่อเอามาวัดตรง ๆ ด้วยผู้เขียน 8 ราย
บน MySQL 8:

| วิธี | repro ที่เขียนอย่างเดียว | repro ที่**อ่านก่อนเขียน** (เหมือนของจริง) |
|---|---|---|
| ล็อกหางสาย (ADR 0032) | สำเร็จ 32/160 · deadlock 128 | — |
| ล็อกแถวเดียว + อ่านหางสายแยก | สำเร็จ 160/160 | **สำเร็จ 21/160 · ชนกุญแจ 139** |
| ล็อกแถวเดียว + หางสายบนแถวล็อก | สำเร็จ 160/160 | **สำเร็จ 160/160** · 16 สาย × 30 รอบ: 480/480 |

**80% ของการเขียนตายด้วย deadlock** ไม่ใช่ 2 ครั้งต่อรอบ · ตัวเลขเดิมของ
Phase 6 ต่ำเพราะ load test ยิงงานที่เป็นการ*อ่าน*เป็นส่วนใหญ่ ไม่ใช่เพราะ
ปัญหาเล็ก

## ทำไมวิธีเดิมถึงไม่ได้ทำให้การเขียนเป็นลำดับ

InnoDB ล็อกช่วง ไม่ได้ล็อกเฉพาะแถว · `ORDER BY id DESC LIMIT 1 FOR UPDATE`
จับ **next-key lock ที่รวมช่องว่างท้ายตาราง** เข้าไปด้วย และกติกาของ InnoDB คือ:

1. **ช่องว่างเข้ากันได้กับช่องว่าง** — ผู้เขียนหลายรายจึงผ่านบรรทัด `FOR UPDATE`
   ไปพร้อมกันได้ทั้งหมด ไม่มีใครรอใคร
2. **insert intention lock ขัดกับช่องว่างของคนอื่น** — พอทุกคนไป `INSERT`
   ที่ท้ายตาราง แต่ละคนต้องรอช่องว่างของอีกคนปล่อย → เป็นวงจร → deadlock

พูดอีกอย่าง: ล็อกเดิม**เปลี่ยนชนิดของความล้มเหลว** จาก "ชนกุญแจ unique"
เป็น "deadlock" โดยไม่ได้เพิ่มการต่อคิวจริงเลย · การที่ตัวเลขการชนกุญแจเป็นศูนย์
จึงอ่านเหมือนแก้สำเร็จ ทั้งที่ผู้ใช้ยังเห็น 500 เท่าเดิม แค่ด้วยข้อความอื่น

## คำตัดสิน

### 1. ต่อคิวที่ **แถวเดียวที่มีอยู่จริง** และ **เก็บหางสายไว้บนแถวนั้น**

`tdl_audit_lock` มีแถวเดียว เก็บสองอย่าง: คีย์หลัก กับ `last_hash` ·
ทุกคนที่จะต่อสายต้องอ่านมันแบบล็อกก่อน

```sql
SELECT last_hash FROM tdl_audit_lock WHERE id = 1 FOR UPDATE
```

การล็อกแถวที่มีอยู่จริงด้วยคีย์หลักเป็น **record lock ล้วน ไม่มีช่องว่าง**
ให้ขัดกัน ผู้เขียนจึงต่อคิวกันจริง

**หางสายต้องเดินทางมากับแถวที่ล็อก ไม่ใช่อ่านแยก** — รอบแรกของ ADR นี้ล็อกแถวนั้น
แล้วไปอ่าน `SELECT row_hash FROM tdl_audit ORDER BY id DESC LIMIT 1` แบบธรรมดา
ซึ่ง**ผิด**: ใต้ REPEATABLE READ การอ่านแบบธรรมดาเห็น snapshot ที่ตั้งไว้ตั้งแต่
query แรกของ transaction และ **คำขอจริงทุกใบอ่านข้อมูลก่อนเขียนเสมอ** snapshot
จึงถูกตั้งไว้ก่อนที่เราจะได้ล็อกมา ผู้เขียนสองรายที่ต่อคิวกันเรียบร้อยจึงยังอ่าน
หางสายเดียวกันได้ แล้วชน `uq_audit_prev_hash` เหมือนเดิมทุกประการ ·
**locking read เห็นค่าล่าสุดที่ commit แล้วเสมอ** ค่านั้นจึงต้องอยู่บนแถวที่ล็อก

### 2. **แถวล็อกเกิดพร้อมตาราง ไม่ใช่เกิดตอนแอปหาไม่เจอ**

สร้างใน migration และผูกกับ `after_create` ของตารางเพื่อให้ `db.create_all()`
ของเทสต์ได้เหมือนกัน — **แอปที่สร้างแถวให้เองเมื่อไม่เจอ คือแอปที่ผู้เขียน
หลายรายสร้างแถวพร้อมกันได้** ซึ่งพากลับไปที่ปัญหาเดิมพอดี

ไม่มีแถวนั้น = `_last_hash()` raise ทันที **ห้ามเดินต่อเงียบ ๆ** เพราะการเขียน
ที่ไม่มีอะไรกั้นจะกลายเป็น 500 ของผู้ใช้ในวันที่มีคนใช้พร้อมกัน

### 3. SQLite ไม่ต้องทำอะไรเพิ่ม เหมือนเดิม

SQLAlchemy ตัด `FOR UPDATE` ทิ้งเองบน SQLite และ SQLite ล็อกทั้งไฟล์ตอนเขียน
อยู่แล้ว · เทสต์ความขนานจึง `skipif` บน SQLite อย่างเปิดเผย

### 4. ราคายังเป็นราคาเดิม และยังยอมรับ

การเขียนที่ต้องลง audit ยัง serialize กันทั้งระบบ ซึ่งเป็นสิ่งที่สาย hash
ต้องการโดยนิยาม (ADR 0032 ข้อ 2 ยังใช้ได้ทุกคำ) — ต่างกันแค่ตอนนี้มัน
**ต่อคิวจริง** แทนที่จะชนกันแล้วตายไปหนึ่งฝ่าย

## บทเรียนที่ต้องเขียนไว้ — สองข้อ และข้อที่สองแพงกว่า

**หนึ่ง: เทสต์ "สองสายเขียนพร้อมกัน" ของ ADR 0032 ผ่านมาตลอดทั้งที่ล็อกล้มเหลวอยู่**
เพราะสองสายไม่พอจะสร้างวงจรของ deadlock · ตัวแปรที่ขาดไม่ใช่ "สัญญาณที่วัด"
แต่เป็น **ขนาดของแรงที่ใส่เข้าไป** — เทสต์ใหม่ใช้แปดสาย และจำนวนนั้นคือหัวใจ

**สอง: การวัดรอบแรกของ ADR นี้เองก็ไม่เหมือนของจริง** ตัว repro ที่ใช้พิสูจน์ว่า
"แก้แล้ว" เรียก `audit.record()` เป็น statement แรกของ transaction ซึ่ง
**ไม่มีคำขอจริงใบไหนทำแบบนั้น** ทุกใบอ่านข้อมูลก่อนเขียน · ผลคือ snapshot ถูกตั้ง
ตอนที่ยังไม่มีใครแข่ง การวัดจึงบอกว่า 160/160 ผ่าน ทั้งที่ของจริงผ่าน 21/160

พอทำ repro ให้อ่านก่อนเขียนหนึ่งบรรทัด ตัวเลขเปลี่ยนจาก "แก้แล้ว" เป็น
"ยังล้มเหลวอยู่ 87%" ทันที · **นี่คือรูปแบบเดิมที่โปรเจกต์นี้เจอมาสามครั้ง
(ด่านที่วัดสัญญาณผิดตัว) แต่คราวนี้เกิดกับเครื่องมือวัดที่เราสร้างเองเพื่อพิสูจน์
ว่าแก้ถูก** — ซึ่งอันตรายที่สุด เพราะมันตอบว่า "ผ่าน" ในจังหวะที่เรากำลังอยากได้ยิน
