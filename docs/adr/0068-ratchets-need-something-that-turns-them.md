# 0068 — ratchet ต้องมีตัวทวงให้หมุน ไม่งั้นมันคือพื้นที่ค้างอยู่ที่เดิม

สถานะ: **accepted** (2026-08-18 — ช่องว่าง D1 ของ audit governance รอบสิบสอง)

**บริบท:** `pyproject.toml` เขียนกำกับไว้ทั้งสองที่ว่า *"ขยับขึ้นได้อย่างเดียว"* —
ทิศถูกแล้ว และเป็นทิศที่โปรเจกต์นี้เลือกโดยตั้งใจตั้งแต่ Phase 0 · **สิ่งที่ไม่มีคือ
แรงหมุน**: ไม่มีอะไรทำให้พื้นขยับตามของจริงที่ดีขึ้น มีแต่คนที่ต้องนึกได้เอง

วัดจริง 2026-08-18 (หกวันหลังตั้งเลข):

| เกณฑ์ | ตั้งไว้ | ของจริง | ห่าง |
|---|---|---|---|
| coverage `fail_under` | 96 (ตั้งตอนวัดได้ 96.31%) | **97.11%** | 1.11 จุด |
| `interrogate` fail-under | 84 (ตั้งตอนวัดได้ 84.9%) | **85.5%** | 1.5 จุด |
| `PLUGIN_DEPS_BUDGET` | 78 | 76 | 2 เทสต์ |

ที่ว่าง 1.11 จุดของ coverage แปลว่า **โค้ดที่มีเทสต์คุมอยู่ราว 54 บรรทัดหายไปได้
โดยไม่มีอะไรแดง** — ของจริงไต่ขึ้นมาเองเพราะ `diff-cover --fail-under 100` บังคับ
บรรทัดที่แก้ทุกใบ แต่ไม่มีอะไรเก็บกำไรนั้นไว้

**กลไกที่ถูกมีอยู่แล้วในโปรเจกต์นี้** — [ADR 0065](0065-instruction-file-ceiling.md)
บังคับว่าเพดานของ `CLAUDE.md` **ต้องไม่ลอยเหนือของจริงเกินระยะที่ประกาศ**
(`LINE_SLACK`) ซึ่งทำให้วันที่มีคนย้ายเนื้อออก เพดานถูกลดตามทันที (เกิดขึ้นจริง
ในรอบ 11) · ใบนี้แค่เอากลไกเดียวกันไปใช้กับ ratchet ตัวอื่นที่ยังไม่มี

## คำตัดสิน

1. **พื้นของ ratchet ต้องไม่ห่างจากของจริงเกิน 1 จุด** — `scripts/check_ratchets.py`
   รันในjob `test` หลัง coverage เสร็จ · อ่านพื้นจาก `pyproject.toml` **จริง**
   และวัดของจริงด้วยการรันเครื่องมือเอง ไม่ใช่อ่านคอมเมนต์ที่เขียนกำกับไว้
   (คอมเมนต์นั้นคือสิ่งที่ audit รอบนี้กำลังตรวจสอบพอดี)
2. **ระยะเป็น 1 จุด ไม่ใช่ 0** — กว้างพอให้ความผันผวนปกติผ่าน (บรรทัดที่
   `# pragma: no cover` ครอบเพิ่ม/ลดหนึ่งจุด) แต่แคบพอที่การปรับปรุงจริงจะถูกเก็บไว้
   · เกณฑ์ที่ต้องขยับทุกครั้งที่ตัวเลขขยับ คือเกณฑ์ที่คนจะเลิกอ่านภายในสัปดาห์เดียว
3. **ทิศเดียว ไม่ใช่สองทิศ** — พื้นที่ *สูงกว่า* ของจริงเป็นเรื่องของด่านหลัก
   (`fail_under` เองแดงอยู่แล้ว) และข้อความที่บอกว่าต้องทำอะไรต่อก็คนละอย่าง ·
   รวมสองทิศเข้าด้วยกันเมื่อไหร่ คนอ่านจะได้คำแนะนำที่ผิดครึ่งหนึ่งของเวลา
4. **ขยับพื้นในคอมมิตเดียวกับที่ทำให้ตัวเลขดีขึ้น** — ใบนี้ขยับ coverage 96 → 97
   และ `interrogate` 84 → 85 พร้อมกับติดตั้งตัวทวง เพื่อไม่ให้ที่ว่างที่มีอยู่แล้ว
   ถูกยกไปเป็นมรดกของกติกาใหม่

## ทางที่ไม่ได้เลือก

- **ให้เครื่องขยับพื้นเองอัตโนมัติทุกครั้งที่วัดได้สูงขึ้น** — พื้นที่ขยับเองจะ
  ผูกกับความผันผวนของการรัน และวันที่มันขยับผิด จะไม่มี commit ไหนอธิบายได้ว่า
  ทำไม · ratchet ที่หมุนเองคือ ratchet ที่ไม่มีใครตัดสินใจ (เหตุผลเดียวกับที่
  `UNPROVEN_CEILING` ต้องถูกลดด้วยมือพร้อมหลักฐาน)
- **ตั้งระยะเป็น 0** — ทุกการรันที่ขยับเศษจุดจะทำให้ CI แดงด้วยเรื่องที่ไม่ใช่
  ของเสีย ซึ่งสอนให้คนกด rerun โดยไม่อ่าน (บทเรียนเดียวกับ [ADR 0067](0067-every-job-declares-a-time-budget.md))
- **เอา `diff-cover` มาแทน** — มันคุมบรรทัดที่แก้ ไม่ได้คุมยอดรวม · สองอย่างนี้
  ทำงานคู่กัน: ตัวหนึ่งทำให้ตัวเลขไต่ขึ้น อีกตัวเก็บกำไรไว้

## เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ

- **วันที่พื้นชนเพดานธรรมชาติของมัน** (coverage ที่เหลือเป็นบรรทัดที่ไม่ควรมีเทสต์)
  — ตอนนั้นการไล่ตามของจริงจะเริ่มซื้อเทสต์ที่ทดสอบ mock แทนพฤติกรรม
  ซึ่ง `docs/DEVELOPMENT.md` ปฏิเสธไว้ตั้งแต่ต้น · สัญญาณคือ PR ที่ต้องเพิ่ม
  `# pragma: no cover` เพื่อผ่านด่านนี้ **มากกว่าหนึ่งใบต่อไตรมาส**
- วันที่มีเกณฑ์ตัวที่สี่ที่วัดหน่วยอื่น (เช่น เวลา) — ระยะ 1 "จุด" จะไม่มีความหมาย
  และต้องแยกระยะต่อเกณฑ์แทนค่าคงที่เดียว

## ผลที่ตามมา

- **ต้นทุน**: PR ที่ทำให้ coverage ดีขึ้นเกิน 1 จุดต้องขยับพื้นด้วย — หนึ่งบรรทัด
  ใน `pyproject.toml` พร้อมเหตุผลใน PR เดียวกัน
- **นอกขอบเขตโดยตั้งใจ** (ไม่ใช่ของที่เลื่อนไว้ — จึงไม่เข้าทะเบียนของที่จงใจเลื่อน):
  เกณฑ์ที่หลวมโดยตั้งใจ (perf-smoke 2× เป้า — ADR 0056 ·
  `timeout-minutes` 10× — ADR 0067) **ไม่ได้ถูกคุมด้วยกลไกนี้** เพราะระยะห่างของ
  มันคือคำตัดสิน ไม่ใช่ความบังเอิญ · ทั้งคู่มี ADR รองรับอยู่แล้ว และการเอา
  ตัวทวงไปครอบจะเปลี่ยนความหมายของมันจาก "ตั้งใจหลวม" เป็น "ยังไม่ได้ขัน"
