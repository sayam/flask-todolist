# 0026 — DB backend เป็น plugin ชนิด `db`: เลือกยี่ห้อได้โดยไม่มีทางตัน

สถานะ: accepted (2026-08-07) — Phase 5 ด่านแรก

**บริบท:** `docs/STANDARDS.md` ข้อ 4 ตัดสินไว้แล้วว่าระบบต้องรองรับฐานข้อมูล
หลายยี่ห้อ และ DoD ของ Phase 5 คือเทสต์เขียวทั้ง SQLite, MySQL 8+ และ MariaDB 11+
วันนี้ยี่ห้อถูกกำหนดด้วย `SQLALCHEMY_DATABASE_URI` เส้นเดียวใน `config.py`
ส่วนความต่างระดับ connection อยู่ใน `app/db_engine.py` ซึ่งเช็ค dialect ด้วย
`isinstance` — พอเพียงสำหรับยี่ห้อเดียว แต่ไม่มีที่ให้ยี่ห้อที่สองลง

Phase 4.5 เพิ่งวางเครื่องมือที่จำเป็นครบพอดี (ADR 0025): ไลบรารีของจุด plug อยู่ใน
pipenv category ของตัวเอง, ไม่มีไลบรารี = ปิดตัวเองไม่ใช่พัง, และมีสวิตช์ปิดตอน
runtime **คำถามที่ต้องตัดสินก่อนเขียนโค้ดคือ DB backend ต่างจาก theme กับ auth
factor ตรงไหน** เพราะกติกาที่ใช้ซ้ำได้ คือกติกาที่จะถูกใช้ผิด

## คำตัดสิน

### 1. `db` เป็น plugin ชนิดหนึ่งบน registry เดิม แต่เป็นชนิดที่ **ต้องมีหนึ่งตัวเสมอ**

ใช้ registry เดิมเพราะได้สิ่งที่ต้องการมาฟรีทั้งหมด: driver ของแต่ละยี่ห้อเข้า
category ของตัวเอง (`db/mysql` → `plugin-db-mysql` → `pymysql`) ซึ่งแปลว่า
**คนที่รัน SQLite ไม่ต้องติดตั้ง driver ของ MySQL และไม่ต้องเฝ้า CVE ของมัน**
นี่คือข้อได้เปรียบเดียวกับที่ ADR 0025 ทำไว้แล้ว ไม่ใช่กลไกใหม่ และการเพิ่มชนิด
ใหม่ไม่ต้องแก้ core เลย (`types()` อ่านจากไดเรกทอรีที่มีอยู่จริง)

แต่ต้องเขียนให้ชัดว่าชนิดนี้**ต่างจากชนิดอื่นสามข้อ**:

| | theme / auth | `db` |
|---|---|---|
| ถอดตัวสุดท้ายออก | ตกกลับไปเป็น "ไม่มีความสามารถนั้น" | **ไม่มี DB = ไม่มีระบบ** |
| จำนวนที่ active พร้อมกัน | กี่ตัวก็ได้ | **หนึ่งตัวเท่านั้น** |
| การสลับตัว | คือการ plug | **คือการย้ายข้อมูล** |

### 2. เลือกด้วย config ไม่ใช่ด้วยการค้นหา และผิดแล้วต้องไม่ start

`DATABASE_URL` ยังเป็นแหล่งความจริงเดียวเหมือนเดิม — **scheme ของ URL คือตัวบอก
ว่าใช้ backend ตัวไหน** (`sqlite://` → `db/sqlite`, `mysql+pymysql://` → `db/mysql`)
ไม่เพิ่ม config ตัวที่สองให้มีโอกาสขัดกันเอง (หลักเดียวกับ `category_of()` ที่
คำนวณจากคีย์แทนที่จะให้ manifest ประกาศซ้ำ)

scheme ที่ไม่ตรงกับ backend ตัวไหนบนดิสก์เลย → **แอปไม่ start** พร้อมบอกว่ามี
อะไรให้เลือกบ้าง **ห้ามตกกลับไป SQLite เงียบ ๆ** เพราะการตกกลับเงียบ ๆ แปลว่า
prod ที่ตั้ง config ผิดจะเขียนลงไฟล์ SQLite เปล่าและ "ทำงานได้" จนถึงวันที่มีคน
ถามว่าข้อมูลหายไปไหน

### 3. migration เป็นของ core **ไม่ใช่ของ backend**

ข้อนี้ตรงข้ามกับ ADR 0023 (plugin ดูแลตารางของตัวเอง) โดยตั้งใจ เพราะโจทย์
คนละข้อกัน:

* **schema ที่เหมือนกันทุกยี่ห้อคือข้อกำหนด ไม่ใช่ผลพลอยได้** ถ้าแต่ละ backend
  ถือ migration ของตัวเอง schema จะแตกเป็นสามสายภายในรีลีสเดียว แล้วคำว่า
  "ย้ายยี่ห้อได้" จะไม่จริงตั้งแต่วันที่สอง
* alembic รองรับความต่างของ dialect ในสายเดียวอยู่แล้ว (`context.dialect.name`)
  ความต่างที่มีจริงคือรายจุด ไม่ใช่ทั้งสาย
* ตารางของ core เป็นของ core — backend ไม่ได้เป็นเจ้าของข้อมูล มันเป็นเจ้าของ
  **ทาง**ที่ข้อมูลวิ่งผ่าน

ดังนั้น **plugin ชนิด `db` ห้ามมี `models.py`** และ `owned_tables()` ต้องไม่คืน
อะไรให้มัน (เหตุผลเดียวกับที่ส่วนเสริมห้ามมี `models.py` ใน ADR 0025:
ถ้ามีข้อมูลของตัวเอง การสลับจะกลายเป็นการย้ายข้อมูล ไม่ใช่การ plug)

สิ่งที่ backend เป็นเจ้าของคือ: การประกอบ URL, driver, engine option และ quirk
ระดับ connection — เช่น `PRAGMA foreign_keys=ON` ที่วันนี้อยู่ใน `db_engine.py`
ของ core ควรย้ายไปเป็นของ `db/sqlite` เพราะมันเป็นเรื่องของยี่ห้อนั้นล้วน ๆ

### 4. ห้ามถอนหรือปิด backend ที่ active

* `DISABLED_PLUGINS` ที่ชี้ไป backend ที่ `DATABASE_URL` กำลังใช้ → **แอปไม่ start**
  พร้อมข้อความที่บอกว่าเพราะอะไร (หลักเดียวกับ "ปิด plugin ของ core ไม่ได้")
* `flask plugin-uninstall` กับ plugin ชนิด `db` → **ปฏิเสธตั้งแต่ต้น** ไม่ใช่ทำ
  แล้วค่อยพัง — และมันไม่มีตารางของตัวเองให้ drop อยู่แล้วตามข้อ 3

เหตุผล: สวิตช์ปิดของ ADR 0025 มีไว้ตอบ CVE ที่ออกตอนบ่ายสาม โดยตั้งอยู่บนสมมติฐาน
ว่า "ปิดแล้วระบบยังเดินได้" ซึ่งใช้กับ backend ที่ใช้อยู่ไม่ได้ **คำตอบของ CVE
ใน driver ของ DB ที่ active คือการอัปเกรดหรือย้ายยี่ห้อ ซึ่งเป็นงานที่มีขั้นตอน
ไม่ใช่สวิตช์** การปล่อยให้ปิดได้คือการเสนอปุ่มที่กดแล้วระบบดับ

### 5. ทุก backend ต้องมี export path — ไม่มี = ไม่รับเข้า

สัญญาขั้นต่ำของชนิด `db`: ต้องมีทางส่งข้อมูลออกมาในรูปที่ backend **ตัวอื่น**
รับกลับเข้าไปได้ (`flask db-export` / `flask db-import`) ไม่ใช่ dump เฉพาะยี่ห้อ
ที่มีแต่ตัวเองอ่านออก

เหตุผล: **"ไม่มี lock-in" ที่ไม่มีใครเคยทดสอบ คือคำโฆษณา ไม่ใช่คุณสมบัติ**
หลักเดียวกับ job `bare` ของ Phase 4.5 ที่ทำให้ "ถอดแล้วไม่พัง" เป็นสิ่งที่วัดได้
ทุก push แทนที่จะเป็นความตั้งใจในเอกสาร

DoD: CI ต้องทำ round trip อย่างน้อยหนึ่งคู่ (`sqlite → mysql → sqlite`) แล้ว
เทียบว่าข้อมูลเท่าเดิม **รวมถึงสาย hash ของ audit ที่ต้อง verify ผ่านหลังย้าย**
(ถ้าสายขาดตอนย้าย แปลว่า export ทำลายของที่มันอ้างว่าเก็บมาครบ)

### 6. exit path ต้องเขียนก่อนผูกมัด managed service

ก่อนผูกกับ RDS / Cloud SQL / บริการจัดการอื่นใด ต้องตอบสามข้อลงเอกสารก่อน:
ข้อมูลออกมาได้อย่างไร, ใช้เวลานานเท่าไรที่ขนาดจริง, และอะไรที่จะหายไปเมื่อออก
(ความสามารถที่มีเฉพาะเจ้านั้น) — ข้อที่สามคือข้อที่มักถูกลืมจนกลายเป็นเหตุผล
ที่ย้ายไม่ได้จริง ๆ ทั้งที่ข้อมูลออกมาได้

## ขอบเขตที่ ADR นี้ **ไม่** ครอบคลุม

* **ไม่ใช่ abstraction ใหม่เหนือ SQLAlchemy** — ยังใช้ SQLAlchemy ตัวเดียว
  ตรง ๆ เหมือนเดิม สิ่งที่ plugin ห่อคือการต่อและค่าเฉพาะยี่ห้อ ไม่ใช่การ query
* **ไม่ได้แปลว่าประสิทธิภาพเท่ากันทุกยี่ห้อ** — เท่ากันแค่ *พฤติกรรม* ส่วนตัวเลข
  เป็นเรื่องของ Phase 6
* **ไม่รองรับการต่อหลายฐานพร้อมกัน** (read replica, sharding) — คนละโจทย์
  และไม่ได้อยู่ในแผนเฟสนี้
* **ไม่มี online migration ระหว่างยี่ห้อ** — การย้ายมี downtime ตามขั้นตอนใน
  `docs/OPERATIONS.md` ไม่ใช่สิ่งที่กดปุ่มแล้วเกิด

## ผลที่ตามมา

* `app/db_engine.py` ของ core จะบางลงเหลือแค่การเรียก hook ของ backend ที่ active
  ส่วน pragma ของ SQLite ย้ายไปอยู่กับ `db/sqlite`
* CI ต้องมี matrix สามยี่ห้อ (P5-04) ซึ่งใช้ service container ของ GitHub Actions
  ไม่ต้องมี container runtime บนเครื่อง dev
* `Pipfile` จะมี category `plugin-db-mysql` / `plugin-db-mariadb` และ
  `pipenv sync --dev` **จะไม่ติดตั้ง driver ให้** ตามหลักของ ADR 0025 —
  คนที่ dev ด้วย MySQL ต้องรัน `flask plugin-deps` แล้ว sync category นั้นเอง
* **job `bare` ยังต้องเขียวเหมือนเดิม** ซึ่งแปลว่าชุดเทสต์ต้องรันจบได้บน SQLite
  เพราะเป็น backend เดียวที่ไม่ต้องติดตั้ง driver เพิ่ม — ข้อจำกัดนี้ดีต่อโครงการ
  เพราะบังคับให้เทสต์ไม่ผูกกับยี่ห้อโดยไม่ตั้งใจ
* เอกสาร `docs/DATA-CLASSIFICATION.md` ต้องครอบไฟล์ที่ `db-export` สร้างด้วย —
  มันคือข้อมูลทั้งระบบในไฟล์เดียว ชั้นสูงสุดเท่าที่มีอยู่ในนั้น

## ทางเลือกที่ไม่เลือก

* **ปล่อยให้ `DATABASE_URL` ทำงานเองตามเดิม แล้วแค่เพิ่ม driver ลง `[packages]`**
  — ได้ MySQL จริง แต่ไม่ได้อะไรที่เหลือเลย: driver ของทุกยี่ห้อถูกติดตั้งให้ทุกคน
  ตลอดไป, quirk กระจายอยู่ใน `db_engine.py` ก้อนเดียวที่โตขึ้นเรื่อย ๆ,
  และไม่มีที่ให้ยี่ห้อที่สี่ลงโดยไม่แก้ core
* **ให้แต่ละ backend ถือ migration ของตัวเอง** — ดูข้อ 3 ได้ความอิสระที่ไม่มีใคร
  ขอ แลกกับ schema ที่แตกเป็นสามสายและคำสัญญาเรื่องการย้ายยี่ห้อที่เป็นโมฆะ
* **เขียน data access layer ของตัวเองเพื่อรองรับหลายยี่ห้อ** — คือการเขียน ORM
  ที่แย่กว่า SQLAlchemy เพื่อทำสิ่งที่ SQLAlchemy ทำอยู่แล้ว
* **รองรับยี่ห้อเดียวแล้วบอกว่าพอ** — ขัดกับ STANDARDS ข้อ 4 ที่ตัดสินไปแล้ว
  และต้นทุนของการเปลี่ยนใจทีหลังคือการรื้อ ไม่ใช่การเพิ่ม
