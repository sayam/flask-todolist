# 0016 — service layer: ตรรกะไม่รู้จัก HTTP และ route เป็นแค่ adapter

สถานะ: accepted (2026-08-03) — Phase 3 ด่านแรก

**บริบท:** Phase 3 ต้องประกาศ `/api/v1` ที่ freeze สัญญาได้จริง ก่อนหน้านี้
ตรรกะทั้งหมดอยู่ใน `app/routes.py` (421 บรรทัด, 20 view) และหยิบค่าจาก
`request.form` / `current_user` ตรง ๆ ในฟังก์ชันเดียวกับที่ตัดสินใจว่า
"ชื่อว่างได้ไหม" หรือ "หมวดนี้เป็นของใคร"

ถ้าปล่อยไว้แบบนั้นแล้วเพิ่ม API เข้าไป มีทางเลือกอยู่สองทางเท่านั้น และ
**แย่ทั้งคู่**: (ก) ให้ API เรียก view ของ HTML ซึ่งต้องปลอม form ขึ้นมา
หรือ (ข) ก๊อปตรรกะไปเขียนใหม่ในฝั่ง API ซึ่งแปลว่าบั๊กทุกตัวต้องแก้สองที่
ตลอดอายุโปรเจกต์ และวันหนึ่งจะแก้ไม่ครบ

## คำตัดสิน

**แยก `app/services/` ออกมาเป็นชั้นที่ไม่รู้จัก HTTP เลย** แล้วให้ทั้ง
route ของ HTML และ view ของ API เป็น adapter บาง ๆ ที่เรียก service ชุดเดียวกัน

กติกาที่บังคับด้วยเทสต์ (`tests/test_service_layer.py`):

1. ไฟล์ใน `app/services/` **ห้าม import** `request`, `session`, `g`, `flash`,
   `abort`, `redirect`, `render_template`, `url_for`, `jsonify`,
   `make_response`, ทั้งโมดูล `flask`, `flask_login`, และ `app.routes`/`app.api`
   (`current_app` **อนุญาต** — ผูกกับแอป ไม่ใช่กับ request จึงอ่าน config ได้)
2. ต้องเรียกได้จริงใน app context เปล่า ๆ — มีเทสต์ที่รันทั้งเส้น
   (สร้างหมวด → สร้างงาน → กรอง → ติ๊กเสร็จ → เคลียร์) โดยไม่มี request เลย

ตัวสแกน import เป็นด่านที่ถูก ส่วนเทสต์ที่รันจริงเป็นด่านที่พิสูจน์ — ต้องมีทั้งคู่
เพราะการเลี่ยงตัวสแกนทำได้ง่าย ๆ ด้วยการ import ทางอ้อม

### สิ่งที่ยังเป็นของ adapter โดยตั้งใจ

* **`session`** — การจำว่าให้โชว์วันเริ่มไหม, และค่าภาษา/ธีมที่ชนะโปรไฟล์
  ในลำดับการเลือก (ดู `app/i18n.py`) เป็นเรื่องของเบราว์เซอร์ตัวนั้น ไม่ใช่ของโดเมน
* **การเลือก status code / template / envelope** และการตัดสินใจว่าจะ `flash`
  หรือจะคืน JSON error
* **การย่อยข้อความจาก input** (`"2026-09-01T16:00"` → `datetime`) — service
  รับ `datetime` ที่ย่อยแล้ว ไม่ใช่สตริงดิบ

### ความล้มเหลวสื่อสารด้วย exception ไม่ใช่ `abort()`

`app/services/errors.py` มี 3 ชนิดตาม "ผู้เรียกต้องทำอะไรต่อ":
`NotFoundError` (ไม่มีหรือไม่ใช่ของคนที่ขอ — ตอบเหมือนกันตาม ADR 0004),
`ValidationError`, `ConflictError` แต่ละตัวมี `code` ภาษาเครื่องแยกจาก
`message` ภาษาคน — `message` เปลี่ยนถ้อยคำ/ภาษาได้ตลอด ส่วน `code` เป็น
ส่วนหนึ่งของสัญญา API v1 (ADR 0017)

### service คุมทรานแซกชันของตัวเอง

แต่ละฟังก์ชัน `commit()` เอง ผู้เรียกไม่ต้องรู้เรื่อง session — ทางเลือกอื่นคือ
ให้ adapter เป็นคน commit ซึ่งแปลว่าคนเขียน view ใหม่ลืม commit ได้ และ
"ลืม commit" คือบั๊กที่เงียบที่สุดชนิดหนึ่ง (ทำงานถูกทุกอย่าง แต่ข้อมูลไม่ถูกเขียน)

## ผลที่ตามมา

* `app/routes.py` เหลือ ~270 บรรทัดที่อ่านแล้วเห็นแค่ "อ่าน request → เรียก
  service → เลือกคำตอบ" และ `index()` ไม่มี branch ของตัวกรองอีกต่อไป
  (ratchet: `max-complexity` ของ ruff ลดจาก 12 → 10 ได้)
* ตัวกรองกลายเป็น `FilterSpec` ที่ normalise แล้วชุดเดียว — ฟอร์ม HTML กับ
  query string ของ API แปลงเข้าโครงเดียวกัน ปิดหนี้ `apply_when()` ที่เคยรับ
  7 อาร์กิวเมนต์ (มี `noqa: PLR0913` คาไว้ตั้งแต่ Phase 0 พร้อมโน้ตว่า "Phase 3 จะยุบ")
* query ในโค้ดแอปเลิกใช้ `Model.query` แบบเก่า เป็น `select()` ของ
  SQLAlchemy 2.0 ทั้งหมด (ตัวกรอง soft delete ยังถูกเติมให้เองทั้งสองแบบ —
  ทดสอบแล้วรวมถึง `func.count()`)
* **audit ไม่ต้องแก้อะไรเลย** เพราะดักที่ event ของ ORM ไม่ได้ดักที่ route
  (นี่คือผลตอบแทนของการตัดสินใจใน ADR 0015 ที่จ่ายไปแล้วใน Phase 2)
* ราคาที่จ่าย: การแก้ฟีเจอร์หนึ่งอาจต้องแตะสองไฟล์ (service + adapter)
  ยอมรับได้เมื่อเทียบกับการมีตรรกะสองชุดที่ต้องแก้ให้ตรงกันตลอดไป

## ทางเลือกที่ไม่เลือก

* **ให้ API เรียก view ของ HTML แล้วแปลงคำตอบ** — ต้องปลอม form/session
  และคำตอบที่ได้เป็น HTML ที่ต้องมาย่อยกลับ เปราะและช้ากว่าทุกทาง
* **repository pattern เต็มรูปแบบ (service + repository แยกชั้น)** — ชั้น
  repository มีค่าเมื่อจะสลับ storage engine ซึ่งแผนข้อ 4.1 ของ ROADMAP ระบุ
  ชัดว่าจะอยู่กับ relational + SQLAlchemy ต่อไป การเพิ่มชั้นตอนนี้คือค่าใช้จ่าย
  ที่ไม่มีผู้ซื้อ
* **ยกตรรกะไปไว้ใน model (fat model)** — งานอย่าง "ตรวจว่าหมวดเป็นของ user
  คนนี้ไหม" กินหลาย model และต้องคุม transaction ซึ่งไม่ใช่หน้าที่ของแถวข้อมูล
