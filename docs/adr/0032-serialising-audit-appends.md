# 0032 — ต่อสาย audit ให้เป็นลำดับจริง เมื่อมีหลาย process เขียนพร้อมกัน

สถานะ: accepted (2026-08-11) — Phase 6 · แก้หนี้ที่ ADR 0015 บันทึกไว้เอง ·
**ข้อ 1 ถูกแทนที่โดย [ADR 0035](0035-audit-appends-queue-on-one-row.md)**
(2026-08-12) — กลไกที่ใบนี้เลือก (`ORDER BY id DESC LIMIT 1 FOR UPDATE` บน
`tdl_audit`) **ห้ามกลับไปใช้** ส่วนคำตัดสินข้ออื่นของใบนี้ยังใช้อยู่

**บริบท:** ADR 0015 บังคับ `prev_hash` ให้ unique เพื่อไม่ให้สาย audit แตกเป็น
สองสายได้เลยในระดับฐานข้อมูล และเขียนผลข้างเคียงไว้ตรง ๆ ว่า:

> ถ้ามีสอง process เขียนพร้อมกันจริง ๆ ตัวหลังจะได้ IntegrityError แล้ว
> transaction ตกไป — **ตั้งใจให้ดังกว่าการมี chain ที่ล้มเหลวอย่างเงียบ ๆ**
> (scale ตอนนี้เป็น SQLite ที่ serialize การเขียนอยู่แล้ว **ถ้าวันหนึ่งต้อง
> เขียนขนานจริงต้องเปลี่ยนไปใช้ sequence/batch**)

**"วันหนึ่ง" มาถึงแล้ว**: Phase 5 ทำให้ ≥2 replica เป็นของจริง และ load test
ของ Phase 6 วัดราคาออกมาเป็นตัวเลข — ที่ 2 replica คำขอเขียน (`POST /add`)
ล้มด้วย 500 ราว **0.36% ที่โหลดเป้าหมาย และ 9.5% ที่โหลดสูง**
(`Duplicate entry ... for key 'tdl_audit.uq_audit_prev_hash'` 225 ครั้งในรอบเดียว)

**ข้อที่ต้องพูดให้ชัด**: ด่านของ Phase 5 ที่ "พิสูจน์ว่า 2 replica ใช้ได้"
ทดสอบแค่การอ่านกับ login — **ไม่เคยมีใครเขียนพร้อมกันจริง** ด่านที่เขียวจึงไม่ได้
ครอบชั้นที่เกิดปัญหาจริงอีกครั้งหนึ่ง

## คำตัดสิน

### 1. **ล็อกแถวท้ายสายก่อนอ่านค่าไปต่อ** ไม่ใช่ลองใหม่เมื่อชน

`_last_hash()` อ่านแถวสุดท้ายด้วย `SELECT ... ORDER BY id DESC LIMIT 1`
เปลี่ยนเป็น `... FOR UPDATE` — ผู้เขียนรายที่สองจะ **รอ** ที่บรรทัดนั้นจนราย
แรก commit แล้วค่อยอ่านค่าที่ถูกต้องไปต่อ

**ทำไมไม่ใช่ retry**: การลองใหม่ต้องย้อน *ทั้ง transaction* เพราะ `prev_hash`
ถูกคำนวณใน `after_flush` หลังงานจริงถูกเขียนไปแล้ว การเขียน retry ที่ถูกต้อง
จึงต้องไปแตะทุกจุดที่เรียก `commit()` — ซึ่งคือทุก service ในระบบ · และ retry
ยังแปลว่า **งานของผู้ใช้ถูกทำซ้ำ** ซึ่งต้องพิสูจน์ว่าทุกเส้นทาง idempotent
ก่อน ล็อกทำให้ปัญหาอยู่ในไฟล์เดียวและไม่ต้องพิสูจน์อะไรเพิ่ม

### 2. **ยอมให้การเขียนเป็นคอขวดโดยรู้ตัว**

ผลที่ตามมาตรง ๆ: การเขียนที่ต้องลง audit **serialize กันทั้งระบบ** ไม่ว่าจะมี
กี่ replica · นี่ไม่ใช่ผลข้างเคียงที่ยอมรับอย่างเสียไม่ได้ แต่เป็น**สิ่งที่สาย
hash ต้องการโดยนิยาม**: สายที่มีลำดับเดียวจะสร้างขนานกันไม่ได้อยู่แล้ว
การมี unique constraint แค่ทำให้ข้อเท็จจริงนั้นดังขึ้น

ตัวเลขจาก Phase 6 บอกว่าคอขวดจริงของระบบตอนนี้อยู่ที่จำนวน process ที่รับงาน
ได้พร้อมกัน (~57–70 req/s) ซึ่งอยู่ห่างจากอัตราการ *เขียน* จริงมาก — การ
serialize การเขียนจึงยังไม่ใช่ขอบที่เราจะชนในเร็ววัน **แต่ต้องวัดซ้ำถ้าวันหนึ่ง
สัดส่วนการเขียนสูงขึ้น** และรายงานใน `docs/PERFORMANCE.md` ต้องอัปเดตตาม

### 3. **SQLite ไม่ต้องทำอะไรเพิ่ม และนั่นถูกต้องแล้ว**

SQLAlchemy ตัด `FOR UPDATE` ทิ้งให้เองบน SQLite (dialect ไม่รองรับ) ซึ่งไม่ใช่
ช่องโหว่ที่ถูกมองข้าม — SQLite ล็อกทั้งไฟล์ตอนเขียนอยู่แล้ว การเขียนจึงเป็น
ลำดับโดยธรรมชาติ · **ตรวจด้วยการ compile จริงทั้งสามยี่ห้อ ไม่ใช่เชื่อเอกสาร**

### 4. **แถวแรกของตารางยังชนกันได้ และปล่อยไว้อย่างรู้ตัว**

ตอนตารางว่าง ไม่มีแถวให้ล็อก (InnoDB จับ gap lock ให้ในโหมด REPEATABLE READ
ซึ่งช่วยได้ แต่ไม่รับประกันข้ามยี่ห้อ) — สองผู้เขียนรายแรกสุดของระบบที่ยิงพร้อม
กันเป๊ะจึงยังชนกันได้หนึ่งครั้ง แล้วรายหลังได้ 500

**ยอมรับเพราะราคาต่างกันมาก**: เหตุการณ์นี้เกิดได้ครั้งเดียวตลอดอายุระบบ
(หลังจากนั้นมีแถวให้ล็อกเสมอ) และเกิดตอนที่ยังไม่มีใครใช้งานจริง ส่วนการ
ไล่แก้ให้ครบต้องเพิ่มตารางล็อกหรือ sequence ซึ่งเป็นโครงสร้างถาวรที่ต้องดูแล
ตลอดไปเพื่อกันเหตุการณ์ที่เกิดครั้งเดียว

## ผลที่ตามมา

- **ต้องมีเทสต์ที่เขียนขนานจริง** ไม่ใช่เทสต์ที่เรียกฟังก์ชันสองครั้งติดกัน —
  ด่านของ Phase 5 พลาดเพราะทดสอบแค่การอ่าน บทเรียนนั้นต้องกลายเป็นเทสต์
- `docs/PERFORMANCE.md` ต้องวัดซ้ำหลังแก้ เพื่อยืนยันว่าอัตราล้มเหลวหายไปจริง
  ไม่ใช่แค่เชื่อว่าแก้แล้ว
- **การล็อกเปลี่ยนชนิดของความล้มเหลว ไม่ได้ทำให้เป็นศูนย์**: การวัดซ้ำหลังแก้
  พบ deadlock ของ MySQL (error 1213) 2 ครั้งต่อรอบ จากเดิมที่ชน unique
  constraint 225 ครั้งต่อรอบ · deadlock **ลองใหม่ได้ตามนิยาม** (ฐานข้อมูล
  ยกเลิกฝ่ายหนึ่งให้เอง ไม่ใช่สถานะที่ล้มเหลวถาวร) ต่างจากการชน `prev_hash` ที่
  ลองใหม่ไม่ได้ถ้าไม่ย้อนทั้ง transaction — **การเพิ่ม retry สำหรับ 1213
  จึงเป็นงานถัดไปที่สมเหตุสมผล และตอนนี้ทำได้โดยไม่ต้องแตะ service ทุกตัว**
- **ยังไม่ทำ**: retry เมื่อ deadlock, เขียน audit เป็น batch, sequence ของ
  ฐานข้อมูล, หรือแยกสายตามผู้ใช้ (ซึ่งจะทำให้ verify ซับซ้อนขึ้นมากและยังไม่มี
  อะไรเรียกร้อง)
