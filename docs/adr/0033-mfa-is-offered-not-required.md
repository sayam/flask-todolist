# 0033 — ไม่บังคับปัจจัยที่สอง และเหตุผลที่ต้องเขียนไว้

สถานะ: accepted (2026-08-11) — Phase 7 · อนุมัติโดยเจ้าของโปรเจกต์

**บริบท:** [ASVS 5.0](../ASVS.md) ข้อ V6.3.3 กำหนดว่าการเข้าถึงแอปต้องใช้
ปัจจัยยืนยันตัวมากกว่าหนึ่ง และเขียนทางออกไว้ในข้อเดียวกันว่า *"การผ่อนข้อ
พิจารณาใด ๆ ในข้อนี้ต้องมีเหตุผลที่บันทึกไว้อย่างครบถ้วน และชุดมาตรการชดเชย
ที่ครอบคลุม"*

ระบบนี้มีปัจจัยที่สองให้ใช้แล้วตั้งแต่ [ADR 0024](0024-mfa-as-an-auth-plugin.md)
แต่**ไม่ได้บังคับ** — ตอนที่ประเมิน ASVS ครั้งแรกจึงตอบว่า "ยังไม่ผ่าน" เพราะ
ไม่มีทั้งการบังคับและเหตุผล ADR นี้เติมส่วนที่ขาด

## คำตัดสิน

### 1. **ไม่บังคับ** — และนี่คือเหตุผล ไม่ใช่ข้ออ้าง

**ก. ขนาดและรูปแบบการใช้งานจริง** ระบบนี้เป็นของส่วนตัว/ครอบครัว ผู้ใช้ราว
1–5 คน ([ADR 0031](0031-performance-targets-and-what-they-mean.md) ใช้ตัวเลข
เดียวกันเป็นเป้าประสิทธิภาพ) ทุกบัญชีถูกสร้างด้วยมือโดยผู้ดูแลที่รู้จักเจ้าของ
บัญชีเป็นการส่วนตัว **ไม่มีหน้าสมัครสมาชิก** จึงไม่มีบัญชีที่ไม่มีใครรู้จัก
และไม่มีการเปิดรับผู้ใช้จากอินเทอร์เน็ต

**ข. ราคาที่ผู้ใช้จ่ายจริงเมื่อบังคับ** ตอนนี้**ยังไม่มี recovery code**
(บันทึกไว้ใน CLAUDE.md ว่าเป็นงานที่เหลืออยู่จริง) การบังคับ MFA ในสภาพนี้แปลว่า
ทำโทรศัพท์หายเมื่อไหร่ = เข้าไม่ได้จนกว่าจะติดต่อผู้ดูแลได้ · สำหรับระบบที่
ผู้ดูแลคือคนในบ้านคนเดียวกัน นั่นแปลว่าวันที่ทั้งบ้านทำโทรศัพท์หายพร้อมกัน
หรือผู้ดูแลไม่อยู่ ข้อมูลจะเข้าถึงไม่ได้เลย **ซึ่งเป็นความเสียหายที่มีโอกาส
เกิดสูงกว่าการถูกเดารหัสผ่านสำเร็จ** ในสภาพที่มีมาตรการข้อ 2 อยู่

**ค. การบังคับโดยไม่มีทางกู้คืนไม่ใช่การเพิ่มความปลอดภัย** แต่คือการย้าย
ความเสี่ยงจาก "ถูกคนอื่นเข้าถึง" ไปเป็น "เจ้าของเข้าถึงไม่ได้" ซึ่งเป็น
ความล้มเหลวของระบบเหมือนกัน

### 3. **เงื่อนไขที่ทำให้คำตัดสินนี้หมดอายุ** — เขียนไว้เพื่อให้มีคนกลับมาอ่าน

ต้องกลับมาทบทวนทันทีเมื่อเกิดข้อใดข้อหนึ่ง ไม่ต้องรอรอบทบทวนประจำปี:

1. **มีหน้าสมัครสมาชิก** หรือเปิดให้คนนอกสร้างบัญชีเองได้
2. **ผู้ใช้เกิน ~10 คน** หรือมีผู้ใช้ที่ผู้ดูแลไม่รู้จักเป็นการส่วนตัว
3. **มี recovery code แล้ว** — ข้อ 1.ข หมดน้ำหนักทันที และควรพิจารณาบังคับ
   อย่างน้อยกับบัญชี `admin`
4. ระบบเริ่มเก็บข้อมูลชั้นที่อ่อนไหวกว่าที่
   [DATA-CLASSIFICATION.md](../DATA-CLASSIFICATION.md) จำแนกไว้ตอนนี้
5. เห็นความพยายาม login ที่ล้มเหลวผิดปกติใน audit หรือใน SIEM

## ผลที่ตามมา

- ASVS V6.3.3 ตอบว่า **ผ่านผ่านทางเหตุผลที่บันทึกไว้** ไม่ใช่ผ่านเพราะบังคับ MFA
  — ช่องหลักฐานในตารางต้องพูดให้ชัดแบบนั้น ไม่ใช่ชี้มา ADR นี้เฉย ๆ แล้วปล่อย
  ให้คนอ่านเข้าใจว่าเราบังคับอยู่
- **การมี recovery code กลายเป็นงานที่มีเหตุผลชัดขึ้น** ไม่ใช่ของสวยงามที่ค้างอยู่
  เพราะมันคือสิ่งที่ปลดล็อกการบังคับ MFA
- เงื่อนไขหมดอายุข้างบนถูกทบทวนตามรอบใน
  [SECURITY-CADENCE.md](../SECURITY-CADENCE.md) ซึ่งมีเทสต์คุมว่าไม่เลยกำหนด

---

**โน้ต (2026-08-17 — audit governance รอบ 5)**: มาตรการชดเชยข้อที่พึ่ง
"ผู้ดูแลปิดให้" เคยไม่มีเครื่องมือรองรับเลย (ต้องแตะฐานข้อมูลเอง) — ตอนนี้มี
`flask mfa-status` / `flask mfa-disable` ที่เรียก service ตัวเดียวกับหน้าเว็บ
และลง audit อัตโนมัติ · **คำตัดสิน "ไม่บังคับ MFA" ยังไม่เปลี่ยน** และเงื่อนไข
หมดอายุข้อ 3 (มี recovery code เมื่อไหร่ให้กลับมาพิจารณาบังคับ) ยังยืนอยู่ —
เหตุผลที่ยังไม่ทำ recovery code เต็มรูปอยู่ในทะเบียน "ยังไม่ได้ทำ" ของ CLAUDE.md
