## Branch protection ของ `main` (2026-08-13 · แก้ตาม ADR 0053 เมื่อ 2026-08-16)

บังคับ PR · required check **27 จาก 30** · linear history · ห้าม force push
และห้ามลบ branch

**`enforce_admins: true` ตั้งแต่ ADR 0053 (2026-08-16)** — กฎทุกข้อข้างบน
มีผลกับเจ้าของด้วย ไม่มีทาง push ตรงเข้า main อีก (ก่อนหน้านั้นเป็น `false`
และการ bypass ถูกใช้จริงสามครั้งในวันเดียว ซึ่งคือเหตุที่ ADR เกิด) ·
ทางฉุกเฉิน: เจ้าของเป็น admin จึงปิดชั่วคราวได้เสมอ — **ต้องเปิดคืนทันที
ที่จบเหตุ และบันทึกเหตุการณ์ลงไฟล์นี้ภายใน 7 วัน** (เงื่อนไขใน ADR 0053)

- **ต้อง approve 0 คน** เพราะโปรเจกต์นี้มีคนดูแลคนเดียวและ GitHub ไม่ให้ approve
  PR ของตัวเอง — ตั้งเป็น 1 เมื่อไหร่ = merge ไม่ได้ตลอดกาล · ตั้งเป็น 1 ตอนที่
  มีคนที่สองจริง ๆ ไม่ใช่ตอนที่อยากให้ดูเข้ม (เงื่อนไขหมดอายุของ ADR 0053)
- **ชื่อ check ต้องตรงกับที่ CI สร้างเป๊ะ** — พิมพ์ผิดตัวเดียวได้ด่านที่ไม่มีวัน
  ผ่าน (PR ค้างตลอดกาล) ส่วน check จริงที่ตกหล่นจากลิสต์คือด่านที่ไม่กันอะไรเลย
  · **เพิ่ม job ใหม่ต้องมาเติมที่นี่ด้วย** ไม่งั้นมันจะรันแต่ไม่กัน
  (`perf-smoke` เข้าเป็นตัวที่ 27 เมื่อ 2026-08-16 — ADR 0056)
- **บังคับ 27 จาก 30 check** — สามตัวที่ไม่บังคับคือ `scorecard` และ `posture`
  (**ไม่รันบน pull request** เลย — trigger เป็น push/schedule/branch_protection_rule)
  กับ job ของ workflow `release` ซึ่งรันตอน publish release (ADR 0058)
  การบังคับจึงเท่ากับให้ PR ทุกใบรอ check ที่ไม่มีวันมา · `scorecard` ยังเป็น
  *คะแนน* ไม่ใช่ผ่าน/ไม่ผ่าน — ด่านที่ไม่มีเส้นแบ่งชัดไม่ควรเป็นด่านที่บล็อกคน
- **ตัวเลขและธงทั้งย่อหน้านี้ถูกเครื่องตรวจแล้ว** ตั้งแต่ ADR 0061 — job
  `posture` เทียบ API ของ GitHub กับสิ่งที่ประกาศไว้ที่นี่ทุกครั้งที่กฎของ
  branch เปลี่ยนและทุก push บน main (`scripts/audit_posture.py`) ·
  **อ่านไม่ได้ = แดง ไม่ใช่ข้าม**
- ปิด merge commit ที่ระดับ repo ด้วย เพราะ linear history จะปฏิเสธมันเสมออยู่แล้ว
  — ปุ่มที่กดแล้วพังทุกครั้งคือกับดัก ไม่ใช่ทางเลือก
- **auto-merge เปิดที่ระดับ repo (2026-08-17)** — วิธี merge มาตรฐานคือ
  `gh pr merge N --rebase --delete-branch --auto`: ให้ GitHub ซึ่งนั่งอยู่
  ในด่านเป็นคนตัดสินตอน required checks ครบ · เกิดจากบทเรียนจริง: script
  ที่รอ-แล้ว-merge เองมีกับดักจังหวะสะสมห้าแบบในวันเดียว (เช็คก่อน check
  เกิด · อ่านผล block ไม่ครบ · ชนกับ merge มือ · poll PR ที่ยังไม่ถูกสร้าง
  · commit ใหม่ทำ check ชุดเก่าหายระหว่างรอ) — auto-merge ไม่มีหน้าต่าง
  จังหวะพวกนี้เลยโดยนิยาม
- **การห้าม force push ตอนนี้ขวางเจ้าของด้วย** (ผลของ `enforce_admins: true`)
  — การเขียนประวัติใหม่แบบ 2026-08-12 ต้องปลด enforce_admins ชั่วคราวแล้ว
  ตั้งกลับ + บันทึกตามเงื่อนไขข้างบน — เขียนไว้ตรงนี้เพราะวันนั้นจะหาไม่เจอ
  ว่าอะไรขวางอยู่

## Dependabot — และสิ่งที่มันมองไม่เห็น

เปิด **security updates** ไว้ (2026-08-12) — มันเปิด PR ให้เองเมื่อมี CVE
ของ dependency

**version updates เปิดเฉพาะของที่ถูกตรึงไว้** — GitHub Actions, base image ของ
Docker และเครื่องมือใน `pins/` · เส้นแบ่งคือ **ของที่ตรึงไว้ที่รุ่นหนึ่งอย่าง
เจาะจงต้องมีคนขยับให้** ไม่งั้นคือการแช่ช่องโหว่ไว้ ส่วน `Pipfile.lock` ของแอป
ไม่ได้ถูกตรึง (ประกาศเป็น `"*"`) และมีร้อยกว่า package — เปิดแล้วจะมี PR แทบทุกวัน
· `tests/test_dependabot.py` บังคับเส้นแบ่งนี้ด้วย **path ไม่ใช่ชื่อ ecosystem**

### action ทุกตัวถูก pin ด้วย commit SHA (2026-08-13)

**tag ย้ายได้ commit ย้ายไม่ได้** — `@v7` ชี้ไปที่ไหนก็ได้ที่เจ้าของ action
ย้ายมันไป และ action รันด้วยสิทธิ์ของ workflow เรา วันที่บัญชีของเขาถูกยึด
tag เดิมจะชี้ไปโค้ดใหม่โดยที่ไฟล์ในนี้ไม่เปลี่ยนสักตัวอักษร

รูปแบบคือ `uses: owner/repo@<sha40> # vX.Y.Z` — คอมเมนต์ไม่ใช่ของประดับ
มันคือสิ่งเดียวที่บอกคนอ่านว่าใช้รุ่นไหน และเป็นสิ่งที่ Dependabot อ่าน
· `tests/test_workflow_pinning.py` บังคับทั้งสามข้อ: pin ครบ · มีคอมเมนต์เลขรุ่น
· และ **action เดียวกันต้องเป็น SHA เดียวกันทุกที่** (ข้อหลังมาจากของจริง —
`upload-artifact` เคยค้างที่ `@v4` อยู่จุดเดียวใน job `dast` สิบวันโดย CI เขียวตลอด)

**tag แบบ annotated ต้อง deref อีกชั้น** — `git/ref/tags/<tag>` ของ
`github/codeql-action` กับ `ossf/scorecard-action` คืน object ชนิด `tag`
ไม่ใช่ `commit` · เอา SHA นั้นไปใส่ตรง ๆ workflow จะพัง

**base image ของ `Dockerfile` ก็ pin ด้วย digest ด้วยหลักเดียวกัน** — และ
**ราคาที่มันเรียกเก็บต่างจาก action**: pin แล้ว security patch ของ base จะไม่มา
เองอีก ซึ่ง**แย่กว่าเดิม**ถ้าไม่มีใครขยับ · จ่ายด้วยการเปิด
`package-ecosystem: docker` ให้ Dependabot เปิด PR ขยับ digest แทน patch จึงยัง
มาเหมือนเดิม แค่มาเป็น PR ที่มีคนเห็นและผ่าน required check ครบชุด · `tests/test_dockerfile_pinning.py`
บังคับว่า **สองอย่างนี้ต้องมาคู่กัน** — ถอด entry ของ Dependabot ออกเมื่อไหร่ต้องแดง
เพราะ pin โดยไม่มีใครขยับคือการแช่ช่องโหว่ไว้

**ต้อง pin digest ของ manifest index ไม่ใช่ของ image ต่อสถาปัตยกรรม** —
pin ผิดตัวจะล็อก build ไว้ที่ arch เดียวโดยไม่มี error จนกว่าจะ build บนเครื่อง
คนละ arch (digest ที่ใช้อยู่ครอบ 7 แพลตฟอร์ม รวม `linux/amd64` ที่ CI ใช้)

### เครื่องมือที่ job ติดตั้งเอง ถูกตรึงด้วย hash (2026-08-13)

ชั้นที่สาม ต่อจาก action (SHA) และ base image (digest) — คราวนี้เป็นของที่
**คำสั่งใน job ไปดึงมาเอง**: `pip install pipenv` และ `npm install pa11y-ci`
ทั้งคู่หยิบของ ณ วินาทีที่รัน และทั้งคู่รันด้วยสิทธิ์ของ workflow เรา
ล็อกไฟล์อยู่ใน `pins/` (ดู `pins/README.md`) · `tests/test_ci_pinning.py` บังคับ

**สองอย่างที่เลขรุ่นอย่างเดียวให้ไม่ได้**:
- `--require-hashes` ผูกกับ *ไบต์* ไม่ใช่ชื่อรุ่น
- และมันปฏิเสธด้วยถ้ามี dependency ตัวไหน **ไม่ได้ถูกระบุไว้** — `npm install
  pa11y-ci@4.1.1` ตรึงได้แค่ตัวมันเอง อีก 161 package ที่ตามมายังเป็น
  "ล่าสุดที่เข้าช่วง" ทุกครั้ง · `npm ci` อ่านจาก `package-lock.json` ซึ่งมี
  integrity hash ครบทั้งต้นไม้ และ **ล้มถ้า lock ไม่ตรงกับ package.json**
  ต่างจาก `npm install` ที่จะแก้ lock ให้เงียบ ๆ แล้วเดินต่อ

ราคาที่จ่ายเป็นตัวเดียวกับ base image และจ่ายด้วยวิธีเดียวกัน: Dependabot
เฝ้าทุกไดเรกทอรีใน `pins/` และเทสต์บังคับว่า **เพิ่ม pin แล้วลืมต่อ Dependabot
= แดง** · ไฟล์ล็อกเป็นผลของ `pip-compile --generate-hashes` ซึ่ง Dependabot
compile ใหม่ให้เอง — `requirements.in` จึงต้องถูก commit ไปด้วย

**pin ของ CI ไม่ได้ครอบ service container** (`redis:7`, `mysql:8`, `mariadb:11`)
โดยตั้งใจ — นั่นคือของที่เรา *ทดสอบว่าเข้ากันได้* ไม่ใช่ของที่เรา *ส่งมอบ*
ตรึงไว้แปลว่าจะไม่มีวันรู้ว่ารุ่นถัดไปทำให้เราพัง ซึ่ง job `dialects` มีไว้เพื่อจับ

### merge PR ของ Dependabot ด้วย **rebase** ไม่ใช่ squash — และอ่านก่อน arm

**arm `--auto` กับ PR ของ Dependabot ได้หลังอ่าน diff ของ lock/SHA แล้ว
เท่านั้น** — check เขียวพิสูจน์*พฤติกรรม* (เทสต์ผ่าน · audit สองทิศไม่แดง)
แต่ไม่พิสูจน์*เจตนาของ upstream* · auto-merge ที่ arm โดยไม่อ่านคือการมอบ
สิทธิ์เขียน main ให้ทุกคนที่ยึดบัญชี publisher ของ dependency ได้ (audit r3
ข้อ 1 — ปฏิสัมพันธ์ใหม่ระหว่าง norm auto-merge กับ PR อัตโนมัติ)

squash ต่อท้ายหัว commit ด้วย ` (#N)` และหัวของ Dependabot ยาวอยู่แล้ว —
PR ใบแรก (2026-08-13) หัวยาว 84 ตัว squash แล้วได้ 89 ซึ่ง**เกินเพดาน 72 ของ
`scripts/lint_commits.py`** แล้ว `commit-lint` จะแดงบน `main` หลัง merge ไปแล้ว
(สายเกินกว่าจะกันได้) · ส่วน commit จริงในกิ่งสั้นกว่าเสมอ rebase จึงใช้ตัวนั้น

ยังไม่ได้ปิดปุ่ม squash ที่ระดับ repo เพราะมันมีประโยชน์กับ PR ของคนที่ commit
กระจัดกระจาย — **ถ้าวันหนึ่งพลาดเรื่องนี้ซ้ำ ให้ปิดมันทิ้ง** ปุ่มที่ต้องจำว่า
"ห้ามกดกับ PR แบบนี้" คือปุ่มที่จะถูกกดสักวัน

**ข้อจำกัดที่วัดแล้ว ไม่ใช่ที่เดา:** dependency graph ของ GitHub อ่าน Pipfile

สักตัว** แปลว่า Dependabot จะไม่มีวันเตือนเรื่องของพวกนี้ให้

## กรอบเวลาแก้ช่องโหว่ของ dependency

นับจาก**วันที่รู้** (job `security` แดง หรือมีคนแจ้ง) ไม่ใช่วันที่ CVE ถูกเผยแพร่

| ระดับ | ต้องแก้ภายใน | ถ้าแก้ไม่ทัน |
|---|---|---|
| critical | **7 วัน** | ต้องปิดความสามารถที่เกี่ยวข้องหรือถอด plugin นั้นออกไปก่อน |
| high | **30 วัน** | บันทึกเหตุผลและวันที่คาดว่าจะแก้ไว้ในตารางส่วนที่ต้องมีคนลงมือ |
| medium | **90 วัน** | รวมเข้ากับรอบทบทวนรายไตรมาส |
| low | รอบทบทวนถัดไป | — |

**ระดับมาจากที่ไหน**: ใช้ CVSS ของตัว advisory เอง ไม่ตีความใหม่ ·
ถ้า advisory ไม่ให้คะแนนมา ให้ถือเป็น **high** จนกว่าจะมีคนอ่านแล้วตัดสินเป็นอย่างอื่น
พร้อมบันทึกเหตุผล — ค่าเริ่มต้นต้องเป็นฝั่งที่ปลอดภัยกว่า

**ไลบรารีของ plugin ต่างจาก core โดยตั้งใจ** ([ADR 0025](adr/0025-plug-points-and-supply-chain-isolation.md)):
ของ core ถอดไม่ได้จึงต้องแก้ ส่วนของ plugin มีทางออกที่เร็วกว่าการรอ patch เสมอ
คือ `DISABLED_PLUGINS` แล้วถอดไดเรกทอรีทิ้ง — กรอบเวลาข้างบนจึงเป็นเพดานของ
"เมื่อไหร่ต้องจบเรื่อง" ไม่ใช่ "เมื่อไหร่ต้องมี patch"
