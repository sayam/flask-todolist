# การจำแนกชั้นข้อมูลและระยะเก็บรักษา

สถานะ: อนุมัติ 2026-08-03 (Phase 2) — การตัดสินใจอยู่ใน
[ADR 0014](adr/0014-pdpa-vs-audit-retention.md)

เอกสารนี้จำแนก **ข้อมูลที่ระบบเก็บจริง ณ ตอนนี้** ไม่ใช่รายการทั่วไป
เพิ่มคอลัมน์ใหม่เมื่อไหร่ **ต้องมาระบุชั้นที่นี่ด้วย** — `tests/test_data_classification.py`
ตรวจว่าไม่มีคอลัมน์ไหนหลุดการจำแนก

## ขอบเขตทางกฎหมาย

ตามความเข้าใจของเรา PDPA (พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562) มาตรา 4
ยกเว้นการเก็บข้อมูลเพื่อประโยชน์ส่วนตนหรือกิจกรรมในครอบครัว **แอปนี้ในสภาพ
ปัจจุบัน (ผู้ใช้คนเดียว ไม่เปิดสาธารณะ) จึงน่าจะยังไม่เข้าข่ายบังคับ**
สิ่งที่ทำที่นี่คือวางท่าให้ถูกไว้ล่วงหน้าเผื่อวันที่มีผู้ใช้จริง ไม่ใช่เพราะถูกบังคับ
— และเอกสารนี้ไม่ใช่คำแนะนำทางกฎหมาย ก่อนเปิดใช้จริงควรให้ผู้เชี่ยวชาญตรวจอีกรอบ

## ชั้นข้อมูล

| ชั้น | ชื่อ | ฟิลด์จริงในระบบ |
|---|---|---|
| **C1** | ความลับ (secret) | `tdl_user.password_hash` |
| **C2** | ระบุตัวบุคคล (PII) | `tdl_user.username`, `first_name`, `last_name` |
| **C3** | เนื้อหาของผู้ใช้ | `tdl_todo.title`, `tdl_category.name`, `start_date`, `due_date` |
| **C4** | การตั้งค่า/metadata | `locale`, `theme`, `mode`, `timezone_name`, `is_done`, `created_at`, `updated_at`, `id`, `*_id` |
| **C5** | หลักฐาน (audit) | ตาราง audit trail |
| **C6** | log ปฏิบัติการ | JSON log ทาง stdout (`actor`, `remote_addr`, `path`, …) |

**หมายเหตุที่สำคัญกว่าที่เห็น**

- **C3 อาจมี PII ของบุคคลที่สามปนอยู่** — ผู้ใช้พิมพ์ "โทรหาคุณสมชาย 08x-xxxxxxx"
  ลงในชื่องานได้ ระบบไม่มีทางรู้ จึงต้องปฏิบัติกับ C3 ระมัดระวังเท่า C2
  ในเรื่องการส่งออกและการเก็บลง audit
- **`remote_addr` ใน C6 เป็นข้อมูลส่วนบุคคล** ไม่ใช่แค่ metadata ทางเทคนิค
- **C4 ไม่ใช่ข้อมูลไร้ตัวตน** — `timezone_name` บอกโซนที่อยู่ได้คร่าว ๆ
  ถือว่าอ่อนพอจะเก็บใน audit ได้ แต่ไม่ควรเผยแพร่รวมกลุ่มโดยไม่คิด

## ระยะเก็บรักษา

ระยะต่างกันตามชั้น **ไม่ใช้ค่าเดียวทั้งระบบ** เพราะเหตุผลที่ต้องเก็บต่างกัน

| ชั้น | ระยะ | ลบเมื่อไหร่/อย่างไร |
|---|---|---|
| C1 | **ล้างทันทีที่ soft delete บัญชี** ไม่รอ grace | ไม่มีเหตุผลใดที่ต้องเก็บ credential ของบัญชีที่ปิดแล้ว — กู้บัญชีคืนภายใน 30 วันได้ แต่ต้องตั้งรหัสใหม่ |
| C2 | soft delete + **30 วัน** → purge | purge = เขียนทับ `username` ด้วย `#deleted-<id>` และตั้ง `first_name`/`last_name` เป็น NULL |
| C3 | soft delete + **30 วัน** → purge | ลบแถวจริงออกจากฐานข้อมูล |
| C4 | ตามอายุของแถวที่มันสังกัด | ไปพร้อม user/todo/category ที่เป็นเจ้าของ |
| C5 | **1 ปี** นับจากเวลาที่บันทึก | purge job ลบแถวเก่ากว่านั้น + เขียน checkpoint (ดูด้านล่าง) |
| C6 | **90 วัน** | ตอนนี้ออก stdout จึงขึ้นกับ runtime ที่รับไป — บังคับจริงเมื่อมี log shipping ใน Phase 5 |

**แถว tombstone:** purge บัญชีไม่ได้ลบแถว `tdl_user` ทิ้ง แต่เหลือไว้เฉพาะ `id`
กับเวลาที่ลบ/purge เพื่อให้ audit ที่อ้าง `actor_id` ยังแสดงผลได้ว่า
"ผู้ใช้ที่ถูกลบ #7" ไม่ใช่ค่าว่างที่ตีความไม่ได้ ชื่อผู้ใช้เดิมถูกปล่อยคืน
ให้คนอื่นสมัครซ้ำได้ และไม่เกิดความกำกวมย้อนหลังเพราะ audit อ้างเลข ไม่ใช่ชื่อ

## กติกาที่ตามมา (มีผลกับโค้ดทันที)

1. **audit ห้ามเก็บค่าของ C1/C2/C3** — เก็บได้แค่ชื่อคอลัมน์ + HMAC ของค่าเก่า/ใหม่
   ค่าจริงเก็บได้เฉพาะ C4 (ดูเหตุผลใน ADR 0014)
2. **C1 ห้ามออกจากระบบทุกกรณี** — ไม่อยู่ใน export, ไม่อยู่ใน log, ไม่อยู่ใน audit
   แม้แต่ในรูป hash
3. **log (C6) เก็บ `username` ไม่เก็บชื่อจริง** — ทำแล้วตั้งแต่ Phase 1
4. ฟีเจอร์ export ข้อมูลตัวเอง (Phase 7) ส่งออก C2/C3/C4 ของเจ้าตัว
   **ไม่ส่ง C1 และไม่ส่ง C5** (audit เป็นหลักฐานของระบบ ไม่ใช่ข้อมูลของ subject)
