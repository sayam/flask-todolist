> กติกาเดิมของ repo มีผลกับงานนี้ทั้งหมด: coverage ratchet ขึ้นทางเดียว ·

## 0. สิ่งที่สำรวจแล้วขัดกับเอกสาร — ทักก่อนตามข้อ 6.1

### 0.1 ⭐ ทะเบียน gate มีอยู่แล้วครึ่งหนึ่ง และอยู่กลับทาง

เอกสารข้อ 3.1 เขียนว่า "สกัดกฎที่ปัจจุบันฝังกระจายอยู่ในเทสต์และ CI ออกมาเป็น
ไฟล์นิยามเดียว" ราวกับเริ่มจากศูนย์ · **ของจริงคือ `docs/ASVS.md` เป็นทะเบียน
นั้นอยู่แล้ว เพียงแต่ชี้กลับทาง**: มันแม็ป *ข้อมาตรฐาน → หลักฐาน* ไม่ใช่
*gate → มาตรฐาน*

| ของที่มีอยู่แล้วใน `docs/ASVS.md` | จำนวน |
|---|---|
| แถวที่ตัดสินว่า "ผ่าน" | 138 |
| การอ้างถึงเทสต์ (`tests/x.py::ชื่อ`) | 108 |
| job ของ CI ที่ถูกอ้าง (`ci:ชื่อ`) | 12 |
| ADR ที่ถูกอ้าง | 24 |

และ `tests/test_asvs.py` **บังคับอยู่แล้ว**ว่าทุกอย่างใน backtick ต้องชี้ไปหา
ของที่มีจริง — referential integrity ที่ `gates.yaml` ต้องการ มีคนทำไว้แล้ว

**ผลต่อแผน**: ถ้าสกัดใหม่จากศูนย์จะได้ทะเบียนคู่ขนานสองอัน ซึ่งขัดกับเงื่อนไข
สำเร็จของข้อ 3.1 เอง ("ไม่มีการเขียนมือคู่ขนานสองที่") · เฟส 8 จึงเป็น
**การกลับทิศ** ไม่ใช่การสร้างใหม่: `gates.yaml` เป็นแหล่งจริง แล้ว
`docs/ASVS.md` ถูก generate จากมัน ในคอมมิตเดียวกัน

### 0.2 migration class เป็นของ *port* ไม่ใช่ของ *type*

เอกสารข้อ 3.3 เขียนว่า "plugin contract ทุก **type** ต้องประกาศ migration class"
· ของจริงมี 5 type / 16 plugin และ **type `auth` ถือ port คนละแบบสองอันอยู่**:

| type | plugin | port | class ที่คาด |
|---|---|---|---|
| `themes` | system, ocean | ชุดสี | `live` |
| `auth` | totp | **ปัจจัยที่สอง** | `live` |
| `auth` | password, oidc, ldap | **ปัจจัยหลัก** | `warm` |
| `cache` | noop, redis | store ที่แชร์ | `live` |
| `secrets` | env, file, vault | แหล่งความลับ | **ดู 0.3** |
| `db` | sqlite, mysql, mariadb | ยี่ห้อฐานข้อมูล | `cold` |

ประกาศที่ระดับ type จะบังคับให้ `auth/totp` กับ `auth/oidc` เป็น class เดียวกัน
ซึ่งผิดทั้งคู่ · manifest แยกสองอันนี้อยู่แล้วด้วยคีย์ `factor` (`second`)
— **class จึงต้องอยู่ใน `plugin.json` ของแต่ละ plugin ไม่ใช่ของ type**

### 0.3 `secrets` อ่านครั้งเดียวตอน start — "dual-read" วัดไม่ได้ตามที่เขียนไว้

เอกสารจัด secret source เป็น `live` พร้อมวงเล็บว่า "(dual-read)" · แต่
[ADR 0030](adr/0030-secrets-come-from-a-declared-source.md) กำหนดว่าแหล่งความลับ
ถูกอ่าน **ครั้งเดียวตอน `create_app`** และ `vault://` ก็อ่านตอน start เท่านั้น
· การสลับแหล่งจึงไม่มีทางเกิดโดยไม่ restart ในสถาปัตยกรรมปัจจุบัน

สองทางที่ต้องเลือก **ก่อน**เริ่มเฟส 10 — ไม่ใช่ระหว่างทาง:
- **(ก)** จัด `secrets` เป็น `cold` ตามความจริงวันนี้ แล้วบันทึกว่าทำไม
- **(ข)** ทำ dual-read จริง (อ่านสองแหล่ง ทับกันตามลำดับ) แล้วค่อยเคลมว่า `live`
  — เป็นงานเพิ่มที่เอกสารไม่ได้นับ

แผนนี้ตั้งต้นที่ **(ก)** เพราะเป็นสิ่งที่วัดได้วันนี้ · เลือก (ข) เมื่อไหร่
ให้เพิ่มเป็นเฟส 10.5 แยก

### 0.4 ที่ตรงกันดีแล้ว — ยืนยัน

- "CI 22 jobs" **ถูก** เมื่อนับสองไฟล์ (`ci.yml` 21 + `scorecard.yml` 1)
  แต่เป็น **24 check** เพราะ `dialects` กับ `codeql` เป็น matrix อย่างละ 2
  · เงื่อนไขสำเร็จข้อ 3.1 ต้องระบุให้ชัดว่าผูกกับ *job* หรือ *check*
- ข้อ 4 ที่ตัดออก สอดคล้องกับ ADR ที่มีอยู่แล้ว: `db` สลับได้ทีละยี่ห้อและ
  `plugin-uninstall` ถูกปฏิเสธกับ type นี้ ([ADR 0026](adr/0026-db-backend-as-a-plugin.md))

## Phase 8 — ทะเบียน gate (`gates.yaml`)

**หัวใจของความ portable — ทุกเฟสถัดไปพึ่งไฟล์นี้**

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 8-01 | ADR โครง `gates.yaml` (คีย์, ใครเป็นแหล่งจริง, ทำไมกลับทิศจาก ASVS.md) | `docs/adr/0039-*` |
| 8-02 | `gates.yaml` ตัวแรก **สร้างจากของที่มีอยู่** ด้วยสคริปต์ แล้วตรวจด้วยมือ | `gates.yaml`, `scripts/build_gates.py` |
| 8-03 | เทสต์ผูกสองทิศ: gate ทุกข้อมีคนรันจริง · job/เทสต์ทุกตัวที่เป็นด่านมี gate id | `tests/test_gates.py` |
| 8-04 | `docs/ASVS.md` generate จาก `gates.yaml` (ถอดการเขียนมือออก) | `scripts/build_asvs_worksheet.py`, `docs/ASVS.md` |

**โครงที่เสนอ** (ตัดสินใน 8-01):

```yaml
gates:
  - id: service-layer-knows-no-http
    standard: [ASVS-V1.2.1]          # ว่างได้ ถ้าเป็นกฎของเราเองไม่ใช่ของมาตรฐาน
    severity: blocking                # blocking | warning
    check: pipenv run pytest tests/test_service_layer.py -q
    pass_criteria: exit 0
    enforced_by: {test: tests/test_service_layer.py, job: lint}
    portable: true                    # กฎสากล → ขึ้น SKILL.md ในเฟส 9
```

**เงื่อนไขสำเร็จ (ตรวจด้วยเครื่อง)**
- `tests/test_gates.py` แดงเมื่อ: มี gate ที่ไม่มี job/เทสต์ไหนรัน · มี job ใน
  `ci.yml` ที่ไม่มี gate id · มี `check:` ที่รันไม่ได้จริง
- `scripts/build_asvs_worksheet.py --check` ยังเขียว โดยอ่านจาก `gates.yaml`
- `git diff --exit-code docs/ASVS.md` หลัง regenerate = ว่าง

**ความเสี่ยง**
- **ทะเบียนคู่ขนานระหว่างทาง** — ลดด้วยการทำ 8-04 ในเฟสเดียวกัน ไม่ทิ้งไว้ข้ามเฟส
- **`check:` ที่เป็นคำสั่งยาว ๆ ของ job ที่ต้องมี stack** (`dast`, `stack`, `siem`)
  รันเดี่ยวไม่ได้ → ต้องยอมให้ gate ประเภทนี้มี `requires: stack` และ harness
  ในเฟส 11 ข้ามมันตอนรันเครื่องเดียว **โดยรายงานว่าข้าม ไม่ใช่เงียบ**

## Phase 9 — แยก skill + overlay

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 9-01 | `SKILL.md` แกนกลาง — กฎสากลที่ `portable: true` ใน `gates.yaml` | `SKILL.md` |
| 9-02 | เทสต์: `SKILL.md` **ห้ามเอ่ยชื่อไลบรารีของ Flask** (เทคนิคเดียวกับที่ `tests/test_plugins.py` ใช้ห้าม core เอ่ยชื่อ plugin) | `tests/test_skill.py` |
| 9-03 | `overlays/flask/` — enforcement script + CI template ทุกอันอ้าง gate id | `overlays/flask/**` |
| 9-04 | job `scaffold` ใน CI: สร้าง repo เปล่าใน temp dir → import skill+overlay → ต้องได้ gate ชุดเดียวกัน | `.github/workflows/ci.yml` |

**เงื่อนไขสำเร็จ** — job `scaffold` เขียว และ**ต้องแดงเมื่อ**: ลบไฟล์ใน
`overlays/flask/` ออกหนึ่งตัว · หรือเพิ่ม gate ใน `gates.yaml` โดยไม่มี
enforcement ใน overlay

**ความเสี่ยง**
- **`CLAUDE.md` ปัจจุบันยาวมากและเป็นความรู้ที่ใช้งานจริงอยู่** — ห้ามตัดทิ้ง
  ระหว่างแตก · แผนคือ `SKILL.md` + `overlays/flask/` **สรุปมาจาก** `CLAUDE.md`
  แล้ว `CLAUDE.md` ชี้ไปหาแทน (เป็นขั้น 9-05 แยก ทำหลัง 9-04 เขียว)
- **repo เปล่าที่ import แล้วต้องได้ gate ครบ จะ "ผ่าน" ไม่ได้จริง** เพราะ
  repo เปล่าไม่มีโค้ดให้ตรวจ → เงื่อนไขต้องเป็น "gate ถูก *ติดตั้ง* ครบและ
  *รันได้*" ไม่ใช่ "ผ่านทุกข้อ" ซึ่งเป็นคนละเรื่องและวัดคนละแบบ

## Phase 10 — migration class + วัด downtime จริง

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 10-01 | เพิ่มคีย์ `migration` ใน `plugin.json` **ของทุก plugin** + ตรวจตอนโหลด | `app/plugins/*/*/plugin.json`, `app/plugins/__init__.py` |
| 10-02 | ADR: class อยู่ที่ port ไม่ใช่ type · และ `secrets` = `cold` (ข้อ 0.3) | `docs/adr/0040-*` |
| 10-03 | bench: สลับ port ภายใต้ load แล้ววัด downtime + request ที่ fail | `loadtest/swap.js`, `scripts/bench_swap.sh` |
| 10-04 | บันทึกตัวเลขลง `docs/PERFORMANCE.md` + เทสต์ผูก class กับตัวเลข | `docs/PERFORMANCE.md`, `tests/test_migration_class.py` |

**เงื่อนไขสำเร็จ** — ทุก plugin มี `migration` · มีตัวเลขวัดจริงอย่างน้อย
**1 คู่สลับต่อ port** (6 port ตามตารางข้อ 0.2) · เทสต์แดงเมื่อประกาศ `live`
แต่ตัวเลขที่บันทึกไว้มี downtime เกินเกณฑ์

**ความเสี่ยง**
- **เกณฑ์ของ `live` ต้องเป็นตัวเลข ไม่ใช่คำว่า "ไม่มีนัยสำคัญ"** — ต้องตัดสิน
  ใน 10-02 (เสนอ: `live` = 0 request fail จากทั้งหมดที่ยิงระหว่างสลับ)
- **วัดรอบเดียวไม่ใช่หลักฐาน** (บทเรียน Phase 6) — ต้องรันซ้ำ ≥3 รอบ และเกณฑ์คือ
  "ไม่มีรอบไหนตก" ไม่ใช่ค่าเฉลี่ย
- `db` เป็น `cold` โดยนิยาม → bench ของมันคือ **วัดว่าหยุดเขียนนานแค่ไหน**
  ไม่ใช่พยายามให้เป็นศูนย์

## Phase 11 — fail-fix loop harness

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 11-01 | runner: อ่าน `gates.yaml` → รันทุก gate → คืนผลเป็น JSON (gate id, สาเหตุ, hint) | `scripts/run_gates.py` |
| 11-02 | บันทึกจำนวนรอบและ gate ที่ fail บ่อยลง log | `scripts/run_gates.py`, `docs/GATE-LOG.md` |
| 11-03 | พิสูจน์ด้วย branch ที่ตั้งใจใส่ช่องโหว่ — loop ต้องจับได้และ feedback พาแก้จนผ่าน | `tests/fixtures/vulnerable/**` |

**เงื่อนไขสำเร็จ** — รัน harness กับ fixture ที่มีช่องโหว่แล้ว: จับได้ทุกข้อที่
ฝังไว้ · ไม่รายงานข้อที่ไม่ได้ฝัง (false positive = แดง) · จำนวนรอบถูกบันทึก

**⚠ ความเสี่ยงที่ใหญ่ที่สุดของเฟสนี้ — ต้องตัดสินก่อนเริ่ม**

**โค้ดที่มีช่องโหว่โดยตั้งใจ จะไปปลุก semgrep/CodeQL/gitleaks ของ repo เอง**
แล้ว `main` แดงด้วยเรื่องที่ตั้งใจให้มี · สามทางที่เป็นไปได้:

1. เก็บ fixture ไว้ใน `tests/fixtures/vulnerable/` แล้ว **เพิ่มลง
   `.semgrepignore` + `paths-ignore` ของ CodeQL** — ง่ายสุด แต่**เท่ากับสร้าง
   ที่หลบให้ตัวเอง** ซึ่งวันหนึ่งจะมีคนวางโค้ดจริงลงไป
2. ให้ fixture อยู่ **นอก repo** (สร้างตอนรัน harness จาก template ที่เก็บเป็น
   ข้อความ ไม่ใช่ไฟล์ `.py`) — สแกนเนอร์มองไม่เห็นเพราะมันไม่ใช่ไฟล์โค้ด
3. เก็บเป็น branch แยกที่ไม่เคย merge — CI ของ branch นั้นแดงตลอด **ซึ่งคือ
   ผลที่ต้องการ** แต่แยกออกจาก `main` อย่างสิ้นเชิง

**เสนอทาง (2)** — fixture เป็น template ข้อความ + สคริปต์กางออกใน temp dir
ตอนรัน ไม่มีไฟล์ที่สแกนเนอร์เห็น และไม่ต้องเจาะรูในขอบเขตการสแกนที่เพิ่งปิดไป
เมื่อวาน (`tests/` เพิ่งถูกเอากลับเข้า scope)

## Phase 12 — harness เปรียบเทียบ

ทำเมื่อ 9 กับ 11 เสถียรแล้วเท่านั้น · spec กลาง 1 ชุด → generate N รอบ
แบบมี/ไม่มี skill → ยิง scanner ชุดเดียวกัน → เทียบ vulnerability density,
ASVS pass rate, จำนวนรอบ fail-fix

**ความเสี่ยงที่ต้องยอมรับไว้ก่อน**: ผลลัพธ์ขึ้นกับโมเดลและ prompt ซึ่งเปลี่ยน
ใต้เท้าได้ · ตัวเลขจึงต้องบันทึกพร้อม **ชื่อโมเดลและวันที่** และเคลมได้แค่
"ในสภาพนั้น" ไม่ใช่ "โดยทั่วไป" — หลักเดียวกับที่ `docs/PERFORMANCE.md` บันทึก
เครื่องที่วัดไว้ด้วยเสมอ · **N ต้องมากพอ** (เสนอ ≥5 ต่อฝั่ง) ไม่งั้นเป็นเกร็ด
ไม่ใช่การวัด
