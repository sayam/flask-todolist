## 1. คำตัดสินรายข้อ — idea ไหนชนะ และเพราะอะไร

| ข้อ | strong idea ของงานเดิม | idea ของเอกสาร | คำตัดสิน |
|---|---|---|---|
| 3.1 gates.yaml | **ความจริง (เทสต์/CI ที่ถูก mutation-test) เป็นแหล่ง** เอกสารถูก generate หรือตรวจสองทิศกับมัน — แบบเดียวกับ `openapi.json`, `ASVS.md`, `pins/` | `gates.yaml` เป็นแหล่ง แล้ว **CI ถูก generate จากมัน** | **งานเดิมชนะเรื่องทิศ · เอกสารชนะเรื่องรูป** — ต้องมีไฟล์ machine-readable (ของเดิมไม่มี ถูกของเอกสาร) แต่มันเป็น *ดัชนี* ที่ถูกบังคับสองทิศ ไม่ใช่ generator ของ CI — ดูเหตุผลใต้ตาราง |
| 3.2 skill/overlay | กฎทุกข้อ**เกิดจากกับดักจริงและมีเทสต์บังคับ** ไม่ใช่รายการความปรารถนา | แยกชั้น portable: `SKILL.md` แกน + overlay ต่อ framework | **เอกสารชนะเรื่องโครง** — portability คือความสามารถใหม่ที่ของเดิมไม่มีคำตอบ · งานเดิมกำกับเนื้อ: กฎใน `SKILL.md` ทุกข้อต้องพก gate id + กับดักที่ให้กำเนิดมัน |
| 3.3 migration class | manifest ประกาศ**ข้อเท็จจริงต่อ plugin** (`factor`, `schemes`, `provides`) · **การวัดเหนือการประกาศ** และวัดรอบเดียวไม่ใช่หลักฐาน | taxonomy `live`/`warm`/`cold` ต่อ **type** + bench | **เอกสารชนะเรื่อง taxonomy** (ของใหม่ที่ดี — เดิมไม่มีภาษาไว้พูดเรื่องนี้) · งานเดิมชนะเรื่องตำแหน่ง (ต่อ plugin ไม่ใช่ type — ดู 2.2) และวิธีพิสูจน์ (วัดซ้ำ ≥3 รอบ ไม่มีรอบไหนตก) |
| 3.4 fail-fix loop | — ไม่มีของเทียบ (CI ตัดสิน*หลัง*เขียนเสร็จ ไม่มี loop ป้อนกลับเป็นเครื่อง) | loop: รัน gate → feedback แบบเครื่องอ่านได้ → แก้ → วน | **เอกสารชนะขาด — ของใหม่แท้ รับเต็ม** · วินัยเดิมกำกับการพิสูจน์: harness ต้องพิสูจน์สองทิศ (จับของที่ฝังได้ครบ + ไม่เตือนลวง) ซึ่งเอกสารก็เรียกร้องเองอยู่แล้ว |
| 3.5 เปรียบเทียบ | บทเรียน Phase 6: การวัดรอบเดียวไม่ใช่หลักฐาน · บันทึกสภาพเครื่องที่วัดเสมอ | spec เดียว → generate N รอบ มี/ไม่มี skill → เทียบ | **เอกสารชนะเรื่องคำถาม** (เป็นบทพิสูจน์ของทั้งโปรเจกต์) · งานเดิมกำกับวิธี: N ≥ 5 ต่อฝั่ง บันทึกโมเดล+วันที่ เคลมได้เฉพาะในสภาพนั้น |

### ทำไม 3.1 ไม่เอา "CI ถูก generate จาก gates.yaml"

- **บทเรียนที่เพิ่งจ่ายเมื่อวาน** (semgrep): ขอบเขตที่ประกาศสองที่ทำให้ตัวตรวจ
  คำนวณเซตที่คาดหวังผิด — generator คือการสร้างที่ที่สองอย่างถาวร: ความรู้ของ
  job (`service container`, ลำดับ step, กับดัก User-Agent ของ ZAP) ต้องย้ายไป
  อยู่ใน YAML หรือไม่ก็ค้างสองที่
- **ด่านของ repo นี้แข็งเพราะมันคือเทสต์ที่ถูก mutation-test** — แปลง gate เป็น
  เอนทรีใน YAML ไม่ได้ทำให้แข็งขึ้น สิ่งที่ขาดคือ *ดัชนี* ให้เครื่องอ่าน ไม่ใช่
  ตัวรันใหม่
- **เอกสารเองเปิดทางนี้ไว้**: "หรืออย่างน้อยมีเทสต์พิสูจน์ว่า CI กับ gates.yaml
  ตรงกัน ไม่มีการเขียนมือคู่ขนานสองที่" — แผนนี้เลือกทางนั้นและทำให้เป็นสองทิศ

ผลพวง: **`docs/ASVS.md` ไม่ถูก generate ทับ** — มันถือ*คำตัดสิน*ของคน
(ผ่าน/ไม่เกี่ยวข้อง/ยังไม่ผ่าน พร้อมเหตุผล) ซึ่งเป็นคนละชนิดข้อมูลกับ*กลไกบังคับ*
ใน `gates.yaml` · สองไฟล์ สองหน้าที่ เชื่อมด้วย id และมีเทสต์บังคับว่าตรงกัน
— ไม่ใช่ทะเบียนคู่ขนาน เพราะไม่มีข้อมูลซ้ำกันสักช่อง

## 2. ข้อเท็จจริงที่เอกสารไม่รู้ (สำรวจ 2026-08-13 ที่ `92a4d11`)

### 2.1 ทะเบียน gate มีอยู่แล้วครึ่งหนึ่ง — อยู่ใน `docs/ASVS.md`

138 แถวที่ตัดสินว่าผ่าน · อ้างเทสต์ 108 จุด · อ้าง CI job 12 ตัว · อ้าง ADR 24 ใบ
และ `tests/test_asvs.py` บังคับอยู่แล้วว่าทุกหลักฐานใน backtick ต้องมีจริง —
referential integrity ที่ `gates.yaml` ต้องการ มีคนสร้างไว้แล้ว · เฟส 8 จึงเป็น
การ**เติมดัชนีฝั่ง enforcement** ไม่ใช่สร้างทะเบียนจากศูนย์

### 2.2 migration class เป็นของ *port* ไม่ใช่ของ *type*

5 type / 14 plugin บนดิสก์ และ type `auth` ถือ port คนละแบบสองอัน:

| port | plugin | class ที่คาด |
|---|---|---|
| ชุดสี | themes/system, themes/ocean | `live` |
| ปัจจัยที่สอง | auth/totp | `live` |
| ปัจจัยหลัก | auth/password, auth/oidc, auth/ldap | `warm` |
| cache store | cache/noop, cache/redis | `live` |
| แหล่งความลับ | secrets/env, secrets/file, secrets/vault | `cold` — ดู 2.3 |
| ยี่ห้อฐานข้อมูล | db/sqlite, db/mysql, db/mariadb | `cold` |

ประกาศที่ระดับ type จะบังคับ `auth/totp` กับ `auth/oidc` เป็น class เดียวกัน
ซึ่งผิดทั้งคู่ · manifest แยกสองอันนี้อยู่แล้วด้วยคีย์ `factor` →
**class อยู่ใน `plugin.json` ของแต่ละ plugin**

### 2.3 `secrets` อ่านครั้งเดียวตอน start — เคลม `live (dual-read)` ยังไม่มีจริง

[ADR 0030](adr/0030-secrets-come-from-a-declared-source.md): อ่านครั้งเดียวใน
`create_app` — สลับแหล่งโดยไม่ restart เป็นไปไม่ได้ในสถาปัตยกรรมปัจจุบัน ·
แผนตั้งต้นที่ `cold` ตามที่วัดได้วันนี้ · อยากได้ `live` ต้องสร้าง dual-read
ก่อน (งานที่เอกสารไม่ได้นับ) — แยกเป็นเฟส 10.5 ถ้าตัดสินใจทำ

### 2.4 ตัวเลขที่เอกสารใช้

**(ตัวเลขของวันสำรวจ 2026-08-13)** "CI 22 jobs" ถูกเมื่อนับสองไฟล์ workflow
(21+1) แต่เป็น **24 check** เพราะ matrix สองตัว — เทสต์ของเฟส 8 ผูกกับ *job*
(หน่วยที่ประกาศในไฟล์) ไม่ใช่ check

หลังเฟส 8–12 ปิดครบ ตัวเลขจริงคือ **23 job / 25 check** (required 24 — ไม่รวม
`scorecard` ที่ไม่รันบน PR) · **อย่าคัดตัวเลขจากหัวข้อนี้ไปใช้ที่อื่น** มันเป็น
บันทึกของวันที่สำรวจ ไม่ใช่สถานะปัจจุบัน — ที่ที่ถูกคือนับจาก `ci.yml` ตอนนั้น

## Phase 8 — ดัชนี gate (`gates.yaml`) ✅ (2026-08-14 · PR #11/#12)

**สถานะ: เฟส 8 เสร็จทั้งเฟส (2026-08-13)** — 8-05 ส่วนลึกไม่ได้เติม gate id
ลงแถว `ASVS.md` มือ (ที่ที่สามให้ drift) แต่ **derive crosswalk จากหลักฐาน**:
`scripts/build_gates_crosswalk.py` → `docs/GATES-ASVS.md` (generate) และด่าน
corroboration บังคับว่า `standard:` ทุกคำอ้างต้องถูกหลักฐานของแถวชี้กลับมาหา
· ผลวัด ณ วันปิด: 138 แถวผ่าน → 117 มีด่านรันหนุน · 21 ผ่านด้วยเหตุผล/เอกสาร

**ทุกเฟสถัดไปพึ่งไฟล์นี้ — และทิศของมันคือคำตัดสินที่สำคัญที่สุดของแผน (ข้อ 1)**

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 8-01 | ADR 0039: `gates.yaml` เป็น**ดัชนี enforcement** ที่ตรวจสองทิศ ไม่ใช่ generator ของ CI · โครงคีย์ · ความสัมพันธ์กับ `ASVS.md` | `docs/adr/0039-*` |
| 8-02 | ADR 0040: สิ่งที่ตัดออกโดยตั้งใจ (ข้อ 4 ของเอกสาร) — เขียนแต่แรกเพื่อกันขอบเขตบาน | `docs/adr/0040-*` |
| 8-03 | `gates.yaml` ตัวแรก สร้างด้วยสคริปต์จากเทสต์นโยบาย ~24 ไฟล์ + job 22 ตัว แล้วตรวจมือ | `gates.yaml`, `scripts/build_gates.py` |
| 8-04 | `tests/test_gates.py` — สองทิศกับ CI: ทุก gate ถูก wire อยู่ใน job จริง · ทุก job/เทสต์นโยบายมี gate id · `check:` ต้องเป็นคำสั่งเดียวกับที่ CI รัน (ห้าม paraphrase) | `tests/test_gates.py` |
| 8-05 | สองทิศกับ `ASVS.md`: gate ที่อ้างข้อ ASVS ต้องมีแถวนั้นจริง · แถว ASVS ที่หลักฐานเป็นเทสต์/job ต้อง map กลับมาหา gate id ได้ | `tests/test_gates.py`, `docs/ASVS.md` (เติม gate id ทีละน้อย) |

**โครงที่เสนอ** (ตัดสินจริงใน 8-01):

```yaml
gates:
  - id: service-layer-knows-no-http
    standard: [ASVS-V1.2.1]      # ว่างได้ — กฎของเราเองที่มาตรฐานไม่มีข้อให้อ้าง
    severity: blocking            # blocking | warning (ตรงกับ job ที่แดงได้/ไม่ได้)
    check: pipenv run pytest tests/test_service_layer.py -q
    enforced_by: {test: tests/test_service_layer.py, job: lint}
    requires: []                  # เช่น [stack] สำหรับ gate ที่ต้องมี TLS+replica
    portable: true                # กฎสากล → ขึ้น SKILL.md ในเฟส 9
    born_from: "Phase 3 — ตรรกะเคยรั่วไป route แล้ว API/HTML เพี้ยนจากกัน"
```

**เงื่อนไขสำเร็จ (ตรวจด้วยเครื่อง)**
- `tests/test_gates.py` แดงเมื่อ: gate ไม่มีคนรัน · job/เทสต์นโยบายไม่มี gate id
  · `check:` ไม่ตรงกับคำสั่งจริงใน CI · gate อ้าง ASVS ข้อที่ไม่มี
- mutation test ของด่านนี้: ลบ gate หนึ่งตัว → แดง · เพิ่ม job ปลอมไม่มี id → แดง
  · แก้ `check:` ให้ต่างจาก CI หนึ่งอักขระ → แดง

**ความเสี่ยง**: gate ของ job ที่ต้องมี stack (`dast`, `siem`, `stack`) รันเดี่ยว
ไม่ได้ → คีย์ `requires:` และ harness เฟส 11 ต้อง**รายงานว่าข้าม ไม่ใช่เงียบ**

## Phase 9 — แยก skill + overlay ✅ (2026-08-14 · PR #13/#14/#15)

**สถานะ: เฟส 9 เสร็จทั้งเฟส (2026-08-14)** — required checks ณ วันนั้น 24 ตัวรวม `scaffold` (เลขสด: ดู SECURITY-CADENCE) — `SKILL.md` **generate ทั้งใบ** จาก
portable gate (ตอนนั้น 58 กฎ · ปัจจุบัน 75) ไม่ใช่เขียนมือ: กฎ = `title` บทเรียน = `born_from`
ของคนมีที่เดียวคือหลักปฏิบัติกลาง 5 ข้อใน PREAMBLE ของ generator ·
ban list ตรวจที่ *render สด* จึงจับชื่อไลบรารี framework ได้ตั้งแต่ตอนถูกพิมพ์
ลง gates.yaml (จับจริง 7 จุดตอน generate ครั้งแรก — แก้ที่ต้นทางทั้งหมด)

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 9-01 | `SKILL.md` แกนกลาง — เฉพาะกฎที่ `portable: true` · **ทุกข้อพก gate id + `born_from`** ห้ามมีกฎที่ไม่มีทั้งสอง | `SKILL.md` |
| 9-02 | เทสต์: `SKILL.md` ห้ามเอ่ยชื่อไลบรารีของ Flask (เทคนิค grep เดียวกับที่ห้าม core เอ่ยชื่อ plugin) + ทุก gate id ที่อ้างมีจริง | `tests/test_skill.py` |
| 9-03 | `overlays/flask/` — enforcement script + CI template อ้าง gate id ทุกอัน | `overlays/flask/**` |
| 9-04 | job `scaffold`: repo เปล่าใน temp dir → import skill+overlay → **gate ติดตั้งครบและรันได้** | `.github/workflows/ci.yml` |
| 9-05 | `CLAUDE.md` ชี้ไปหา `SKILL.md`/overlay แทนส่วนที่ย้ายไป — ทำ**หลัง** 9-04 เขียวเท่านั้น | `CLAUDE.md` |

**เงื่อนไขสำเร็จ** — job `scaffold` เขียว และแดงเมื่อ: ลบไฟล์ overlay หนึ่งตัว
· หรือเพิ่ม gate `portable: true` โดยไม่มี enforcement ใน overlay

**สองอย่างที่ต้องไม่พลาด**
- เงื่อนไขของ repo เปล่าคือ "gate ถูก*ติดตั้ง*ครบและ*รันได้*" ไม่ใช่ "ผ่านทุกข้อ"
  — repo เปล่าไม่มีโค้ดให้ผ่าน สองอย่างนี้วัดคนละแบบ

## Phase 10 — migration class + วัด downtime จริง ✅ (2026-08-14 · PR #16/#18)

**สถานะ: เฟส 10 เสร็จทั้งเฟส (2026-08-14)** — manifest ทั้ง 14 บังคับตอนโหลด ·
bench วัดจริง 6 port × ≥3 รอบใต้โหลดใน VM (`scripts/bench_swap.sh` · ตัวเลขใน
`docs/PERFORMANCE.md`) · **cache ถูกลดชั้น live → warm ด้วยการวัด** (rolling บน
nginx แบบ DNS หลุด 1 request ใน 2/6 รอบ — แก้คำประกาศ ไม่ใช่แก้เกณฑ์) ·
เทสต์ผูก class ↔ ตัวเลข: live ต้อง 0 ทุกรอบ · warm ต้อง session รอดครบ ·
cold ต้องมี pause_ms ≥3 รอบ

| ขั้น | งาน | ไฟล์ที่กระทบ |
|---|---|---|
| 10-01 | ADR 0041: class อยู่ที่ plugin ไม่ใช่ type (ข้อ 2.2) · `secrets` = `cold` (ข้อ 2.3) · **เกณฑ์ของแต่ละ class เป็นตัวเลข**: `live` = 0 request fail · `warm` = session เดิมอยู่ครบ · `cold` = ประกาศช่วงหยุดเขียนที่วัดได้ | `docs/adr/0041-*` |
| 10-02 | คีย์ `migration` ใน `plugin.json` ทั้ง 16 ตัว + ตรวจตอนโหลด (ค่าไม่รู้จัก = ไม่ start ตามแบบแผนของ registry) | `app/plugins/*/*/plugin.json`, `app/plugins/__init__.py` |
| 10-03 | bench: สลับอย่างน้อย 1 คู่ต่อ port (6 port) ภายใต้ load — ซ้ำ ≥3 รอบ เกณฑ์คือ**ไม่มีรอบไหนตก** | `loadtest/swap.js`, `scripts/bench_swap.sh` |
| 10-04 | ตัวเลขลง `docs/PERFORMANCE.md` (พร้อมสภาพเครื่อง ตามแบบแผนเดิม) + เทสต์ผูก class ↔ ตัวเลข: ประกาศ `live` แต่ตัวเลขที่บันทึกมี fail > 0 = แดง | `docs/PERFORMANCE.md`, `tests/test_migration_class.py` |

**ความเสี่ยง**: bench ต้องรันกับ stack จริง (compose + โหลด) — ทำเป็น job แยก
หรือรวมใน `stack` ให้ตัดสินตอน 10-03 โดยดูเวลารันจริง ไม่เดา

## Phase 12 — harness เปรียบเทียบ ✅ (2026-08-14)

spec กลาง 1 ชุด → generate **5 ต่อฝั่ง** มี/ไม่มี skill → battery ชุดเดียวกัน
→ เทียบ · ของทั้งหมดอยู่ที่ `docs/comparison/` (วิธีการ · spec · ผล · ข้อมูลดิบ)
ตัวสั่งงานคือ `scripts/measure_generated.py` + `scripts/asvs_probe.py`

**ผล (claude-opus-5 · 2026-08-14 · 3 แขน แขนละ 5 แอป)**:

| แขน | ASVS เฉลี่ย | finding ของ gate | บรรทัด .py เฉลี่ย |
|---|---|---|---|
| ควบคุม (spec เปล่า) | 7.6 | 16 | 372 |
| ควบคุม + **"ทบทวนงานตัวเองหนึ่งรอบ"** | 9.2 | 11 | 541 |
| skill + overlay + doctor | 9.8 | 0 | 2454 |

semgrep ฟ้องแขน skill 4 ครั้ง — ตรวจแล้วเป็น false positive ตัวเดียวกันทั้งหมด
(helper คำนวณกุญแจ rate limit ที่กฎอ่านว่าเป็น view · โผล่ข้างเดียวเพราะมีแต่
แขนนั้นที่เขียนฟีเจอร์ซึ่งกฎอ่านผิด)

**แขนที่สามคือส่วนที่เปลี่ยนข้อสรุป** — เกิดขึ้นเพราะข้อจำกัดที่รายงานฉบับแรก
บันทึกไว้เอง (ฝั่ง skill ได้รอบตรวจเพิ่มที่ฝั่งควบคุมไม่ได้) แล้ว**เลือกวัดมัน
แทนที่จะเขียนกำกับไว้เฉย ๆ**: ประโยคเดียวปิดช่องว่าง ASVS ไป 1.6 จาก 2.2
เหลือส่วนที่เป็นของ skill ~0.6 · สิ่งที่รอบทบทวนหาเจอเองคือเรื่องที่เดาได้ด้วย
สามัญสำนึกด้านความปลอดภัย (timing oracle ตอน login, `PRAGMA foreign_keys`,
session fixation) · สิ่งที่มัน **หาไม่เจอเลย** คือ `delete-means-soft-delete`
(ตก 5/5 ทั้งแขน) เพราะนั่นคือ*ข้อตกลงของโปรเจกต์* ไม่ใช่ข้อผิดพลาดที่มองเห็น
จากการอ่านโค้ดตัวเอง — พร้อมกับความสม่ำเสมอ (แอปแย่สุดของแต่ละแขน 7 → 8 → 9)

**ข้อสรุปที่ใช้ตัดสินใจ**: อยากยกพื้นความปลอดภัยของโค้ดที่ generate ให้บังคับ
รอบทบทวนก่อน (ถูกที่สุด) · scaffolding คุ้มตรงข้อตกลงเฉพาะโปรเจกต์กับความ
สม่ำเสมอ ไม่ใช่ตรงความปลอดภัยพื้นฐาน

**สิ่งที่ต้องอ่านคู่กับตัวเลขเสมอ** อยู่ในรายงาน — ที่สำคัญที่สุดคือ probe รอบแรก
รายงานว่าฝั่ง skill *แย่กว่า* ในสามข้อ และทั้งสามเป็นความผิดของตัววัดเอง
(จับ `session.get()` ของ Flask เป็นการหาแถว · ลงโทษ helper กลาง · ลงโทษฝั่งที่
เขียนเทสต์) — **ตัวเลขที่ค้านตัวเองอันตรายกว่าตัวเลขที่เข้าข้างตัวเอง เพราะมัน
ถูกเชื่อทันทีโดยไม่มีใครขอหลักฐาน**

ผลขึ้นกับโมเดลและ prompt ซึ่งเปลี่ยนใต้เท้า → บันทึก**ชื่อโมเดล + วันที่ + spec**
คู่กับตัวเลขเสมอ และเคลมได้เฉพาะ "ในสภาพนั้น" — แบบแผนเดียวกับที่
`docs/PERFORMANCE.md` บันทึกเครื่องที่วัด (`tests/test_asvs_probe.py` บังคับว่า
รายงานต้องตรงกับข้อมูลดิบ และต้องมีสามอย่างนั้นครบ)

**งานที่การทดลองนี้เปิดออกมา (ยังไม่ทำ)**: `scan_templates_inline` เป็น regex
รายบรรทัดจึงจับ *คอมเมนต์ที่อธิบายว่าห้ามมีอะไร* เป็น finding — 3 ใน 5 แอป
