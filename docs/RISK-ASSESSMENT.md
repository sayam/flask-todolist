# วิธีประเมินความเสี่ยง และทะเบียนความเสี่ยง

ปิดช่องว่างข้อ `6.1`/`8.2` ของ [ISO27001.md](ISO27001.md) (backlog ของ G2 —
เจ้าของสั่งปิด 2026-08-16) — ก่อนหน้านี้การตัดสินความเสี่ยงกระจายอยู่ใน ADR
รายใบโดยไม่มีวิธีกลาง · ไฟล์นี้คือวิธีนั้น + การประเมินรอบแรกที่ทำจริง
· `tests/test_risk_assessment.py` ตรวจโครง ระดับตามสูตร และหลักฐานทุกชิ้น

## วิธี (methodology)

- ประเมินเป็น **โอกาส × ผลกระทบ** สามระดับ: `ต่ำ` = 1 · `กลาง` = 2 · `สูง` = 3
- **ระดับความเสี่ยง = ผลคูณ**: ≥ 6 → `สูง` · 3–4 → `กลาง` · ≤ 2 → `ต่ำ`
  (สูตรตายตัวเพื่อให้เครื่องตรวจได้ — เถียงกันที่คะแนนตั้งต้น ไม่ใช่ที่ผลคูณ)
- ขอบเขตเดียวกับ ISMS (หัวไฟล์ [ISO27001.md](ISO27001.md)): ซอฟต์แวร์ +
  วิธีทำงานของ repo · ความเสี่ยงเฉพาะสภาพ deploy เป็นของผู้ deploy

## เกณฑ์รับความเสี่ยง (acceptance)

- `สูง` — ต้องมีการจัดการที่เป็น**กลไกจริง** (gate/ADR/เทสต์) ไม่รับเฉย ๆ
  · ช่องโหว่ใหม่ที่ทำให้ความเสี่ยงขึ้นระดับนี้เดินตามกรอบเวลาของ
  [SECURITY-CADENCE.md](SECURITY-CADENCE.md) (critical 7 วัน · high 30)
- `กลาง` — ต้องมีการจัดการ หรือการรับความเสี่ยงที่**จดพร้อมเหตุผล**
  (แบบเดียวกับ `pins/accepted-advisories.txt` ที่ตรวจสองทิศ)
- `ต่ำ` — รับได้ จดไว้ในทะเบียนเพื่อให้รอบถัดไปเห็น
- ความเสี่ยงคงเหลือ (residual) ที่ตั้งใจรับ ต้องเขียนในคอลัมน์สุดท้าย
  ไม่ปล่อยให้เข้าใจว่า "จัดการแล้ว = หมดแล้ว"

## ทะเบียนความเสี่ยง — รอบแรก 2026-08-16

| ความเสี่ยง | โอกาส | ผลกระทบ | ระดับ | การจัดการ (กลไกจริง) | คงเหลือที่ตั้งใจรับ |
|---|---|---|---|---|---|
| supply chain ถูกฝัง (dependency/action/image) | กลาง | สูง | สูง | แกนอิสระ 18 gate — pin ทุกชั้นด้วย hash · CVE audit สองทิศ · SBOM · Scorecard (`docs/SUPPLY-CHAIN.md`) | zero-day ใน upstream ก่อน advisory ออก — ตรวจจับไม่ได้จนกว่าโลกจะรู้ |
| ข้อมูลสูญหาย (ดิสก์พัง/ลบผิด/migration พัง) | กลาง | สูง | สูง | soft delete ทั้งระบบ (`ADR 0014`) · backup/restore ที่ซ้อมทุก push (`docs/RUNBOOK-BACKUP.md` · `tests/test_backup_drill.py`) | ช่วงเวลาระหว่างรอบ backup ของผู้ deploy |
| ผู้ดูแลคนเดียว (bus factor) | สูง | กลาง | สูง | ความรู้ถูกบังคับให้อยู่ในเครื่อง ไม่ใช่ในหัว: gate "ลืมแล้วแดง" ทุกกฎ (`gates.yaml`) · เอกสาร/ADR ครบ · repo สาธารณะ (`CLAUDE.md`) | โปรเจกต์ส่วนตัวโดยนิยาม — ไม่มีคนที่สองมารับช่วงทันที |
| เดารหัสผ่าน / credential stuffing | กลาง | กลาง | กลาง | โควตาสองมิติ (IP+ชื่อ — `ADR 0021`) · นโยบาย NIST + blocklist (`ADR 0019`) · MFA แบบสมัครใจ (`ADR 0024`) | MFA ไม่บังคับ — เหตุผลและเงื่อนไขหมดอายุใน `ADR 0033` |
| คีย์ encrypt หาย (`DATA_ENCRYPTION_KEY`) | ต่ำ | สูง | กลาง | runbook สั่งเก็บคีย์แยกจากฐานเสมอ (`docs/RUNBOOK-BACKUP.md`) · คีย์หาย = plugin ปิดตัวเองไม่พังทั้งแอป (`ADR 0046`) | ความลับ TOTP ที่ encrypt ด้วยคีย์ที่หายแล้วกู้ไม่ได้ — enroll ใหม่ทางเดียว |
| session hijack / API token รั่ว | ต่ำ | สูง | กลาง | คุกกี้ผูก credential ปัจจุบัน + timeout สองชั้น (`ADR 0020`) · เพิกถอน token = ล้าง hash ทันที (`ADR 0017`) | ช่วงเวลาก่อนเจ้าของรู้ตัวว่า token รั่ว |
| ข้อมูล private รั่วข้ามผู้ใช้ผ่านการแชร์/dependency | ต่ำ | สูง | กลาง | จุดตัดสินการมองเห็นเดียว + ไม่เผยแม้การมีอยู่ + เทสต์สองทิศทุกช่องทาง (`ADR 0049` · `tests/test_org_graph.py`) | inference จาก metadata ที่แชร์โดยชอบ (สี่ฟิลด์) — ยอมรับโดยออกแบบ |
| ด่านที่เขียวเปล่า (เทสต์/scanner ไม่ได้ตรวจจริง) | กลาง | กลาง | กลาง | mutation test บังคับสองทิศทุกเทสต์ใหม่ (`CONTRIBUTING.md` กฎข้อ 1) · บทเรียน scanner เงียบกลายเป็น gate (`gate codeql-can-parse-the-app`) | ด่านเก่าก่อนยุค mutation ที่ยังไม่เคยถูกพิสูจน์ซ้ำ |
| บัญชี GitHub ของเจ้าของถูกยึด — root of trust เดียวของ repo และของ release ที่ถูกเซ็น | ต่ำ | สูง | กลาง | main รับของทาง PR + required checks บังคับถึง admin (`ADR 0053`) · การเซ็นเป็น keyless ผูกกับ identity ของ workflow ไม่มีคีย์ให้ขโมย (`ADR 0058`) · ประวัติสาธารณะ + audit ทำให้ของปลอมมีพยาน | ความแข็งของตัวบัญชี (2FA/passkey · PAT) อยู่นอกขอบเขตที่ repo บังคับได้ — ทวงเป็นงานเจ้าของใน `docs/SECURITY-CADENCE.md` |
| การเขียนขนานล้มที่โหลดสูง (audit serialize · deadlock) | กลาง | ต่ำ | ต่ำ | แก้ที่สถาปัตยกรรมแล้ว (`ADR 0035`) · เหลือ retry ของ error 1213 จดเปิดเผยใน `docs/ROADMAP.md` | ~2 ครั้ง/รอบที่ 25 VUs — เหนือสเกลเป้าห้าเท่า (`ADR 0031`) |
