# วิธีประเมินความเสี่ยง และทะเบียนความเสี่ยง

ปิดช่องว่างข้อ `6.1`/`8.2` ของ [ISO27001.md](ISO27001.md) (backlog ของ G2 —
เจ้าของสั่งปิด 2026-08-16) — ก่อนหน้านี้การตัดสินความเสี่ยงกระจายอยู่ใน ADR
รายใบโดยไม่มีวิธีกลาง · ไฟล์นี้คือวิธีนั้น + การประเมินรอบแรกที่ทำจริง
· `tests/test_risk_assessment.py` ตรวจโครง ระดับตามสูตร และหลักฐานทุกชิ้น

## วิธี (methodology)

- ประเมินเป็น **โอกาส × ผลกระทบ** สามระดับ: `ต่ำ` = 1 · `กลาง` = 2 · `สูง` = 3
- **ระดับความเสี่ยง = ผลคูณ**: ≥ 6 → `สูง` · 3–4 → `กลาง` · ≤ 2 → `ต่ำ`
  (สูตรตายตัวเพื่อให้เครื่องตรวจได้ — เถียงกันที่คะแนนตั้งต้น ไม่ใช่ที่ผลคูณ)
- ขอบเขตเดียวกับ ISMS (หัวไฟล์ [ISO27001.md](ISO27001.md)): ซอฟต์แวร์ +
  วิธีทำงานของ repo · ความเสี่ยงเฉพาะสภาพ deploy เป็นของผู้ deploy

## เกณฑ์รับความเสี่ยง (acceptance)

- `สูง` — ต้องมีการจัดการที่เป็น**กลไกจริง** (gate/ADR/เทสต์) ไม่รับเฉย ๆ
  · ช่องโหว่ใหม่ที่ทำให้ความเสี่ยงขึ้นระดับนี้เดินตามกรอบเวลาของ
  [SECURITY-CADENCE.md](SECURITY-CADENCE.md) (critical 7 วัน · high 30)
- `กลาง` — ต้องมีการจัดการ หรือการรับความเสี่ยงที่**จดพร้อมเหตุผล**
  (แบบเดียวกับ `pins/accepted-advisories.txt` ที่ตรวจสองทิศ)
- `ต่ำ` — รับได้ จดไว้ในทะเบียนเพื่อให้รอบถัดไปเห็น
- ความเสี่ยงคงเหลือ (residual) ที่ตั้งใจรับ ต้องเขียนในคอลัมน์สุดท้าย
  ไม่ปล่อยให้เข้าใจว่า "จัดการแล้ว = หมดแล้ว"

## ทะเบียนความเสี่ยง — รอบแรก 2026-08-16

| ความเสี่ยง | โอกาส | ผลกระทบ | ระดับ | การจัดการ (กลไกจริง) | คงเหลือที่ตั้งใจรับ |
|---|---|---|---|---|---|
| supply chain ถูกฝัง (dependency/action/image) | กลาง | สูง | สูง | แกนอิสระ 20 gate — pin ทุกชั้นด้วย hash (รวม image ของ stack ที่ CI รัน ตั้งแต่ audit รอบ 15) · CVE audit สองทิศ · SBOM · Scorecard (`docs/SUPPLY-CHAIN.md`) | zero-day ใน upstream ก่อน advisory ออก — ตรวจจับไม่ได้จนกว่าโลกจะรู้ |
| ข้อมูลสูญหาย (ดิสก์เสียหาย/ลบผิด/migration ล้มเหลว) | กลาง | สูง | สูง | soft delete ทั้งระบบ (`ADR 0014`) · backup/restore ที่ซ้อมทุก push (`docs/RUNBOOK-BACKUP.md` · `tests/test_backup_drill.py`) | ช่วงเวลาระหว่างรอบ backup ของผู้ deploy |
| ผู้ดูแลคนเดียว (bus factor) | สูง | กลาง | สูง | ความรู้ถูกบังคับให้อยู่ในเครื่อง ไม่ใช่ในหัว: gate "ลืมแล้วแดง" ทุกกฎ (`gates.yaml`) · เอกสาร/ADR ครบ · repo สาธารณะ (`CLAUDE.md`) | โปรเจกต์ส่วนตัวโดยนิยาม — ไม่มีคนที่สองมารับช่วงทันที |
| เดารหัสผ่าน / credential stuffing | กลาง | กลาง | กลาง | โควตาสองมิติ (IP+ชื่อ — `ADR 0021`) · นโยบาย NIST + blocklist (`ADR 0019`) · MFA แบบสมัครใจ (`ADR 0024`) | MFA ไม่บังคับ — เหตุผลและเงื่อนไขหมดอายุใน `ADR 0033` |
| คีย์ encrypt หาย (`DATA_ENCRYPTION_KEY`) | ต่ำ | สูง | กลาง | runbook สั่งเก็บคีย์แยกจากฐานเสมอ (`docs/RUNBOOK-BACKUP.md`) · คีย์หาย = plugin ปิดตัวเองไม่ล้มเหลวทั้งแอป (`ADR 0046`) | ความลับ TOTP ที่ encrypt ด้วยคีย์ที่หายแล้วกู้ไม่ได้ — enroll ใหม่ทางเดียว |
| session hijack / API token รั่ว | ต่ำ | สูง | กลาง | คุกกี้ผูก credential ปัจจุบัน + timeout สองชั้น (`ADR 0020`) · เพิกถอน token = ล้าง hash ทันที (`ADR 0017`) | ช่วงเวลาก่อนเจ้าของรู้ตัวว่า token รั่ว |
| ข้อมูล private รั่วข้ามผู้ใช้ผ่านการแชร์/dependency | ต่ำ | สูง | กลาง | จุดตัดสินการมองเห็นเดียว + ไม่เผยแม้การมีอยู่ + เทสต์สองทิศทุกช่องทาง (`ADR 0049` · `tests/test_org_graph.py`) | inference จาก metadata ที่แชร์โดยชอบ (สี่ฟิลด์) — ยอมรับโดยออกแบบ |
| ด่านที่เขียวเปล่า (เทสต์/scanner/**ตัวตัดสิน**ไม่ได้ตรวจจริง) | กลาง | สูง | สูง | mutation test บังคับสองทิศทุกเทสต์ใหม่ (`CONTRIBUTING.md` กฎข้อ 1) · บทเรียน scanner เงียบกลายเป็น gate (`gate codeql-can-parse-the-app` · `gate semgrep-scope-proven`) · **ตัวตัดสินของแกน supply chain มีเทสต์ planted+clean ของตัวเอง** (`gate checkers-proven-two-way` — audit r4) | ด่านเก่าก่อนยุค mutation ที่ยังไม่เคยถูกพิสูจน์ซ้ำ — 76 ตัวในรายการของ `tests/test_gate_evidence.py` ซึ่งมีแถวทวงให้หดแล้ว · เครื่องมือภายนอกที่เราอ่านผลของมันอย่างเดียว (trivy/pip-audit เองรายงานผิดได้) · **และด่านที่ไม่ได้เป็น required check ซึ่งล้มเงียบได้ทั้งวัน** — เกิดจริง 2026-08-18: ด่านของ `gate platform-posture-verified` ไม่เคยรันเลยตั้งแต่เกิดเพราะ workflow ไม่ start ทั้งไฟล์ (ปิดด้วย `gate workflows-are-startable` และสำมะโนที่นับ run ที่ไม่ได้ start) |
| บัญชี GitHub ของเจ้าของถูกยึด — root of trust เดียวของ repo และของ release ที่ถูกเซ็น | ต่ำ | สูง | กลาง | main รับของทาง PR + required checks บังคับถึง admin (`ADR 0053`) · การเซ็นเป็น keyless ผูกกับ identity ของ workflow ไม่มีคีย์ให้ขโมย (`ADR 0058`) · ประวัติสาธารณะ + audit ทำให้ของปลอมมีพยาน | ความแข็งของตัวบัญชี (2FA/passkey · PAT) อยู่นอกขอบเขตที่ repo บังคับได้ — ทวงเป็นงานเจ้าของใน `docs/SECURITY-CADENCE.md` |
| token ของ Zenodo ที่ฝังอยู่ใน URL ของ webhook — อ่านได้จาก GitHub API และไม่มีทางหมุนผ่านหน้าเว็บ | ต่ำ | กลาง | ต่ำ | ขั้นตอนใน `docs/RELEASE.md` สั่งให้เรียก hook แบบกรองส่วน query string ทิ้งเสมอ และตัดสินการหมุนด้วยลายนิ้วมือของค่า ไม่ใช่เลข id — เกณฑ์เลข id ที่เขียนไว้ก่อน **ผ่านได้ทั้งที่ token ไม่เปลี่ยน** วัดจริงแล้ว 2026-08-20 · ตัวจับคือขั้นถาม Zenodo หลังออกรุ่น ซึ่งเห็น record ที่โผล่มาโดยไม่มีใครสั่ง | **หมุนไม่ได้จริง ๆ**: ไม่อยู่ในหน้า token ของ Zenodo (เป็นใบที่ Zenodo ถือเอง) · ถอด linked account ไม่ได้เพราะ GitHub เป็นทางล็อกอิน · ปิด-เปิดสวิตช์ repo ได้ hook ใบใหม่แต่ token เดิม · revoke ที่ GitHub ตัดคนละใบและทำให้ archive พัง — ปลดเมื่อ Zenodo มีทางหมุน หรือทันทีที่พบ deposit ที่ไม่ได้สั่ง |
| ระยะเก็บรักษาหยุดเป็นจริงโดยไม่มีใครรู้ — งานลบข้อมูลพ้นระยะล้มเงียบ | กลาง | กลาง | กลาง | OnFailure ของหน่วยพิมพ์บรรทัดระดับ err ที่ค้นเจอด้วยเครื่อง (`deploy/systemd/todolist-purge-failed.service`) · `ci:purge-timer` ตรวจทุก push ว่าหน่วยหลักยังชี้ไปหามันและหน่วยนั้นถูกติดตั้งมาด้วย · Persistent=true กันรอบที่หายเพราะเครื่องดับ · แถวทวงใน `docs/SECURITY-CADENCE.md` | **journal ยังไม่ถูกส่งต่อไปไหน** — ตัวเก็บ log อ่านเฉพาะของ container (`ADR 0037`: ยังไม่มีคนรับ) การรู้จึงยังต้องมีคนหรือ log shipper ของผู้ deploy มาอ่าน · และระยะที่ `docs/ROPA.md` ประกาศ เป็นจริงเฉพาะ deployment ที่ติดตั้งหน่วยนี้ไว้ |
| ปลายทางภายนอกที่รับสายแล้วเงียบ ทำให้คำขอค้างและ worker หายไป | กลาง | กลาง | กลาง | ทุกจุดที่รอประกาศเพดานของตัวเอง (`ADR 0067`) — LDAP ตั้งเพดานของการรอคำตอบเอง · `app/plugins/db/mysql/backend.py` ตั้ง read/write timeout ต่อ connection · pool_pre_ping ที่ core · `tests/test_job_timeouts.py` กันไม่ให้คำสั่งของเครื่องมือเราค้างตลอดกาล | **ค่าเริ่มต้นของ container ยังเป็น 1 worker** (`ADR 0052`) — คำขอที่ชนเพดานจึงยังทำให้ช่วงนั้น ไม่มีใครรับงานอื่น · และเพดานของคำขอทั้งใบ (gunicorn) ยังเป็นค่าเริ่มต้นของเครื่องมือ ไม่ใช่ค่าที่เราเลือก |
| การเขียนขนานล้มที่โหลดสูง (audit serialize · deadlock) | กลาง | ต่ำ | ต่ำ | แก้ที่สถาปัตยกรรมแล้ว (`ADR 0035`) · เหลือ retry ของ error 1213 จดเปิดเผยใน `docs/ROADMAP.md` | ~2 ครั้ง/รอบที่ 25 VUs — เหนือสเกลเป้าห้าเท่า (`ADR 0031`) |
