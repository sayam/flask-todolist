# Design — ตัวตนของ UI และกติกาการแตะมัน

ไฟล์นี้เกิดจากบทเรียนของ CR#4: caption ตารางลอยกึ่งกลางอยู่หลายหน้า
เพราะ "แนวอ่านของทั้งหน้า" ไม่เคยถูกเขียนไว้ที่ไหน — หน้าใหม่จึงเกิดมา
ตามค่าเริ่มต้นของ browser แล้วเจ้าของต้องมาไล่จี้ทีหลังทีละจุด

**อ่านไฟล์นี้ก่อนแตะ `app/templates/` หรือ `app/static/base.css` ทุกครั้ง**
กรอบ "โหมดของหน้า" และวินัยการตรวจยืมมาจาก skill
[impeccable](https://github.com/pbakaus/impeccable) แล้วตัดให้เหลือเท่าที่
แอปนี้มีจริง · ตารางหน้า↔โหมดมีเทสต์คุมสองทิศ (`tests/test_design_doc.py`)

## 1. ตัวตน (identity)

- **เครื่องมือใช้งาน ไม่ใช่หน้าโฆษณา** — ข้อความล้วน ไม่มีภาพประกอบ
  ไม่มี animation คอลัมน์เดียวกว้างสุด `60rem` (เหตุผลของเลขอยู่ในคอมเมนต์
  ของ `app/static/base.css` — แถวงานทั้งแถวต้องอยู่บรรทัดเดียวได้)
- **ฟอนต์ระบบ** (`system-ui` + `Noto Sans Thai`) — ไม่โหลดฟอนต์ภายนอก
  (CSP เป็น `'self'` ล้วนอยู่แล้ว) · `line-height: 1.6`
- **สีทั้งหมดมาจากธีมผ่านตัวแปร 8 ตัว**: `--bg` `--fg` `--surface`
  `--border` `--muted` `--accent` `--accent-fg` `--overdue`
  — `base.css` เป็นเลย์เอาต์ล้วน ห้ามมีสีดิบ (มีเทสต์ดัก) และการเพิ่ม
  ตัวแปรสีใหม่คือการแก้**ทุกธีม**พร้อมกัน จึงต้องคิดก่อนว่าคุ้มไหม
- **โหมดสว่าง/มืด server ตัดสินเสมอ** (`data-theme` บน `<html>`) —
  CSS ไม่พึ่ง `prefers-color-scheme`
- **แนวอ่านชิดซ้ายทั้งหน้า** — หัวเรื่อง ตาราง caption ฟอร์ม เดินแนวเดียวกัน
  (CR#4) · ข้อยกเว้นเดียวคือหน้าโหมด Enter ที่จัดกล่องกลางจอ
- **ลำดับชั้นของปุ่ม**: ปุ่ม submit หลักเป็นสี `--accent` · ปุ่มในแถวรายการ/
  เมนูเป็นปุ่มเบา (พื้น `--surface`) · ลิงก์ที่ทำหน้าที่ปุ่มใช้ `a.button`
  ให้เข้าชุดกัน — หนึ่งหน้าควรมี action หลักสีเข้มไม่เกินหนึ่งจุดต่อฟอร์ม
- **ความหนาแน่นมาจากโครงสร้าง ไม่ใช่การย่อส่วน** — คอลัมน์ตรึงความกว้าง
  (`task-when` · `task-flag`) ให้ทุกแถวตรงแนวกัน · เป้าที่กดไม่เล็กกว่า
  24px ไม่ว่าจะแน่นแค่ไหน (WCAG 2.2 · 2.5.8 — ห้ามพึ่งข้อยกเว้นระยะห่าง)

## 2. โหมดของหน้า

หน้าเต็มทุกหน้าถูกตัดสินว่าอยู่โหมดใดโหมดหนึ่ง — โหมดคือคำตอบของคำถาม
"ผู้ใช้มาทำอะไร" และเป็นเกณฑ์ตัดสินตอนออกแบบ/รีวิวหน้านั้น:

- **Operate** — มาทำงาน: ลดภาระสมอง ทุก action มองเห็นและคาดเดาได้
  ความหนาแน่นสูงได้ถ้าแนวตรง · ฟอร์มแก้ไขอยู่หน้าแยก ไม่ยัดใส่แถวรายการ
- **Read** — มาอ่าน: โครงสร้างเพื่อความเข้าใจ (หัวข้อ · ตาราง · `<dl>`)
  ไม่มี action หลัก มีได้แค่ปุ่มกลับ/ลิงก์ต่อ
- **Enter** — มายืนยันตัวตน: งานเดียวกลางจอ ฟอร์มเดียว ปุ่มเดียว
  ไม่มี nav ของแอป (ยังไม่ได้เป็นสมาชิกของหน้าไหน)

| template | โหมด | หมายเหตุ |
|---|---|---|
| `index.html` | Operate | หน้าหลัก — แถวงานอ่านอย่างเดียว การแก้อยู่ `/edit/<id>` |
| `edit_todo.html` | Operate | ฟอร์มแก้งานเต็มหน้า + ส่วนแชร์เข้าวง |
| `categories.html` | Operate | จัดการหมวด — ปุ่มลบ disabled ตามกติกา แต่การกันจริงอยู่ route |
| `settings.html` | Operate | โปรไฟล์/รหัสผ่าน/token/MFA/ภาษา/ธีม รวมที่เดียว |
| `teams.html` | Operate | วงที่ฉันอยู่ |
| `team_detail.html` | Operate | งานที่แชร์ในวง + งานของฉันที่จะแชร์ |
| `admin_index.html` | Operate | hub ของ Site administration จัดกลุ่มตามหมวด |
| `admin_users.html` | Operate | บทบาท/ระงับ/unmask — ข้อมูลผ่านชั้น mask เสมอ |
| `admin_teams.html` | Operate | สร้าง/จัดการวง + เปลี่ยนชื่อ (เหตุผลบังคับ) |
| `admin_environment.html` | Read | ตารางข้อมูลระบบ — ไม่มี action |
| `admin_lifecycle.html` | Read | สถานะ lifecycle/retention |
| `admin_observability.html` | Read | ชี้ทาง metrics/log |
| `admin_sbom.html` | Read | รายการ dependency |
| `privacy.html` | Read | หน้า PDPA สาธารณะ + ปุ่มกลับที่ตก fallback |
| `team_info.html` | Read | ประวัติเปลี่ยนชื่อวง when/who/from/to/reason |
| `token_created.html` | Read | โชว์ความลับครั้งเดียว — อ่านแล้วเก็บ ไม่มีทางดูซ้ำ |
| `login.html` | Enter | มีตัวสลับภาษา/โหมดของตัวเอง |
| `login_verify.html` | Enter | ขั้นที่สองของ MFA — สถานะครึ่งทาง 5 นาที |

ไฟล์ที่ไม่อยู่ในตาราง: `base.html` (โครงของทุกหน้า ไม่ใช่หน้า) และ partial
ที่ขึ้นต้น `_` (`_admin_nav.html`) — เทสต์บังคับว่านอกเหนือจากนี้
**ทุกหน้าเต็มต้องมีแถว และทุกแถวต้องชี้ไฟล์ที่มีจริง**

## 3. refine หรือ redesign — ประกาศก่อนแตะ

ทุกงาน UI ต้องบอกได้ว่าเป็นแบบไหน (ยืมเส้นแบ่งจาก impeccable):

- **refine** (ค่าเริ่มต้น) — รักษาตัวตนข้อ 1 ทุกข้อ: งานคือทำหน้าให้เข้าแนว
  ที่ประกาศไว้ ไม่ใช่เปลี่ยนแนว · CR#1–#4 ทั้งหมดเป็น refine
- **redesign** — เปลี่ยนตัวตน: ต้องแก้ไฟล์นี้**ใน PR เดียวกัน** ให้ตัวตนใหม่
  ถูกเขียนก่อนที่หน้าแรกจะเดินตาม ไม่ใช่ปล่อยให้เอกสารกับจอวิ่งคนละทาง
- **brief ของเจ้าของชนะไฟล์นี้เสมอ** — ถ้าคำสั่งขัดกับตัวตนที่เขียนไว้
  คำตอบคือแก้ไฟล์นี้ตามคำสั่ง ไม่ใช่เถียงกลับด้วยรสนิยมของเอกสาร

## 4. วินัยการตรวจงาน UI (bounded verification)

สร้างให้จบ → ตรวจ**หนึ่งรอบแบบ batch** (เดินหน้าจริง + pa11y + เทียบข้อ 1)
→ แก้ทุกอย่างที่เจอในชุดเดียว → ยืนยันอีก**ไม่เกินหนึ่งรอบ** → หยุด
การ polish ต่อจากนั้นต้องมาจาก CR ของเจ้าของ ไม่ใช่จากการเปิดหน้าจอวนซ้ำ
