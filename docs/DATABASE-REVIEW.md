# ทบทวนการออกแบบฐานข้อมูลเทียบแนวปฏิบัติที่ดี (2026-08-20)

> **สถานะ: เป็นการทบทวนเพื่อบันทึกเท่านั้น — ยังไม่มีการแก้ไขใด ๆ ในรอบนี้**
> ตามคำสั่งของเจ้าของโปรเจกต์ ข้อค้นพบทุกข้อถูกบันทึกเป็นงานในอนาคต
> (ดูตาราง §3 และแถวใน [`ROADMAP.md`](ROADMAP.md) หัวข้อ "ของค้าง")

เกณฑ์ที่ใช้เทียบ: แนวปฏิบัติด้านการออกแบบฐานข้อมูลเชิงสัมพันธ์ให้แข็งแรงและ
ขยายตัวได้ และแนวปฏิบัติด้าน RDBMS สมรรถนะสูง — สรุปเป็นแกนที่ตรวจได้แปดแกน
คือ **การตรวจสอบย้อนหลัง (audit) · ประวัติของข้อมูล (historical) · การปิดบัง
ข้อมูล (masking) · สมรรถนะของคำสั่งค้นหา · การแบ่งพาร์ทิชัน · การสำรองและกู้คืน ·
การรองรับเครื่องมือติดตามสมรรถนะของแอปพลิเคชัน (APM) · วินัยของ schema**

**วิธีทบทวน**: อ่านจากไฟล์จริง (`app/models.py` · `app/audit.py` ·
`app/soft_delete.py` · `app/purge.py` · `migrations/` · `app/services/*.py` ·
`scripts/backup_drill.py` · `compose.*.yaml`) แล้วยืนยันทุกข้อความที่ขึ้นต้นว่า
"ยังไม่มี" ด้วยการค้นหาในซอร์สก่อนบันทึก ตามกติกาที่ `CLAUDE.md` กำหนดไว้

## 1. ภาพรวม — สิ่งที่ทำได้ดีอยู่แล้ว

| แกน | สถานะ | หลักฐานในโค้ด |
|---|---|---|
| วินัยของ schema | ✅ | ทุกตารางขึ้นต้น `tdl_` · ชื่อ constraint มาจาก `NAMING_CONVENTION` · model เป็น SQLAlchemy 2.0 typed · `tests/test_declared_prohibitions.py` บังคับ prefix ตั้งแต่ audit รอบ 18 |
| ความถูกต้องของเวลา | ✅ | คอลัมน์เวลาทุกตัวใช้ `UTCDateTime` (`app/db_types.py`) ซึ่งรักษาเศษวินาทีบน MySQL/MariaDB ที่ `DATETIME` เปล่าตัดทิ้ง · `gate dialect-discipline` บังคับทั้งฝั่ง model และฝั่ง migration |
| ความสมบูรณ์เชิงอ้างอิง | ✅ | foreign key ครบทุกความสัมพันธ์ · `ondelete="CASCADE"` ที่ตาราง org graph · SQLite เปิดบังคับ FK ต่อ connection (`app/plugins/db/sqlite/backend.py`) และ `tests/test_db_integrity.py` วัดที่ *ผล* ไม่ใช่ที่ค่า pragma |
| การตรวจสอบย้อนหลัง | ✅ | `tdl_audit` เติมได้อย่างเดียว ผูกเป็น hash chain · ดักอัตโนมัติที่ `after_flush` จึงครอบทั้ง route, CLI และสคริปต์ · การต่อสายเป็นลำดับด้วยแถวล็อกเดี่ยว (ADR 0035) · `flask audit-verify` ตรวจทั้งสาย |
| ระยะเก็บรักษา | ✅ | soft delete 30 วัน · audit 1 ปี · log 90 วัน ประกาศไว้ใน `docs/DATA-CLASSIFICATION.md` และมีคำสั่ง `purge-expired` กับ systemd timer จริงเป็นตัวบังคับ |
| การปิดบังข้อมูล | ✅ (ที่ชั้นแอป) | `app/services/masking.py` ตัดสินตามชั้นข้อมูล C1–C3 · การเปิดเผยเป็น POST ที่ลง audit · `tests/test_masking.py` บังคับให้คอลัมน์ใหม่ต้องถูกตัดสิน |
| การสำรองและกู้คืน | ✅ (SQLite) | `scripts/backup_drill.py` ซ้อม backup → ทำให้เสียหาย → restore → ตรวจ **ทุก push** ไม่ใช่พิธีปีละครั้ง |
| ความเท่าเทียมข้ามยี่ห้อ | ✅ | job `dialects` ยิงชุดเทสต์ทั้งชุดใส่ MySQL 8 และ MariaDB 11 จริงทุก push · job `schema` ตรวจ drift · job `n-1` พิสูจน์สัญญา N-1 |
| สุขภาพของข้อมูลที่มีอยู่จริง | ✅ | `flask data-doctor` (audit รอบ 19) ตรวจแถวกำพร้า · สายที่ขาด · ชื่อผู้ใช้ที่ชนกันแบบ casefold · ของที่พ้นระยะแล้วยังอยู่ |

## 2. ข้อสังเกตที่ยังไม่ได้ปิด

ทุกข้อด้านล่างมาจากการอ่านไฟล์จริง และระบุหลักฐานกำกับไว้ทุกข้อ

### D-01 · ดัชนีไม่ตรงกับรูปของคำสั่งค้นหาที่ใช้จริง (สำคัญ)

คำสั่งหลักของหน้ารายการงานคือ

```
WHERE user_id = ? AND deleted_at IS NULL [AND is_done = ?] [AND due_date BETWEEN ? AND ?]
ORDER BY (due_date IS NULL), due_date, created_at DESC
```

แต่ดัชนีที่ประกาศไว้เป็นคอลัมน์เดี่ยวสองตัวแยกกัน (`user_id` และ `deleted_at`)
ตัววางแผนคำสั่งจึงเลือกได้ทีละตัว แล้วต้องเรียงผลลัพธ์ในหน่วยความจำเสมอ

**ทางที่ควรเป็น**: ดัชนีผสม `(user_id, deleted_at, due_date)` และอาจมี
`(user_id, deleted_at, is_done)` เพิ่ม

**เงื่อนไขก่อนลงมือ**: ต้องวัดกับข้อมูลปริมาณจริงระดับแสนแถวก่อน ไม่ใช่เพิ่ม
ดัชนีเพราะเชื่อว่าจะเร็วขึ้น — บทเรียนของ Phase 6 ระบุไว้แล้วว่าคอขวดปัจจุบัน
อยู่ที่จำนวน process ที่รับงานได้พร้อมกัน ไม่ใช่ที่คำสั่งค้นหา และการเพิ่มดัชนี
โดยไม่มีการวัดคือการแก้สิ่งที่การวัดไม่ได้ระบุว่าเสีย

### D-02 · ไม่มีการแบ่งหน้า (สำคัญ)

`list_todos()` คืนทุกแถวที่ตรงเงื่อนไข และ `/api/v1` ประกาศไว้เองว่ายังไม่มี
pagination · ทั้งเวลาตอบสนองและหน่วยความจำจึงโตเป็นเส้นตรงตามจำนวนงานของผู้ใช้
หนึ่งคน · เป็นข้อจำกัดที่ยอมรับได้ในขนาดการใช้งานปัจจุบัน (ส่วนตัว/ครอบครัว)
แต่เป็นข้อแรกที่จะเจ็บเมื่อขนาดเปลี่ยน

**หมายเหตุด้านสัญญา**: การเพิ่ม pagination ให้ `/api/v1` ต้องไม่เปลี่ยนความหมาย
ของคำตอบเดิม ไม่เช่นนั้นต้องขึ้น v2 ตามกติกาใน `CLAUDE.md`

### D-03 · ไม่ได้ประกาศ character set และ collation (ปานกลาง)

ไม่มีการตั้ง `utf8mb4` หรือ collation ที่ใดเลย — ทั้งใน migration, `compose.mysql.yaml`
และ `compose.mariadb.yaml` · ผลคือแต่ละยี่ห้อใช้ค่าเริ่มต้นของตัวเอง และค่าเริ่มต้น
เหล่านั้น**ให้ความหมายกับ `UNIQUE(username)` ไม่เหมือนกัน**: MySQL 8 ใช้ collation
แบบไม่สนตัวพิมพ์ ส่วน SQLite เทียบแบบไบต์ต่อไบต์

audit รอบ 19 ปิดช่องนี้ที่ชั้นแอปแล้ว (ห้ามชื่อที่ชนกันแบบ casefold) แต่ชั้นฐาน
ข้อมูลยังไม่ได้ประกาศเจตนาไว้ — และเจตนาที่ไม่ได้ประกาศ คือเจตนาที่เปลี่ยนได้
เมื่อมีการอัปเกรดรุ่นของฐานข้อมูล

### D-04 · ค่าที่เป็นชุดจำกัด ไม่มี CHECK constraint (ปานกลาง)

`tdl_user.role` · `tdl_todo_dependency.status` · `tdl_audit.source` ล้วนเป็นสตริง
ที่แอปกำหนดค่าที่ยอมรับไว้ในโค้ด แต่ฐานข้อมูลรับค่าใดก็ได้ · สคริปต์หรือการแก้
ข้อมูลด้วยมือที่เขียนค่านอกชุดจึงผ่านไปได้ และจะไปแสดงผลผิดที่ชั้นแอปแทน

### D-05 · ตาราง audit ยังไม่มีแผนการแบ่งพาร์ทิชัน (ปานกลาง)

`tdl_audit` เก็บหนึ่งปีและถูกตัดจากหัวสายด้วยการลบทีละแถว · เมื่อปริมาณโตขึ้น
การลบรอบหนึ่งจะใช้เวลานานและถือล็อกนานตามไปด้วย · การแบ่งพาร์ทิชันตามเดือน
จะเปลี่ยนการลบเป็นการตัดพาร์ทิชันทิ้ง ซึ่งถูกกว่ามาก

**ข้อควรระวัง**: การแบ่งพาร์ทิชันต้องไม่ทำให้ hash chain ตรวจสอบข้ามพาร์ทิชัน
ไม่ได้ และ SQLite ไม่รองรับความสามารถนี้ จึงต้องเป็นค่าที่ตั้งได้ต่อยี่ห้อ
ตามรูปของ plugin ชนิด `db` ที่มีอยู่แล้ว

### D-06 · ไม่มีตัวชี้วัดของชั้นฐานข้อมูลใน `/metrics` (ปานกลาง)

`/metrics` ส่งออกเฉพาะ histogram ของเวลาตอบสนองต่อ endpoint · ไม่มีขนาดของ
connection pool, จำนวน connection ที่ใช้อยู่, เวลาที่ใช้ในคำสั่งค้นหา หรือจำนวน
คำสั่งต่อคำขอ · เครื่องมือ APM ที่มาต่อจึงเห็นได้แค่ว่า endpoint ไหนช้า แต่ตอบ
ไม่ได้ว่าช้าเพราะรอ connection, เพราะคำสั่งค้นหา หรือเพราะรอคิวใน gunicorn

### D-07 · การซ้อมกู้คืนครอบเฉพาะ SQLite (ปานกลาง)

`scripts/backup_drill.py` ทำงานกับไฟล์ SQLite เท่านั้น · ไม่มีขั้นตอนสำรองหรือ
กู้คืนสำหรับ MySQL/MariaDB และไม่มีการกู้คืนถึงจุดเวลา (point-in-time recovery)
เขียนไว้ที่ใด — ทั้งที่ stack ที่รันจริงรองรับสองยี่ห้อนั้นและ `compose.scale.yaml`
บังคับให้ใช้ยี่ห้อที่ไม่ใช่ SQLite

### D-08 · ประวัติของข้อมูลอ่านได้ทางเดียวคือเล่นซ้ำจาก audit (เล็กน้อย)

มีตารางประวัติเฉพาะการเปลี่ยนชื่อวง (`tdl_team_name_change`) · การเปลี่ยนแปลง
อื่นทั้งหมดอยู่ใน audit trail ซึ่งเก็บเป็น HMAC สำหรับคอลัมน์ชั้น C1–C3 ตามกติกา
· คำถามอย่าง "งานชิ้นนี้เคยมีกำหนดส่งเป็นวันไหน" จึงตอบไม่ได้จากฐานโดยตรง

นี่เป็นผลของการตัดสินใจที่บันทึกไว้แล้ว (audit ต้องไม่เก็บค่าของข้อมูลชั้นสูง)
ไม่ใช่ความบกพร่อง — บันทึกไว้เพื่อให้รู้ว่าถ้าวันหนึ่งต้องการมุมมองย้อนเวลา
ต้องออกแบบตารางประวัติแยก ไม่ใช่ผ่อนกติกาของ audit

### D-09 · คำสั่งส่งออกข้อมูลส่วนบุคคลอ่าน audit โดยไม่มีดัชนีรองรับ (เล็กน้อย)

`personal_data.py` ค้น audit ด้วยเงื่อนไข `actor_id = ?` **หรือ**
`(table_name = 'tdl_user' AND row_id = ?)` · มีดัชนีเฉพาะ `actor_id` ส่วน
`(table_name, row_id)` ไม่มี — ครึ่งหลังของเงื่อนไขจึงต้องอ่านทั้งตาราง
และตารางนี้คือตารางที่โตเร็วที่สุดในระบบ

### D-10 · `changes` เป็น JSON ในคอลัมน์ข้อความ ค้นภายในไม่ได้ (เล็กน้อย)

เป็นเจตนาเดิม: hash คำนวณจากข้อความ canonical ตรง ๆ การเปลี่ยนไปใช้ชนิด JSON
ของฐานข้อมูลจะทำให้ผลลัพธ์ขึ้นกับวิธี normalise ของแต่ละยี่ห้อ · บันทึกไว้ว่า
ถ้าวันหนึ่งต้องค้นภายใน ทางที่ถูกคือเพิ่มคอลัมน์ที่ derive มาและมีดัชนีของตัวเอง
ไม่ใช่เปลี่ยนรูปของสิ่งที่ถูก hash

## 3. สรุปงานที่บันทึกไว้ทำภายหลัง

| รหัส | เรื่อง | ระดับ | เงื่อนไขที่ทำให้ถึงคิว |
|---|---|---|---|
| D-01 | ดัชนีผสมให้ตรงกับรูป query | สำคัญ | เมื่อวัดกับข้อมูลระดับแสนแถวแล้วเห็นผลจริง |
| D-02 | pagination ของรายการงานและ API | สำคัญ | เมื่อผู้ใช้รายใดมีงานเกินหลักพัน หรือเมื่อเปิดใช้งานนอกวงส่วนตัว |
| D-03 | ประกาศ charset/collation ให้ชัด | ปานกลาง | เมื่อแตะ migration ของตาราง `tdl_user` ครั้งถัดไป |
| D-04 | CHECK constraint ของค่าที่เป็นชุดจำกัด | ปานกลาง | เมื่อเพิ่มค่าที่ยอมรับใหม่ให้คอลัมน์เหล่านั้น |
| D-05 | แผนแบ่งพาร์ทิชันของตาราง audit | ปานกลาง | เมื่อ `tdl_audit` แตะหลักล้านแถว หรือเมื่อ `purge-expired` ใช้เวลาเกินหนึ่งนาที |
| D-06 | ตัวชี้วัดชั้นฐานข้อมูลใน `/metrics` | ปานกลาง | เมื่อมีผู้ใช้ APM จริง หรือเมื่อวินิจฉัยปัญหาสมรรถนะครั้งถัดไป |
| D-07 | ซ้อมกู้คืนของ MySQL/MariaDB + PITR | ปานกลาง | เมื่อมี deployment ที่ใช้ยี่ห้อนั้นเก็บข้อมูลจริง |
| D-08 | ตารางประวัติของงาน | เล็กน้อย | เมื่อมีคำขอที่ต้องตอบว่า "เมื่อก่อนค่านี้เป็นอะไร" |
| D-09 | ดัชนี `(table_name, row_id)` ของ audit | เล็กน้อย | พร้อมกับ D-05 หรือเมื่อการส่งออกข้อมูลใช้เวลานานผิดปกติ |
| D-10 | ทางค้นภายใน `changes` | เล็กน้อย | เมื่อมีคำถามที่ต้องค้นเนื้อของการเปลี่ยนแปลง |

**ทั้งสิบข้อยังไม่ลงมือในรอบนี้** ตามคำสั่ง · ข้อที่มีเงื่อนไขผูกกับการวัด
(D-01 · D-05 · D-09) ต้องมีตัวเลขก่อนเสมอ ไม่ใช่ลงมือเพราะเชื่อว่าดีขึ้น
ซึ่งเป็นหลักเดียวกับที่ `docs/PERFORMANCE.md` ใช้มาตลอด
